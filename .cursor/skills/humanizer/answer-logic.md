# 答案的思考顺序（data-team-interview 及同类手册）

handbook-voice.md 管语气，这份管结构：答案要按一个人被问到这题时真实的思考顺序展开：先回答，再讲理由，最后讲做法。

## 常见病

- **首段是目录**：把所有结论、例外和 `见 dt-xxx` 压进一段，读者不知道哪句是回答。
- **先跳到无关前提**：问抽取，先讲许可和 robots；问阈值，先讲合规。前提只在真正改变答案时提。
- **顺序倒置**：先给做法再给理由；数字堆在末尾的「公开锚点」段，和它支撑的论点脱节。
- **重复**：同一句话在首段、正文、追问各出现一次。
- **电报体与怪标签**：「URL / 文档 id。」「嵌入近邻。」「不这么选的理由：」「接到苹果：」「口播：」「公开锚点：」。改成完整句子，或者用正常小标题。
- **稻草人**：「把泄漏当数据增强」这种没人会主张的反方，删掉。
- **交叉链接打断推理**：句中每隔两句一个 `见 dt-xxx`。
- **硬套公司场景**：每题都加一段「落到苹果」，把端侧 3B、Applebot、产品功能塞进一道通用数据题。题目本身没问公司，就不要找场景。
- **对比句式**：「不是 X，而是 Y」「X 而不是 Y」「X 不对，反而 Y」「不能只 X」「真正的问题是」。人回答问题时直接说该怎么做、为什么。确实有常见错误要提醒时，用一句平实的后果陈述，例如「只看精确匹配，会漏掉改过数字的题」。

## 目标顺序

1. **直接回答**（首段，2–4 句）：先回答题目问的那件事，给立场和一句核心理由。不列全部细节，不放交叉链接。
2. **为什么**：讲清机制或因果链——问题出在哪、为什么会这样、不处理会怎样。公开论文的数字放在它支撑的那句话旁边。
3. **怎么做**：按实际动手的先后顺序写步骤，每步说明为什么这样做、怎么判断做对了。代码题：思路 → 代码 → 复杂度/规模 → 测试。
4. **（可选）实践中的变化**：不同能力（通用知识、推理、代码、数学、多语、长上下文、工具 / agent）上做法有什么不同，或者规模变大后哪里会变。没有可说的就省略。
5. **追问**：只放正文没讲过的新问题和新信息。每条先给一句直接回答，再补理由。
6. **相关题**（可选）：交叉链接集中放在最后一行，例如「相关：`dt-web-extract`、`dt-global-dedup`」。正文里只在确实需要读者跳过去时保留个别链接。

不是每题都要五个小标题。短题可以只有「直接回答 + 两三段推理 + 追问」。行为题（HM、Culture）用 情境 → 判断 → 做了什么 → 结果 → 学到什么 的顺序。概览/地图类卡片保持表格或列表结构，只理顺说明文字。

## 必须保留

- frontmatter 除 `quick` 外一字不动；`quick` 也按「直接回答 → 理由 → 做法」重写，独立可读，不超过原长度太多。
- 和题目相关的事实、数字、论文名、代码块、公式、`dt-xxx` 链接 id（可以挪位置，不能删掉引用关系，除非重复）。只为套公司场景而存在的产品细节可以删。
- 不新增原文没有的数字、论文或公司说法。

## 公司与公开报告

答案聚焦通用 LLM 能力，不为某家公司编场景。AFM 技术报告和 FineWeb、Llama 3、DCLM 一样，只作为公开证据引用，用一句话放在它支撑的论点旁边，例如「AFM 2025 报告也减弱了过强的启发式规则」。产品细节（端侧模型尺寸、Applebot、Image Playground、Foundation Models 框架、Private Cloud Compute、用户日志政策）只在题目本身问到时出现。HM / Culture / 备考地图这类本来就是关于 Apple 面试的卡片不受此限。

## 自检

- 只读首段，能否知道这题怎么答？
- 每段的第一句是否承接上一段？删掉任意一段，后文是否还说得通？
- 同一事实是否出现超过一次？
- 有没有残留的「XX：」电报标签？
- 有没有「不是…而是」「而不是」「反而」「不能只」？能直接说的就直接说。
- 有没有为公司硬加的场景段落？
