# 答案的思考顺序（data-team-interview 及同类手册）

handbook-voice.md 管语气，这份管结构：答案要按一个人被问到这题时真实的思考顺序展开：先回答，再讲理由，最后讲做法。

## 常见病

- **首段是目录**：把所有结论、例外和 `见 dt-xxx` 压进一段，读者不知道哪句是回答。
- **先跳到无关前提**：问抽取，先讲许可和 robots；问阈值，先讲合规。前提只在真正改变答案时提。
- **顺序倒置**：先给做法再给理由；数字堆在末尾的「公开锚点」段，和它支撑的论点脱节。
- **重复**：同一句话在首段、正文、追问各出现一次。
- **电报体与怪标签**：「URL / 文档 id。」「嵌入近邻。」「不这么选的理由：」「接到苹果：」「口播：」「公开锚点：」。改成完整句子，或者用正常小标题。
- **稻草人**：「把泄漏当数据增强」这种没人会主张的反方，删掉。
- **交叉链接打断推理**：句中每隔两句一个 `见 dt-xxx`。
- **硬套公司场景**：每题都加一段「落到苹果」，把端侧 3B、Applebot、产品功能塞进一道通用数据题。题目本身没问公司，就不要找场景。
- **对比句式**：「不是 X，而是 Y」「X 而不是 Y」「X 不对，反而 Y」「不能只 X」「真正的问题是」。人回答问题时直接说该怎么做、为什么。确实有常见错误要提醒时，用一句平实的后果陈述，例如「只看精确匹配，会漏掉改过数字的题」。

## 目标顺序

1. **直接回答**（首段，2–4 句）：先回答题目问的那件事，给立场和一句核心理由。不列全部细节，不放交叉链接。
2. **为什么**：讲清机制或因果链——问题出在哪、为什么会这样、不处理会怎样。公开论文的数字放在它支撑的那句话旁边。
3. **怎么做**：按实际动手的先后顺序写步骤，每步说明为什么这样做、怎么判断做对了。代码题：思路 → 代码 → 复杂度/规模 → 测试。
4. **（可选）实践中的变化**：不同能力（通用知识、推理、代码、数学、多语、长上下文、工具 / agent）上做法有什么不同，或者规模变大后哪里会变。没有可说的就省略。
5. **追问**：只放正文没讲过的新问题和新信息。每条先给一句直接回答，再补理由。
6. **相关题**（可选）：交叉链接集中放在最后一行，例如「相关：`dt-web-extract`、`dt-global-dedup`」。正文里只在确实需要读者跳过去时保留个别链接。

不是每题都要五个小标题。短题可以只有「直接回答 + 两三段推理 + 追问」。行为题（HM、Culture）用 情境 → 判断 → 做了什么 → 结果 → 学到什么 的顺序。概览/地图类卡片保持表格或列表结构，只理顺说明文字。

## 必须保留

- frontmatter 除 `quick` 外一字不动；`quick` 也按「直接回答 → 理由 → 做法」重写，独立可读，不超过原长度太多。
- 和题目相关的事实、数字、论文名、代码块、公式、`dt-xxx` 链接 id（可以挪位置，不能删掉引用关系，除非重复）。只为套公司场景而存在的产品细节可以删。
- 不新增原文没有的数字、论文或公司说法。

## 公司与公开报告

答案聚焦通用 LLM 能力，不为某家公司编场景。AFM 技术报告和 FineWeb、Llama 3、DCLM 一样，只作为公开证据引用，用一句话放在它支撑的论点旁边，例如「AFM 2025 报告也减弱了过强的启发式规则」。产品细节（端侧模型尺寸、Applebot、Image Playground、Foundation Models 框架、Private Cloud Compute、用户日志政策）只在题目本身问到时出现。HM / Culture / 备考地图这类本来就是关于 Apple 面试的卡片不受此限。

## 自检

- 只读首段，能否知道这题怎么答？
- 每段的第一句是否承接上一段？删掉任意一段，后文是否还说得通？
- 同一事实是否出现超过一次？
- 有没有残留的「XX：」电报标签？
- 有没有「不是…而是」「而不是」「反而」「不能只」？能直接说的就直接说。
- 有没有为公司硬加的场景段落？

## 口述型答案（案例 / 项目题）

讲自己做过的项目、或者拿公开工作当案例讲的卡，用口述写法。知识题的「直接回答 → 为什么 → 怎么做」放在这里会变成报告体：小标题、表格、五步清单、把所有情况列全，读起来像交 spec。参考样例：`content/handbooks/data-team-interview/questions/cases/dt-case-web-grounding.md`。

正文要求：

1. **第一句给结论。** 一句话回答标题问的事。「简单说，……」可以偶尔用，别每张卡都这样开头，大多数时候直接说结论就行。可以接一句「这个方案是一步步改出来的」再进经过。
2. **一个具体例子。** 用一个场景让人马上明白问题，比如「用户给一张季度销售表，页面上却出现『同比增长 34%』，表里根本没有去年的数」。只列类别（增长率、用户数、图表点）不算例子。示意例子要告诉用户替换成真实的。
3. **按事情的经过讲。** 怎么发现 → 原因 → 第一反应 / 理想方案 → 卡在哪、怎么退一步 → 最后的做法 → 结果 → 回头看会怎么改。后来才加的东西写成「后来又加了……」，别写得像一开始就预见到。
4. **正文不用小标题、表格、编号清单。** 五六段口语，一分钟左右说完。几种情况用一句话说完（「编出来的扣得最重，标签写错扣得轻一些，写『未提供』不扣」），别做成表。
5. **正文不引论文。** 论文和数字放进追问。
6. **口语措辞。** 「对一下就行」「原因有一大半在我们自己」；避免「第一……第二……」「需要注意」「最后一行很关键」「起同样的作用」「用在三个地方：」。
7. **用户的经历不替他编。** 数字、原因、怎么发现的，留〔填：……〕，括号里写清要填什么；正文里〔填〕尽量少，放在开口自然要说的位置。不写「我们见过」「踩过坑」这类替用户编的经历。

追问要求：

- 4–5 条，挑面试官最可能问的，意思重复的合并。
- 每条标题写成面试官会说的一句话（加粗问句），回答第一句直接答（「会。」「一页二十个数错了一个，整页给 0 分，模型不知道该改哪个。」），再给理由。
- 论文顺带一提，最多一个关键数字：「ALCE 测下来，当时最好的模型也有大约一半回答引用不完整。」

`quick` 也按口述写：结论 → 关键的一两个设计 → 当时的限制，三句以内。

纯公开研究案例（没有用户经历）同样适用：第一句给结论，用「这几篇放在一起看说明了……」串起来，每篇讲它说明了什么，数字只留最有说服力的一个。

## 口述写法按题型套用

口述型答案的精神（第一句给结论、一个具体例子、按人说话的顺序、口语措辞、论文顺带提、追问 4–5 条）适用于所有卡，但结构按题型调整：

| 题型 | 怎么写 |
| --- | --- |
| 案例 / 项目 / 行为题（HM、Culture、讲自己的经历） | 完全按上面的「口述型答案」：正文无小标题、表格、清单、论文；按经历顺序；用户经历留〔填〕。 |
| 知识 / 设计题（「X 怎么做」「为什么 Y」） | 第一句给结论；接一个具体例子；推理用几段口语讲清机制和做法，按动手的先后顺序说。正文最多 1–2 个小标题，只在内容确实分两块时用；能用一句话说完的情况不做表格，真正需要对照多个维度的表格可以保留。论文名和数字只留支撑关键论点的一两处，用「X 那篇发现……」顺带一提，其余挪进追问。 |
| 代码题 | 思路用口述讲（第一句说用什么方法、为什么），然后代码块原样保留，再一两句讲复杂度和规模，测试用例保留。代码、公式一字不改。 |
| 地图 / 概览 / 对照表类卡 | 表格保留，只把说明文字改成口语，开头一句话说这张卡怎么用。 |

所有题型通用：

- 不加原文没有的事实、数字、论文；不删 `dt-xxx` 链接引用关系（可以挪到追问或末尾「相关：」）。
- frontmatter 除 `quick` 外不动；`quick` 按口述写，三句以内。
- 追问标题写成加粗问句，单独一行，下一行第一句直接回答。
- 自检：只读第一句能不能知道答案；有没有「XX：」电报标签；有没有「不是…而是」「而不是」「反而」「反倒」「不能只」「真正的问题」「需要注意」；有没有一段在罗列所有情况。
