## 题目描述

输入为“企业聊天需要发消息与补取历史”的需求。请输出发送和历史查询接口、最小数据模型及索引，并给出一次重复发送、一次断线补取的结果。需要说明发送成功、权限校验、分 page boundaries 和顺序范围；不要求实际编写 HTTP 服务。示例会话为 C7，用户为 U1，客户端消息标识为 M9。

### 作答要求与场景

请用文字与图说明输入或业务事件怎样到达最终输出，写清失败或重试时用户能观察到的结果。给至少一个具体请求或事件序列作为示例，最后说明怎样验证设计。场景假设与补充规则由本手册设定。

## 回答思路

> **问题与场景：** 假设架构图里写了一个“订单服务”，我会继续具体到创建请求带什么字段、如何去重、什么时候返回成功，以及客户端超时后怎样查状态。
>
> **做法与原因：** 数据模型要支持这些行为，例如稳定 order ID、业务状态和版本，而不只是列几个数据库表。
>
> **检查与取舍：** 最后走一遍正常请求与响应丢失的过程。

## 可以这样回答

假设架构图里写了一个“订单服务”，我会继续具体到创建请求带什么字段、如何去重、什么时候返回成功，以及客户端超时后怎样查状态。

数据模型要支持这些行为，例如稳定 order ID、业务状态和版本，而不只是列几个数据库表。不同服务之间也要明确错误、重试与状态所有权。

最后走一遍正常请求与响应丢失的过程。若讲不清用户最后能观察到什么，架构图还没有落到可实现的约定。

## 参考答案与设计讨论

为一条写路径、一条读路径定义请求、返回、主键和索引，再说明重试、分页与版本冲突。

### 先定接口行为

发送接口接收会话、消息正文和客户端幂等标识，返回服务端消息标识、会话内序号与提交状态。历史查询接收会话与上次连续收到的序号，按升序返回后续消息和分页游标。每次查询都检查当前用户是否仍有会话权限。

### 把访问模式落到表上

会话成员关系用于鉴权；消息记录以会话和序号组织，并保存作者、消息标识、提交时间、编辑版本。幂等记录应限定到用户或设备及会话，绑定请求内容摘要。同一标识换了正文应报冲突，不能默默返回另一条消息。

### 具体走一次请求

U1在 C7发送 M9，服务端提交为 seq=101。响应丢失后重试 M9，返回同一条101；另一个设备保存连续游标100，补取后拿到101，再推进游标。收到103而缺102时不能直接把连续游标推进到103。

### 取舍与追问

时间戳不天然提供唯一顺序，偏移分页在插入和删除时可能重复或漏读。若消息编辑和删除需要同步，应增加变更版本或事件游标，单靠创建序号不够。是否支持全局排序要单独讨论成本。
