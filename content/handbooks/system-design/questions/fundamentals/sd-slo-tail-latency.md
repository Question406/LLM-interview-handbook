## 题目描述

为一个读取推荐结果的 API 定义可用性与延迟目标。输入是产品希望“快且稳定”，没有具体数字。输出需要包括请求成功条件、统计窗口、超时与空结果是否算失败，以及一个示例延迟预算。练习可暂设 p99端到端200ms，但必须说明这是待确认假设，且各依赖的 p99不能直接相加当作精确端到端 p99。

### 作答要求与场景

请用文字与图说明输入或业务事件怎样到达最终输出，写清失败或重试时用户能观察到的结果。给至少一个具体请求或事件序列作为示例，最后说明怎样验证设计。场景假设与补充规则由本手册设定。

## 回答思路

> **问题与场景：** 假设平均响应是 100ms，但每百次就有一次要等几秒。
>
> **做法与原因：** 我会先定义哪些请求、从哪里开始计时、成功意味着什么，再给出 latency 与可用性目标。
>
> **检查与取舍：** 检查 p95、p99 和错误时还要看样本量、请求类型与时间窗口。

## 可以这样回答

假设平均响应是 100ms，但每百次就有一次要等几秒。对频繁调用的用户，这些慢请求仍会明显影响体验。

我会先定义哪些请求、从哪里开始计时、成功意味着什么，再给出 latency 与可用性目标。之后把预算分给排队、依赖与执行，并为超时和降级留余量。

检查 p95、p99 和错误时还要看样本量、请求类型与时间窗口。没有明确计量方式，一个漂亮的 SLO 数字很难约束设计。

## 参考答案与设计讨论

先定义用户动作、统计窗口和成功条件，再把端到端延迟拆到依赖；平均值不能替代尾部延迟。

### 先定义用户看到的结果

HTTP 200但返回空白或过期到不可用的内容，未必满足产品目标。按符合条件的用户请求定义成功率；健康探针不能替代真实流量。区分系统拒绝与客户端无效请求，写清哪些进入分母。

### 沿关键路径分预算

例如总预算200ms，可暂分入口20ms、召回50ms、特征40ms、排序60ms、组装与网络余量30ms。这是工程预算分配，不是各组件分位数的数学等式；最终用全链路 trace 和压测测端到端分布。并行依赖关注最慢关键支路。

### 超预算时怎么处理

每次调用携带剩余 deadline，超时立即释放资源。弱依赖可用缓存或较小候选集降级，涉及权限与风控的依赖不能随意跳过。监控各切片 SLO、错误预算消耗和降级比例，防止用低质量“成功”隐藏故障。

### 具体例子与追问

推荐特征服务耗时150ms，剩余50ms 不足以跑原排序模型，可以用允许的轻量模型返回，并记录降级。若轻量路径违反已承诺的质量底线，则应明确失败。可用性99.9%按30天时间比例约对应43.2分钟，但请求型 SLO 需要按请求数计算。
