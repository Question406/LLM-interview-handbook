## 题目描述

订单提交后需要异步发放一张优惠券。输入是订单事件，网络故障时同一事件可能被重复投递。输出要求最终有一张券，并能恢复失败处理。请给出订单与事件提交方式、消费去重键、确认时点和补偿策略，说明如果发券服务不支持幂等，会剩下什么风险。

## 回答思路

> **问题与场景：** 假设消费者已经创建订单，却在确认消息之前崩溃。
>
> **做法与原因：** 我会让同一个业务请求携带稳定 ID，并让重复执行能查到已有结果。
>
> **检查与取舍：** At-least-once delivery 允许消息重复；我们真正要保证的是重复不会变成重复的业务结果。

## 可以这样回答

假设消费者已经创建订单，却在确认消息之前崩溃。队列再次投递时，如果业务直接重做，就可能创建两张订单。

我会让同一个业务请求携带稳定 ID，并让重复执行能查到已有结果。处理消息、写业务状态和记录已处理 ID 需要有明确的一致性安排，不能先确认消息再希望业务一定完成。

At-least-once delivery 允许消息重复；我们真正要保证的是重复不会变成重复的业务结果。还要测试处理一半、响应丢失和消费者重启这些过程。

## 参考答案与设计讨论

队列重投很常见；持久化确认、消费者提交和外部副作用之间的崩溃窗口，需要用业务幂等处理。

### 避免数据库与队列双写空洞

订单和 outbox 事件在同一数据库事务中提交，发布器不断扫描或订阅变化并投递；投递成功后标记。发布器崩溃可导致重复发布，所以 outbox 解决遗漏窗口，不自动消除重复。

### 让效果与去重记录一起提交

若发券就在消费者数据库中，用事件标识与券类型做唯一约束，在事务里写券和消费记录，然后确认消息。先确认后写券会丢效果；先写券但去重不可靠会重复发。重试时返回既有券，不能再生成一张。

### external-call guarantees

若券由外部 API 创建，应把稳定 idempotency key 传给对方。调用成功但响应丢失时先查询结果，不能无条件再创建。对方既不幂等也不可查询时，不能承诺任意故障下严格一次效果，需要业务对账、人工修复或更改接口。

### 例子与追问

事件 E3第一次消费写券成功，提交 offset 前进程崩溃。重投 E3时唯一约束命中并返回原券，然后确认。Kafka 事务在其支持的 transaction scope 内很有用，但不能凭此保证任意数据库或 HTTP 副作用也恰好一次。
