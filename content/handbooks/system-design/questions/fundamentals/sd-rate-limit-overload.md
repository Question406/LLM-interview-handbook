## 题目描述

一个推理 API 平时每秒100个请求，突然涨到1000个；请求时长与上下文长度不同。请设计租户配额、全局准入、有界排队和重试规则，输出429/503与排队超时的使用语义。需要说明只按请求数限流的不足，以及取消后如何释放已预留的资源。

### 作答要求与场景

请用文字与图说明输入或业务事件怎样到达最终输出，写清失败或重试时用户能观察到的结果。给至少一个具体请求或事件序列作为示例，最后说明怎样验证设计。场景假设与补充规则由本手册设定。

## 回答思路

> **问题与场景：** 假设下游只能处理每秒 1,000 次调用，上游却来了 10,000 次。
>
> **做法与原因：** 我会在入口按租户与资源预算准入，对内部队列设置上限，让下游压力能传回上游。
>
> **检查与取舍：** 验证突发流量和下游变慢时的拒绝、排队与恢复。

## 可以这样回答

假设下游只能处理每秒 1,000 次调用，上游却来了 10,000 次。无限排队会把等待时间和内存一起推高，最终连正常流量也失败。

我会在入口按租户与资源预算准入，对内部队列设置上限，让下游压力能传回上游。重试需要退避与预算，否则一次故障会被放大成更多请求。

验证突发流量和下游变慢时的拒绝、排队与恢复。目标是在负载过高时仍有可预测的服务行为。

## 参考答案与设计讨论

限流约束到达速率，准入控制约束可承受的在途资源，背压通知上游放慢；队列必须有上限和等待期限。

### 同时看速率与资源

租户令牌桶可以限制每分钟请求或 token 预算；全局准入还要估算 KV、GPU 执行槽和最大输出长度。每个请求预留多少、何时返还必须明确，不能取消后仍长期占用额度，也不能只信任客户端报的小长度。

### 有界队列与截止时间

队列长度根据允许等待时间和实际服务能力确定，先检查请求 deadline，过期任务不要继续执行。对长请求与短请求采用可说明的公平策略，必要时拆分批任务，避免交互请求被无限阻塞。

### 让重试有预算

租户配额超限可以返回明确的重试建议；全局过载可拒绝或受控降级。上游用指数退避与抖动，并限制总尝试次数和总耗时。每层都独立重试会让一次用户请求放大成几十次执行。

### 例子与追问

1000次/秒到来而只能稳定完成100次/秒，队列每秒净增900个，不会靠“等一会儿”自行恢复。先限制入口、减少非必要工作并保护关键请求，再扩容。扩容需要启动时间，不能作为即时保护的唯一手段。
