## 题目描述

给定按用户查询的订单服务，需要把单机数据拆到多机，并允许某台存储节点失效。请输出分片键、复制策略、路由与在线迁移流程，说明跨用户查询、热门用户和旧路由写入的处理。练习假设同一订单不能创建两次，不要求给所有用户的订单提供全局严格顺序。

### 作答要求与场景

请用文字与图说明输入或业务事件怎样到达最终输出，写清失败或重试时用户能观察到的结果。给至少一个具体请求或事件序列作为示例，最后说明怎样验证设计。场景假设与补充规则由本手册设定。

## 回答思路

> **问题与场景：** 假设按用户 ID 分片后，一个大客户占了大部分访问。
>
> **做法与原因：** 分片是分数据与负载，复制是保留同份数据以改善读取或容错。
>
> **检查与取舍：** 我会用倾斜流量测扩容效果，并验证迁移期间不丢写、不重复处理。

## 可以这样回答

假设按用户 ID 分片后，一个大客户占了大部分访问。增加副本可以分担读取，但它的写入仍可能集中在一个分片。

分片是分数据与负载，复制是保留同份数据以改善读取或容错。选 shard key 时要看热点、查询方式与跨分片操作，迁移还要处理新旧路由并存。

我会用倾斜流量测扩容效果，并验证迁移期间不丢写、不重复处理。机器更多，不代表热点自然消失。

## 参考答案与设计讨论

分片拆开数据与写负载，复制改善读与容灾；两者都不能自动消除单个热门键的瓶颈。

### 分片键必须对应访问模式

按用户散列利于用户订单点查，但全站按时间导出要另建分析路径。按时间范围切分便于归档，却可能把当前写流量集中到最新分区。一致性哈希减小成员变化时的迁移范围，不保证负载相等，也不解决热门用户。

### 复制需要说清写成功的含义

主副本确认后才回复，还是主节点本地提交就回复，会改变丢失窗口和延迟。读副本可能落后；创建订单后立即查看可以读主或带会话版本要求。副本切换时还要隔离旧主，防止双方同时接受有效写。

### 迁移不能只画一个新分片

先复制历史快照，追赶增量日志，校验一致性，再切换带版本的路由。迁移期间写入以明确的权威节点为准；旧路由请求转发或拒绝。双写需要去重、冲突与修复机制，不是开关一开就结束。

### 例子与追问

U9所有订单都在一个分片，某自动化客户突然每秒写大量订单。增加虚拟节点不能拆开这个单键热点，可进一步按用户和订单桶划分，但查询与事务复杂度会增加。应先测限流、队列和热点隔离是否足够。
