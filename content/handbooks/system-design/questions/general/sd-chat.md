## 题目描述

设计企业聊天服务，支持私信、千人频道、多设备在线与离线历史。手册练习假设100万日活，每人每天发50条消息，保留一年。请输出发送与补取 API、会话内顺序规则、消息和成员数据模型及推送路径，说明发送确认、重复发送、断线重连、成员退出和大频道热点的处理。

### 作答要求与场景

请用文字与图说明输入或业务事件怎样到达最终输出，写清失败或重试时用户能观察到的结果。给至少一个具体请求或事件序列作为示例，最后说明怎样验证设计。场景假设与补充规则由本手册设定。

## 回答思路

> **问题与场景：** 假设用户在手机发了一条消息，电脑离线后再上线，应看到同一条消息且顺序一致。
>
> **做法与原因：** 我会用稳定 message ID 支持重试去重，用会话内序号或明确排序规则组织消息，并让设备按游标补取。
>
> **检查与取舍：** 测试重复发送、断线和乱序。

## 可以这样回答

假设用户在手机发了一条消息，电脑离线后再上线，应看到同一条消息且顺序一致。先定义“发送成功”表示服务已持久化，还是对方已经收到。

我会用稳定 message ID 支持重试去重，用会话内序号或明确排序规则组织消息，并让设备按游标补取。在线推送负责及时通知，持久记录负责恢复与多设备同步。

测试重复发送、断线和乱序。不能把 WebSocket 连着就当作消息已可靠交付。

## 参考答案与设计讨论

将服务端持久化、设备接收和用户已读分成不同状态；会话内序号与设备游标支持断线补取。

### 先限定顺序与确认

要求同一会话有序，不要求跨会话全局有序。发送成功表示消息已经达到约定的持久化确认点；送到设备和用户已读分别记录。客户端断线重发相同幂等标识不会新增消息。

### 核心架构

客户端通过网关认证，消息服务验证成员权限，在会话分区追加消息并分配序号；投递事件异步发送到连接网关或离线收件路径。历史查询直接按会话与序号读取，WebSocket 负责低延迟通知，不承担唯一持久副本。

### 多设备与热点

各设备保存连续已收序号，缺口通过历史接口补取；编辑删除需额外变更游标。大频道避免对所有设备同步持久化多份正文，可以推通知并按需拉取。单热点会话的有序写入仍是瓶颈，不能靠按用户分片随意打散。
