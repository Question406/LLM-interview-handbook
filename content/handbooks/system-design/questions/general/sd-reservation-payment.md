## 题目描述

设计限量课程预约服务，只有100个席位，需要支付后确认。输入包含预约请求、支付回调和超时事件；它们可能重复、乱序或延迟。输出要保证不超卖，并区分待支付、确认、过期和退款。请给出资源保留与支付接口、状态机、并发控制和对账流程；不要求实现银行支付网络。

请用文字与图说明输入或业务事件怎样到达最终输出，写清失败或重试时用户能观察到的结果。给至少一个具体请求或事件序列作为示例，最后说明怎样验证设计。场景假设与补充规则由本手册设定。

## 回答思路

> **问题与场景：** 假设最后一个名额先保留十分钟，用户付款时保留刚好过期。
>
> **做法与原因：** 我会明确预留、确认、过期和补偿状态，用稳定业务 ID 处理支付回调与重试，并记录可对账的状态变化。
>
> **检查与取舍：** 测试超时支付、重复回调和退款失败。

## 可以这样回答

假设最后一个名额先保留十分钟，用户付款时保留刚好过期。系统需要决定库存与支付状态怎样协调，避免收钱却没有名额。

我会明确预留、确认、过期和补偿状态，用稳定业务 ID 处理支付回调与重试，并记录可对账的状态变化。跨系统失败时需要可恢复流程，不能指望两个服务总是同时成功。

测试超时支付、重复回调和退款失败。定时任务与对账要能把中间状态收敛到明确结果。

## 参考答案与设计讨论

用状态机管理资源保留和支付，用稳定 idempotency key 与唯一约束避免重复效果，超时后查询最终结果。

### 先定义状态转移

原子预留一个席位后建立限时待支付预约；支付确认且预约仍有效时转为确认。过期释放资源。每个转移检查当前状态与版本，回调以支付事件标识去重，不让迟到回调把已退款预约又变回确认。

### 不能只看超时

支付 API 超时可能已经扣款，先用商户请求标识查询。预约过期后才收到成功支付，需要明确退款或重新争取资源的产品规则，不能无条件恢复席位造成超卖。所有钱相关效果保留可审计账本。

### transaction scope 与 external effects

数据库内的席位与预约可用事务协调；外部支付无法纳入同一普通数据库事务。使用可恢复的 outbox、幂等支付请求和补偿状态机；补偿也可能失败，需要重试与对账。不要把 saga 称作自动回滚所有世界状态。

### 例子与追问

只剩一席，A 条件预留成功，B 失败。A 付款请求响应丢失，重复请求返回原支付结果；A 已过期时应进入既定补偿路径。监控预留占用、超时支付、重复回调和账实不符，而不只看接口错误率。
