## 3. 指标先于方案：这套流水线自己怎么算成功 ⭐⭐⭐

大多数候选人在这里直接开始列 benchmark。更好的做法是**先给评测系统自己定义指标**——它是一个产品，用户是模型团队和发布决策者。

### 3.1 评测流水线的元指标

| 元指标 | 定义 | 目标量级（可讲的举例） |
|---|---|---|
| **决策正确率** | 事后回看：pipeline 说"可以发"的版本，上线后有多少出现了本该拦住的退化 | 每季度复盘一次；出现一次漏网就补一条 canary（§8） |
| **judge–人类一致性** | 在人工双标集上的 accuracy 与 Cohen's κ，与人类间基线并列报 | κ ≥ 人类间 κ 的 0.9 倍即视为到顶 |
| **可复现性** | 同一模型同一配置跑两次，主指标之差 | 目标 < 1pp；超过说明温度/sampling/judge 抖动未控住 |
| **灵敏度（power）** | 在既定样本量下能以 80% power 检出多大的真实差异 | 明确写出来："当前配置能稳定检出 ≥2pp 的差异，1pp 以内我们无法区分" |
| **覆盖率** | 生产 query 的 embedding 聚类中，有多少cluster在 eval 集里有代表样本 | 报"未覆盖cluster占流量 X%"，这是补题的优先级列表 |
| **端到端时延与成本** | 一次完整发布 gate 的 wall-clock 和美元 | 它在发布关键路径上；跑 3 天的评测等于没有评测 |
| **污染健康度** | private holdout 与 public 对应集的分差趋势 | 分差持续扩大 = public 集正在被吃掉 |

**必背句**：评测流水线的成功标准不是"分数准"，而是"**决策对**"，以及"**当决策错了的时候，我们能在事后定位到是哪一层出的问题**"。所以每条评测结果都要带模型版本、judge 版本、prompt 模板版本、数据集版本四个字段（对应 [08 §10](?book=drustz-interview-2026&section=mlsd&question=drustz-f15a9e25a058981436) 的 trace schema），一次只允许变一个。

### 3.2 哪些常见指标不能用，以及为什么

| 指标 | 为什么不能当主指标 | 还能用在哪 |
|---|---|---|
| **Perplexity / 验证集 loss** | 跨 tokenizer 不可比；RLHF 后模型 PPL 通常变差但人类偏好变好；它衡量的是分布拟合不是有用性 | 预训练阶段的健康监控、检测训练崩溃 |
| **BLEU / ROUGE** | 开放式回答没有唯一参考。**我在 Anthropic take-home 里实测过**：用 ROUGE 预测"医生标注为不安全的回复"，AUROC 只有 **0.569**（≈掷硬币）；换成 claim 级 grounding grader 后是 **0.844**，两个confidence interval不重叠 | 有严格参考且措辞受限的任务（机器翻译粗筛、结构化摘要），或者当作"是否完全跑题"的极粗过滤 |
| **单一 Elo / Arena 排名** | 依赖对手池和 prompt 分布；受长度和 markdown 驱动（Arena 后来引入 style control 就是为此）；非传递性；对手池变了分就变 | 对外沟通的相对位置感、发现自己没想到的失败类型 |
| **一个加权总分** | 权重是偷偷做的产品决策；掩盖切片退化；容易被单一维度拉动 | 高管汇报的封面数字，但必须附最差切片 |
| **thumbs up 率** | 覆盖率 <1%，极化，且系统性奖励讨好（§9） | 作为**变化检测**信号（突然掉了说明出事了），不作为水平判断 |
| **拒答率单独看** | 调低就是不安全，调高就是over-refusal | 必须与越狱成功率成对报（§11） |

**高分句**：ROUGE 这类指标失败的原因不是"不够先进"，而是**构念错配**——它测的是词面重叠，我们要的是"这段话有没有被证据支持"。这两件事在开放式生成上几乎不相关。所以我的第一步不是换更强的相似度指标，而是把评测目标拆成可以被逐条验证的 claim。
