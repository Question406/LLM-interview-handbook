## 5. 环境设计 ⭐⭐⭐

### 5.1 确定性 vs 随机性：三档，不是两档

| | 全确定 | **受控随机** | 真实随机 |
|---|---|---|---|
| 形态 | 冻结镜像 + 固定 seed + 全 mock | 固定 seed 的 user simulator、按 schedule 注入的故障 | 打真实网站 / 真实第三方 API |
| 优点 | 可复现、可 debug、方差只来自模型 | 能测鲁棒性与恢复，且方差**可归因** | 保真度最高 |
| 代价 | agent 会overfitting到环境怪癖；测不到恢复能力 | 故障分布本身要设计和辩护 | 不可复现、有真实副作用、分数随时间漂移 |
| 用在哪 | 回归 CI、模型间比较 | **能力评估主集** | 上线前的小规模保真度calibration（20–50 题） |

**核心判断：方差要么消除，要么可归因，不能既存在又不可控。** 落地做法是把所有随机源做成显式参数并写进 run manifest：

```text
run_manifest: {
  image_digest, dep_lockfile_hash, harness_version, model_id+version,
  env_seed, user_sim_seed, user_sim_model, fault_schedule_id,
  frozen_clock, step_budget, temperature, tool_schema_version
}
```



有了这个，任何一次失败都能**精确重放**。没有这个，"这题为什么挂了"要花半天，而这半天会重复几百次。

### 5.2 可复现的四层（一层都不能少）

| 层 | 具体做法 | 漏掉会怎样 |
|---|---|---|
| **依赖** | 容器镜像锁 digest（不是 tag）；lockfile 到 hash；网络默认 deny | 三个月后同一个 commit 跑出不同分数，且没人知道为什么 |
| **状态** | 每题从快照启动、跑完销毁；用 copy-on-write（docker layer / btrfs snapshot）让 reset 是秒级 | reset 要 2 分钟的话，$N \times k = 4000$ 次 rollout 光 reset 就是 **133 机时**（串行 5.5 天，并行 32 路也要 4 小时纯等待） |
| **时间** | 冻结系统时钟（`libfaketime` 之类），任务描述用相对时间 | "查最近 7 天的订单"这类任务的正确答案会随日历静默改变——这是最隐蔽的漂移 |
| **随机** | 所有 seed 显式记录；judge 若用 LLM 则固定版本 + temperature=0 + 多次投票 |  $\mathrm{pass}^k$  里混进了 harness 的方差（§7.3） |

### 5.3 沙箱与副作用隔离

- **网络默认关闭**，需要的外部内容做本地录制回放（VCR / WARC 快照）。这不只是复现性问题——**联网的 agent 可以直接搜到答案**，这是污染的运行时形态（§8）。
- **资源上限**：CPU / 内存 / 磁盘 / 进程数 / wall-clock。防 fork bomb，也防 agent 用"跑 10 万次暴力枚举"换成功率。
- **环境卫生 checklist**（每条都有真实先例）：
  - [ ] strip `.git`（SWE-bench Pro 抓到模型读 git 历史直接取 gold patch）
  - [ ] 评分用的测试文件在评分阶段才挂载，agent 阶段不可见
  - [ ] 答案不能出现在注释、README、日志、fixture 里
  - [ ] verifier 的代码和数据 agent 不可写（否则 agent 会改测试）
  - [ ] 环境里不能有指向公开题库的 URL
- **真实副作用必须硬失败**：eval 模式下调用真实支付/发信接口应当抛错并记为 `unsafe_action`，**而不是静默 mock 成功**。静默 mock 会让你永远测不出 agent 是否敢做危险动作。

### 5.4 user simulator：既是噪声源也是被攻击面

多轮 agent 必须有一个模拟用户，而它是 benchmark 里**方差最大且最容易被忽视**的组件。

| 问题 | 表现 | 做法 |
|---|---|---|
| 方差 | 同一任务重跑就挂，根因是对话分支敏感 | 固定 simulator 模型版本 + seed；给剧本约束（persona、已知信息、**不能主动透露的信息**） |
| 被诱导 | agent 说服 simulator 偏离剧本，或直接问出答案 | simulator 的系统提示里写死"你不知道 X"；对 simulator 输出做泄漏检测（gold 关键字出现即判该 run 无效） |
| 判分权错配 | simulator 说"我满意了"就算成功 | **simulator 绝不持有判分权**，判分只看环境终态 |
| 同源偏差 | simulator 和被测 agent 同一个模型 → 相同的误解会互相配合 | 用不同 family 的模型做 simulator，并做一次交叉检验（换 simulator 模型看排名是否稳定） |

### 5.5 verifier 自己是未经测试的软件 ⭐⭐⭐

这是面试里最能体现"真做过 eval"的一段。两个公开证据：

- OSWorld 原版 369 题里 **~10% 的任务本身是坏的**（评分脚本失效、依赖挂了），所以才有了 OSWorld-Verified。
- SWE-bench Pro 的第三方审计发现 grader **约 1/3 试次误判**（错收 8.5%、错拒 24%）。

一个 500 题的 execution-based benchmark，它的评分逻辑就是 **500 个小程序**。没有测试的 500 个小程序会坏，这是常识。所以：

```text
每个任务必须附带:
  gold_trajectory        人工或强模型跑通并经人工确认 → verifier 必须判过
  known_bad_trajectory   至少 1 条（跳步 / 越权 / 假成功）→ verifier 必须判不过
  last_verified_at       时间戳 + owner
CI: 每日在 gold / known-bad 上重跑 verifier，任何一条翻转即告警
```



> **高分句**：verifier 是 benchmark 里唯一没人评测的组件。我会给每个任务配一条 gold 轨迹和一条已知坏轨迹当单元测试——这一步的成本大概是任务制作成本的 20%，但它是 OSWorld 和 SWE-bench Pro 两次公开翻车的根因。
