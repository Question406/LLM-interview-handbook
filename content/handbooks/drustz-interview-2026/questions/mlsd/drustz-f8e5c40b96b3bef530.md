## 4. 质量闸门：三级漏斗 ⭐⭐⭐

一个 LLM judge 打分不是质量闸门。真正的闸门是**成本递增、覆盖递减**的多级漏斗，每一级只做它擅长的事。

### 4.1 漏斗结构与预期通过率

| 级 | 手段 | 抓什么 | 抓不到什么 | 相对成本 | 典型通过率 |
|---|---|---|---|---|---|
| **L0 规则** | 长度、语言 ID、格式/schema、必需字段、答案可解析、重复 n-gram、明显截断、禁用词 | 垃圾和管道故障 | 一切语义问题 | ~0 | 70–95% |
| **L1 程序 / verifier** | 执行代码跑测试、数值答案比对、单位与量纲检查、约束求解、schema 一致性、**与 seed 文档的一致性检查** | 硬错误（答案错、代码不跑、违反约束） | 题目本身不合理（有答案但题烂） | 低 | 40–80%（可验证域） |
| **L2 模型校验** | LLM/LRM judge 按 rubric 打**离散标签**（不是 1–10 分），多维度：自包含性、矛盾性、假设完备性、与 seed 的相关性 | 语义层缺陷 | 自己也会错、也不一致（§4.3） | 中（可占总成本 20–40%） | 50–85% |
| **L3 人工抽检** | 分层抽样 + 领域专家；**不是全量标注**，是calibration前三级 | 前三级的系统性盲区 | 规模 | 高 | —（这是测量，不是过滤） |

**关键设计原则：越便宜的闸门放越前面，且每一级都要记录被丢弃的原因。** 丢弃原因的分布本身是最有价值的监控信号（§4.4）。

**L3 抽样怎么抽（面试常追问）**：不要均匀抽。按**闸门判定分层**抽——L2 判"通过"的抽一部分、判"拒绝"的抽一部分、判在阈值附近的重点抽。这样才能同时估计 judge 的 precision 和 recall。只抽通过的样本，你永远发现不了 judge 把好数据误杀了多少。

### 4.2 质量特征清单（可直接背，来自我实际用过的）

对每条生成的题目，我打的是这几个**二元/三值标签**而不是一个总分：

| 特征 | 判什么 | 为什么它单独成一维 |
|---|---|---|
| **是否自包含** | 题目脱离原始上下文后还能不能解（有没有"如上图"、"根据上一题"、指代不明的 it/they） | 这是网页/论坛来源数据最常见的坏法。不自包含的题在训练时会教模型瞎猜 |
| **是否含矛盾信息** | 条件之间是否冲突（"三角形三边 1,2,5"） | 矛盾题会有"答案"，verifier 也可能给过，但它教的是错的 |
| **解题假设是否给足** | 缺失的必要前提（未给定单位、未说明定义域、隐含约定） | 假设不足的题会让强模型和弱模型给出不同但都"合理"的答案 → reward 噪声 |
| **答案是否唯一可判定** | 是否存在多解 / 表述等价但字符串不同 | 决定这条题能不能进 RL |
| **与 seed 的一致性** | 改写后是否偏离了原文事实 | 抓改写型 pipeline 特有的事实漂移 |

**为什么用离散标签而不是 1–10 分**：judge 给的连续分数在不同题目上不可比（§4.3），而"是否自包含"这种问题有明确定义，一致性高得多。**把主观打分拆成一组客观判定，是提升 judge 可靠性最有效的一招。**

### 4.3 LRM-as-judge 的一致性问题（我真踩过）

我在做数据筛选时遇到的具体问题是：**同一条评判标准，judge 在不同题目上判得不一致**。同一个"是否自包含"的要求，在几何题上判得严，在应用题上判得松。

诊断和缓解手段（按性价比排序）：

| 手段 | 做法 | 效果 |
|---|---|---|
| **把 judge 一致性本身当指标** | 同一批样本重复判 3 次测自一致；不同 judge 之间测互一致（Cohen's κ / Krippendorff α） | 先量化，不量化就没法改。**κ < 0.4 的维度直接不要用** |
| **rubric 锚点样例** | 每个标签给 2–3 条正例 + 2–3 条边界反例，放进 prompt 前缀（顺便吃满 prompt cache） | 最见效的一招 |
| **拆维度 + 二元化** | 见 §4.2 | 大幅提升 |
| **成对比较代替绝对打分** | 判"A 和 B 哪个更自包含"而不是"A 打几分" | 一致性更好，但成本 O( $n^{2}$ )，只用于calibration子集 |
| **人工锚点集** | 固定一套 200 条人标样本，每次换 judge / 换 prompt / 换模型版本都重跑，报和人标的一致率 | **这是 judge 的回归测试**。没有它，换个模型版本你的数据质量就静默漂移了 |

**高分句**：judge 不是 ground truth，是一个**需要被calibration和被回归测试的模型组件**。我会给 judge 建版本号、建固定的人工锚点集，并把 judge 与人标的一致率作为一个必须监控的生产指标——因为 judge 一旦漂移，整条数据管线的质量会静默退化，而下游要几周后才发现。

### 4.4 漏斗监控：通过率是最灵敏的告警

每一级的通过率、以及被拒原因的分布，都要按天画出来（对应 [07 §15.2](?book=drustz-interview-2026&section=mlsd&question=drustz-a31756199987603573) 的 funnel dashboard）。

- L0 通过率突降 → 上游 seed 来源变了，或者 generator 输出格式变了（最常见：换了模型版本）
- L1 通过率突升 → 警惕，可能是 verifier 坏了在放水，不是质量变好了
- L2 通过率突变但 L1 不变 → judge 漂移，去查 judge 的锚点集
- **各级通过率都正常但下游不涨** → 闸门在筛"合法"而不是在筛"有用"，回到 §2
