## 题目

现场阅读一份设计文档，指出其中的遗漏和风险，并给出可行的修改方案。

> 来源：一亩三分地 Anthropic 题卡摘要（2026-10-18 用 Chrome 读取），是网站对候选人报告的二手整理，没有逐条核对原帖；收录为面经题型不代表公司官方确认。下面的示例文档、规模数字和故障情景是手册补的练习约定。

## 思路

先复述文档的需求和约束，确认自己理解对了，再按几个维度找缺口：数据一致性、失败恢复、安全、容量和可运维性。

每条批评都要说明在什么场景下会触发、影响有多大，并给出一个附带成本的替代方案。先处理能改变设计决策的大问题，不要把时间花在纠正措辞上。

## 完整非编程练习（场景与参考回答）

### 具体题目与需求澄清

假设拿到一份推理服务的设计文档，里面的设计是：API 直接同步调用 GPU，状态只存在内存里，超时就整体重试，没有配额。要求在 45 分钟内完成评审，并给出能落地的修订。

开始时先复述文档的目标，问作者（面试官）哪些约束是硬性的，比如上线时间和现有团队规模。

### 一套可展开的参考答案

**1. 先复述并找结构性缺口。** 复述目标和 SLO，画出一次请求从进入到返回、以及被取消时的完整路径。沿着这条路径逐项指出缺口：状态没有持久化、没有幂等、队列没有上限、没有资源准入、没有租户隔离、没有部署回滚方案。

**2. 提出最小改动。** 每项改动都附上负责人、上线顺序和验证方式：

- 用 request id 加参数 hash 识别重复请求。
- 加有界队列。
- 用任务租约管理执行中的请求。
- 记录模型版本。
- 增加成本账本，记录每次计费。

**3. 用一次超时把问题讲具体。** 沿原设计走一个请求：客户端调用 API，API 同步占住一块 GPU 生成；生成到一半网关超时，客户端按文档规定整体重试。此时第一次生成仍在 GPU 上跑，第二次又占了一份 KV，用户被计费两次；流量高时这种重试会层层叠加，直到 KV 耗尽。把这个场景摆出来，比抽象地说"缺少幂等"更有说服力，也直接引出 request id 去重和准入限额这两项修改。

**4. 排定修复优先级。** 先修"超时导致重复计费、并发打爆 KV"这种会真实发生的故障，再谈缓存优化。对现有实现里不确定的地方，提出需要验证的问题，不把猜测写成事实。

**5. 交付风险表并说明怎样验证。** 给一页风险表，每行写清：触发条件、用户影响、概率依据、修复成本和回滚条件。用压测得到的队列曲线和故障注入结果验证修改，而不是只给每项打一个抽象分。

### 面试追问与参考回答

**为什么不建议整体重写？** 先用可回滚的小改动止住主要风险，保留现有服务边界。只有当数据证明现有约束下确实无法扩展时，再拿着数据提出重构。

**作者不同意你的某条意见怎么办？** 回到触发场景和数据：说明在什么条件下会出问题、发生概率的依据是什么。如果作者有你不知道的约束（比如流量其实很小），就调整优先级并把这个假设写进文档。
