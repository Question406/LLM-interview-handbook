## 题目

现场阅读一份设计文档，指出其中的遗漏和风险，并给出可行的修改方案。

> 来源：一亩三分地 Anthropic 题卡摘要（2026-10-18 用 Chrome 读取），是网站对候选人报告的二手整理，没有逐条核对原帖；收录为面经题型不代表公司官方确认。下面的示例文档、规模数字和故障情景是手册补的练习约定。

## 思路

先复述文档的需求和约束，确认自己理解对了，再按几个维度找缺口：数据一致性、失败恢复、安全、容量和可运维性。

每条批评都要说明在什么场景下会触发、影响有多大，并给出一个附带成本的替代方案。先处理能改变设计决策的大问题，不要把时间花在纠正措辞上。

## 完整非编程练习（场景与参考回答）

### 具体题目与需求澄清

假设拿到一份推理服务的设计文档，里面的设计是：API 直接同步调用 GPU，状态只存在内存里，超时就整体重试，没有配额。要求在 45 分钟内完成评审，并给出能落地的修订。

开始时先复述文档的目标，问作者（面试官）哪些约束是硬性的，比如上线时间和现有团队规模。

我会先沿一次请求找故障，把能改变设计的大风险排在前面，再给可以回滚的修订。练习要求 45 分钟评审，文档里 API 同步调用 GPU、状态只放内存、超时整体重试且没有配额。我会先复述需求和 SLO，确认上线时间、团队规模等硬约束。

比如一个请求生成到一半，网关超时，客户端重试。第一次生成可能还占着 GPU，第二次又占一份 KV，最后用户被计费两次；流量高时重试叠加，KV 可能耗尽。这个场景直接指向幂等和准入控制，也提示我们把正常返回和取消的整条路径画清楚。

最小修订是用 request id 加参数 hash 去重，加有界队列，以任务租约管理执行中的请求，记录模型版本，再用成本账本记录每次计费。每项修改写清负责人、上线顺序和验证办法，先止住重复计费、并发耗尽 KV，再看缓存优化。

沿这条路径继续检查一致性、失败恢复、安全、容量和可运维性，包括状态持久化、租户隔离和部署回滚。每条意见都要给触发条件、用户影响、概率依据、替代方案的成本和回滚条件，汇成一页风险表。现有实现不确定的地方作为待验证问题，不能猜成事实；最后用压测队列曲线和故障注入验证修订。

### 面试追问与参考回答

**为什么不建议整体重写？**
先用可回滚的小改动止住主要风险，保留现有服务边界。只有当数据证明现有约束下确实无法扩展时，再拿着数据提出重构。

**作者不同意你的某条意见怎么办？**
回到触发场景和数据：说明在什么条件下会出问题、发生概率的依据是什么。如果作者有你不知道的约束（比如流量其实很小），就调整优先级并把这个假设写进文档。
