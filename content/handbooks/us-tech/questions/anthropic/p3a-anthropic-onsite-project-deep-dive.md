## 题目

Onsite 中准备一段对过去技术项目的讲解，讲完后接受深入问答。面试官会顺着你的材料追问实现细节、实验和你没讲到的地方。

> 来源：一亩三分地 Anthropic 题卡摘要（2026-10-18 读取），属于网站对候选人报告的二手整理，没有逐条核对原帖，网站收录也不代表公司官方确认；网站提到的演讲时长只是面经版本，最终以邀请为准。下面的演示回答是手册写的假想示例，不是候选人原话或真实经历。

## 思路

主体材料覆盖五个部分：需求、约束、考虑过的候选方案、最终决策和结果。规模数字、实验细节、状态机和 trace 截图放进备份页，正文里不展开，被追问时再翻出来。这样正文能在规定时间里讲完，深挖时又不至于空手。

要能解释关键实现，并且敢于承认不确定：哪些结论有数据支持，哪些只是当时的判断，哪些到现在也没验证过。

## 完整非编程练习（参考回答与追问）

### 练习题

准备一段过去项目的讲解和问答。只能用自己真实参与过的经历；下面用一个假想的推理网关改造项目演示材料怎么排，不能直接当成自己的故事背诵。

### 参考回答

正文可以分六页，每页回答一个问题：

1. 问题与约束：原来的 P95 首 token 等待是 2.4 秒，长短请求共用 FIFO 队列（演示数字）。
2. 测量证据：从 trace 拆出排队、prefill 和 decode 各占多少时间，证明瓶颈在排队。
3. 备选与选择：按长度硬分桶，以及按 token 预算准入加公平队列；先试了前者，长请求尾延迟恶化，于是改成按等待时间提升优先级。
4. 实现细节：调度契约、取消请求后的 KV 回收。
5. 验证与结果：同模型、同 GPU 池、同一段回放流量下，P95 降到 1.3 秒，长请求 P99 恢复；上线先 1% 灰度。
6. 失败与反思：硬分桶为什么失败，现在会怎样更早发现。

备份页放调度状态机、关键 trace 和灰度期间的监控曲线。讲解时说清楚分工：调度契约、诊断和实现是自己做的，GPU kernel 和模型训练是同事负责的。

如果真实数据撑不起某个结论，就删掉那个数字，而不是编一个。

### 面试追问与参考回答

**面试官问到一个备份页里也没有的细节，怎么办？** 直接说不记得具体数字，再说明当时是怎么测的、去哪里能查到，或者给出一个有把握的数量级。现场编一个精确数字，被追问两层就会露馅。

**你当时最不确定的判断是什么？** 准备一个真实的答案。比如演示里可以说：灰度期间流量偏小，长请求样本不多，P99 恢复的结论置信度有限，后来是靠全量上线后一周的数据才确认的。

**时间不够时先砍哪部分？** 先砍实现细节页，把时间留给问题、选择和结果。实现细节最容易在问答环节被问到，放进备份页正合适。
