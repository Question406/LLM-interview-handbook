## 题目

Onsite 中准备一段对过去技术项目的讲解，讲完后接受深入问答。面试官会顺着你的材料追问实现细节、实验和你没讲到的地方。

> 来源：一亩三分地 Anthropic 题卡摘要（2026-10-18 读取），属于网站对候选人报告的二手整理；网站提到的演讲时长只是面经版本，最终以邀请为准。下面的演示回答是手册写的假想示例。

## 思路

主体材料覆盖五个部分：需求、约束、考虑过的候选方案、最终决策和结果。规模数字、实验细节、状态机和 trace 截图放进备份页，正文里不展开，被追问时再翻出来。这样正文能在规定时间里讲完，深挖时又不至于空手。

要能解释关键实现，并且敢于承认不确定：哪些结论有数据支持，哪些只是当时的判断，哪些到现在也没验证过。

## 完整非编程练习（参考回答与追问）

### 练习题

准备一段过去项目的讲解和问答。只能用自己真实参与过的经历；下面用一个假想的推理网关改造项目演示材料怎么排，不能直接当成自己的故事背诵。

### 参考回答

这个假想项目的结论是：把长短请求共用的 FIFO 改为按 token 预算准入、带等待时间提升优先级的公平队列，缓解排队。演示数字是 P95 首 token 等待从 2.4 秒降到 1.3 秒。下面只是讲解结构，数字和分工必须换成自己的真实经历。

一开始先用 trace 拆开排队、prefill、decode 的耗时，确认主要瓶颈在排队。考虑过按长度硬分桶，也考虑过 token 预算准入加公平队列，先试前者，却让长请求尾延迟恶化，于是改为等待越久优先级越高。

实现里要解释调度契约，以及取消请求后怎样回收 KV。验证保持同模型、同 GPU 池、同一段回放流量，除了 P95 还看长请求 P99 是否恢复，再从 1% 灰度开始上线。复盘时讲硬分桶为何失败，现在会怎样更早发现。

主体可以安排六页，分别讲问题约束、测量证据、备选与选择、实现、验证结果、失败反思。状态机、关键 trace、灰度监控曲线放备份页。讲清调度契约、诊断、实现哪些是自己负责的，GPU kernel、模型训练哪些是同事负责的。

真实证据撑不起的结论就不报精确数字，不确定的地方说明哪些未验证。

### 面试追问与参考回答

**面试官问到一个备份页里也没有的细节，怎么办？**
直接说不记得具体数字，再说明当时是怎么测的、去哪里能查到，或者给出一个有把握的数量级。现场编一个精确数字，被追问两层就会露馅。

**你当时最不确定的判断是什么？**
准备一个真实的答案。比如演示里可以说：灰度期间流量偏小，长请求样本不多，P99 恢复的结论置信度有限，后来是靠全量上线后一周的数据才确认的。

**时间不够时先砍哪部分？**
先砍实现细节页，把时间留给问题、选择和结果。实现细节最容易在问答环节被问到，放进备份页正合适。
