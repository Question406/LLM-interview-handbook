Teams 纪要、GitHub / 仓库问答、M365 长文档都是微软的长上下文产品，不是「把窗口开到 128k 就结束」。研究岗会问 Phi-3 的长上下文怎么训；应用岗会问 **评测怎么切**，否则线上全是「摘要很流畅但行动项是编的」。针在干草堆里（needle-in-a-haystack）只能证明模型有时能从某位置抄出一句，证明不了产品。

## 为什么单一分数不够

Lost-in-the-middle：证据在序列中间时，很多模型比放在头尾更差。会议记录里决定往往在中间讨论，不在开场自我介绍。仓库里真正的函数定义可能在第 40 个文件。如果你的评测针总是插在开头，分数会虚高。

长度也不均匀。8k 能做好不代表 64k 还能引用。必须按 **输入长度桶**（8k / 32k / 128k）报曲线，而不是一个「长上下文准确率」。Azure 上长度还直接变成 TPM，见 `msft-azure-tpm`；评测切片应和成本切片一起看。

产品任务也不是复制那根针：

- **会议纪要：** 行动项、负责人、截止时间、未决分歧。要能指回时间戳或发言人。把两小时录音压成流畅散文但丢了「Alice 反对上线」，产品是失败的。
- **仓库问答：** 先定位文件/符号，再解释。编一个「看起来像我们风格」的 API 比答错更危险。引用要落到路径和行跨度，见 `msft-copilot-ground`。
- **多文档政策：** 哪一份生效、哪一份作废。长上下文里旧文件和新文件同时在，模型爱用措辞更顺的那份。

所以离线集要按 **失败模式** 切片，不要按「我们有 128k 模型」切片。

## 我会怎么切评测

固定一套金标，每条 case 带元数据，报表是一张表不是一个数：

| 切片 | 测什么 | 会议纪要例子 | 仓库问答例子 |
| --- | --- | --- | --- |
| 长度桶 | 能力是否随 $T$ 掉 | 15 分钟 vs 2 小时 | 3 个文件 vs 整仓拼接 |
| 证据位置 | lost-in-the-middle | 决定在录音 40% 处 | 定义在 prompt 中部 |
| 跳数 | 是否要拼多处 | 开头提需求、结尾才定人 | 接口在 A，实现坑在 B |
| 归因 | 能否指回证据 | 时间戳 / 说话人 | 文件路径 + 行 |
| 拒答 | 证据不在窗口时 | 没开麦的决定 | 仓库里没有的 API |
| 新鲜度 | 冲突版本 | 上周 vs 今天的会 | 主分支 vs 过期注释 |

指标：归因准确（句子能否在证据里定位）、行动项 F1、文件定位 recall、拒答率（该拒时拒、不该拒时别拒）。生成流畅度当辅助，不当主指标。BLEU 对纪要几乎无用，改写和金标字面差很大。

工程上我会避免「把整个仓库 / 整段录音塞进 128k」当默认。先检索或分段摘要，再在短窗口上生成，长上下文当兜底。评测要同时跑 **检索+短上下文** 和 **naive 全塞**，看哪条切片上全塞真的赢。很多仓库问题 8k 检索就赢过 128k 全塞，因为噪声少。视觉会议白板还要算视觉 token，见 `msft-llava`。

污染：用公开会议或著名仓库当评测，模型可能背过。内部租户的时间切片、合成的「中间才出现的决定」，更可信。

会议和仓库的切片权重不一样。纪要更怕 **说话人 / 时间戳错** 和 **把讨论当决议**；仓库更怕 **定位错文件** 和 **编造符号**。我会分开报，不合成一个「长上下文分」。产品上默认路径仍是检索或分段摘要再生成，128k 全塞当对照和兜底，而不是当唯一架构。这样评测才能回答「我们到底是窗口赢了，还是检索赢了」。

## 追问

- **Needle 完全没用吗？** 有用，当回归：位置×长度的热力图，用来抓 RoPE / 窗口实现 bug。它不是产品验收。
- **说话人错了但内容对？** 纪要场景算错。行动项绑错人比措辞差一点更贵。说话人错误单独计。
- **128k 训了还要检索？** 要。窗口是上限，不是质量保证。检索控制 ACL 和噪声；长上下文处理检索漏召回的那一段。两者叠，不互相取消。
- **怎么测「编造 API」？** 金标里列出仓库不存在的符号，问模型能不能实现。正确行为是拒答或先搜。答出一份完整假函数记为严重幻觉，不要用「代码能编译」当通过。
