## 题目

围绕一个自选项目，面试官会深入追问你的 ownership、做过的关键决策，以及事后的反思。问题可能从架构一路追到实现、实验和故障处理。

> 来源：一亩三分地 Microsoft 题卡摘要（2026-10-18 读取），属于网站对候选人报告的二手整理，没有逐条核对原帖，网站收录也不代表公司官方确认；这道题跨 MAI 和其他 Microsoft 团队，不能据此推断固定的轮次安排。下面的演示回答是手册写的假想示例，不是候选人原话或真实经历。

## 思路

开场先讲问题和约束，然后把时间集中在一个最关键的技术选择上：当时有哪些选项，为什么选了这个，被放弃的方案在什么条件下会更好。结果用真实的指标支撑。

准备好被一路追下去：从架构到具体实现，从实现到实验怎么做的，再到上线后出过什么故障、怎么处理的。ownership 的问题要回答得很具体：哪些决定是你做的，哪些是团队一起定的，哪些是别人负责的。

## 完整非编程练习（参考回答与追问）

### 练习题

讲一个你有 ownership 的项目，重点讲一个关键决策和你的反思。只能用自己真实参与过的经历；下面是一个明确标为假想的演示，不能直接当成自己的故事背诵。

### 参考回答

假设候选人负责过一个推理网关改造，以下数字只用于演示表达：

“问题是 P95 首 token 等待 2.4 秒，原因是长短请求共用一个 FIFO 队列。我负责诊断和调度方案。

最关键的选择是怎么把长短请求分开。我先试的是按长度硬分桶，实现简单，短请求马上就变快了，但长请求的尾延迟变差。后来改成按 token 预算准入，再让等待时间逐步提升优先级。在同模型、同 GPU 池、同一段回放流量下，P95 降到 1.3 秒，长请求 P99 也恢复了。上线先放 1% 灰度，观察取消后的 KV 回收、公平份额和失败重试。

我的贡献是调度契约、诊断和实现；GPU kernel 和模型训练由同事负责。

回头看，硬分桶的问题本可以更早发现：我当时只看了整体 P95，没有把长请求单独拉出来看。现在我做调度类改动时，会先按请求类型分组定义指标，再开始实验。”

如果真实数据撑不起某个结论，就删掉那个数字，而不是编一个。

### 面试追问与参考回答

**如果重来一次，你会怎么做？** 给出一个具体的改变，而不是“我会沟通得更好”这种空话。演示里的答案是：先按请求类型拆分指标，硬分桶的副作用就能在第一轮实验里暴露出来。

**这个方案是你一个人定的吗？** 说清楚决策过程：谁提出的问题、谁评审了方案、有没有人反对、最后由谁拍板。演示里调度方案由候选人提出，kernel 相关的改动需要和负责 GPU 的同事对齐。

**上线后出过什么问题？** 准备一个真实的小故障，比如取消请求后 KV cache 没有及时回收导致显存上涨，说明是怎么发现的、怎么修的、加了什么监控防止复发。
