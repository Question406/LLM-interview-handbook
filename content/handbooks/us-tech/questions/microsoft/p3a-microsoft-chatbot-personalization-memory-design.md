## 题目

为一个个性化聊天助手设计长期记忆，让它记住用户的偏好和经历，又不用每轮对话都重读全部历史。面试会关心记忆怎么存、怎么检索、新旧信息冲突时怎么办，以及用户如何查看和删除。

> 来源：一亩三分地 Microsoft 题卡摘要（2026-10-18 读取），属于网站对候选人报告的二手整理，没有逐条核对原帖，网站收录也不代表公司官方确认；规模数字、SLO 和故障情景是手册补的练习约定。

## 思路

记忆至少要分三类：用户明确说过的事实（“我对花生过敏”）、模型从对话里推断出的偏好（“似乎喜欢简短回答”）、只在当前会话有用的临时上下文。三者可信度不同，保留策略也不同。每条记忆都要记录来源、置信度和更新时间，这样冲突时才有依据判断该信谁。

检索必须限定在当前用户的权限范围内。用户的旧偏好要允许被覆盖和删除，删除还要真正传播到所有派生数据里。

评估不能只看“个性化有没有让回答更好”，还要覆盖三类风险：错误记忆能否被纠正、是否发生跨用户泄漏、多轮对话中记忆是否前后一致。

## 完整非编程练习（场景与参考回答）

### 具体题目与需求澄清

练习设定：十万用户的聊天助手，保存长期偏好和事件，每个用户最多一千条记忆；用户可以查看、纠正、删除记忆，并且跨设备看到一致的结果。

开场可以问：哪些内容不允许记（如敏感健康信息是否需要用户同意），删除后多久必须生效，以及记忆是自动写入还是需要用户确认。

### 一套可展开的参考答案

**1. 架构与关键路径。** 记忆从对话里产生，到被下一次对话用上，经过这几步：

1. 对话事件写入日志。
2. 提取器从事件中生成记忆候选。
3. 校验置信度，并检查是否与已有记忆冲突。
4. 写入版本化的 memory store。
5. 新对话开始时，按用户过滤召回相关记忆。
6. 压缩成一段上下文交给模型。

用户的明确声明优先于模型推断。

**2. 数据模型和状态变化。** 每条记忆记为 memory(id, user, type, value, source, confidence, `valid_from`, `valid_to`, version, deleted)。原始对话证据和归纳出来的结论分开存，便于事后追溯。短期聊天内容和长期事实用不同的保留期。

**3. 追踪一次正常写入和读取。** 用户说“我下个月搬去西雅图”。提取器生成候选 (type=事件, value=搬到西雅图, source=对话 id, confidence=高, `valid_from`=下个月)。校验发现已有一条“住在纽约”，于是不删除旧记忆，而是给它设 `valid_to`，新记忆版本号加一，用户的 memory version 也随之递增。两周后用户在另一台设备上问“周末去哪玩”，召回时按当前日期过滤出仍然有效的记忆，回答以西雅图为准。

**4. 失败、重复与恢复。** 新记忆与高置信度的旧事实冲突时，不直接覆盖：要么向用户确认，要么给两条记忆加上时间范围。删除操作要传播到向量索引和由记忆生成的摘要；旧缓存通过 user memory version 失效。

**5. 容量和验证指标。** 衡量记忆精确率、更新是否及时、错误记忆的纠正率、跨用户泄漏次数，以及个性化带来的效果提升。同时评估那些不需要记忆也能完成的任务，防止过度个性化。

### 面试追问与参考回答

**怎样避免把“我以前是 X”记成“我现在是 X”？** 抽取时要带上有效时间和语境，保留原句作为来源；检索时按当前问题和时间过滤。只靠 embedding 相似度做不到这一点，因为“以前是 X”和“现在是 X”的向量非常接近。

**用户删除了一条记忆，怎样确认它真的不会再出现？** 删除后检查三处：memory store 中这条记录标记为 deleted，向量索引里对应的条目已移除，包含这条信息的摘要已经重新生成。可以写一个回归测试：删除之后马上问一个只有这条记忆才能回答的问题，回答里不应该再出现它。
