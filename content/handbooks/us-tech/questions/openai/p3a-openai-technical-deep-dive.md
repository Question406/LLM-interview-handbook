技术深挖要讲清一个真实项目中自己做了什么判断，以及有什么证据支持这个判断。开场说明问题和约束，再按发现问题、尝试方案、碰到限制、调整和结果往下讲，面试官随后会追到规模、成本、实验设计、故障和备选方案。

> 来源：一亩三分地 OpenAI 题卡摘要（2026-10-18 读取），属于网站对候选人报告的二手整理，没有逐条核对原帖，网站收录也不代表公司官方确认；下面的演示回答是手册写的假想示例，不是候选人原话或真实经历。

准备时可以把开头写成“我负责〔填：真实项目及本人范围〕，当时要解决〔填：具体问题和约束〕”。规模、成本、实验和故障各准备一两个能核实的数字，也说清同事负责的部分。放弃过的方案要解释它在什么条件下更好、当时为什么不满足；不能披露的内部资料就换到公开可讲的抽象层次。

下面保留原手册的假想推理网关例子，数字只用于展示表达方式，不能当成自己的经历。例子里的 P95 首 token 等待是 2.4 秒，长短请求共用 FIFO 队列。候选人负责从 trace 拆开排队、prefill、decode 时间，提出按 token 预算准入，并让短等待请求进入公平队列。

最初按请求长度硬分桶，短请求变快了，长请求尾延迟却变差。之后改成等待越久优先级越高，再用同一模型、同一 GPU 池、同一段回放流量对照，P95 降到 1.3 秒，长请求 P99 也从恶化状态恢复。这段讲法把第一次尝试和后来修正连在一起，真实项目也应有自己的判断依据。

假想例子里先放 1% 灰度，观察取消后的 KV cache 回收、各用户公平份额和失败重试。候选人的贡献限定为调度契约、诊断和实现，GPU kernel 与模型训练由同事负责。实际回答要换成真实分工；数据撑不起的结论就删掉，不能补一个数字。

回头看时，除了结果，还要讲清回放是否一致、长请求是否被饿死、为什么不直接加 GPU，以及出了问题怎样回滚。每个判断都应该能落到当时看过的数据或做过的动作上。

## 追问

**基线流量一致吗？**
说明是否用同一段录制生产流量回放、相同模型版本和 GPU 池，只修改策略。再给出真实统计窗口和样本量，确认 P95 改善超出多次回放的波动。

**怎么确认长请求没被饿死？**
单独看长请求 P99 和最长等待时间，并说明谁用什么数据确认。假想例子正是发现长请求变差，才从硬分桶改成等待时间提升优先级。

**为什么不直接加 GPU？**
加 GPU 可以缓解排队，但成本随流量线性增加，短请求排在长请求后面的结构仍在。用 trace 先证明调度瓶颈，再展示相同硬件下的承载变化。

**出问题怎样回滚？**
策略放在开关后面，灰度期间公平份额或错误率越过阈值就回到 FIFO。具体指标和阈值必须来自真实项目。
