## 题目

准备一个自己做过的项目，先整体讲一遍，再接受面试官对技术细节的连续追问。追问通常会落到规模、成本、实验设计、故障处理，以及为什么没有选别的方案。

> 来源：一亩三分地 OpenAI 题卡摘要（2026-10-18 读取），属于网站对候选人报告的二手整理，没有逐条核对原帖，网站收录也不代表公司官方确认；下面的演示回答是手册写的假想示例，不是候选人原话或真实经历。

## 思路

材料按五块组织：要解决的问题、当时的约束、关键决策、结果、事后反思。每一块都要说清楚哪些是你本人做的，哪些是同事做的。

为规模、成本、实验和故障各准备一两个可以核实的数字。被放弃的方案要讲清楚：它在什么条件下会更好，当时为什么不满足这个条件。

不要用无法披露的内部资料来证明能力。遇到保密内容，可以说明“这部分细节不能讲”，然后换成公开可讲的抽象层次。

## 完整非编程练习（参考回答与追问）

### 练习题

讲一个你主导的技术项目，并准备被追问到实现细节。只能用自己真实参与过的经历；下面是一个明确标为假想的完整演示，用来展示讲法，不能直接当成自己的故事背诵。

### 参考回答

假设候选人负责过一个推理网关改造，以下数字只用于演示表达。可以这样讲：

“我们原来的 P95 首 token 等待是 2.4 秒，主要原因是长请求和短请求共用一个 FIFO 队列。我负责从 trace 里把排队、prefill 和 decode 的时间拆开，并提出按 token 预算做准入、短等待请求走公平队列。

最初的方案是按请求长度硬分桶。短请求确实变快了，但长请求的尾延迟变差了。于是我改成让等待时间逐步提升优先级，重新做了对照。在同一个模型、同一个 GPU 池、同一段回放流量下比较，P95 降到 1.3 秒，长请求的 P99 也从恶化的状态恢复了。

上线时先放 1% 灰度，重点观察取消请求后 KV cache 是否回收、各用户的公平份额，以及失败重试。我的贡献是调度契约、问题诊断和实现；GPU kernel 和模型训练由同事负责。”

如果真实数据撑不起某个结论，就删掉那个数字，而不是编一个。

### 面试追问与参考回答

**对照实验的基线流量一致吗？** 回答要具体到怎么保证一致：两组用的是同一段录制的生产流量回放，模型版本和 GPU 池相同，只改调度策略。还要说明统计窗口有多长、样本量多少，P95 的改善是否超出了多次回放之间的波动。

**怎么确认长请求没有被饿死？** 光看整体 P95 不够，要单独看长请求的 P99 和最长等待时间，并说明是谁、用什么数据确认的。演示里正是因为发现长请求变差，才把硬分桶改成按等待时间提升优先级。

**为什么不直接加 GPU？** 加 GPU 能缓解排队，但成本随流量线性上涨，而且没有解决短请求排在长请求后面这一结构性问题。可以先用 trace 证明瓶颈在调度上，再说明调度改造后同样的硬件能支撑更多流量。

**出问题时怎么回滚？** 新调度策略放在开关后面，灰度期间如果公平份额或错误率越过阈值，就切回 FIFO。要能说出具体是哪几个指标、阈值是多少。
