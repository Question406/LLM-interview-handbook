## 题目

围绕真实咖啡店的点单和结账场景设计支付流程。候选人需要说清楚顾客下单、付款、门店制作，以及取消和退款时系统怎样保持一致。

> 来源：一亩三分地 OpenAI 题卡摘要（2026-10-18 用 Chrome 读取），是网站对候选人报告的二手整理，没有逐条核对原帖；收录为面经题型不代表公司官方确认。规模数字、SLO 和故障情景是手册补的练习约定。

## 思路

先把三件事分开：订单状态、库存状态和支付状态。它们各自有状态机，彼此通过业务 id 关联，而不是混在一张表的一个 `status` 字段里。

然后补上让支付可靠的几样东西：创建订单的幂等键、支付回调的去重，以及每天和支付提供方的对账。最容易出错的地方是超时。支付请求超时并不等于失败，正确做法是去查询外部支付状态，再决定是推进订单还是走补偿。

开场值得问一句规模。如果需求就是一家或一百家咖啡店，就不要先搭一个泛化的金融平台，把时间花在状态和失败语义上更划算。

## 完整非编程练习（场景与参考回答）

### 具体题目与需求澄清

设计 100 家咖啡店的预付点单系统：每天 100 万单，峰值 500 单/秒。流程包括下单、支付、店内制作、取消和退款，先限定每张订单只属于一家门店。

开始回答时先复述这些范围，再问面试官是否要改用户类型、数据规模、一致性要求或失败语义。

### 一套可展开的参考答案

**1. 架构与关键路径。** 请求依次经过这些组件：

1. 客户端提交订单到订单 API。
2. 订单 API 写订单库，并在同一事务里写 Outbox 事件。
3. Outbox 驱动支付适配器发起扣款，付款成功后把制作任务投到门店队列。

支付提供方负责资金交易本身；订单服务只保存业务状态和对账用的标识。

**2. 数据模型和状态变化。** 三张核心表：

- `order(id, store, user, items, total, status, version)`
- `payment(id, order, provider_id, status)`
- `event(id, order, type)`

订单状态按 `pending_payment` → paid → making → ready → completed 推进。取消和退款是两个不同状态：取消发生在付款前或制作前，退款意味着钱已经扣了，需要反向资金操作。

**3. 走一遍正常订单。** 顾客点一杯拿铁，客户端带幂等键调用下单接口，订单落库为 `pending_payment`。支付适配器带订单 id 调用提供方，拿到 `provider_id` 后写入 payment。提供方回调成功时，订单用 `version` 条件更新到 paid，同一事务写出"开始制作"事件，门店屏幕收到任务后把状态推进到 making、ready，顾客取走后为 completed。顾客在 paid 时就能看到"已付款"，制作进度是之后的异步更新。

**4. 失败、重复与恢复。**

- 创建订单的幂等键绑定用户和请求内容，重复提交返回同一张订单。
- 支付超时时先查询提供方状态，不能直接再扣一次。
- 回调按提供方的事件 id 去重；付款后 Outbox 即使重投，也只产生一个制作任务。

**5. 容量和验证指标。** 每天 100 万单平均约 11.6 单/秒，峰值 500 单/秒，是平均的约 43 倍，所以容量要按峰值设计。重点监控三项：支付成功但订单没推进的积压、退款完成时长，以及各门店的制作排队长度。

### 面试追问与参考回答

**库存应该先预留，还是付款后再确认？** 热门商品可以在下单时限时预留，过期未付款就释放；已经付款但预留过期的情况走退款。付款成功和预留到期可能同时发生，这个竞争要用带 `version` 的条件更新裁决，只能有一方生效。

**支付回调丢了，订单一直停在 `pending_payment` 怎么办？** 后台定时扫描超过阈值的待支付订单，主动向提供方查询状态并补齐。每日对账再把提供方流水和本地 payment 表逐笔比对，找出"钱扣了但订单没推进"或"订单 paid 但没有流水"的差异。
