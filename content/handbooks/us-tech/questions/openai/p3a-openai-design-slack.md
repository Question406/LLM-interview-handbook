## 题目

设计一个类似 Slack 的企业聊天系统，涵盖消息、通知、跨设备投递和扩展。

> 来源：一亩三分地 OpenAI 题卡摘要（2026-10-18 用 Chrome 读取），是网站对候选人报告的二手整理，没有逐条核对原帖；收录为面经题型不代表公司官方确认。规模数字、SLO 和故障情景是手册补的练习约定。

## 思路

每条消息有稳定的 id 和会话内的序列号。"已经存下来"和"已经推到设备"是两个不同的确认，要分开。

离线设备按自己的游标补取缺失消息，推送重复时客户端按 id 去重。大群按活跃度采用推拉结合；热点会话可以单独分区，但分区策略不能破坏会话内的排序契约。

## 完整非编程练习（场景与参考回答）

### 具体题目与需求澄清

企业聊天支持私信、频道、多设备、离线补取和大频道。顺序只保证频道内有序，不要求全局有序。

开始回答时复述这些范围，问面试官是否需要线程回复、搜索和已读回执。

### 一套可展开的参考答案

**1. 架构与关键路径。**

1. 客户端调用会话 API 发送消息。
2. 消息写入按 conversation 分片的持久消息日志。
3. fanout 服务把消息推给在线设备的连接。

搜索索引和通知异步消费消息日志，不阻塞消息落库。

**2. 数据模型和状态变化。** `message(conversation, seq, id, sender, body)`、membership 和 `device_cursor`。发送带幂等键，重试时返回同一条消息；设备按 seq 补取。

**3. 走一遍一条频道消息。** Alice 在 #eng 发"部署好了"，客户端带幂等键调用 API。消息服务把它追加到 #eng 所在分片的日志，分配 seq=1042，持久化成功后才回复 Alice"已发送"。fanout 查 #eng 的成员，把消息推给 Bob 的手机和笔记本；笔记本当前离线，它的 `device_cursor` 停在 1040，下次上线时拉取 1041 和 1042。

**4. 失败、重复与恢复。**

- 持久写成功之后才向发送端确认。
- 推送丢了可以靠补取恢复；重复推送用 id 去重。
- 成员退群后，旧链接和缓存也要重新鉴权，不能只在加入时检查一次权限。

**5. 容量和验证指标。** 监控持久确认延迟、设备缺口的恢复时间和热点会话分片负载。大频道可以只推通知、让客户端再拉正文，避免每条消息同步写进百万个设备队列。

### 面试追问与参考回答

**多地域部署时顺序怎么保证？** 每个频道选一个权威区域，或者走一条一致写路径。网络分区时要在可用性和顺序之间取舍，不能承诺零延迟的全球总序。

**同一用户的手机和电脑怎样同步已读状态？** 已读是一个按用户记录的游标（读到某个 seq），任一设备推进它后作为事件广播给该用户的其他设备。它和每台设备的投递游标 `device_cursor` 是两回事。
