## 题目

设计一个实时双人在线象棋系统，包括对局、评级匹配和由服务端管理的棋钟。

> 来源：一亩三分地 OpenAI 题卡摘要（2026-10-18 用 Chrome 读取），是网站对候选人报告的二手整理，没有逐条核对原帖；收录为面经题型不代表公司官方确认。规模数字、SLO 和故障情景是手册补的练习约定。

## 思路

核心是每盘棋只有一个权威：一个服务端状态机负责校验走子合法性并扣减棋钟。每次成功走子让版本号加一，客户端断线重连时报告自己看到的最后版本，服务端把之后的事件补给它。

棋钟不需要每秒写一次数据库。只要记录"上次走子的服务端时间"和双方剩余时长，任何时刻的剩余时间都能算出来；只有走子、超时这类事件才落库。

匹配池按评级配对，等待越久可接受的评级差越大。断线、重复走子和超时判负这三件事必须由同一个权威裁决，否则会出现双方看到不同结局。

## 完整非编程练习（场景与参考回答）

### 具体题目与需求澄清

一百万在线连接、同时十万局。支持实时双人对弈、评级匹配、断线恢复和权威棋钟，走子顺序以服务端为准。

开始回答时复述这些范围，问面试官是否需要观战、悔棋或多种时间规则。

### 一套可展开的参考答案

**1. 架构与关键路径。** 网关维护 WebSocket 连接，按 game id 把消息路由到这盘棋的权威处理器。匹配服务按评级范围找对手，范围随等待时间扩大。事件日志加定期快照用来在进程崩溃后恢复局面。

**2. 数据模型和状态变化。** game 记录 FEN、`side_to_move`、version、双方剩余时长，以及上一次确认走子的服务端时间。move 记录 game、version 和 `client_move_id`。

**3. 走一遍正常走子。** 白方在 version 12 时走 e4，客户端发送 `(game, version=12, client_move_id, e2e4)`。权威处理器确认轮到白方、着法合法，用单调时钟算出白方这步用时并从剩余时长里扣掉，写入事件日志后把 version 改为 13，再把新局面和双方时钟推给两端。黑方的计时从这次提交的服务端时间开始。

**4. 失败、重复与恢复。**

- 同一个 version 只接受一次合法走子；重复的 `client_move_id` 直接返回原结果。
- 处理器进程崩溃后，从最近快照加日志重放恢复局面。
- 客户端重连时先补齐 `last_seen_version` 之后的事件，再恢复实时推送。

**5. 容量和验证指标。** 棋钟按走子事件之间的单调时钟差扣减，不做每秒写库。监控权威提交时延、重连成功率和超时判负的争议数。容量按连接数和平均每局的走子频率估算。

### 面试追问与参考回答

**两台服务器同时以为自己在管同一盘棋怎么办？** 需要租约加 fencing epoch：接管时拿到更大的 epoch，存储只接受当前 epoch 的写入。不能依赖负载均衡器"通常只会路由到一台"。

**一方在最后一秒走子，同时服务端判他超时，听谁的？** 以权威处理器的服务端时钟为准：走子消息到达时如果剩余时间已经耗尽，就判超时，否则接受走子。两件事在同一个状态机里串行处理，所以不会同时成立。
