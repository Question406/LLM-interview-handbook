## 题目

设计一个短链服务：把长 URL 转成短码，并提供可靠的重定向。

> 来源：一亩三分地 OpenAI 题卡摘要（2026-10-18 用 Chrome 读取），是网站对候选人报告的二手整理，没有逐条核对原帖；收录为面经题型不代表公司官方确认。规模数字、SLO 和故障情景是手册补的练习约定。

## 思路

短码有两种生成方式：把全局唯一 id 编码成短字符串，或者随机生成再检测碰撞。重定向路径先查缓存，未命中再查持久映射。

开场要问清楚是否支持自定义短码、是否会过期、能否修改目标地址，因为这几点决定了缓存怎样失效。热点链接要防缓存击穿，同时预留处理滥用链接的接口。

## 完整非编程练习（场景与参考回答）

### 具体题目与需求澄清

支持创建短链、跳转、过期和可选的自定义 alias。写读比假设 1:100，跳转 P99 &lt;50ms。

开始回答时复述这些范围，问面试官是否需要点击统计和链接修改。

### 一套可展开的参考答案

**1. 架构与关键路径。** 写路径：创建 API 生成唯一 id 或随机短码，写入持久映射。读路径：重定向网关先查本地缓存，再查共享缓存，最后回源数据库。点击分析事件异步发送，不阻塞跳转。

**2. 数据模型和状态变化。** `mapping(code, long_url, owner, expires_at, status, version)`。自定义 code 由唯一约束保证不重复；禁用状态参与缓存版本，禁用后旧缓存会失效。

**3. 走一遍创建和跳转。** 用户提交一个长 URL，服务拿到下一个唯一 id 并编码成 7 位短码，写入 mapping 后返回短链。别人点开短链时，网关在本地缓存没命中，查共享缓存也没命中，回源数据库读到 mapping，确认没过期、没禁用，写回缓存后返回 302 和 `long_url`。之后的点击直接命中缓存。

**4. 失败、重复与恢复。**

- 随机短码碰撞就重试，或者直接改用唯一 id 编码。
- 缓存命中时仍然检查是否过期；链接被禁用时主动撤回热点缓存。
- 数据库慢的时候，对未知 code 也不能返回任意默认 URL。

**5. 容量和验证指标。** 一亿次日跳转平均约 1157 次/秒，峰值需要单独假设。按热点分布估算缓存容量，监控命中率、数据库回源量和恶意重定向。

### 面试追问与参考回答

**用 301 还是 302？** 可以修改目标的短链用 302 或短期缓存，方便更新。永远不变的链接可以用 301，但浏览器缓存之后很难撤回。选哪个必须和产品契约一致。

**用自增 id 编码会不会让别人猜出所有短链？** 会，相邻的码能被枚举。如果链接需要一定私密性，可以对 id 做可逆的混淆后再编码，或者改用足够长的随机短码并承担碰撞检测的成本。
