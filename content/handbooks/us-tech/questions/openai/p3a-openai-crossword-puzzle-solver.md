## 题目

设计一个基于大词典的填字游戏求解服务，要求能把搜索分摊到多台机器，并在找到解后尽早终止。

> 来源：一亩三分地 OpenAI 题卡摘要（2026-10-18 用 Chrome 读取），是网站对候选人报告的二手整理，没有逐条核对原帖；收录为面经题型不代表公司官方确认。规模数字、SLO 和故障情景是手册补的练习约定。

## 思路

单机算法先讲清楚：用词长和交叉位置上已确定的字母为每个槽位建立候选集，每次选候选最少的槽位展开，填一个词后把约束传播给交叉槽位，候选变空就回溯。

分布式部分要克制。只有搜索前沿足够大时才切分工作，否则来回传输巨大的搜索状态反而更慢。找到解后发布终止信号，让其他 worker 安全停下。还要说明一点：分布式不能消除最坏情况下的指数复杂度。

## 完整非编程练习（场景与参考回答）

### 具体题目与需求澄清

50×50 棋盘、大约 100 个槽位、百万词的词典。返回任意一个合法解，允许无解，要求能限时和取消。分布式只是性能手段，不改变正确性。

开始回答时复述这些范围，问面试官同一个词能否重复使用。

### 一套可展开的参考答案

**1. 架构与关键路径。** 求解按这些阶段进行：

1. 按"词长 + 某位置的字母"建立词典索引。
2. 根据已知字母求出每个槽位的候选集，并传播约束。
3. 选候选最少的槽位做 DFS。
4. 前沿足够大时，把分支拆成 worker 任务。
5. 协调者接收第一个解，并终止其他分支。

**2. 数据模型和状态变化。**

- `search_job(board, dictionary_version, budget)`
- `branch(assignments, remaining_candidates, seed, state)`

分支 id 是确定的、可以重放；前沿保存的状态足够让任务在别处恢复。

**3. 走一遍一次求解。** 请求到达后建 `search_job`，协调者先在本地做约束传播，发现某个 5 字母横槽只剩 3 个候选，就按这 3 个词拆成 3 个 branch 分给 worker。某个 worker 在自己的分支里继续"选最少候选槽 → 填词 → 传播"，直到所有槽位填满，上报完整赋值。协调者独立校验全部交叉约束后提交为 winner，再给同一 job 的其他分支发取消。

**4. 失败、重复与恢复。**

- worker 失联可以重跑同一个分支，结果按 branch id 去重。
- 找到解后先独立校验全部交叉约束，再提交 winner。
- 取消信号带 job epoch，防止旧任务在取消后继续发布结果。

**5. 容量和验证指标。** 测节点展开数、约束收缩率、worker 空闲比例、状态传输字节数和首个解的时延。只加 worker 而不剪枝，大部分算力可能都会浪费掉。

### 面试追问与参考回答

**一定能在限时内解出来吗？** 不能保证，最坏情况仍是指数级。要判定无解必须穷尽搜索空间；如果是预算耗尽，就明确返回"超时未找到"，不能宣称无解。

**为什么每次选候选最少的槽位？** 候选少的槽位分支因子小，而且如果它没有可行词，能最早暴露矛盾并回溯，从而剪掉大片搜索树。
