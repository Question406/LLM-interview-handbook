## 题目

设计一个简单的 AI 聊天系统。题目有一个明确限制：服务端不能持久化对话内容。

> 来源：一亩三分地 OpenAI 题卡摘要（2026-10-18 用 Chrome 读取），是网站对候选人报告的二手整理，没有逐条核对原帖；收录为面经题型不代表公司官方确认。规模数字、SLO 和故障情景是手册补的练习约定。

## 思路

既然服务端不存对话，会话、消息和流式增量就都在客户端本地维护。服务端只负责认证、限额，以及代理对模型的请求（模型密钥不能下发到浏览器）。

本地用消息 id 区分并发的多次生成。刷新后能否恢复、多个标签页怎样同步，取决于本地存储的契约。先和面试官确认隐私和容量要求，再选 IndexedDB 之类的存储。不要违背题意偷偷加一个服务端聊天库。

## 完整非编程练习（场景与参考回答）

### 具体题目与需求澄清

聊天状态只存在浏览器里，支持多会话、流式生成、取消和刷新恢复。服务端不保存对话，但负责代理模型密钥。

开始回答时复述这些限制，问面试官是否需要支持多设备，以及服务端日志能否记录请求元数据。

### 一套可展开的参考答案

**1. 架构与关键路径。**

1. 浏览器里的会话模型读写 IndexedDB。
2. 发送消息时用 SSE 或 fetch streaming 请求服务端。
3. 服务端做鉴权和限额，再转发给模型。

用户输入和生成过程是两个独立的生命周期：输入已保存，生成可以失败或重试。

**2. 数据模型和状态变化。** 本地有 conversation、message、run 和 `chunk_cursor`。每次生成有一个 request id；消息状态为 draft / streaming / done / failed。编辑旧消息时要么产生分支，要么有明确的覆盖规则。

**3. 走一遍发送一条消息。** 用户输入问题回车，前端先把这条用户消息写入 IndexedDB，再新建一个 run 和一条 streaming 状态的助手消息。前端从本地取出这个会话的上下文，连同 request id 发给服务端；服务端校验身份和额度后转发给模型，并把流式片段原样转回。前端每收到一段就追加到助手消息并推进 `chunk_cursor`，流结束时把状态改为 done。服务端请求结束后不留任何对话内容。

**4. 失败、重复与恢复。**

- 掉线时保留已收到的片段，并把消息标为 failed。
- 重试时新建一个 run，或者复用明确支持断点恢复的 run。
- 多个标签页通过版本号或广播协调，不能同时写坏同一个会话。

**5. 容量和验证指标。** 监控首 token 时延、流式渲染帧率、浏览器存储配额错误和取消响应速度。对话太长时分页加载；本地删除消息后，下一次请求的上下文里要立即不再包含它。

### 面试追问与参考回答

**用户想跨设备同步怎么办？** 题目禁止服务端保存聊天，所以默认不支持。可以让用户显式导出和导入，或者和面试官重新讨论端到端加密同步的范围。

**用户清了浏览器数据，聊天记录还能找回吗？** 不能，这是"服务端不存对话"直接带来的后果，产品上应该提前告诉用户，并提供导出入口。
