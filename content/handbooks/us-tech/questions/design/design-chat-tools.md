Amazon Seller / 买家客服、Google 账户支持、Microsoft Copilot 工单、Apple 支持都会问这题。Bedrock 给的是托管检索和 agent 底座；Apple 强调接地和隐私。白板要的是路由、工具确认、升级包、事故。不是某次现场逐字题。检索细节见 `design-prod-rag`，工具预算见 `design-agent-harness`。

## 路由：政策、动作、人工

我会先问：能否动金钱和账号、工单系统 API、政策更新频率、是否要引用、p95、人工队列 SLA、多语言。然后把对话做成显式状态，而不是「一个大模型看着所有 API」。

三类意图：

1. **只读问答。** 保修、政策、操作步骤。RAG，答案必须带 `chunk_id`，对不上就说「政策没写」并给人工入口。过期条款事故定义同企业 RAG。
2. **写操作。** 查订单、改地址、退款、改密。走工具：先读后写，写前确认框（金额、订单号、用户看到的明文参数）。鉴权：会话里的用户 id 必须等于资源所有者，模型不得把「帮我朋友退款」绕过。幂等键防重复退款。
3. **升级人工。** 用户明确要求、模型低置信、政策规定必须人审（欺诈、医疗、法律）、情绪升级、工具连续失败。升级不是认输，是产品路径。

路由可用小分类器 + 规则，不必每轮都上大模型。分错的代价：该退款时只贴政策，或该拒答时直接退款。高风险意图默认保守，宁可多一次确认。

工单：创建 / 追加 / 关单都是工具。字段：意图、引用过的政策版本、已调用工具和结果、用户确认记录、建议动作。人工接过来不应再问一遍订单号——那是 harness 没把状态传过去。

## 延迟、权限、失败模式

p95 拆：意图分类、RAG 检索、工具 RPC、生成。读路径可以对齐 2 秒级；写路径可以更慢但必须有进度（「正在查订单」）。工具并行：查订单和查政策可以一起；写操作必须等确认。流式输出时，引用校验仍按句，不能先许诺退款再在最后改口。

权限：政策文档 ACL、订单 PII、工具凭证。日志脱敏。模型上下文里的订单属于当前用户，切换账号要清会话。存在性泄漏：不能让用户 A 靠客服话术探测用户 B 的订单。

失败模式：政策日更但索引滞后，机器人引用作废条款同意退货；模型把两段政策拼成「可以退款」但其实互斥；确认 UI 和 JSON 不一致；遏制率 KPI 导致系统死活不升级，用户被循环话术；人工队列被当成垃圾桶，升级包是空的。错误退款率、重复工单率是一等指标。

退款我会写成状态，而不是「模型决定退不退」：查订单 → 拉政策块 → 算是否满足窗口 → 展示确认（金额、订单号）→ 用户点了才调退款 API。政策含糊或金额超过自动阈值，直接升级并附上这四步的证据。幂等键用 `(user_id, order_id, intent)`，重试不得二次打款。

## 指标和发布

线上：遏制率（未升级且用户解决）、CSAT、错误退款 / 错误改密、过期引用、升级精确率（该升的升了）、p95、人工处理时延。遏制率和 CSAT 一起看：遏制很高、CSAT 掉，是在强行自助。离线：政策问答接地、工具参数准确（订单号、金额）、升级决策和金标。A/B 护栏是金钱和安全事故，见 `design-eval-platform`。

评测集要含对抗：用户自称是管理员、社会工程套退款、把过期截图当政策。这些是内容安全 + 工具权限，不是 RAG 召回问题。

发布闸门我会写成：接地准确、错误退款率、过期引用、p95、人工 SLA。缺一项不发。遏制率单独看会激励系统死活不升级。

升级包最小字段：对话摘要、引用过的 `chunk_id` 和文档时间、已调用工具及响应码、用户确认/取消、建议动作。人工 SLA 和机器人 p95 分开报。机器人很快但升级包是空的，总时长仍会爆。

## 追问

- **为什么不把所有政策微进模型？** 日更和引用对不上。参数记忆没有 `chunk_id`，作废也无法分钟级生效。
- **用户说「你就退吧」？** 不是授权。仍走鉴权和政策工具；政策不允许就拒并升级。
- **多轮把上下文撑爆？** 摘要已确认事实和工具结果，政策块每次按当前问题重检索，不要无限追加旧块。
- **和纯 Agent 题的差别？** 客服多了工单状态机、金钱确认、人工 SLA。harness 通用件复用，产品约束更硬。
