## 真题记录

- 公司：美团
- 团队 / 岗位：大模型算法
- 届别 / 流程：原帖未披露；一面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“对比 Memory 机制与 RAG 检索增强的区别、优势和落地场景差异”**

RAG 和 Memory 解决的是两件事。RAG 回答「这次需要哪段外部知识」，强调新鲜、可引用；Memory 回答「跨轮、跨会话要记住什么」，强调任务连续和少重复问。生产里通常组合用：检索增强生成（RAG）取事实，Memory 约束个性化，但写入、权限和评测要分开做，冲突时权威知识库优先于未确认的记忆。

美团到店和配送场景两种都有。用户说「还是老样子」，Memory 提供槽位，比如花生过敏、公司地址；RAG 提供当前可点的菜和库存。如果知识库写着「该店已停花生酱」，记忆里一条没确认过的、和它矛盾的条目就不能覆盖它。场景选错了会出问题：用 Memory 记菜单，菜单会过期；用 RAG 记过敏原，容易漏写，也很难遗忘。

RAG 这边，菜单、满减规则、配送政策、配送范围、商品库按 query 检索后写进当前上下文，要做新鲜度控制和租户过滤。索引更新走发布流程，对话中一般不自动改写知识库。好处是事实可追溯，过时了靠重建索引；风险是漏召、切片过时、生成越界。

Memory 这边，过敏原、常订地址、未完成订单、已确认的口味要经过抽取、确认、版本化才能写入，还要支持遗忘和审计。好处是任务连续、少重复问；风险是隐私，以及错误记忆污染后面的决策。没校验过的模型摘要不能当长期事实，污染怎么纠错见 `byte-memory-pollution`。把整段聊天记录都叫 Memory，或者说「Memory 就是个人 RAG」，都不对：整段聊天当 Memory，开销大，还会把错误和无关信息一起留下。

| | RAG | Memory |
| --- | --- | --- |
| 内容 | 文档 / 商品 / 政策 | 偏好、任务状态、历史决策 |
| 写入 | 索引更新 | 抽取并确认后写入 |
| 风险 | 检索错、过时 | 隐私、错误记忆 |
| 评测 | 引用正确、grounded | 长期任务成功、冲突解决 |

权限也分开管。RAG 按门店、城市过滤；Memory 按用户加密、最小注入，和当前意图无关的偏好不要灌进 prompt。Memory 还要提供可删除、可导出的接口，满足遗忘。评测同样分开：RAG 看召回与忠实，Memory 看跨会话任务成功、错误记忆有没有被引用。放到上下文工程里看，检索进窗口的是证据，记忆进窗口的是已确认状态，见 `byte-rag-memory-context`。落地前我会先问清三件事：这条信息谁有权改、过期了怎么发现、冲突时听谁的。

如果一面追问「各自的优势」，我会按场景说：RAG 的优势是外部事实可引用、可更新，Memory 的优势是跨单连续、少重复问，比谁更先进没有意义。记忆的分类见 `agent-memory`，京东零售的连问见 `jd-long-memory`。

## 追问

**聊天记录向量化算 Memory 吗？**
最多算粗糙的情景日志。没有确认、失效条件和权限，污染起来比没有记忆更糟。

**用户改口怎么处理？**
显式修正优先，旧条目失效并留审计。别让两条矛盾的记忆一起被检索出来，让模型去猜。

**只用 RAG 模拟 Memory 行不行？**
把用户档案当文档检索可以起步，但缺少写入 acceptance checks 和遗忘，高风险字段还是要用结构化 Memory。

**和 Skill 怎么分？**
Skill 是做法，比如怎么点餐、怎么改地址；Memory 是状态，比如过敏原、默认地址，见 `jd-skills-essence`。
