## 真题记录

- 公司：美团
- 团队 / 岗位：大模型算法
- 届别 / 流程：原帖未披露；一面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“对比 Memory 机制与 RAG 检索增强的区别、优势和落地场景差异”**

这块容易直接答成把整段聊天记录都叫 Memory，或说「Memory 就是个人 RAG」。美团到店 / 配送场景里，菜单和政策要可引用、可更新，过敏原和常订地址要跨单记住。两者解决的问题不同，写入、权限和评测也不同。生产常组合：RAG 取事实，Memory 约束个性化；冲突时权威知识库优先于未确认记忆。分类见 `agent-memory`，京东零售连问见 `jd-long-memory`。

## 一个取外部知识，一个沉淀状态

RAG 回答「这次需要哪段外部知识」：菜单、配送政策、商品库按 query 检索后写入当前上下文，强调新鲜度、可引用、租户过滤。索引更新是发布流程，对话中一般不自动改写知识库。优势是事实可追溯、过时靠重建索引；风险是漏召、过时切片、生成越界。

Memory 回答「跨轮 / 跨会话要记住什么」：过敏原、常订地址、未完成订单、已确认的口味。写入必须经过抽取、确认、版本化，并支持遗忘与审计。优势是任务连续、少重复问；风险是隐私、错误记忆污染后续决策。字节侧污染纠错见 `byte-memory-pollution`。不要把未校验的模型摘要当长期事实。

| | RAG | Memory |
| --- | --- | --- |
| 内容 | 文档 / 商品 / 政策 | 偏好、任务状态、历史决策 |
| 写入 | 索引更新 | 抽取并确认后写入 |
| 风险 | 检索错、过时 | 隐私、错误记忆 |
| 评测 | 引用正确、grounded | 长期任务成功、冲突解决 |

## 落地：组合，但分库分权

场景：菜单 / 满减规则 / 配送范围用 RAG；「记住我花生过敏 / 公司地址」用 Memory。用户说「还是老样子」时，Memory 提供槽位，RAG 提供当前可点的菜和库存。冲突：知识库写「该店已停花生酱」，未确认记忆不能覆盖。提供可删除、可导出接口，满足遗忘。

权限分开：RAG 按门店 / 城市过滤；Memory 按用户加密、最小注入，当前意图不相关的偏好不要灌进 prompt。评测也不要混：RAG 看召回与忠实；Memory 看跨会话任务成功、错误记忆是否被引用。和上下文工程的关系见 `byte-rag-memory-context`：检索进窗口的是证据，记忆进窗口的是已确认状态。整段聊天当 Memory，既贵又脏。一面若追问「优势」，不要比较谁更先进：RAG 的优势是可引用、可更新的外部事实；Memory 的优势是跨单连续和少重复问。场景选错会反过来，用 Memory 记菜单会过期，用 RAG 记过敏原会漏写且难遗忘。落地检查三问：这条信息谁有权改、过期怎么发现、冲突听谁的。三问答不清，就还没到上线组合系统的时候。

## 追问

- **聊天记录向量化算 Memory 吗？** 最多算粗糙情景日志。没有确认、失效条件和权限，污染会比没记忆更糟。
- **用户改口怎么处理？** 显式修正优先，旧条目失效并留审计，不要两条矛盾记忆一起检索让模型猜。
- **能不能只用 RAG 模拟 Memory？** 把用户档案当文档检索可以起步，但缺少写入门禁和遗忘，高风险字段仍要结构化 Memory。
- **和 Skill 怎么分？** Skill 是做法（怎么点餐改地址），Memory 是状态（过敏原、默认地址），见 `jd-skills-essence`。
