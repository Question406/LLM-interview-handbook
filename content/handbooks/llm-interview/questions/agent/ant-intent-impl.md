## 真题记录

- 公司：蚂蚁集团
- 团队 / 岗位：大模型
- 届别 / 流程：一面
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“是否做过意图识别？如果要做意图识别，可以怎么实现？”**

没做过也可以这样讲：先定意图表和每类要确认的槽位，明确的情况用规则拦，剩下的交给小分类器或 LLM，低置信就向用户澄清；评估按意图分别看精确率和召回，再单独算错进高风险流程的代价。在这类场景里，意图识别决定请求进哪个流程，一上来就让端到端 Agent 自己猜用户是要转账还是投诉，风险太大。

举个例子，用户说「上次那笔钱怎么还没到，我不想转了」，里面可能同时有查询、投诉、撤销转账几个意图。分类器给出的分布要是很散，就该问一句「您是想先查进度，还是撤销这笔转账」，硬路由进转账流程是最糟的结果。

落地顺序大概是这样。先定义意图表和槽位，把不允许静默猜测的高风险类单独拎出来，比如转账、改绑、额度、销户，每类写清要澄清哪些槽、哪些默认值禁止用。然后用规则先拦明显的 case，订单号、卡号、固定话术、关键词黑白名单，这样能减少模型在明显情况上的抖动。剩下的交给小分类器或 LLM 做多标签，输出意图分布和置信度，低置信或多意图并行时澄清，别硬路由。数据从日志抽样，专门补否定、反讽、多意图、口语、方言这些难例。评估时宏平均不够，要按意图切片看精确和召回，并单列「错成高风险意图」的代价。具体可以先冻结 20 个高频意图和 5 个高风险意图，规则覆盖能覆盖的，其余进分类器；高风险类先追求精确率，长尾再补召回。

和 Agent 接起来时，高确定、低风险的请求，规则或小模型直接走工作流；模糊、多槽的进入带状态的澄清循环，一次 function call 解决不了。意图只决定走哪条技能或哪组工具，执行时还要鉴权，见 `agent-tool-permissions`；工具怎么选见 `agent-tool-routing`。金融场景宁可多一轮澄清，也别把投诉打成支付。也别指望「大模型什么都能分」来替代 taxonomy，没有意图表，就没法回归，也算不出误路由成本。taxonomy 要版本化，新增意图不能悄悄改掉旧类的含义，不然历史标注就全废了。上线后用人工抽检和用户改写率看漂移，指标设计可以对照 `jd-intent-accuracy`，意图恢复见 `kuaishou-agent-intent-recovery`。

## 追问

**为什么不让 Agent 直接选工具？**
可以放在后段。前段意图识别把高风险动作挡在路由层，工具层再验权，两道闸比单靠模型选 tool 稳。

**多意图怎么办？**
拆成主意图加次意图，或者先问「这次先处理哪件」。合并成一个超级意图，槽位和权限都会爆炸。

**用小模型还是 LLM？**
高频、feedback loop、标签稳定的用小模型；长尾、口语化、需要解释的用 LLM，低置信时再升级。

**没有标注怎么冷启动？**
先用规则加少量种子数据，再从日志做主动学习；先保证高风险类的精确率，再铺长尾召回。
