- 原始措辞：**“如果一个agent误判导致策略冲突，如何处理？”**

一个 Agent 误判造成策略冲突，先停下冲突的 action、冻结相关资源的写入，再用证据、权限和版本回放找出是谁误判；能按预先声明的 invariant 自动仲裁的就仲裁，证明不了安全的就升级给人；已经发生的副作用做补偿或人工确认，误判样本写回评测和训练。让另一个 Agent 用自然语言去「说服」冲突方继续执行是常见的错法，共享状态上的口头协商不可审计、不可重放，也拦不住已经发出去的写操作。

举个例子，两个 Agent 对同一个文件给出了相反的 patch，其中一个基于的还是旧版本。先要把冲突定义成能检测的状态：对同一资源提出互斥目标、基于过期版本写入、或者证据撑不起高风险动作，光是两个意见不一样还不算冲突。高风险写操作要有 lease / capability；一旦发现互斥、版本不一致或证据不足，协调器暂停相关分支，记下每个 Agent 的 proposal、输入证据、置信度、权限和 action plan。没有这份快照，后面没法判断是谁误判。

冻结范围尽量小，只锁冲突的资源，别把整个系统停掉，读操作可以继续，写操作进队列。权限本身也可能是冲突源：一个 Agent 有写仓权限，另一个只有读，却都在改同一份配置。所以仲裁的输入里必须有 ACL，比谁更「自信」没有意义。团队内部人、仓、命令的授权见 `byte-team-agent-security`。

仲裁规则要预先写在协调器里，按业务 invariant 和风险等级来，比如「测试必须绿才能合入」「生产密钥不可进上下文」「同一文件同一时刻只有一个 writer」，别临场让模型投票。两个 proposal 都满足 invariant 时，选 diff 更小的、证据等级更高的，或者更早拿到 lease 的那个。证明不了安全，比如证据矛盾、权限不足、影响面里有不可逆副作用，就升级给用户或人工 reviewer，附上冲突摘要和可选项。升级算不上失败，是把自动判定不了的决策交回给负责的人。再开一个裁判 Agent 也解决不了治理问题，裁判要是没有独立的证据通道，只是把幻觉升了一级。

如果冲突发生时已经改了文件、发了请求、写了记忆，就按补偿事务一步步撤销已完成的操作，并说清哪些不可逆，比如对外邮件、支付、没备份的删库。可逆的做补偿并校验终态，不可逆的先停止扩大、保留审计、等人确认。之后用 execution graph 定位误判来源：输入被污染、路由错了、工具 Observation 错了，还是两条 policy 本身就不一致。这条轨迹标成 bad case，再补对抗性的冲突评测，比如两个 Agent 对同一文件给出相反 patch。原则是隔离状态和权限、保留可重放的审计。单 Agent 执行层的工具失败重试见 `byte-tool-fail-retry`，这张卡讲的是多 Agent 策略层，别混成「再 retry 一次」。多 Agent 协作形态见 `baichuan-multi-agent-collab`，什么时候不该上多 Agent 见 `pdd-multi-vs-single-agent`。

## 追问

**为什么不能让 Agent 互相说服？**
自然语言协商没有幂等和权限检查，失败也没法回放。协调器要消费结构化的 proposal，聊天记录不算数。

**lease 断了怎么办？**
超时回收，禁止凭过期 lease 写入，冲突方重新申请。别默认「谁还活着谁赢」。

**误判样本怎么用？**
按原因分组统计，检索污染、路由错、观察错、policy 冲突，分别去改数据、工具描述、执行器或仲裁规则。统一再训一个「更听话」的模型解决不了。

**单 Agent 会不会也有策略冲突？**
会，表现为计划和工具结果对不上，或者记忆和测试不一致。处理方法一样，冻结高风险写、用证据仲裁；多 Agent 只是把冲突摆到了明面上。
