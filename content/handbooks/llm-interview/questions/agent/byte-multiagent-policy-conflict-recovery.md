- 原始措辞：**“如果一个agent误判导致策略冲突，如何处理？”**

陷阱是让另一个 Agent 用自然语言「说服」冲突方继续执行。共享状态上的口头协商不可审计、不可重放，也挡不住已经发出的写操作。这面要先把冲突定义成可检测状态，停掉冲突 action、冻结共享写入，再靠证据、权限和版本回放定位误判；能自动仲裁的按预先声明的 invariant 处理，不能证明安全就升级。多 Agent 协作形态见 `baichuan-multi-agent-collab`，何时不该上多 Agent 见 `pdd-multi-vs-single-agent`。

## 先检测、停写，再谈仲裁

冲突不是「两个意见不一样」，而是：对同一资源提出互斥目标、基于过期版本写入、或证据不足以支撑高风险动作。高风险写操作要有 lease / capability；发现互斥、版本不一致或证据不足时，协调器暂停相关分支，记录每个 Agent 的 proposal、输入证据、置信度、权限与 action plan。没有这份快照，后面无法判断是谁误判。

冻结范围要尽量小：只锁冲突资源，不要把整个系统停掉。读操作可以继续，写操作进队列。权限本身也可能是冲突源——一个 Agent 有写仓权限、另一个只有读，却都在改同一配置——所以仲裁输入必须含 ACL，而不是只比谁更「自信」。团队内部的人/仓/命令授权见 `byte-team-agent-security`。

## 仲裁规则要预先声明，无法证明安全就升级

可自动解决的冲突按业务 invariant 和风险等级：例如「测试必须绿才能合入」「生产密钥不可进上下文」「同一文件同一时刻只有一个 writer」。规则要写在协调器里，而不是临场让模型投票。两个 proposal 都能满足 invariant 时，可选更小 diff、更高证据等级、或更早获得 lease 的一方。

无法证明安全——证据矛盾、权限不足、影响面含不可逆副作用——就升级给用户或人工 reviewer，并附上冲突摘要和可选项。升级不是失败，是把不可自动判定的决策交回有责任的人。不要用「再开一个裁判 Agent」假装解决了治理问题；裁判若没有独立证据通道，只是把幻觉升了一级。

## 已有副作用：补偿，并回流评测

若冲突发生时已经改了文件、发了请求、写了记忆，按 saga / compensating action 恢复，并明确哪些操作不可逆（对外邮件、支付、删库无备份）。可逆的做补偿并校验终态；不可逆的停止放大、保留审计、等人确认。

之后用 execution graph 定位误判：输入污染、路由错误、工具 Observation 错误，还是两条 policy 本身不一致。轨迹标为 bad case，补上对抗冲突评测（两个 Agent 对同一文件给出相反 patch）。原则是隔离状态和权限、保留可重放审计。工具失败重试见 `byte-tool-fail-retry`，那是单 Agent 执行层；本卡是多 Agent 策略层，不要混成「再 retry 一次」。

## 追问

- **为什么不能让 Agent 互相说服？** 自然语言协商没有幂等和权限检查，失败不可回放。协调器要消费结构化 proposal，而不是聊天记录。
- **lease 断了怎么办？** 超时回收、禁止凭过期 lease 写入，冲突方重新申请。不要默认「谁还活着谁赢」。
- **误判样本怎么用？** 按原因分桶：检索污染、路由错、观察错、policy 冲突，分别改数据、工具描述、执行器或仲裁规则，而不是统一再训一个「更听话」的模型。
- **单 Agent 会不会也有策略冲突？** 会，表现为计划与工具结果、或记忆与测试不一致。处理仍是冻结高风险写、用证据仲裁；多 Agent 只是把冲突表面化了。
