## 真题记录

- 公司：京东
- 团队 / 岗位：Agent 开发
- 届别 / 流程：27 暑期实习；二面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“除了导购，你认为在电商领域（如京东）还有哪些场景可以用到 Agent？”**

陷阱是报十个业务名词，或把库存扣减、价保打款也交给 Agent「自动决策」。京东这面要的是：场景带工具、带风险、带评测。路径事先写不全但每步有 API 的，适合 Agent；强一致、高资金的写操作走 Workflow + 人审。Agent 与工作流的分界见 `meituan-workflow-vs-agent`，和 RAG 的差别见 `jd-agent-vs-rag`。

## 适合的场景：诊断、起草、排查，而不是静默写资金

可讲的例子都要落到工具：

- **广告计划诊断**：拉消耗、ROI、素材拒绝原因，输出改建议稿，不直接改出价。
- **库存周转预警**：查周转、滞销、补货建议；真正调拨需审批。
- **售后政策问答与工单归类**：检索 SOP、填工单字段、建议赔付口径；打款动作人审。
- **运营选品对比**：拉类目、评价、竞品属性，生成对比表。
- **客服侧多步查询**：订单、物流、发票，路径随用户话术变化，适合 ReAct 式探查。

共同特征：观察会改变下一步，规则树写不全，但每个动作有明确 API 和权限。导购只是「对话 + 检索 + 推荐」的一种；二面想听你有没有把 Agent 用到商家/运营/售后内部工具上。

## 不适合：强一致写链路和无审计批量改价

库存扣减、价保自动打款、无审计的批量改价、生产配置变更，这些要 Workflow + 规则 + 幂等。失败语义是钱和库存，不是「再生成一次」。Agent 可以出现在前面：解释规则、起草申请、核对材料；副作用必须走审批和可回放日志。权限模型与内部工具安全同构，见 `byte-team-agent-security` 的分层思路——身份、资源、命令、审计。

若把下单全交给模型，评测会对不准：一次幻觉 SKU 或一次重复提交，业务损失远大于导购说错一句推荐语。这时应明确说「我把 Agent 放在诊断和起草，写操作默认拒绝」。

## 答题按「场景 → 工具 → 风险 → 评测」

比列名词强。例如售后工单：工具是工单 API、订单查询、SOP 检索；风险是越权看他人订单、错误承诺赔付；评测除了答案对，还要看路由、工具选择、拒答和高风险保守性，见 `jd-agent-eval-beyond-qa`。线上再看客诉、人工接管率、越权拦截次数。

意图识别会决定进导购、进售后还是进广告诊断，测法见 `jd-intent-accuracy`。不要在这题里只聊模型品牌。二面加一句落地条件：每个场景点名 2–3 个 API（订单查询、库存、工单、广告报表），以及哪一步必须人审。没有工具和审批的「还能做客服、还能做运营」只是换皮导购，面试官听不出你有没有想过京东内部系统的副作用。

## 追问

- **导购为什么不够当唯一例子？** 导购偏检索+推荐，面试官想听你是否理解内部运营工具和副作用。
- **选品分析为什么算 Agent 而不是报表？** 因为要按自然语言目标选指标、补数、解释异常，路径不固定；固定日报仍用 Workflow。
- **能不能让 Agent 自动改广告出价？** 可以出建议和模拟，真正改出价要权限、限额、人审和回滚，不能只靠模型自信。
- **这些场景和 RAG 的关系？** SOP 问答是 RAG；查实时库存、改草稿是 Agent 调工具。RAG 常是动作之一，见 `jd-agent-vs-rag`。
