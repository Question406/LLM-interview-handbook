## 真题记录

- 公司：京东
- 团队 / 岗位：Agent 开发
- 届别 / 流程：27 暑期实习；二面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“除了导购，你认为在电商领域（如京东）还有哪些场景可以用到 Agent？”**

除了导购，我会讲商家、运营、售后这些内部场景：广告计划诊断、库存周转预警、售后政策问答和工单归类、运营选品对比、客服侧的多步查询。它们的共同点是观察会改变下一步、规则树写不全，但每个动作都有明确的 API 和权限。库存扣减、价保打款这类强一致、涉及资金的写操作，我会交给 Workflow 加人审，Agent 只负责前面的诊断和起草。

每个场景都要落到工具上讲。广告计划诊断，拉消耗、ROI、素材拒绝原因，输出改建议稿，不直接改出价。库存周转预警，查周转、滞销、补货建议，真正调拨要审批。售后这块，检索 SOP、填工单字段、给出建议的 compensation rules，打款动作人审。运营选品对比，拉类目、评价、竞品属性，生成对比表。客服侧查订单、物流、发票，路径跟着用户的话术变，适合 ReAct 式的探查。导购只是「对话 + 检索 + 推荐」这一种，二面想听的是你有没有把 Agent 用到商家、运营、售后的内部工具上。

不适合的也要说清楚。库存扣减、价保自动打款、无审计的批量改价、生产配置变更，这些要 Workflow + 规则 + 幂等，因为失败了会影响资金或库存，重新生成一遍回答也恢复不了。Agent 可以出现在它们前面，解释规则、起草申请、核对材料，副作用一律走审批和可回放的日志。权限模型和内部工具安全是同一套分层，身份、资源、命令、审计，可以参考 `byte-team-agent-security`。要是把下单全交给模型，一次 hallucination SKU 或者一次重复提交，业务损失比导购说错一句推荐语大得多，评测也对不准。所以我会明确说「我把 Agent 放在诊断和起草，写操作默认拒绝」。

答的时候按「场景 → 工具 → 风险 → 评测」讲，比列一串名词强。拿售后工单举例，工具是工单 API、订单查询、SOP 检索；风险是越权看到别人的订单、错误承诺赔付；评测除了答案对不对，还要看路由、工具选择、拒答和高风险保守性，见 `jd-agent-eval-beyond-qa`，上线后再看客诉、人工接管率、越权拦截次数。进导购、进售后还是进广告诊断，由意图识别决定，测法见 `jd-intent-accuracy`。二面可以再加一句落地条件：每个场景点名两三个 API（订单查询、库存、工单、广告报表），再说哪一步必须人审。只说「还能做客服、还能做运营」，面试官听不出你有没有想过京东内部系统的副作用。这题也别只聊模型品牌。

## 追问

**导购为什么不够当唯一的例子？**
导购偏检索加推荐，面试官想听你懂不懂内部运营工具和副作用。

**选品分析为什么算 Agent，不算报表？**
它要按自然语言目标选指标、补数、解释异常，路径不固定。固定日报还是用 Workflow。

**能让 Agent 自动改广告出价吗？**
可以出建议和模拟。真正改出价要有权限、限额、人审和回滚，光凭模型自信不够。

**这些场景和 RAG 是什么关系？**
SOP 问答是检索增强生成（RAG），查实时库存、改草稿是 Agent 调工具。RAG 常常只是 Agent 的一个动作，见 `jd-agent-vs-rag`。
