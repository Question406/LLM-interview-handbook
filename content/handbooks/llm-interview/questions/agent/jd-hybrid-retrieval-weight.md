## 真题记录

- 公司：京东
- 团队 / 岗位：大模型应用开发实习
- 届别 / 流程：实习；一面
- 面试时间：原帖未披露；帖子发布于 2026-03-14
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“如何处理问题输入不标准的情况？混合检索的权重怎么配置？”**

我会先把输入规范化，再按 query 类型动态配权重：ID、型号、专有名词偏 BM25，口语描述偏向量，租户、类目、时间作为硬过滤先做，跟权重无关。权重用验证集扫出来，看分类型的 Recall 和下游任务结果，别给 BM25 和向量拍一个固定的 $0.5/0.5$。

比如用户发来一句「我那单怎么还没到」，后面跟着一个写错一位的订单号。脏 query 直接整句 embed，稠密近邻会把错号映射到无关的近邻，帮不上忙；固定 1:1 的话，BM25 那一路又被对半稀释，整路都会失败。这时先做实体识别，识别到 ID 就走精确字段并降低向量权重，稀疏检索也要对规范化之后的串做；识别失败再走描述型。口语同义的情况正好相反，向量那一路更有用。

规范化包括纠错、繁简、大小写、商品别名，以及把口语改写成检索 query。输入不标准还包括错别字、口语省略主语、把 SKU 和活动名混在一句话里。能抽到订单号、SKU、运单号，就走精确字段，别把整句 embed。改写模型怎么选见 `baichuan-query-rewrite-model-choice`，改写是为了检索，把用户的话写得更长没有意义。规范化要可回放，trace 里同时留 raw query 和 rewrite，评测才知道失败在改写还是在检索。改写过度会丢掉唯一的型号词，太弱又召不中口语。没把握时走双路，原句走稀疏，改写走稠密，融合后再 rerank。

然后是加权。稀疏抓编号和型号，稠密抓同义，结构化过滤管租户、类目、时间。过滤是硬约束，不过滤就融合，权限和类目已经错了；$\alpha$ 可以随类型变，过滤条件不随类型放松。融合可以用 Reciprocal Rank Fusion，减少两路分数不可比的问题；也可以用 query 分类器输出权重，导航型、ID 型升高 BM25，描述型升高向量。分类器用规则（像不像 ID）加轻量模型，低置信时走 RRF 保守融合，并准备好澄清。不要对所有查询都使用同一个 $\alpha$。

## 和切块、重排一起验证

单独调一个 $\alpha$ 没有意义。切块粒度变了，稀疏和稠密的最优混合会跟着变；rerank 模型变了，召回的 $k$ 也要变。所以我会用分类型的 Recall@k 和端到端答对率一起看，外加人工看 top 结果。验证集按时间切，别用同一个运营活动的文案既调权又验收。调权记录要进配置版本，和切块、embedding 版本一起发布，免得「上周的 0.7 向量」在新索引上默默失效。

Agent 场景还要看检索到的证据有没有被引用。权重调高后召回一大堆，窗口被噪声占满，工具选择也会跟着坏，见 `jd-agent-eval-beyond-qa`。无答案的 query 要允许两路都空，别为了凑融合结果硬返回。ES 和向量怎么分工见 `jd-es-vector-usage`，BM25 混合的原则见 `ant-bm25-hybrid`。

## 追问

**为什么不直接学一个端到端打分？**
可以学，但上线要按切片回归，学出来的权重在 ID 型上仍可能崩。规则分类加 RRF 往往更可解释，面试里也好讲清楚。

**改写错了怎么办？**
保留原 query 那一路，融合时别只信改写。改写失败要能在 trace 里单独归因。

**RRF 还要权重吗？**
RRF 本身对分数尺度不敏感，但仍可以按类型调整两路的 $k$ 或排名截断。

**和意图识别是什么关系？**
意图决定搜 SOP 还是搜订单字段，类型加权是检索内部的事。意图的测法见 `jd-intent-accuracy`。
