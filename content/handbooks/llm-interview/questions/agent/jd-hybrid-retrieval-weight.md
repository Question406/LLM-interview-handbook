- 原始措辞：**“如何处理问题输入不标准的情况？混合检索的权重怎么配置？”**

错法：脏 query 直接进 embedding，再给 BM25 和向量固定 $0.5/0.5$。订单号写错一位时，稠密近邻帮不上忙，稀疏也要对规范化后的串；口语同义则相反。权重必须随 query 类型变，并用验证集扫 Recall 与下游任务，别拍一个比例。ES 与向量怎么分工见 `jd-es-vector-usage`，BM25 混合原则见 `ant-bm25-hybrid`。

## 不标准输入先规范化，再检索

纠错、繁简、大小写、商品别名、口语改写成检索 query。能抽到订单号、SKU、运单号就走精确字段，不要把整句 embed。改写模型的选择见 `baichuan-query-rewrite-model-choice`：改写是为了检索，不是为了把用户话变得更长。

规范化要可回放：trace 里同时留 raw query 和 rewrite，评测才能知道失败在改写还是在检索。过度改写会丢掉唯一的型号词；过弱则口语召不中。无把握时双路：一路原句稀疏，一路改写稠密，融合后再 rerank。

## 按类型动态加权，过滤永远先做

稀疏抓编号和型号，稠密抓同义，结构化过滤租户 / 类目 / 时间。过滤是硬约束，跟权重无关：不过滤再融合，权限和类目已经错了。

融合可用 Reciprocal Rank Fusion，减少分数不可比的问题；或用 query 分类器输出权重：导航型 / ID 型升高 BM25，描述型升高向量。固定 1:1 会在「订单号写错一位」时整路失败，向量把错号映射到无关近邻，BM25 又被对半稀释。分类器可用规则（是否像 ID）加轻量模型，低置信则走 RRF 保守融合并准备澄清。

## 权重和切块、rerank 一起扫

单独调一个 $\alpha$ 没有意义。切块粒度变了，稀疏和稠密的最优混合会变；rerank 模型变了，召回 $k$ 也要变。用分类型 Recall@k 和端到端答对率，外加人工看 top 结果。验证集按时间切，防止用同一运营活动文案既调权又验收。

Agent 场景还要看「检索到的证据是否被引用」：权调高了召回一堆，窗口被噪声占满，工具选择会跟着坏，见 `jd-agent-eval-beyond-qa`。无答案 query 应允许两路都空，别为了凑融合结果强行返回。输入不标准还包括错别字、口语省略主语、把 SKU 和活动名混在一句。先做实体识别再检索：识别到 ID 就走精确字段并降低向量权重；识别失败再走描述型。不要用同一套 $\alpha$ 伺候所有话术。$\alpha$ 随类型变，过滤条件不随类型放松。调权记录要进配置版本，和切块、embedding 版本一起发布，避免「上周的 0.7 向量」在新索引上默默失效。

## 追问

- **为什么不用学一个端到端打分？** 可以，但上线要用切片回归；学习权重在 ID 型上仍可能崩。规则分类 + RRF 往往更可解释，适合面试讲清楚。
- **改写错了怎么办？** 保留原 query 一路，融合时不要只信改写。改写失败应能在 trace 里单独归因。
- **RRF 还要权重吗？** RRF 本身对分数尺度不敏感；仍可对两路的 $k$ 或排名截断做类型相关调整。
- **和意图识别什么关系？** 意图决定搜 SOP 还是搜订单字段；类型加权是检索内部的事。意图测法见 `jd-intent-accuracy`。
