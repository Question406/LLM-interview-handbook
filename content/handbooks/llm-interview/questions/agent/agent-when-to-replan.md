Plan-and-execute 把「想」和「做」分开，能省上下文，但环境会变。ReAct 每步都想，灵活但贵、且容易抖动。现场要的是 **触发器**，不是口号「我们会反思」。陷阱是两个极端：每步推倒重来，或死守已经失败的步骤清单。

## 触发器

维护显式 plan + 进度断言（子目标、预期观测、预算）。满足任一则 re-plan：

- 工具返回与假设冲突（文件不存在、权限被拒、页面结构变了）；
- 连续 $k$ 步无进展（同一动作、同一错误）；
- 用户目标或约束变更；
- 成本 / 延迟 / 风险预算告急；
- 发现原计划未覆盖的新约束。

未触发则继续原计划，只把观测追加进工作记忆。局部修补优先于全局重规划：只改失败的那一支，保留已获取状态和已对用户做过的承诺。目标不清时应先澄清而不是换一张更大的计划表，见 `agent-ask-clarify`。

## 代价与冷却

重规划消耗上下文和时间，可能丢掉已执行步骤的承诺（对用户重复提问、重复下单）。给 re-plan 次数上限和冷却，防止反思循环。局部失败先走 retry 状态机：只读错误可改参；有副作用的写操作先查终态再决定是否改目标分解，见 `arl-retry`。评测在中途注入环境变化（文件被删、权限回收、页面改版），比较死守 vs 自适应的成功率、多余动作数、以及错误的全局推倒次数。

## 和每步思考的差别

ReAct 把推理和动作交错，适合短程、观测噪声大的任务；长程任务若每步重写整份 plan，会把已验证的中间结论冲掉。工程上把 plan 当成带断言的工作流：步骤有预期观测，偏差超阈值才重写受影响的子图。模型可以提议「要不要重规划」，但闸门应是规则：无进展计数、schema 级错误、预算耗尽。没有闸门，模型会为了「看起来勤快」而空转。长程任务还要把「已对用户承诺的动作」写进 plan 状态：已经下过的单、已经问过的澄清、已经申请过的权限，重规划时默认保留，除非用户或政策明确作废。否则 re-plan 会表现为重复打扰。评测除了注入环境变化，还应注入「第一次其实已成功但回包丢失」，看 Agent 是查状态还是推倒重来后又执行一遍。面试收口：触发器 + 局部修补 + 冷却；不是每步反思，也不是死守清单。

## 追问

- **$k$ 怎么定？** 按工具幂等性：只读失败可以 $k=1$ 就改；有副作用的写操作先确认再改计划，避免把超时当成失败后换一条会双花的路径。
- **和 retry 的差别？** Retry 是同一计划下换参数 / 等瞬态错误；re-plan 是目标分解或约束变了。见 `arl-retry`、`code-retry`。
- **要不要每步都让模型投票「要不要重规划」？** 可以当信号，但要用规则闸门兜底，否则会空转。
- **局部修补还不够呢？** 连续两次局部修补仍无断言满足，才升级到全局 re-plan，并记录已承诺动作以免重复执行。
