我会在计划背后的假设被打破时才 re-plan，其余时候继续原计划，只把新观测追加进工作记忆。Plan-and-execute 先定计划再执行，省上下文，但计划可能跟不上环境变化；ReAct 每步结合结果重新思考，更灵活，成本也更高。所以设计时要把触发条件写具体，避开两头的坑：每步推倒重来，或者死守一张已经失败的步骤清单。

比如 Agent 按计划要去改一个配置文件，工具却返回文件不存在。这时继续执行后面的步骤没有意义，计划的前提已经变了，该重新规划受影响的那一支。

具体做法是维护一份显式的 plan，每步带进度断言：子目标、预期观测、预算。触发重规划的情况有这几种：工具返回和假设冲突，比如文件不存在、权限被拒、页面结构变了；连续 $k$ 步没有进展，重复同一个动作、同一个错误；用户的目标或约束变了；成本、延迟或风险预算告急；发现了原计划没覆盖的新约束。目标本身不清楚时，先澄清，别急着换一张更大的计划表，见 `agent-ask-clarify`。

触发之后，局部修补优先。只改失败的那一支，已经拿到的状态和对用户做过的承诺都保留。这些承诺要写进 plan 状态，已经下过的单、问过的澄清、申请过的权限，重规划时默认保留，除非用户或政策明确作废，不然 re-plan 就会表现成重复打扰，甚至重复下单。

重规划要花上下文和时间，所以要有次数上限和冷却时间，防止陷进反思循环。模型可以提议「要不要重规划」，闸门由规则来定：无进展计数、schema 级错误、预算耗尽，否则模型可能反复重写计划，却没有实际进展。局部失败先走 retry 状态机，只读错误改参数重试；有副作用的写操作先查终态，再决定要不要改目标分解，见 `arl-retry`。

和 ReAct 那样每步思考相比，长程任务每步重写整份 plan，会把已经验证过的中间结论冲掉。ReAct 把推理和动作交错，更适合短程、观测噪声大的任务。长程任务我会把 plan 当成带断言的工作流，步骤有预期观测，偏差超过阈值才重写受影响的子图。

评测时在中途注入环境变化，比如文件被删、权限回收、页面改版，比较死守和自适应两种策略的成功率、多余动作数，以及错误的全局推倒次数。还要注入「第一次其实成功了，只是回包丢了」，看 Agent 是先查状态，还是推倒重来又执行了一遍。

## 追问

**$k$ 怎么定？**
按工具的幂等性定。只读失败可以 $k=1$ 就改；有副作用的写操作先确认终态再改计划，免得把超时当成失败，换一条会双花的路径。

**re-plan 和 retry 有什么区别？**
Retry 是在同一个计划下换参数，或者等瞬态错误恢复；re-plan 是目标分解或约束变了，见 `arl-retry`、`code-retry`。

**要不要每步让模型投票决定是否重规划？**
可以当信号用，但要有规则闸门兜底，否则会空转。

**局部修补还是不够怎么办？**
连续两次局部修补后断言仍然不满足，再升级到全局 re-plan，并带上已承诺的动作，避免重复执行。
