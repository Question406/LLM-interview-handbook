## 真题记录

- 公司：京东
- 团队 / 岗位：AI Agent 开发
- 届别 / 流程：一面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B（公司、岗位与轮次明确）
- 原始措辞：**“模型效果评估为什么不能只看问答准确率，Agent 系统至少还要评什么”**

陷阱是把轨迹压成「最后一句对不对」。Agent 还会选工具、填参、决定继续或拒答；答对但乱调工具、越权、成本爆炸，工程上不合格。问答准确率掩盖了这些失败。京东这面要最低评测集覆盖轨迹，而不是一个总分。维度对照见 `kuaishou-agent-eval-dims`；评完怎么修见 `jd-agent-reflection-error-attribution`。

## 最低要覆盖的轨迹指标

按决策链拆，而不是按「聪明程度」拆：

- **意图 / 路由准确**：进对技能或业务域，见 `jd-intent-accuracy`。
- **工具选择准确**：该调库存还是该调 SOP 检索。
- **参数 schema 合法率**：缺字段、类型错、越权 ID。
- **平均调用轮数与无效调用率**：空转、重复同一失败调用。
- **失败恢复率**：超时、空结果后是否按策略恢复，而不是幻觉填空。
- **拒答是否该发生、高风险是否保守**：退款、改址、改价前该停则停。

最终答案仍要评，但必须和轨迹一起看。用固定沙箱和可回放 trace，按任务桶（导购 / 售后 / 广告诊断 / 无答案）出表。一个微平均 accuracy 会让高风险桶被海量闲聊淹没。

## 怎么测才测得到，而不是测到会考试

环境要可回放：同一 tool mock、同一时间快照、同一权限角色。否则「库存接口今天超时」会让离线分抖动。金标不仅是最终句，还包括允许的工具集合、禁止的工具、必须引用的订单号。工具目录变化后要回归，治理见 `jd-agent-tool-catalog-context`。

不要用「模型自评这次调用合理吗」当主指标。Reflection 若无 oracle 和替换实验，会把自信当成正确。归因实验见 `jd-agent-reflection-error-attribution`。成本类指标（token、延迟、调用次数）要进同一张表，否则优化准确率时把 QPS 打爆。

## 线上补什么

离线沙箱看不到真实客诉和权限边角。线上加：延迟、token、客诉、人工接管率、越权拦截次数、用户改写率。离线分涨但接管率升，说明评测集没覆盖真实歧义。和 RAG 评测也要拆开：检索命中是 RAG 卡的事；工具乱调是 Agent 卡的事，见 `jd-agent-vs-rag`。

Skill 级评测（某个技能内部步骤是否按清单走）可接到 `agent-skill-eval`。本卡的重点是：为什么 QA 准确率不够，以及最少还要哪些系统指标。汇报时固定模型、任务、token 预算和 harness 版本，否则轨迹指标无法归因。答对率上升若伴随无效调用和越权尝试上升，不能当成上线理由。

## 追问

- **答对但调了多余工具算失败吗？** 产品上可能过关，工程上要记无效调用。内部工具有副作用或计费时，多余调用就是缺陷。
- **没有金标轨迹怎么办？** 至少标允许工具集和禁止工具集，再用规则打 schema 和越权；最终句可用人工抽检，不要等完整逐步金标才开始测。
- **和模型能力评测怎么切？** 同一模型换 Harness，轨迹指标会变。汇报时写清 harness 版本，避免把脚手架增益当成模型增益，见 `agent-harness`。
- **高风险保守性如何量化？** 构造「不该执行」集：无权限改价、模糊退款。看拦截率；同时看「该执行的查询」有没有被误杀。
