## 真题记录

- 公司：字节跳动
- 岗位：Agent 开发实习
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“你刚才讲到这个过程中的压缩啊，你压缩方案是啥（三级压缩）”**；**“为什么是五轮？”**；**“上下文压缩之后，你怎么判断压缩没有破坏当前任务？”**

错法：把「五轮」神化成算法，或压缩后只报告 token 降了。三级压缩是窗口预算策略：近轮必须能指代，中期变成摘要，远期变成可检索笔记。阈值按 token 和任务阶段调，不是魔法数字。压缩若丢掉路径、测试命令、禁止改的文件，任务已经坏了。上下文选择总览见 `agent-context`，和短长记忆的分层见 `byte-short-long-memory`。

## 三级分别留什么

- **L0 近轮原文**：最近对话、未完成 diff、刚拿到的工具观察、当前失败测试。指代（「刚才那个文件」「第三条用例」）依赖这段还在窗口里。
- **L1 中期摘要**：更早轮次压成任务进度、已验证结论、打开过的文件列表。摘要要带来源句柄（path、test name），不要只剩散文。
- **L2 远期笔记**：跨任务才需要的约束进长记忆或可检索笔记；过程吐槽丢掉。L2 不自动进窗口，检索命中再注入。

摘要和笔记分开维护，避免把「试过但失败的错误假设」写进长期记忆，污染见 `byte-memory-pollution`。溢出时优先丢 L1 里无句柄的闲聊，而不是丢 L0 的失败栈。失败栈是下一步动作的输入。同类「先压再装」的思路见 `pdd-compress-first-70`，窗口爆了怎么处理见 `pdd-context-overflow`。

## 为什么常按轮次切，而不是只按 token

按轮次是工程启发式：保证「当前指代还活着」。五轮只是经验起点。对话短、每轮 Observation 很大时，可能两轮就要压；步骤都是短 tool call 时，可以留更久。更稳的触发是双重条件：轮次或 token 预算触线就压缩，并在任务阶段切换时（检索结束进入改代码）主动把检索原文换成切片句柄。

不要在面试里坚持「必须五」。应说：选一个能保住当前指代的窗口，用评测看压缩后任务成功率，而不是看平均压缩比。指代失败的典型症状是模型再 `read_file` 已经读过且未变更的文件，或问用户已经回答过的路径。

## 压缩后如何证明没破坏任务

硬约束清单（目标路径、测试命令、禁止改的文件、用户确认的范围）在压缩前后必须能对上；对不上就回放 L0 原文或重读文件，而不是继续用坏摘要规划。校验是确定性比对，不是再问模型「你还记得吗」。

评测集应包含：压缩前后约束保持率、错误回读率、任务成功率。只优化长度会得到空而错的摘要。压缩是 Context Engineering 的手段，和 RAG/Memory 的分工见 `byte-rag-memory-context`。实践上把硬约束做成 checklist 结构（路径、命令、禁止项），压缩函数必须原样拷贝这些字段；摘要模型只压缩叙事。字段级拷贝比「请保留关键信息」可靠，也方便做确定性 diff。

## 追问

- **五轮是论文结论吗？** 不是。是「指代还活着」的启发式，应按预算和 Observation 大小调。
- **摘要模型用哪个？** 重点是摘要必须保留句柄和硬约束，而不是品牌。摘要失败就回退原文，不要用更糊的二次摘要硬扛。
- **和长记忆写入怎么衔接？** 只有已验证结论进 L2/长记忆；压缩产生的过程摘要默认留在 L1。
- **工具 Observation 特别长怎么办？** 结构化抽字段、留分页句柄，不要把整页 JSON 当 L0 原文一直带着，见 `jd-agent-tool-catalog-context`。
