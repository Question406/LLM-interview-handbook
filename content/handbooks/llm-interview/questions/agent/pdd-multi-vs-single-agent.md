## 真题记录

- 公司：拼多多
- 团队 / 岗位：AI Agent
- 届别 / 流程：二面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“为什么项目采用多 Agent？如果改成单 Agent，会遇到什么问题？”**

陷阱是把多 Agent 当成架构先进性。面试官要听的是「拆的收益是否大于同步成本」，不是跟风堆三个 chatbot。正当理由只有几类：工具权限不同、上下文必须隔离、需要独立 checker。能用路由加单执行器解决的，不要上辩论团。协议细节见 `baichuan-multi-agent-collab`；本题重点是「何时不该拆」。

## 什么时候拆才正当

检索 / 下单 / 风控往往不能共用同一把工具钥匙：客服话术混进结算参数会下错单，风控模型不该看见可改价的写接口。上下文隔离也是硬需求：长 observation 会污染规划，把退货政策全文塞进下单 Agent 只会增加误调。独立 checker 适合高风险结论（价格、库存、违规），但 checker 必须有自己的证据和权限，不能和执行者共享可变 state。不正当理由包括「看起来更像 Agent」「每个技能一个人格」——那是包装层，延迟和冲突会立刻上来。

## 改回单 Agent 会碰到什么

一个 context 装所有 observation，长任务污染和越权风险上升；提示变胖，路由变糊，模型更容易调用不该调的工具。单 Agent 不是不能做复杂任务，而是要把隔离外置：单政策 + 工具白名单 + 外部 workflow。权限在工具服务端强制，而不是靠「你现在是风控助手」。很多所谓多 Agent，其实是多个 prompt 角色共用同一 runtime 和同一凭证，拆了名字没拆信任边界，失败模式和单 Agent 一样，还多了同步。若路径完全固定，Workflow 往往更合适，见 `meituan-workflow-vs-agent`。

## 怎么证明拆对了

评测对比任务成功、越权次数、步数、冲突次数和延迟。不要用「Agent 之间聊了几轮」当效果。若单 Agent 加白名单后成功率和越权不差，就不要拆。交接必须结构化（JSON / 工具参数），失败时重试当前角色或升级人，而不是让两个 Agent 无限讨论。电商下单链路上，检索专家和下单执行器可以拆；闲聊推荐和比价不必各开一个进程。拼多多这题常和「项目为什么这么设计」绑在一起：先承认多 Agent 的同步税，再讲你拆的那一条隔离是权限还是上下文。答「因为业界都在用」会立刻被追问改回单 Agent 会怎样——那时就要能指出污染和越权，而不是重复人格设定。

## 追问

- **多 Agent 一定更准吗？** 不一定。同步、冲突和延迟会吃掉收益。先证明权限或上下文真的需要隔离。
- **单政策加白名单算不算多 Agent？** 不算。那是单执行器加外部隔离，往往是更优解。
- **checker 和执行者能共享记忆吗？** 只读共享证据可以，可写 state 必须唯一写者，否则互相覆盖，见 `baichuan-multi-agent-collab`。
- **什么信号说明不该拆？** 角色之间没有不同权限、没有独立校验、还要靠自然语言互相「请你接着说」。
