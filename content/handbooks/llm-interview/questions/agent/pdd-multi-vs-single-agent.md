## 真题记录

- 公司：拼多多
- 团队 / 岗位：AI Agent
- 届别 / 流程：二面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“为什么项目采用多 Agent？如果改成单 Agent，会遇到什么问题？”**

我会先讲拆的收益是否大于同步成本。多 Agent 的正当理由只有几类：工具权限不同、上下文必须隔离、需要一个独立的 checker。如果路由加单执行器能解决问题，就不必安排多个 Agent 反复讨论。把多 Agent 当成架构先进性、跟风堆三个 chatbot，面试官马上会追问改回单 Agent 会怎样。

拿电商下单链路举例。检索、下单、风控往往不能共用同一把工具钥匙：客服话术混进结算参数会下错单，风控模型也不该看见可改价的写接口。上下文隔离也是硬需求，长观测结果（observation）会污染规划，把退货政策全文塞进下单 Agent，只会增加误调。这种情况下，检索专家和下单执行器可以拆开；闲聊推荐和比价就没必要各开一个进程。

独立 checker 适合价格、库存、违规这类高风险结论，但 checker 必须有自己的证据和权限，不能和执行者共享可变的 state。「看起来更像 Agent」「每个技能一个人格」不算拆的理由，那只是包装层，延迟和冲突会立刻上来。

如果改回单 Agent，一个 context 装下所有 observation，长任务的污染和越权风险都会上升；提示词变长，工具路由更难判断，模型更容易调用不该调的工具。单 Agent 也能做复杂任务，前提是把隔离外置：单政策加工具白名单加外部 workflow，权限在工具服务端强制，靠一句「你现在是风控助手」挡不住。很多所谓的多 Agent，其实是几个输入提示（prompt）角色共用同一个 runtime 和同一份凭证，角色名称分开了，权限和信任边界没有隔离，失败模式和单 Agent 一样，还多了同步。路径完全固定的话，Workflow 往往更合适，见 `meituan-workflow-vs-agent`。

证明拆对了，要对比任务成功、越权次数、步数、冲突次数和延迟，「Agent 之间聊了几轮」说明不了效果。如果单 Agent 加白名单后，成功率和越权都不差，就不要拆。交接必须结构化（JSON 或工具参数），失败时重试当前角色或升级给人，别让两个 Agent 无限讨论。这题常和「项目为什么这么设计」绑在一起，我会先说明多 Agent 带来的同步开销，再讲自己拆的那一条隔离是权限还是上下文；答「因为业界都在用」，被追问时就只能重复人格设定，指不出污染和越权。协作协议的细节见 `baichuan-multi-agent-collab`，这题的重点是什么时候不该拆。

## 追问

**多 Agent 一定更准吗？**
不一定。同步、冲突和延迟会吃掉收益，先证明权限或上下文确实需要隔离。

**单政策加白名单算不算多 Agent？**
不算。那是单执行器加外部隔离，往往是更优解。

**checker 和执行者能共享记忆吗？**
只读共享证据可以，可写的 state 必须只有一个写者，否则会互相覆盖，见 `baichuan-multi-agent-collab`。

**什么信号说明不该拆？**
角色之间没有不同的权限，没有独立校验，还要靠自然语言互相「请你接着说」。
