## 真题记录

- 公司：京东
- 团队 / 岗位：大模型应用开发实习
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“ES、向量数据库具体怎么使用？”**；**“向量检索的准召率如何保障？你使用的向量数据库之间的差异是什么？”**

错法：背品牌（某向量库「更快」），或只报相似度分数。京东应用开发这面要：ES 和向量各管什么、检索时如何先过滤再近邻、准召用金标 Recall 而不是 cosine。从 ES 切到纯向量会降精确 ID 命中，见 `byte-es-to-vector`；权重怎么配见 `jd-hybrid-retrieval-weight`。

## 具体怎么用：字段决定走哪路

**ES / 倒排**：商品属性、订单号、SOP 标题、错误码、必须命中的专有名词、以及租户/类目/时间过滤。日志和工单检索也是它的主场：过滤成熟、相关性可调权、结果可解释。

**向量库**：口语改写、同义、「那个老超时的接口」这类没有稳定关键词的 query。两边都要带租户、类目、时间字段；检索时 **先过滤再 ANN**，否则近邻会穿过权限和类目。不要把订单号 embed 完再近似匹配，错一位时稀疏检索更合适。

混合才是生产默认：过滤与专有名词留 ES，语义近邻走向量，再用 rerank。三路召回的思路也可对照 `baichuan-three-path-recall`。Agent 里它们是检索工具，不是把整库塞进上下文。

## 准召率：金标 + 分层，别靠阈值玄学

建「必须召回的证据 ID」金标，按 query 类型切片（ID 型、口语型、无答案型）。报告 Recall@K、无结果率、权限误召（不该看到的租户文档）。相似度分数不能当准召：分布随 embedding 版本漂移，固定阈值会在新模型上失效。

保障手段：元数据强过滤、稀疏+稠密双路、交叉编码器或业务规则 rerank、无答案集防止「强行找一篇」。评测集要时间切分，避免用同一批文档既建索引又当测试。embedding 升级必须重刷索引并回归金标，否则「换了更好的模型」会把召回打穿。

含「无答案」很重要：向量总能返回近邻，不评拒答就会把无关 SOP 送给生成，幻觉表现为检索问题。权限误召要当 P0：召回了别的商家工单，比少召回一篇 FAQ 严重。准召保障里「准」包含 ACL，不只是语义像不像。把租户 ID 只放在 rerank 之后过滤，ANN 阶段已经泄露候选，应在过滤条件里下推。

## 库之间别背品牌，看接进 RAG 的能力

差异看：过滤（尤其是高基数租户字段）、混合检索是否一等公民、多租户隔离、重建与增量成本、与 embedding 版本绑定、运维和 SLA。IVF/HNSW 图结构已有专门卡，这里强调「库怎么接进 RAG」：能否在过滤后做 ANN、能否和 ES 做 RRF、权限字段能不能下推。选库理由要落到这些约束，别背官网 QPS 数字（那些数字随数据分布变化，面试里不要编）。

## 追问

- **为什么不能只用向量？** 精确 ID、错误码、权限过滤会降。口语场景升，见 `byte-es-to-vector`。
- **Recall@K 高就够了吗？** 不够。还要看权限误召、无答案、以及下游是否引用了金标证据。高召回低精度会把噪声塞满 Agent 窗口。
- **ES 里的 kNN 能不能代替专用向量库？** 可以作为混合的一环；仍要核对过滤下推、集群资源和重建成本，按数据规模选，不要先站队。
- **和 BM25 混合怎么调？** 按 query 类型动态加权，不要 0.5/0.5，见 `jd-hybrid-retrieval-weight`、`ant-bm25-hybrid`。
