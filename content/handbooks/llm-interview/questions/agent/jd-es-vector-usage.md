## 真题记录

- 公司：京东
- 团队 / 岗位：大模型应用开发实习
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“ES、向量数据库具体怎么使用？”**；**“向量检索的准召率如何保障？你使用的向量数据库之间的差异是什么？”**

我会按字段分工：订单号、错误码、专有名词和各种过滤交给 ES，口语和同义改写交给向量库，生产上两路混合，先过滤再做近邻，最后 rerank。准召率靠一份「必须召回的证据 ID」金标来测，按 query 类型切片，还要包含无答案题和权限误召，cosine 这类相似度分数当不了准召。不同向量库也别背品牌（某个库「更快」），看它能不能这样接进检索增强生成（RAG）。

举个例子，用户问「那个老超时的接口怎么处理」，这句话没有稳定的关键词，适合走向量。可如果用户贴了一个订单号、还错了一位，embed 之后再近似匹配，只会找到一堆无关的近邻，这时稀疏检索更合适。所以订单号别 embed。

具体分工是这样。ES 和倒排管商品属性、订单号、SOP 标题、错误码、必须命中的专有名词，还有租户、类目、时间过滤；日志和工单检索也是它的主场，过滤成熟、相关性可以调权、结果可解释。向量库管口语改写、同义这类 query。两边都要带租户、类目、时间字段，检索时**先过滤再 ANN**，否则近邻会穿过权限和类目。过滤和专有名词留在 ES，语义近邻走向量，再做 rerank，这是生产上的默认做法；三路召回的思路可以对照 `baichuan-three-path-recall`。放到 Agent 里，它们是检索工具，用不着把整库塞进上下文。从 ES 切到纯向量会降低精确 ID 的命中，见 `byte-es-to-vector`。

## 准召率怎么保障

先建金标，记下每条 query「必须召回的证据 ID」，按 query 类型切片：ID 型、口语型、无答案型。报 Recall@K、无结果率和权限误召，也就是召回了不该看到的租户文档。相似度分数的分布会随 embedding 版本漂移，固定阈值换了新模型就失效，所以它不能当准召。

保障手段有几样：元数据强过滤、稀疏加稠密双路、交叉编码器或业务规则 rerank，再加一个无答案集，防止系统「强行找一篇」。无答案集很重要，向量总能返回近邻，不评拒答，就会把无关 SOP 送给生成，幻觉看起来就像检索问题。权限误召按 P0 处理，召回了别的商家的工单，比少召回一篇 FAQ 严重得多，所以「准」里包含 ACL，光看语义像不像不够。租户 ID 要下推到过滤条件里；只放在 rerank 之后过滤，ANN 阶段就已经把候选泄露出去了。评测集按时间切分，别用同一批文档既建索引又当测试。embedding 升级时必须重刷索引、回归金标，不然「换了更好的模型」可能让召回质量下降。

至于库之间的差异，我会看这些约束：过滤（特别是高基数的租户字段）、是否原生支持混合检索、多租户隔离、重建和增量成本、和 embedding 版本的绑定、运维和 SLA。IVF/HNSW 的图结构有专门的卡，这里关心的是库怎么接进 RAG：能不能过滤后再做 ANN、能不能和 ES 做 RRF、权限字段能不能下推。选库理由落到这些约束上，官网 QPS 数字别背，那些数字随数据分布变化，面试里也不要编。

## 追问

**全换成向量检索为什么不行？**
精确 ID、错误码、权限过滤的效果会降，口语场景会升，见 `byte-es-to-vector`。

**Recall@K 高就够了吗？**
不够。还要看权限误召、无答案，以及下游有没有引用金标证据。召回高、精度低，会把噪声塞满 Agent 的窗口。

**ES 里的 kNN 能代替专用向量库吗？**
可以作为混合检索的一环，但要核对过滤下推、集群资源和重建成本，按数据规模选，别先站队。

**和 BM25 混合怎么调？**
按 query 类型动态加权，别用 0.5/0.5，见 `jd-hybrid-retrieval-weight`、`ant-bm25-hybrid`。
