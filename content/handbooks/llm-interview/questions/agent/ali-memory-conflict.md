Agent 记忆要有更新规则，冲突在写入时就解决掉。如果只是不断把新句子放进向量库，新旧地址或偏好会被同时检索出来，模型就会随机选一个。

比如上周用户说送到公司地址 A，今天说以后送到家里地址 B。这时把 B 设为当前值，同时保留 A 被替换的历史、时间和会话来源，下次检索只拿到 B。

先分清两种记忆存什么。短期记忆服务当前任务：最近的对话、还没问清的字段、当前订单编号。上下文满了可以做摘要，近期内容多留细节，较早的压缩；订单号、地址这类关键字段要结构化保存，见 `ali-prompt-optimize`。长期记忆存跨会话仍有效的事实或偏好，比如默认地址、忌口、配送偏好，每条都带实体键、时间、来源和置信度，来源要说明是谁说的、来自哪个会话或哪次工具结果。重新开始长周期对话时，检索相关事件就够了，不用把几个月的聊天全放进上下文。证据检索和用户偏好也要分开管，见 `ali-rag-eval` 和 `ali-skill-memory-rag`。

处理冲突时，第一步判断是不是「同一个实体、同一个字段、不同值」。相似的文本不一定指同一件事，光靠向量相似度判断不了。确认是同一件事后，用户偏好按这个优先级取舍：用户明确更正 $\gt$ 工具提供的权威数据 $\gt$ 模型推断。会员资料和用户口述的地址冲突时，按这次明确更正处理，并复述新地址以防听错。「可能喜欢辣」只是模型推断，保持低置信度，不直接变成长期事实。

具体字段还要区分：实际履约状态以工具记录为准，用户自己的偏好以明确更正为准。时间更新也不一定优先，比如新政策可能让旧的退货约定失效，这时要说明依据的是哪条政策。存储层最好维护实体键、单一当前值和历史版本，让检索只取当前有效值，别把冲突留给生成模型临场猜。

最后要有删除机制。过期事实、被替换的旧值、低置信度推断，以及保留政策不允许存的敏感信息，都要能清理；低置信度记忆可以定期衰减，减少错误累积。用户要求不再记住家庭地址时，要真正删除并留下可审计的记录，只从这次 prompt 里删掉一句话，保证不了下次不再检索到它。

## 追问

**向量检索能完成冲突检测吗？**
单靠它不行，还需要明确的实体键，比如用户编号加字段名。

**摘要会不会丢掉关键字段？**
会，所以订单号、地址这类字段另外结构化保存。

**怎么验收记忆系统？**
更正之后开一个新会话，检查是不是用了新值、还会不会检索到旧值。写入了多少条证明不了记忆有效。
