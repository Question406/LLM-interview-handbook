## 真题记录

- 公司：京东
- 团队 / 岗位：Agent 开发
- 届别 / 流程：27 暑期实习；二面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B（公司、岗位、届别与轮次明确）
- 原始措辞：**“在使用 RAG 的程中有没有出现大模型幻觉？如何设计兜底方案？”**

先承认 RAG 不能消灭幻觉。检索召回错、上下文被截断、模型忽略证据、或把相邻 SKU 属性拼起来，都会「看起来很像官网」。面试别把「加一句不要编造」当成兜底——那是提示词，不是策略。京东零售场景里价格、库存、售后政策一旦编造就是客诉，兜底必须按失败桶落到拒答、结构化字段或人工。

## 按失败桶设计动作，而不是统一道歉

1. **检索空 / 低分**：直接说找不到，给缩小条件或转人工。禁止用参数知识补价格、库存、时效、价保规则。低分阈值要按类目校准，不是全局一个相似度。
2. **检索到但生成越界**：强制引用 span，答案断言必须能在证据中对齐。金额、时效、运费险等字段用结构化抽取或接口，而不是自由生成。对不上就输出「证据不足」而不是圆一遍。
3. **引用错挂**：展示来源 ID / 商品页，让用户点回原文；日志记证据哈希，便于复盘是切块错还是模型张冠李戴。
4. **高风险**：退款、医疗器械说明、法律承诺默认保守，触发人工或只复述政策原文。

面向用户的文案要诚实：已查到什么、不能确认什么、下一步是改查询还是转人工。不要把空检索包装成「暂无此商品优惠」。护栏还可以参考 `ant-hallucination-guard`：无依据断言直接拦截，而不是生成后再靠用户发现。

## 用替换实验证明桶分对了

兜底策略要能被评测打脸。同一 query：换成 gold 检索仍错，才罚生成 / prompt；固定 gold 答案、打乱或抽空检索则罚检索。详见 `kuaishou-rag-retrieve-vs-generate`。线上监控无引用断言率、用户纠正、客诉里的「说错价格 / 政策」；离线集必须含无答案题，见 `jd-rag-accuracy-eval`。

归因清楚才能选对修法：检索桶改切分、混合检索、索引新鲜度；生成桶加引用约束、字段抽取头、禁止额外知识；错挂桶查 chunk 边界和重排。Agent 若还能调库存接口，高风险字段应走工具而不是 RAG 文档——那已经超出「加拒答」，是路由问题，见 `jd-agent-vs-rag`。二面若问「有没有出现过幻觉」，不要编造线上事故；按机制承认必然会出现，并讲清你们用哪几个桶接住。兜底的产品形态可以是卡片：证据不足、建议缩小条件、转人工，而不是一段道歉散文。评测要把「该兜底却生成了价格」当成 P0，权重高于闲聊幻觉。意图识别阈值和兜底是前后环：高风险意图先澄清，检索空再转人工，见 `jd-intent-accuracy`。

## 追问

- **加一句「不要编造」算不算兜底？** 不算。没有拒答动作、字段约束和监控，提示词挡不住相邻 SKU 拼接。
- **检索分数高就不用兜底？** 分数高仍可能生成越界或引用错挂。分数只是检索信号，忠实层要单独对齐 span。
- **兜底会不会伤害体验？** 会，所以按风险分层：闲聊可宽松，价格库存必须严。用拒答率与客诉一起看，而不是只压拒答。
- **和意图识别怎么配合？** 退款 / 改址等高风险意图先走 `jd-intent-accuracy` 的阈值与澄清，再决定是否检索；检索空则转人工而不是编政策。
