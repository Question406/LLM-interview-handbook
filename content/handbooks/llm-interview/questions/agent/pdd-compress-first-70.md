## 真题记录

- 公司：拼多多
- 团队 / 岗位：大模型算法日常实习
- 届别 / 流程：一面
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“了解上下文压缩机制吗？”**；**“为什么压缩前 70%？最开始的几轮对话明确需求不是很重要吗？”**

开头的需求当然重要，但重要的是从里面抽出来的槽位，开场白原文不必留。压缩前 70% 时，先把已经确认的需求写进不可压缩的状态，再去压原文；最近几轮保留原文，因为它们承担指代。70% 只是工程启发式，要按 token 预算和任务阶段调，别把这个数字神化。这和 `pdd-context-overflow`、`byte-three-level-compress` 是同一条原则：压的是原文，硬约束不压。

举个例子，用户先说预算 200，三轮后改成 150。如果前面的原文原样留着，两个预算会同时出现在窗口里，就可能造成冲突。自然语言的开场经常被后面的轮次修正。在拼多多这类成交对话里，开场的「随便看看」和中段改口后的预算、收货地址、优惠 threshold，信息密度完全不一样，最终约束往往在中后段确认，很少出现在第一句。

所以压缩要按信息类型分层，别按时间一刀切。已确认的预算、地址、过敏、订单号、权限、未完成的步骤、用户改口后的最终槽位，这些绝对不能压。寒暄、重复澄清、超长的工具 JSON、已经被后续轮次覆盖的旧说法，可以压。过长的 observation 和历史商品卡，留一个 ID 当可检索句柄，需要时再拉。把前 70% 当垃圾整段扔掉，会连已确认的槽位一起扔；前部原文可以压，前部抽出来的状态不可压。

为什么常压前部、留近轮？近轮承担两件事：指代，比如「就那个红色的」，还有尚未结构化的临时信息。前部多是探索、改口和客服套话，信息密度低，也容易过期。这和三级压缩是同一个直觉：L0 放近轮原文，L1 放任务摘要，L2 放长期可检索笔记，见 `byte-three-level-compress`。只做滑动窗口会丢掉硬约束；只做摘要会丢掉可执行细节，摘要一旦写错，还会污染后续所有轮次。

压完要验证。评测用超长会话的任务成功率和约束保持率，看地址、优惠、过敏还在不在，压缩比和平均长度说明不了什么。每次压缩后做一次硬约束对账，清单对不上就回放原文或重新问用户，别接着生成。超出预算时，先压工具 observation，再压旧闲聊，最后才压当前用户的原话，见 `pdd-context-overflow`。写进记忆的内容还要有过期和权限，否则压缩后的摘要会把过期地址写成长期事实，见 `pdd-openclaw-spec-driven`。

## 追问

**70% 是超参吗？**
是启发式。要按 token 预算、后续是否仍依赖前文指代、硬约束是否已入库来调，别当定理背。

**开头的需求很重要，怎么办？**
抽成不可压缩的状态字段，再压原文。重要的是槽位，开场白原文可以压。

**摘要写错了怎么发现？**
压缩前后对一遍硬约束清单，丢了就回放或重问。模型自己说「记住了」不能当校验。

**和滑动窗口怎么选？**
组合用：窗口保近轮，摘要保目标，检索保可引用，见 `pdd-context-overflow`。
