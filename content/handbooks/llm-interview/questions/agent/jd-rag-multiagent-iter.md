## 真题记录

- 公司：京东
- 团队 / 岗位：大模型应用开发实习
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“顺着RAG和Multi Agent方向，说说你对它们认知和迭代是怎样的？”**

陷阱是一上来讲「我们拆了检索 Agent、生成 Agent、审核 Agent」。京东应用开发问的是认知怎么迭代：你先解决哪类失败、加模块后哪项指标动了。同面 ES / 准召 / Transformer 是深度，不是让你再背定义。RAG 补静态知识，Agent 补可执行动作，二者不是互斥，见 `jd-agent-vs-rag`。没有 golden 和归因就拆人设，多半是把同样的幻觉复制成三份。

## 先单路可归因，再按失败类型加能力

迭代顺序要比架构口号具体：

1. **单检索 + 拒答**：建立证据金标和三层指标（召回 / 忠实 / 任务），无答案必须能拒。见 `jd-rag-accuracy-eval`。
2. **混合检索 / rerank**：专治漏召和专有名词（货号、活动名）。ES 管关键词与过滤，向量管同义，见 `jd-es-vector-usage`。
3. **工具与权限**：专治「该查订单却在编」。库存、物流、售后状态走接口，文档 RAG 不再回答可变字段。
4. **多 Agent**：只在出现可分离角色且有冲突协议时再拆——例如生成 vs 审核、售前话术 vs 售后政策。拆之前要能指出：单模型在哪类 case 上稳定越权或自相矛盾。

「认知迭代」要能讲你亲手关掉过哪个模块、指标怎么变。加了第二 Agent 但漏召没降、只是延迟涨了，就应该回退。对照实验必须对上错误类型：改检索只许动检索层，加审核 Agent 只许动无依据断言率。

## 什么时候还不该上 Multi-Agent

多 Agent 的合理理由是职责冲突或工具集合过大：同一上下文里既要热情推荐又要严格执行售后政策，单 prompt 会摇摆。不合理的理由是「看起来更高级」。拆分代价是协议：如何传递证据、谁有终裁、失败如何回滚。没有这些，只是多个 chat 角色在互相复述。拼多多侧也有单 vs 多的取舍，见 `pdd-multi-vs-single-agent`：能用路由解决的不要升维成多智能体。

评测上继续看三类 case 谁在涨：漏召、幻觉、工具越权。新模块必须在对应切片上显著，且不把另外两类打坏。路由错了用 `jd-intent-accuracy` 的切片修，而不是再加一个「总控 Agent」把问题藏起来。认知迭代还要能讲清「什么算一次失败」：漏召是检索没把必读证据带上，幻觉是带上了但仍越界，工具越权是不该动的接口被调用。三类失败的修法、负责人、回滚方式都不同。面试用自己做过的最小对照即可，不必虚构多 Agent 大盘数字；说清假设、对照组和观察指标，比画出三个人设更像应用开发。同面 ES / 向量库差异也不要在这里展开成品牌对比，那是准召支撑，见 `jd-es-vector-usage`。

## 追问

- **什么叫可分离角色？** 两个角色的成功标准互相冲突，或工具权限必须隔离（生成不能直接调退款接口）。只是「分步骤」用 Workflow 即可，见 `meituan-workflow-vs-agent`。
- **怎么证明新模块有效？** 对照实验：固定其余部分，只开新模块，看对应错误桶下降、无关桶不恶化。
- **RAG 做到哪一步才考虑 Agent？** 静态知识已可归因，但仍有「必须查实时状态 / 必须写操作」的失败，再加工具环，而不是先加人格。
- **关掉模块算迭代吗？** 算，而且更有说服力。面试要能说出关了之后哪项指标回升或延迟下降。
