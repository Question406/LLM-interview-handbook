## 真题记录

- 公司：京东
- 团队 / 岗位：大模型应用开发实习
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“顺着RAG和Multi Agent方向，说说你对它们认知和迭代是怎样的？”**

我会按失败类型讲迭代：先把单路检索增强生成（RAG）做到失败能定位、无答案能拒答，再按出现的问题加混合检索、加工具，最后才考虑多 Agent。每加一个模块，都要说得出它治的是哪类失败、对应的指标动了没有。直接答成「我们拆了检索 Agent、生成 Agent、审核 Agent」，没有 golden 和归因就拆人设，多半只是把同样的幻觉复制成三份。

举个例子，系统老在活动名上答错。先查是漏召还是生成越界：漏召就上混合检索；证据召回了还答错，加审核 Agent 才可能有用。顺序搞错的话，加了第二个 Agent，漏召没降，只是延迟涨了。

迭代的起点是单检索加拒答，建好证据金标和召回、忠实、任务三层指标，无答案的题必须能拒，见 `jd-rag-accuracy-eval`。然后加混合检索和 rerank，专治漏召和货号、活动名这类专有名词，ES 管关键词和过滤，向量管同义，见 `jd-es-vector-usage`。再加工具和权限，专治「该查订单却在编」，库存、物流、售后状态走接口，文档 RAG 不再回答会变的字段。RAG 提供静态知识，Agent 负责选择并执行动作，两者是配合的，见 `jd-agent-vs-rag`。最后才是多 Agent，只在出现可分离的角色、并且有冲突协议时拆，比如生成和审核、售前话术和售后政策。拆之前要能指出，单模型在哪类 case 上稳定地越权或自相矛盾。

讲「认知迭代」，要能讲出亲手关掉过哪个模块、指标怎么变。加了第二个 Agent，漏召没降、只是延迟涨了，就该回退。对照实验要对上错误类型：改检索只许动检索层，加审核 Agent 只许动无依据断言率。我会用做过的最小对照来讲，说清假设、对照组和观察指标，不虚构多 Agent 的大盘数字。

## 什么时候还不该上 Multi-Agent

多 Agent 合理的理由是职责冲突或者工具集合太大。同一个上下文里既要热情推荐、又要严格执行售后政策，单个 prompt 可能很难同时满足两个目标。「看起来更高级」不算理由。拆分的代价是协议：证据怎么传、谁有终裁、失败怎么回滚，没有这些，就只是几个 chat 角色在互相复述。拼多多那边也有单 Agent 和多 Agent 的取舍，见 `pdd-multi-vs-single-agent`，能用路由解决的，就别升级成多智能体。

评测上继续盯三类 case 谁在涨：漏召、幻觉、工具越权。它们的修法、负责人、回滚方式都不一样，漏召是检索没把必读证据带上，幻觉是带上了还越界，工具越权是调了不该动的接口。新模块要在对应切片上有显著改善，而且不能把另外两类打坏。路由错了，用 `jd-intent-accuracy` 的切片去修，别再加一个「总控 Agent」把问题藏起来。同面问到的 ES、Transformer 属于深度题，ES 和向量库的差异也别在这里展开成品牌对比，那是准召的支撑。

## 追问

**什么叫可分离角色？**
两个角色的成功标准互相冲突，或者工具权限必须隔离，比如生成不能直接调退款接口。只是分步骤的话，用 Workflow 就行，见 `meituan-workflow-vs-agent`。

**怎么证明新模块有效？**
做对照实验：固定其余部分，只开新模块，看对应的错误桶下降、无关的桶没恶化。

**RAG 做到哪一步才考虑 Agent？**
静态知识的问题已经能归因，但还剩「必须查实时状态 / 必须写操作」的失败，这时再加工具环，别先加人格。

**关掉模块算迭代吗？**
算，而且更有说服力。要能说出关掉之后哪项指标回升了，或者延迟降了。
