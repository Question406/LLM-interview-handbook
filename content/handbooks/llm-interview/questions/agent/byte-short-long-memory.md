## 真题记录

- 公司：字节跳动
- 岗位：AI Agent 开发；秋招一面
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“短记忆和长记忆分别存什么？怎么避免长记忆污染当前任务？”**

短记忆放当前任务的工作状态，比如本轮打开的文件、失败测试、未提交的 diff、刚拿到的工具观察，易变可丢，任务结束就能清；长记忆放跨会话仍然成立的约束和已验证结论，比如仓库规范、用户偏好、确认过的架构事实，写入必须过校验，使用前还要按文件哈希之类判断有没有失效。把整段对话、中间试错时的错误假设写进长记忆，下次任务就会被当成事实用；隔离做不好，污染会压过本轮的证据。总览见 `agent-memory`。

举个例子，修登录超时。短记忆里留着这次改了 `auth.py`、pytest 第三条失败、diff 还没 commit；长记忆最多写一条超时配置的路径与哈希，比如「本仓登录超时默认 30s，见 `config/auth.yaml`」可以进长记忆，「我觉得 `auth.py` 里那个函数没用」不能进。下次换任务，短记忆清空，长记忆只在检索命中「超时 / 登录」时注入那一条。短记忆的生命周期等于这次会话或这次任务，只用来组装当前上下文，不用于跨会话的长期检索；长记忆每条都带来源、时间和可失效条件（文件哈希、文档版本）。

这种拆分适合用户会回来、约束又相对稳定的多会话 Coding Agent。单次问答、窗口已经装得下全部证据时，不必硬拆两套存储。拆的目的是控制写入质量和注入范围，架构图好看不算理由。

怎么避免长记忆污染当前任务？当前任务优先用短记忆加实时检索；长记忆只注入「已确认且仍有效」的约束，并且要经过检索命中，别每次把全部偏好都顶进窗口。注入前校验哈希，文件已变则条目失效，见 `byte-memory-pollution`。写入门槛是能指出证据，测试绿了、用户口头确认、文档哈希，模型自己总结了一句不算。过程吐槽、失败栈、中间的错误假设留在短记忆，最多写成「未验证」。长记忆检索要带任务类型过滤，修登录超时时别把「前端组件库偏好」灌进来。还有一条污染路径是长记忆抢窗口：用户这次修的是无关模块，全量偏好列表照样把失败测试挤出 L0。所以注入要有预算，硬约束优先于软偏好；冲突时以本轮的测试和 diff 为准，让长记忆让路。

和检索增强生成（RAG）的区别在于，RAG 按需取外部只读文档，Memory 是 Agent 自己沉淀的、带 provenance 的状态。对话摘要别当 RAG 证据，检索到的 README 也别当长期记忆，见 `byte-rag-memory-context`。

常见失败有三种：没验证的结论入了库，后面的任务一直绕开正确入口；文件改了，摘要没跟着哈希失效；短记忆太长，被误写进长记忆。写长记忆要走独立的审核路径（规则或人审），别在压缩回调里偷偷落库；压缩时把过程吐槽和可检索的笔记分开，见 `byte-three-level-compress`。评测看约束是否保持、过期是否失效、错误结论被证伪后有没有回滚，别只数「记忆条数」。

## 追问

**对话摘要能不能当长记忆？**
不能。摘要丢了证据指针，还常带着错误假设，最多当短记忆的压缩，不能当跨会话的事实。

**长记忆和向量库是一回事吗？**
检索可以用向量，但存储语义是带失效条件的状态，和又一份文档索引不一样。

**用户改口了怎么办？**
新的确认覆盖旧偏好，旧条目标成废弃并留审计；两条相反的偏好不能同时注入。

**同一面常接着问什么？**
记忆污染怎么纠、RAG 和 Memory 差在哪。这三连问要能讲清读写、失效和评测，换三个同义词糊弄会被追穿。
