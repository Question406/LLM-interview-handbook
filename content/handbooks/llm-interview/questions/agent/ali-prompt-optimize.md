Prompt 自动推荐，我会按意图选模板、按相似度选示范；压缩则是按预算压上下文，关键槽位单独留着。效果用任务指标来验证，成功率、拒答率、引用正确率、槽位完整率都要看，token 变少本身说明不了什么。单意图的短指令、模板已经稳定的场景，上自动压缩收益很小，还可能丢槽位。

举个例子，一段退货对话里，压缩时把订单号揉进了摘要，摘要模型又漏掉了它，后面的模型就可能编一个订单号出来，这比多用 200 token 严重得多。

推荐这边，先按意图路由到短模板，退货、物流、闲聊各一份，别塞一份万能的长 system。再用 embedding 检索相似的成功 case 当 few-shot；用聚类选示范时要卡住意图，免得把投诉话术塞进咨询单。示范要带正确的工具轨迹，光贴最终回复不够。工具说明也要裁剪，只暴露当前任务相关的 tools，五十个字段和类型规范（schema）全塞进去，既贵又诱导误调，见 `agent-tool-routing`；工具集裁剪和延迟的关系见 `ali-latency-3tools`。推荐系统本身要版本化，模板、示范库、路由阈值的变更都能回滚，否则「自动」就成了线上漂移，出了问题说不清是模型的事还是 prompt 库的事。

压缩这边，长历史走摘要加结构化 state，不做全文拼接。订单号、地址、售后条款、用户更正是不能压的槽位，必须结构化留下，不交给摘要模型碰运气。近期信息留细节，较早的留摘要，比如最近两轮保留原文，更早的只留事件。Memory 里实体键和摘要怎么分工见 `ali-memory-conflict`，记忆分层见 `ali-skill-memory-rag`。

验收时对照压缩前后的任务成功率、槽位完整率、错误工具率和 p95 首个 token 的等待时间（TTFT），只报平均 prompt 长度不够。准备一套金标槽位，压缩后做 exact match。聚类选出的 few-shot 和当前意图对不上，模型会抄错定义，所以要在离线集上测「示范意图 = 当前意图」的命中率。压缩比也要设上限，到预算再压，不要每轮都压到最短。

## 追问

**摘要模型会不会再产生 hallucination？**
会。所以槽位不走摘要，只压叙述性的上下文，并抽检槽位完整率。

**few-shot 越多越好吗？**
不是。太长会挤掉当前证据，示范之间冲突时模型还会摇摆，按相似度取 2-4 条通常就够。

**prompt 压缩和检索增强生成（RAG）是一回事吗？**
不是一回事。RAG 取的是外部证据，prompt 压缩管的是对话和工具说明，见 `ali-rag-eval`。

**怎么证明更短了还不掉点？**
做 A/B，看成功率和槽位完整率，长度只当约束，不当目标。
