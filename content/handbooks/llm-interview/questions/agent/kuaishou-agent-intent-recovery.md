## 真题记录

- 公司：快手
- 团队 / 岗位：大模型算法
- 届别 / 流程：实习；轮次未披露
- 面试时间：原帖未披露；帖子发布于 2026-03-18
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“如果我们这边的agent对于用户意图识别不准确，在工程上有哪些方法进行优化。”**

我会先从线上 trace 把错误分桶，再按桶决定改哪一层，换更大的分类模型通常排在最后。意图「识别不准」的原因可能在用户表达、taxonomy、路由、上下文污染，也可能执行是对的、回复却没有 grounding。只把离线分类准确率刷上去，线上完成率可能下降：模型更敢路由，高风险意图的假阳性变多。

举个例子，用户说「那个不行了」，没说指的是什么。这可能是表达歧义，该澄清；也可能是上一个任务的意图被长期 memory 带了过来，router 固执地走旧任务。两种情况的修法完全不同，所以得先分清楚。

case 从线上误路由、abstain、用户改写、人工转接里抽，按高流量和高风险分组统计。常见的几类是：表达歧义，比如上面那句「那个不行了」；taxonomy 本身就糊，创作辅助和数据查询的边界不清；router 或小模型标错；上下文或长期 memory 把上一任务的意图带过来；检索把相邻业务的文档混进来，模型跟着走偏；tool catalog 描述雷同，选错工具；下游执行对了，回答却编了没返回的字段。没有这张表，任何「优化」都没法回归。删除、发布、消耗额度这类高风险意图的假阳性要单独设阈值，别和闲聊共用一个 softmax。

改法跟着错误类型挑，不必一次全加上。可以定义结构化的意图 schema 并校验所需字段；用 small router 加候选 rerank；置信度或 margin 不够就澄清，别猜，见 `agent-ask-clarify`；会话状态和长期 memory 分层，防止旧任务污染，见 `byte-short-long-memory`；限制当前可见的工具，catalog 描述里写清互斥条件；把 execution outcome 回流成训练和 eval 样本。回流的样本要带最终执行结果，只标「用户说的 intent」不够，用户改写前后的说法可能都合理，错在路由策略。顺序上，通常先修 taxonomy 和工具描述，成本低、能马上减少混淆；再加置信度门槛和澄清；最后才考虑换模型或加训练数据。快手侧的内容和创作者工具多、名字接近，catalog 写清互斥条件，比再训一个分类头更有效。

## 怎么验收

光看分类 accuracy 不够。要看澄清后的解决率、端到端任务成功、错误工具调用、用户二次改写、时延和人工兜底率，按 intent slice 报，微平均会被简单意图拉高。规划阶段也要问一句「这步还是原任务吗」，防止计划漂到别的产品上，见 `kuaishou-modular-planning`。评测集里放歧义句和隐藏目标，乱路由要能被抓住。报进度时按错误类型分别给 before / after，免得用一个 accuracy 掩盖高风险切片的恶化。京东侧的测法见 `jd-intent-accuracy`，同样按意图切片，并报澄清率和错误路由的业务后果。

## 追问

**要不要全程用一个大模型做意图？**
不必。ID 和口令先用规则接住，其余交给小分类器或带 schema 的 LLM，低置信时再上大模型或澄清。

**澄清会不会伤害体验？**
会。只在不同解释会导向不同的高代价动作时才问；能用廉价检索消歧的，先去查。

**memory 会不会让意图更准？**
确认过的偏好有帮助；没校验过的摘要会让 router 固执地走旧任务，所以写入要设门禁。

**指标升了，客诉却没降？**
多半是高风险切片被微平均淹没了。按业务后果加权，假阳性单独设阈值。
