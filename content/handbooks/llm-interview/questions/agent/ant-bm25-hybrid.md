## 真题记录

- 公司：蚂蚁集团
- 团队 / 岗位：大模型 / 智能体应用
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“讲一下 BM25算法原理”**；**“讲讲 RAG 的混合召回”**

BM25 是按查询词和文档的词项匹配打分：稀有词权重大，同一个词出现多了收益会饱和，长文档会被长度归一压一压。混合召回就是把 BM25 和稠密向量各自的候选并到一起，去重、过滤权限，再交给 rerank。蚂蚁这题常连着问，先能写 BM25，再接到金融知识库的混合召回。金融场景里合同编号、错误码这些专有名词要是漏了，比语义差一点更要命，所以两路都要留。

先讲 BM25。对每个查询词 $q$，BM25 累加 IDF 和饱和后的词频，再用文档长度相对平均长度做惩罚。直觉上是三件事：稀有词权重大；同一个词重复出现，收益递减，$k_1$ 控制饱和得多快；长文档不该只因为更长就得高分，$b$ 控制长度归一的力度。面试追公式，写清 IDF、饱和 TF、长度归一这三项就够，不必默写所有变体。所以别把它说成「就是 TF-IDF」。BM25 不懂同义词，「还款日」和「账单日」可能对不上，可是「合同编号」「错误码」这种它比向量稳。

混合召回接检索增强生成（RAG）的流程是这样：稀疏取 top-$n$，稠密取 top-$n$，并成一个统一的候选池去重，做权限和生效日期过滤，再用交叉编码器或 LLM rerank，最后截断放进上下文。混合也别理解成「两个分数加起来」，两路分数量纲不同，融合可以用 RRF。权重按 query 类型调：短的精确词、ID、错误码偏 BM25，长的口语问法、同义改写偏稠密。如果从 ES 整个切到纯向量，会丢掉哪些能力见 `byte-es-to-vector`；三路召回见 `baichuan-three-path-recall`，权重动态化见 `jd-hybrid-retrieval-weight`。

金融 RAG 出问题，很多时候出在导入环节，和模型关系不大：切块把条款编号切断了，没带租户权限，已经废止的制度还留在索引里。索引脏了，混合召回也救不回来。所以导入知识库时就要记录来源、生效日期和 ACL，免得过期制度被召回当成事实；切块时保留条款号和标题路径，BM25 才能据此匹配。蚂蚁场景还会追问「这条制度现在还有效吗、当前用户能不能看」，这要靠元数据里记下的有效期和权限来回答，交给 rerank 是答不了的。评测按 query 类型切片报 Recall@$k$ 和下游答对率，再单列一个「必须命中的关键词」集。

## 追问

**为什么不固定 1:1 加权？**
导航型 query 的精确命中会被语义近邻的噪声挤掉。用验证集按 query 类型扫权重，或者先做 query 分类再加权。

**BM25 对同义词就没办法了？**
可以在 query 侧改写，或者用同义表扩召，但扩召要受控，不然召回噪声会爆炸。改写模型怎么选见 `baichuan-query-rewrite-model-choice`。

**只做 rerank、不做混合行不行？**
不行。rerank 只能在候选池里挑，精确 ID 没进池，rerank 救不回来。

**权限过滤放在哪一步？**
放在融合前。先召回再过滤，会把无权文档的分数漏进排序，也浪费候选配额。
