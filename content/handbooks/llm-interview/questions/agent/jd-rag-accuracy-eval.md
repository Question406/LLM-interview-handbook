- 原始措辞：**“如何评测RAG系统的准确率？”**

陷阱是只报一个「问答准确率」。检索召回错和生成编造会混在同一个数字里，改索引还是改 prompt 无法归因。京东应用开发面还连问 ES / 向量库准召，见 `jd-es-vector-usage`：那些是支撑指标，不是最终准确率。Agent 场景还要再看工具与拒答，见 `jd-agent-eval-beyond-qa`。

## 三层分开报，不要合成一个总分

1. **检索层**：相关证据块是否进入 top-$k$。报 Recall@$k$、nDCG，并按 query 类型切片：货号精确查、口语同义、政策条款、无答案。金标是「必须召回的文档 / chunk ID」，不是生成文本像不像。
2. **忠实层**：答案里每条断言能否对齐到引用 span。报无依据断言率、引用错挂率。价格、库存、时效、售后政策必须能指回证据，对不上就该拒答或降级到结构化字段。
3. **任务层**：用户问题是否真正解决——字段对、可下单、政策解释对。零售里「答得很像官网但下不了单」仍算失败。

自动层用字符串匹配、结构化字段比对或 NLI 对齐；人工抽检校准自动标签。不要只报 RAGAS 一类合成总分，它会掩盖「检索更差但生成在背答案」。

## 集合设计与归因实验

集合要时间切分，防文档更新泄漏到评测。必须含无答案题：系统应拒答而不是补参数知识。按类目、语言、新老商品切片，微平均 accuracy 会被简单货号题拉高。线上抽样要覆盖客诉和高风险（退款、价保）。

归因用替换实验，否则不知道改哪一层：给 gold 检索后变对，主因在检索；固定 gold 证据仍编造，主因在生成。详见 `kuaishou-rag-retrieve-vs-generate`。改检索只许动检索层指标，改 prompt 只许动忠实层；总准确率升了但召回掉了，是在背答案。向量库 IVF / HNSW 和混合检索权重是支撑，见 `jd-hybrid-retrieval-weight`，不要把相似度分数当成准确率。幻觉兜底怎么设计见 `jd-rag-hallucination-fallback`。实习面如果只给得起小集合，也要三层各有几条金标，并固定「改哪一层看哪一列」的对照表；否则一周后的调参无法复盘。线上抽样频率应覆盖大促前后的政策变更，静态离线集会迅速过时。报数时主动说分母：Recall 的分母是必须召回的证据，任务成功的分母是用户问题，两者不能共用一个百分比。

## 追问

- **没有金标怎么办？** 先抽线上 query 做小规模人工标证据 ID，再用以校准自动 oracle；不要用模型给自己打总分当最终数。
- **和 Agent 评估有何不同？** RAG 三层只覆盖「知识是否用对」；Agent 还要评路由、工具合法、恢复，见 `jd-agent-eval-beyond-qa`。
- **无答案题为什么必须有？** 没有拒答金标，模型靠参数知识「答对」会虚高，上线就在编价格库存。
- **准召率和准确率是一回事吗？** 不是。准召是检索支撑；准确率要加上忠实和任务成功。只优化 Recall 可能把干扰文档也灌进上下文。
