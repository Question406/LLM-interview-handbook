## 真题记录

- 公司：快手
- 团队 / 岗位：大模型 LLM / 算法
- 届别 / 流程：日常实习二面；26 校招一面也问 检索增强生成（RAG） 评估指标
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“如何构建评估体系来验证一个 RAG 系统是否真正 Work？”**；校招帖：**“你们在 RAG 应用中是如何做效果评估的？具体用了哪些指标？”**

我会把「RAG work」定义成三件事同时成立：该召回的证据在、答案不越出证据、用户任务完成了，对应检索、忠实、任务三层指标，再用替换实验证明改动改善的是哪一层。只报一个 RAGAS 总分或者开放域聊天分，证明不了 work；没有无答案题和时间切分，模型靠参数知识「答对」，分数也会虚高。

举个例子，创作者问怎么关掉某个设置，系统给的步骤读起来很顺，但用的是政策变更前的旧表述，证据里根本没有。按流畅度或「像不像官方口吻」打分，这条是对的；按忠实层看，它越界了；按任务层看，创作者没改对设置。

三层具体这样量。检索看 Recall@$k$、nDCG、空召回率，金标是证据 ID。忠实看引用对齐率、无依据断言率。任务看业务成功，比如创作者能改对设置、运营能取对指标。工程上再看延迟，以及拒答是不是发生在该拒的时候。自动层用字段比对或 span 对齐，人工抽检 calibration，别用流畅度代替忠实。切片按 query 类型、时间、有没有答案、是否含专有名词，微平均会被简单题拉高。京东同类的拆法见 `jd-rag-accuracy-eval`。

## 集合怎么建，改动怎么证明有效

集合由线上抽样、难改写和无答案题组成，文档和 query 按时间切分，防止更新泄漏。难 case 来自专有名词、数字指标，以及政策变更后还在用旧表述的情况。建之前先写一份「失败说明书」：什么叫漏召、什么叫越界、什么叫任务没完成，再找对应的 case。没有失败定义，标注员会把流畅的错答标成对。集合要版本化，文档仓库 commit、embedding 版本、prompt 版本一起记，否则「work 了」没法复现。

改检索只许动检索层的指标，改 prompt 主要看忠实度的变化；总准确率升了、召回却掉了，是生成在背答案。归因实验本身就是「work」的一部分，说不清主因，就不能说系统 work，只能说「这个版本分数更高」。校招一面还追问了「检索还是生成」的归因，评估体系必须撑得起那种实验，见 `kuaishou-rag-retrieve-vs-generate`。索引新鲜度、混合检索是支撑，别把相似度阈值调到「分数好看」。域内生成模型和基座对比时，开放域聊天分会偏爱更会聊的基座，域内是否 work 要看引用和拒答，别拿闲聊偏好当 work。

RAG 要是只是 Agent 的工具之一，还要看它选没选检索、空结果有没有诚实反馈，见 `kuaishou-agent-eval-dims`、`kuaishou-tool-timeout-empty-result`。面试时按问法调整：校招帖问具体指标，就把三层的名字和金标形态说出来，再补上怎么做替换实验；二面问是否 work，就把对照表和切片说出来。

## 追问

**只有生成端的标注、没有证据 ID，行不行？**
不够。区分不了检索错和生成编，也做不了替换实验。

**RAGAS 能不能当唯一的 KPI？**
不能。可以做辅助，但必须拆层并人工 calibration，否则就是在优化一个合成分数。

**怎么防评测泄漏？**
按文档版本的时间切分，禁止事后把评测 query 的答案页写进被测索引。

**业务成功不好标怎么办？**
先标可检查的字段和动作，比如数值、开关、链接，再抽样看用户是否真的完成了任务。
