## 真题记录

- 公司：快手
- 团队 / 岗位：大模型 LLM / 算法
- 届别 / 流程：日常实习二面；26 校招一面也问 RAG 评估指标
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“如何构建评估体系来验证一个RAG系统是否真正Work？”**；校招帖：**“你们在 RAG 应用中是如何做效果评估的？具体用了哪些指标？”**

陷阱是只报一个 RAGAS 总分或开放域聊天分。快手二面问「是否真正 work」，校招一面还问具体指标和「检索还是生成」归因——评估体系必须能支撑那种实验，见 `kuaishou-rag-retrieve-vs-generate`。没有无答案题和时间切分，模型靠参数知识「答对」会虚高。域内生成模型和基座对比时，维还应含拒答和引用，而不是闲聊偏好。

## Work 的定义对应三层指标

Work 至少同时成立：该召回的证据在、答案不越界、用户任务完成。

- 检索：Recall@$k$、nDCG、空召回率；金标是证据 ID。
- 忠实：引用对齐率、无依据断言率。
- 任务：业务成功（创作者能改对设置、运营能取对指标）。
- 工程：延迟、拒答是否发生在该拒的时候。

京东同构拆法见 `jd-rag-accuracy-eval`。自动层用字段比对或 span 对齐，人工抽检校准。不要用流畅度或「像不像官方口吻」代替忠实。切片按 query 类型、时间、是否有答案、是否专有名词；微平均会被简单题拉高。

## 怎么构建集合，以及如何证明改动有效

构建：线上抽样 + 难改写 + 无答案题；文档与 query 时间切分，防更新泄漏。难 case 来自专有名词、数字指标、政策变更后仍用旧表述。改检索只许动检索层指标，改 prompt 只许动忠实层；总准确率升了但召回掉，是生成在背答案。归因实验是「work」的一部分：说不清主因，就不能说系统 work，只能说「这个版本分数更高」。

和 Agent 评估衔接：若 RAG 只是工具之一，还要看选没选检索、空结果有没有诚实反馈，见 `kuaishou-agent-eval-dims`、`kuaishou-tool-timeout-empty-result`。基座 vs 域内模型对比时，开放域聊天分会偏爱更会聊的基座；域内 work 看引用和拒答。索引新鲜度、混合检索是支撑，不要把相似度阈值调到「分数好看」。构建评估时先写「失败说明书」：什么叫漏召、什么叫越界、什么叫任务未完成，再找对应 case。没有失败定义，标注员会把流畅答错标成对。校招帖问具体指标，就把三层名字和金标形态说出来，并补一句如何做替换实验；二面问是否 work，就把对照表和切片说出来。两问同一体系，只是切口不同。集合要版本化：文档仓库 commit、embedding 版本、prompt 版本一起记，否则「work 了」无法复现。

## 追问

- **只有生成端标注、没有证据 ID 行不行？** 不够。无法区分检索错和生成编，也无法做替换实验。
- **RAGAS 能不能当唯一 KPI？** 不能。可作辅助，必须拆层并人工校准，否则优化合成分数。
- **如何防评测泄漏？** 按文档版本时间切分，禁止把评测 query 的答案页事后写入被测索引。
- **业务成功不好标怎么办？** 先标可检查的字段和动作（数值、开关、链接），再抽样看用户是否真正完成任务。
