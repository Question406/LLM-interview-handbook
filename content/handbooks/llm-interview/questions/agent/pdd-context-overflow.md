## 真题记录

- 公司：拼多多
- 团队 / 岗位：AI Agent
- 届别 / 流程：原帖列出二面题单；轮次为技术二面
- 面试时间：原帖未披露；帖子为 2026 年讨论
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“对话超过上下文限制后怎么处理？滑动窗口、摘要压缩和向量召回怎么选择？”**

三种方法我不会只挑一个，超窗之后按信息类型分工：近轮细节用滑动窗口，跨轮目标用摘要或记忆条目，精确的条款和 SKU 用向量加倒排召回。电商 Agent 忘了已确认的地址或优惠，比闲聊不连贯致命得多，所以已确认的槽位要单独存成不可压缩的状态。这和 `pdd-compress-first-70` 是同一个原则：压原文，留硬约束。

现场可以画一条预算条：左边是最近 $k$ 轮原文，中间是结构化槽位，右边是按需召回的条款句柄。哪一段先溢出，就先压那一段对应的可压缩物，别把整段对话一刀切。

先说三种方法各自的局限。滑动窗口丢掉最早的轮次，实现简单、延迟稳，但会忘掉用户已经确认的地址和优惠约束，适合闲聊连贯，不适合电商成交。摘要压缩把旧轮变成要点，能保住目标和槽位，但丢了原文措辞和可引用性；摘要一旦错了，会污染后续所有轮次，所以必须版本化，并允许「展开原文句柄」。向量召回按当前 query 取历史片段或知识库，适合「上次那个红色那款」这类指代，但它依赖切块、权限过滤和时效，替代不了当前轮的窗口；召回错了，模型会一本正经地引用过期活动，见 `xiaohongshu-rag-limits`。

生产里的默认拼装是：最近 $k$ 轮原文 + 结构化记忆摘要 + 按需检索增强生成（RAG）。$k$ 由 token 预算和指代距离决定，不是固定轮数。超出预算时的驱逐顺序是先压工具 observation，再压旧闲聊，最后才压当前用户的原话。已确认的槽位进不可压缩状态，别写进一段可能被改写的摘要。检索要带权限和时效过滤，冲突的条款要一起保留，别只留最高分，见 `pdd-pick-relevant-chunks`。摘要带上版本和来源句柄，压缩后对硬约束做一次对账，对不上就回放，见 `pdd-compress-first-70`。

评测别用「窗口还能塞多长」当指标，要看成交或任务成功、硬约束保持率、错误引用次数、延迟和 token。摘要污染要专门测「改口后旧约束是否还在」，向量召回要把指代题和过期活动题分开看。三者组合的目标是一份尽量精简、又包含决策所需信息的上下文，把历史尽量留下没有意义，见 `agent-context`。如果和「压缩前 70%」连着问，我会说明：70% 解释的是窗口怎么切，三种方法解释的是超窗后怎么分工，两者可以一起用，并不互斥。

## 追问

**把窗口开到最大行不行？**
容量不等于有效利用。长历史会稀释关键约束、留下过期的计划，输入 prefill 的成本也会涨。

**摘要和记忆条目有什么区别？**
摘要是自然语言压缩，容易错；记忆条目是带字段和类型规范（schema）的槽位，能校验、能过期。优先用结构化的。

**召回能替代窗口吗？**
不能。当前轮的指代和刚发生的工具结果必须在窗口里，检索会漏检。

**预算不够先砍什么？**
工具 observation → 旧闲聊 → 当前用户原话。硬约束最后砍，通常根本不该砍。
