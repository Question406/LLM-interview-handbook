- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“对话超过上下文限制后怎么处理？滑动窗口、摘要压缩和向量召回怎么选择？”**

错法：三种方法里选一个最先进的。超窗之后按信息类型分工：近轮细节用滑动窗口，跨轮目标用摘要或记忆条目，精确条款 / SKU 用向量加倒排召回。电商 Agent 忘了已确认地址或优惠，比闲聊不连贯更致命。和 `pdd-compress-first-70` 同一原则：压原文，留硬约束。

## 三种方法各自会死在哪

滑动窗口丢掉最早轮次，实现简单、延迟稳，但会忘用户已确认的地址 / 优惠约束。适合闲聊连贯，不适合电商成交。摘要压缩把旧轮变成要点，保住目标和槽位，损失原文措辞和可引用性；摘要错误会污染后续所有轮。必须版本化，并允许「展开原文句柄」。向量召回按当前 query 取历史片段或知识库，适合「上次那个红色那款」这类指代，但依赖切块、权限过滤和时效，不能替代当前轮窗口。召回错了，模型会一本正经引用过期活动，见 `xiaohongshu-rag-limits`。

## 生产组合：窗口 + 结构化记忆 + 按需 RAG

默认拼装：最近 $k$ 轮原文 + 结构化记忆摘要 + 按需 RAG。$k$ 由 token 预算和指代距离决定，不是固定轮数。超出预算的驱逐顺序：先压工具 observation，再压旧闲聊，最后才压当前用户原话。已确认槽位进不可压缩状态，别写进一段可能被改写的摘要。检索要带权限和时效过滤，冲突条款不能只留最高分，见 `pdd-pick-relevant-chunks`。摘要要带版本和来源句柄，压缩后对硬约束做对账，对不上就回放，见 `pdd-compress-first-70`。

## 评测用超长会话任务成功

不要用「窗口还能塞多长」当指标。看成交 / 任务成功、硬约束保持率、错误引用次数、延迟和 token。摘要污染要用「改口后旧约束是否还在」专门测。向量召回要用指代题和过期活动题分开看。三者组合的目标是最小但高信号的 context，别把历史尽量留下，见 `agent-context`。现场可以画一条预算条：左边是近 $k$ 轮原文，中间是结构化槽位，右边是按需召回的条款句柄。哪一段先溢出，就先压那一段对应的可压缩物，别整段对话一刀切。和「压缩前 70%」连问时，70% 只解释窗口切法，三种方法解释超窗后的分工，不是两套互斥方案。

## 追问

- **能不能只把窗口开到最大？** 容量不等于有效利用。长历史会稀释关键约束、留下过期计划，prefill 成本也涨。
- **摘要和记忆条目有何区别？** 摘要是自然语言压缩，易错；记忆条目是带 schema 的槽位，可校验、可过期。优先结构化。
- **召回替代窗口行不行？** 不行。当前轮指代和刚发生的工具结果必须在窗口里，检索有漏检。
- **预算不够先砍什么？** 工具 observation → 旧闲聊 → 当前用户原话。硬约束最后砍，通常根本不该砍。
