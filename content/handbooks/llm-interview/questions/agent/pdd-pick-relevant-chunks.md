- 原始措辞：**“如果检索返回了很多相关的内容，如何选择最相关的？”**

我会把「最相关」定义成「能填完用户当前槽位的最小集合」，分最高的十条近重复未必是。流程是过滤 → rerank → 覆盖检查 → 多样性截断，冲突的条款要一起保留，别只留最高分。这是切块、混合检索那条链路的后半段，见 `xiaohongshu-mmkg-chunk`。

「很多相关」往往是近重复加槽位不全：十条都在讲同一款的颜色，运费和售后一块都没有。拼多多的商品页、活动页、售后政策语义经常很接近，向量分挤在一起，按向量相似度裸取 top-$k$，窗口就被近重复占满了。电商问答里，相关不等于可答。

第一步做权限、类目、时效过滤，过期活动和大盘政策不要和当前 SKU 的条款混排。第二步用交叉编码器或业务 rerank，把「语义近但买不了」的块压下去。第三步按问题里的实体做覆盖检查：价格、运费、售后、库存各至少一块，缺槽位就补召或改写 query，别拿同分的近重复填满窗口。第四步在 token 预算内做多样性截断，可以用 MMR 等方法兼顾相关性和内容多样性，已选集合里太像的块，让位给还没覆盖的槽位。MMR 不必背成唯一公式，核心是相关、不重复、盖住问题。

冲突要明确展示。两个退货时效、两个价格同时出现时，并列展示来源，或者升级澄清、转人工。静默选出一个赢家，会把幻觉伪装成检索成功，见 `xiaohongshu-rag-limits`。引用必须能指回块 ID，生成后做引用完整性检查，这和产物护栏是同一个思路。

选完块也还没结束，进模型前要按预算截断：优先保留覆盖槽位的块，再留 rerank 分高的多样性块，工具 JSON 和重复的政策全文最后进。超窗时的驱逐顺序见 `pdd-context-overflow`。被丢掉的块要记原因（权限、过期、近重复、超预算），这样下周调的是切块粒度和召回通道，光把 $k$ 加大没用。选块和分块要一起改：切得太碎，覆盖检查永远缺半句；切得太宽，又会把冲突条款揉进同一块，见 `xiaohongshu-mmkg-chunk`。评测除了 nDCG，还要看槽位覆盖率、冲突有没有被抹掉、错误引用次数和最终任务成功。

## 追问

**为什么不用纯 top-$k$？**
近重复会占满窗口，关键槽位缺失。相似度高也不等于可执行。

**冲突为什么不能取最高分？**
条款冲突是业务风险，不能当排序噪声处理。要并列展示或升级。

**MMR 的 $\lambda$ 怎么定？**
在验证集上扫「重复率 vs 槽位覆盖」，按类目分档，别写死一个数。

**丢块要不要记日志？**
要。否则判断不了是切块太碎、召回通道偏了，还是 rerank 把售后打下去了。
