## 真题记录

- 公司：月之暗面（Moonshot AI）
- 团队 / 岗位：研发工程师（AI-Native 方向）
- 届别 / 流程：原帖未披露；三面
- 面试时间：2026-07-23；帖子发布于 2026-07-30
- 来源类型与可信度：牛客候选人原帖，B（公司、岗位、轮次与面试日期明确，届别未披露）
- 原始措辞：**“如果桌面产物质量忽高忽低，前端能做哪些护栏?”**

陷阱是把护栏理解成「模型输出后弹一句 AI 可能出错」。前端判断不了所有事实，但能拦住不可逆坏结果，并把风险做成可见、可验证、可恢复的关口。桌面产物会落到本地文件、窗口甚至用户工作流，一次坏输出直接覆盖，比聊天里说错话代价高。护栏必须绑在产物链路上，而不是绑在聊天气泡上。没有 `moonshot-desktop-task-center` 里的 Task / Attempt / Artifact 版本，护栏无处可挂。

## 可观测：输入、版本、失败原因

每份产物绑定输入版本、模型或工具版本和生成配置。用户看到的不应是「AI 写好了」，而是「基于哪次 Task、哪次 Attempt、哪份证据」。生成后按类型触发结构校验：JSON schema、表格公式、代码构建、引用完整性、业务规则。失败原因映射成能行动的 UI：「缺字段 X」「引用打不开」「敏感路径未授权」，而不是笼统「出错了」。低置信、超预算、未覆盖用户约束或扫到敏感数据时，自动降级为草稿，不进入发布路径。权限相关失败接到 `moonshot-desktop-local-file-permission` 的 capability 校验，而不是让模型再试一次碰运气。

## 可验证与可恢复：preview、确认、回滚

修改型或发布型产物默认走 preview → diff → 用户确认 → 发布。保留版本和一键回滚；重试生成新 Attempt，不覆盖旧产物。任务中心要能回答：当前在等谁、副作用已经发生了哪些、哪里能取消。这些对象若没在任务中心建模，回滚只能靠「再让模型改回去」，那不是回滚。多窗口场景下，同一产物被另一窗口改写时，要用版本冲突提示，而不是静默覆盖，见 `moonshot-desktop-multiwindow-state`。

## 用护栏数据闭环质量

埋点连接「输入质量—模型/工具路径—检查结果—用户修改/接受—最终成功率」，按失败簇回放任务。护栏同时是产品反馈，不是一层弹窗。评测看拦截率、误拦、用户改写率和回滚次数，不要只看一次生成通过率。质量忽高忽低往往是输入漂移、工具路径切换或未覆盖约束，而不是「模型心情」；前端把这些维度切开，才能把不稳定变成可修的问题。面试收束时主动说三道闸：生成后校验、发布前确认、发布后回滚。缺任何一道，桌面产物都会在某次「看起来能用」的输出上不可逆地写坏用户文件。多模态上下文里还要检查引用的截图/选区是否还在，见 `moonshot-desktop-multimodal-context`；窗口状态和产物版本冲突时先提示，不要静默覆盖。

## 追问

- **前端做不了事实检查怎么办？** 做结构、安全、引用完整性；事实走工具核实或用户确认。不要假装前端能当知识库。
- **每次都 preview 会不会烦？** 按影响分级：草稿自动落、覆盖写必须确认、外发或删除二次确认。
- **和权限提示什么关系？** 权限拦访问面，产物护栏拦落地质量，两套闸门，见 `moonshot-desktop-local-file-permission`。
- **质量波动怎么归因？** 按输入版本、模型路径、检查失败簇切片，而不是只看总通过率。
