## 真题记录

- 公司：月之暗面（Moonshot AI）
- 团队 / 岗位：研发工程师（AI-Native 方向）
- 届别 / 流程：原帖未披露；三面
- 面试时间：2026-07-23；帖子发布于 2026-07-30
- 来源类型与可信度：牛客候选人原帖，B（公司、岗位、轮次与面试日期明确，届别未披露）
- 原始措辞：**“如果桌面产物质量忽高忽低，前端能做哪些护栏?”**

前端护栏我会做成三道闸：生成后校验、发布前确认、发布后回滚。前端判断不了所有事实，但能拦住不可逆的坏结果，把风险做成看得见、能验证、能恢复的关口。模型输出后弹一句「AI 可能出错」没有用。桌面产物会落到本地文件、窗口甚至用户的工作流里，一次坏输出直接覆盖文件，比聊天里说错一句话代价高得多，所以护栏要绑在产物链路上，别绑在聊天气泡上。

比如 Agent 帮用户更新一份周报表格，这次生成漏了一列、公式引用也错了。没有护栏，旧文件就被直接覆盖；有护栏的话，结构校验先报「缺字段 X」，产物降为草稿，用户在 diff 里看到改动，确认后才写盘，写坏了还能一键回到上一版。

第一道闸是可观测和校验。每份产物绑定输入版本、模型或工具版本和生成配置，用户看到的应该是「基于哪次 Task、哪次 Attempt、哪份证据」，光写「AI 写好了」不够。这些对象要在任务中心建模，没有 `moonshot-desktop-task-center` 里的 Task / Attempt / Artifact 版本，护栏就无处可挂。生成后按类型触发结构校验：JSON schema、表格公式、代码构建、引用完整性、业务规则。失败原因映射成能行动的 UI，比如「缺字段 X」「引用打不开」「敏感路径未授权」，笼统一句「出错了」用户没法处理。低置信、超预算、没覆盖用户约束、扫到敏感数据时，自动降为草稿，不进发布路径。权限相关的失败接到 `moonshot-desktop-local-file-permission` 的 capability 校验，别让模型再试一次碰运气。多模态上下文里还要检查引用的截图和选区还在不在，见 `moonshot-desktop-multimodal-context`。

后两道闸是确认和回滚。修改型或发布型产物默认走 preview → diff → 用户确认 → 发布，保留版本和一键回滚；重试生成新的 Attempt，不覆盖旧产物。任务中心要能回答：当前在等谁、哪些副作用已经发生、哪里能取消。这些对象没在任务中心建模的话，回滚只能靠「再让模型改回去」，那算不上回滚。多窗口场景下，同一份产物被另一个窗口改写了，要提示版本冲突，别静默覆盖，见 `moonshot-desktop-multiwindow-state`。三道闸缺任何一道，桌面产物都可能在某次「看起来能用」的输出上不可逆地写坏用户文件。

护栏数据还能用来改进质量，它本身就是产品反馈，作用不止一层弹窗。埋点把输入质量、模型 / 工具路径、检查结果、用户修改或接受、最终成功率连起来，按失败簇回放任务。质量忽高忽低，往往是输入漂移、工具路径切换或者有约束没覆盖，归因成「模型心情」解决不了；前端把这些维度切开，不稳定就变成了能修的问题。评测看拦截率、误拦、用户改写率和回滚次数，一次生成的通过率只是其中一项。

## 追问

**前端做不了事实检查怎么办？**
前端做结构、安全和引用完整性；事实交给工具核实或用户确认。别假装前端能当知识库。

**每次都 preview 会不会烦？**
按影响分级：草稿自动落，覆盖写必须确认，外发或删除二次确认。

**和权限提示什么关系？**
是两套闸门。权限拦访问面，产物护栏拦落地质量，见 `moonshot-desktop-local-file-permission`。

**质量波动怎么归因？**
按输入版本、模型路径、检查失败簇切片来看，只看总通过率找不到原因。
