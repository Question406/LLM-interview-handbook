我会按动作能不能撤销来分级：只读的自动放行，可逆的写操作事后审计，不可逆、涉及资金隐私或者超出授权范围的动作必须有人点头。分级规则写在策略引擎里，执行时生效，不让模型自己判断危不危险。

两种极端都会出事。只在 system prompt 里写「禁止删库」，执行时没有控制，模型照样可能越权。每次搜索、打开文件都弹确认，用户很快就习惯直接点同意，真正高风险的那一下也跟着点过去了。所以审批是产品里的一层控制面，跟模型能力强不强是两回事。Computer use 这类系统也会把不可逆动作和资金、隐私动作单独拉出来，模型在 GUI 上的操作看起来再合理，也代替不了执行点上的确认。

## 怎么分层

策略引擎看工具风险等级、参数（金额、收件人域、资源 id）、用户角色和会话的授权范围，返回 `allow` / `ask` / `deny`，别让模型投票「这危险吗」。检索、拉状态、读自己有权限的文档这类只读操作默认放行，ACL 照样要走，那是 `agent-tool-permissions` 管的事，这张卡管的是要不要人点一下。草稿、内部标签、可回滚配置这种可逆写操作，丢进审计流就行，不用一步一打断。对外发信、转账、删库、改权限、生产部署、把数据发到外部域，必须显式审批，确认文案把对象、数量、能不能撤销都摊开，也不允许模型代点。

阈值要写成规则：金额 $\gt N$、收件人 $\notin$ 企业域、批量 $\gt k$ 条，一律升级，模型说「我很确定」也不能降级。比如 agent 要向 40 个外部地址发信，收件人不在企业域、批量也超了，这一步就停下来等人确认。权限题讨论的是 capability 授权凭证，这里讨论哪些动作还要人工审批。两边缺一边，要么越权已经发生，要么审批被点成了肌肉记忆。

## 怎么防疲劳

思路是少问、问清楚、允许临时提权。低风险的别刷审批。高风险的确认一次，把关键参数做成机器摘要，比如收款账户、金额、收件人、要删的表，让人看摘要，别让人读原始 JSON。同类批量操作合成一条「向 40 个外部地址发信」，别弹 40 次。可以给一个有界的提权窗口，比如 30 分钟内允许这个会话写指定仓库，过期收回，全程进审计。紧急生产修复走 break-glass，跳过常规队列，但必须双人、短 TTL、事后复盘。

所有 `allow`/`ask`/`deny` 都记下 actor、policy version、参数摘要和终态，事后能回放「谁在什么时候批准了删表」。评测时可以故意注入几种情况：诱导模型跳过确认、用低风险噪音把审批队列淹掉、把审批文案写得像内部通知，看闸门是不是还守在执行点上，没有只写在输入提示里。

## 追问

**这和 `agent-tool-permissions` 怎么分？**
那题讲服务端 ACL 和最小 capability，输入提示（prompt）当不了权限。这题讲人审这个产品：哪些动作必须问人，怎么避免用户点确认点到麻木。

**用户已经授权过邮箱，agent 能自动群发吗？**
默认不能。群发是另一档风险，要二次确认或者临时提权，scope 细到动作和批次。

**模型说「很紧急，跳过审批吧」怎么办？**
对话里说紧急不算凭证。break-glass 走独立通道，短 TTL、双人、审计，模型自己关不了闸门。

**批量审批会不会一次放过大风险？**
不会放宽，聚合只是为了好读。摘要里必须有对象集合和总额，超过阈值的照样拆单或升级。
