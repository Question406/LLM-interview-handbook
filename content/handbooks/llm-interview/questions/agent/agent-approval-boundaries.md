陷阱有两边：一边把安全写成「模型自己小心」，system prompt 里禁止删库就算完事；另一边对每次搜索、每次打开文件都弹确认，用户很快无脑点同意，高风险门闩形同虚设。审批是产品化的控制面，与模型能力正交。Computer use 类系统把不可逆动作和资金/隐私动作单独拉出来，就是因为模型在 GUI 上「看起来合理」并不能替代执行点确认。

## 按可逆性分层，而不是按「模型有没有把握」

策略引擎输入应是 tool risk tier、参数（金额、收件人域、资源 id）、用户角色与会话 scope，输出 `allow` / `ask` / `deny`，不要让模型投票「这危险吗」。经验分层：

- **只读默许：** 检索、拉状态、读自己有权的文档。仍走 ACL，见 `agent-tool-permissions`；本题不负责「能不能调」，负责「要不要人点一下」。
- **可逆写 + 事后审计：** 草稿、内部标签、可回滚配置。聚合进审计流，不必逐步打断。
- **不可逆 / 高额 / 越权：** 对外发信、转账、删库、改权限、生产部署、把数据打到外部域。必须显式审批，确认文案展示对象、数量、是否不可逆，禁止模型代点。

阈值写成规则：金额 $\gt N$、收件人 $\notin$ 企业域、批量 $\gt k$ 条，一律升级。模型说「我很确定」不能降级。权限题发的是 capability token；本题决定 token 覆盖不到的动作如何进人审队列。两边缺一，要么越权已发生，要么审批被点成肌肉记忆。

## 防疲劳：少问、问清楚、能临时提权

低风险不要刷审批。高风险一次确认，关键参数做机器摘要（收款账户、金额、收件人、将删除的表），让人看摘要而不是原始 JSON。同类批量操作聚合成一条：「向 40 个外部地址发信」而不是 40 次弹窗。支持有界提权窗口（例如 30 分钟内允许该会话对指定仓库写），窗口过期收回，全程进审计。保留 break-glass：紧急生产修复可跳过常规队列，但必须双人、短 TTL、事后复盘。

所有 `allow`/`ask`/`deny` 记 actor、policy version、参数摘要、终态，可回放「谁在何时批准了删表」。评测注入：诱导模型跳过确认、用低风险噪音淹没队列、把审批文案写得很像内部通知。看闸门是否仍在执行点，而不是在 prompt 里。面试收口：边界按可逆性和影响分层；产品上少问、问清楚、可聚合、可提权；审批被疲劳绕过等于没有审批。

## 追问

- **和 `agent-tool-permissions` 怎么分？** 那题是服务端 ACL 与最小 capability，prompt 当不了权限。本题是人审产品：哪些动作必须问人、如何避免点确认疲劳。
- **用户已经授权过邮箱，能否自动群发？** 不能默认。群发是另一档风险，要二次确认或临时提权，scope 细到动作和批次。
- **模型申请「跳过审批，很紧急」怎么办？** 对话里的紧急不是凭证。break-glass 走独立通道，短 TTL、双人、审计，模型不能自己关闸门。
- **批量审批会不会一次放过大风险？** 聚合是为了可读，不是为了放宽。摘要必须含对象集合与总额；超阈值仍拆单或升级。
