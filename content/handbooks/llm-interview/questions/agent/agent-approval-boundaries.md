两种做法都有问题。只在 system prompt 里禁止删库，没有执行时的控制，模型仍可能越权。每次搜索和打开文件都弹确认，又会让用户习惯直接点同意，忽略真正高风险的操作。审批是产品化的控制面，跟模型能力是两回事。Computer use 这类系统会把不可逆动作和资金、隐私动作单独拉出来，因为模型在 GUI 上看起来合理，替代不了执行点确认。

## 按可逆性分层，别按模型有没有把握

策略引擎根据工具风险等级、参数（金额、收件人域、资源 id）、用户角色和会话授权范围，返回 `allow` / `ask` / `deny`。别让模型投票「这危险吗」。我一般这么分：

- 只读默许：检索、拉状态、读自己有权的文档。ACL 还是要走，见 `agent-tool-permissions`。本题不管「能不能调」，管的是「要不要人点一下」。
- 可逆写 + 事后审计：草稿、内部标签、可回滚配置。丢进审计流就行，不必一步一打断。
- 不可逆 / 高额 / 越权：对外发信、转账、删库、改权限、生产部署、把数据打到外部域。必须显式审批。确认文案把对象、数量、能不能撤销摊开，禁止模型代点。

阈值写成规则：金额 $\gt N$、收件人 $\notin$ 企业域、批量 $\gt k$ 条，一律升级。模型说「我很确定」不能降级。权限题讨论的是 capability 授权凭证；本题讨论哪些动作还需要人工审批。两边缺一，要么越权已经发生，要么审批被点成肌肉记忆。

## 防疲劳：少问、问清楚、能临时提权

低风险别刷审批。高风险一次确认，关键参数做成机器摘要（收款账户、金额、收件人、将删除的表），让人看摘要，别看原始 JSON。同类批量操作合成一条：「向 40 个外部地址发信」，别弹 40 次。支持有界提权窗口，比如 30 分钟内允许该会话对指定仓库写，窗口过期收回，全程进审计。紧急生产修复可以走 break-glass，跳过常规队列，但必须双人、短 TTL、事后复盘。

所有 `allow`/`ask`/`deny` 记 actor、policy version、参数摘要、终态，事后能回放「谁在何时批准了删表」。评测上可以注入：诱导模型跳过确认、用低风险噪音淹没队列、把审批文案写得很像内部通知。看闸门是不是还在执行点，别只写在 输入提示里。

## 追问

- **和 `agent-tool-permissions` 怎么分？** 那题是服务端 ACL 和最小 capability，输入提示（prompt） 当不了权限。本题是人审产品：哪些动作必须问人，怎么避免点确认点到麻木。
- **用户已经授权过邮箱，能否自动群发？** 不能默认。群发是另一档风险，要二次确认或临时提权，scope 细到动作和批次。
- **模型申请「跳过审批，很紧急」怎么办？** 对话里的紧急不是凭证。break-glass 走独立通道，短 TTL、双人、审计，模型不能自己关闸门。
- **批量审批会不会一次放过大风险？** 聚合是为了可读，不是为了放宽。摘要必须含对象集合和总额；超阈值仍拆单或升级。
