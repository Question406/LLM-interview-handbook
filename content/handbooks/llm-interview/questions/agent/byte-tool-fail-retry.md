## 真题记录

- 公司：字节跳动
- 岗位：Agent 开发
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“如果工具调用失败，比如文件不存在、命令超时、权限不够，你的 Agent 是直接报错，还是会做恢复和重试？”**；秋招帖：**“如果调用外部工具或API出现异常、超时等情况，通常如何设计容错和恢复机制？”**；**“是否考虑过让大模型参与异常检测、问题分析以及自动修复？这种方案有什么优缺点？”**

这块容易直接答成二选一：失败一律报错，或失败一律再调一次。这面要一张分类表：可重试错误走退避；不可重试错误改计划或澄清。盲着重跑 403 不会变成 200，盲着重跑超时可能把下游打爆。选错工具和执行失败也要分开，前者见 `byte-react-tool-select`，超时空结果也可对照 `kuaishou-tool-timeout-empty-result`。

## 按错误码分类，而不是「会重试」

- **可重试**：超时、连接抖动、429 限流。有限次数 + 指数退避 + 抖动；写操作必须幂等键，避免重试变成重复下单。预算耗尽则升级，不要在模型 Thought 里写「再试一次」绕过上限。
- **可恢复但不可盲重试**：文件 404。先 `ls` / 搜索 / 用仓库检索定位，仍没有就问用户路径，而不是对同一错误路径循环。
- **不可重试**：403、鉴权失败、明确的 schema 校验失败。停，升权限或拒执行。把无权限当成「再试」会在审计里留下一串攻击性重试。
- **业务空结果**：工具成功但内容为空。这不是传输失败，应改 query 或换工具，见检索空结果处理，而不是 HTTP 重试。

分类发生在 Harness，模型只看到规范化 Observation（错误类型、是否可重试、已尝试次数）。不要把原始堆栈整页灌进窗口。权限拒绝要和安全策略一致，见 `byte-team-agent-security`。

## 让模型自动修：能覆盖长尾，也必须关进笼子

优点：长尾错误文案多、规则写不全，模型可以把「路径拼错」「缺依赖」变成一次搜索或一次补装。缺点：会把错误当成功、无限循环、在沙箱外「修复」成更危险的命令（例如为了过 403 去猜凭证）。

约束：自动修只在沙箱；次数上限；每次修复必须记录原因和动作；高风险命令（删、推、发网）不能由修复路径自动放行。检测可以用规则（错误码）+ 模型分类，但执行策略仍走 Harness，而不是「模型说可以就再打一次」。训练侧若要把错误调用写进 SFT/RL，见 `ali-tool-call-error-sft-rl`，那是学策略；运行时仍要有硬上限。

## 和选错工具、和报错给用户的边界

选错工具时 Observation 可能是成功但无关；应改路由而不是 retry。执行失败才进本卡的分类表。对用户报错的时机：不可恢复、需要缺失信息、或修复预算用尽。报错要带已尝试过的假设和需要用户给的那一维（正确路径、是否授权），而不是把原始异常扔回去。把失败分类写进 trace：错误类型、重试次数、是否改计划，评测才能分开「恢复成功」和「靠幻觉填空看起来成功」。没有这类字段，线上会把超时重试和选错工具混成同一个「工具不行」故事。

## 追问

- **超时重试几次？** 面试给策略不给魔法数字：有限次、退避、写操作幂等、计入总步数预算。具体次数用下游 SLA 和评测定。
- **429 和 404 为什么不能同一套？** 429 是暂时容量问题；404 是目标不存在。同一套重试会把错误放大。
- **自动修会不会掩盖产品 bug？** 会。所有修复轨迹要进评测：同类错误是否应改工具本身。Harness 恢复不是用来藏执行器缺陷的。
- **失败要不要让另一个 Agent 接着干？** 先分类。权限和不可逆失败不要换一个 Agent 绕过策略；多 Agent 冲突恢复见 `byte-multiagent-policy-conflict-recovery`。
