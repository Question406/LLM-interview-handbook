## 真题记录

- 公司：字节跳动
- 岗位：Agent 开发
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“如果工具调用失败，比如文件不存在、命令超时、权限不够，你的 Agent 是直接报错，还是会做恢复和重试？”**；秋招帖：**“如果调用外部工具或 API 出现异常、超时等情况，通常如何设计容错和恢复机制？”**；**“是否考虑过让大模型参与异常检测、问题分析以及自动修复？这种方案有什么优缺点？”**

先分类再决定。失败一律报错太僵，失败一律再调一次又很危险：盲着重跑 403 不会变成 200，盲着重跑超时还可能把下游服务压垮。可重试的错误走退避，不可重试的就改计划或者找用户澄清。

拿一个场景说。Agent 要读 `config/app.yaml`，第一次超时，第二次返回 404。超时、连接抖动、429 限流属于可重试，做法是有限次数加指数退避加抖动，写操作要带 idempotency key，免得重试变成重复下单；预算用完就升级，模型也不能在 Thought 里写一句「再试一次」绕过上限。404 能恢复但不该盲重试，先 `ls`、搜索或用仓库检索定位，还找不到就问用户路径，别对着同一个错路径循环。要是返回 403、鉴权失败，或者明确的字段和类型规范（schema）校验失败，就停下来，升权限或者拒绝执行；把无权限当成「再试试」，审计里会留下一串像攻击一样的重试。还有一种是工具成功了但内容为空，这是业务空结果，传输层没出错，该改 query 或换工具，按检索空结果的办法处理，HTTP 重试没用。

分类放在 Harness 里做，模型只看到规范化后的 Observation，包括错误类型、是否可重试、已经试了几次，原始堆栈别整页灌进窗口。权限拒绝要和安全策略一致，见 `byte-team-agent-security`。选错工具和执行失败也要分开。选错工具时 Observation 可能是成功的、只是和任务无关，这时该改路由，retry 没用，这部分见 `byte-react-tool-select`；执行失败才走上面这套分类。超时和空结果的处理也可以对照 `kuaishou-tool-timeout-empty-result`。

## 让模型参与自动修复

好处是长尾错误的文案太多，规则写不全，模型能把「路径拼错」「缺依赖」变成一次搜索或一次补装。坏处是它可能把错误当成功、陷入无限循环，或者在沙箱外「修复」成更危险的命令，比如为了绕过 403 去猜凭证。所以要加约束：自动修只在沙箱里跑，有次数上限，每次修复都记录原因和动作，删除、推送、发网络请求这类高风险命令不能走修复路径自动放行。检测可以用错误码规则加模型分类，执行策略仍由 Harness 决定，「模型说可以就再打一次」是不行的。训练侧要把错误调用写进 SFT/RL 的话，见 `ali-tool-call-error-sft-rl`，那是在学策略，运行时照样要有硬上限。

什么时候报给用户？不可恢复、缺只有用户才有的信息、或者修复预算用完的时候。报错时带上已经试过的假设和需要用户补的信息，比如正确路径、是否授权，别把原始异常直接扔回去。失败分类也要写进 trace：错误类型、重试次数、有没有改计划。有了这些字段，评测才分得开「恢复成功」和「靠 hallucination 填空看起来成功」；没有的话，线上会把超时重试和选错工具混成同一个「工具不行」的故事。

## 追问

**超时重试几次？**
面试时给策略，不给魔法数字：有限次、退避、写操作幂等、计入总步数预算。具体次数按下游 SLA 和评测定。

**429 和 404 为什么不能用同一套？**
429 是暂时的容量问题，404 是目标不存在。用同一套重试会把错误放大。

**自动修复会不会掩盖产品 bug？**
会。所有修复轨迹都要进评测，看同类错误是不是该改工具本身。Harness 的恢复不是拿来藏执行器缺陷的。

**失败了要不要换另一个 Agent 接着干？**
先分类。权限和不可逆的失败，不能换个 Agent 绕过策略；多 Agent 冲突恢复见 `byte-multiagent-policy-conflict-recovery`。
