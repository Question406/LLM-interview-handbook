该问的情况只有一种：用户的话有几种合理解释，这些解释会导向差别很大、代价高或者不可逆的动作，而搜索、读文件这类廉价观察又排除不了。其他情况先自己去看。背后是一笔账：打断用户的成本，和猜错意图的期望损失，哪个更大。

比如用户说「把那个文件删了」，测试目录和主仓里各有一个同名文件。删错了没法撤销，`ls` 一下也看不出用户指的是哪个，这就该停下来问。如果几种理解下一步都是「先 `ls` / 先检索」，猜错的期望损失几乎为 0，这时候提问只是把延迟转嫁给用户。

这笔账可以说得形式一点。记当前对用户意图的几种合理解释为 $h_1,\ldots,h_k$。它们下一步几乎一样，澄清的信息价值（value of information）就低；导向差得很远又很贵的动作，比如删库还是备份、给 A 汇款还是给 B、覆盖文件还是另存，廉价观察又分不开，就该问。常见的几类是：目标或范围缺失，没说改哪个环境、影响到谁；不可逆的 side effect，像发送、支付、删除、对外部客户可见的变更；权限和身份不明，用谁的凭证、能不能读生产数据；多个对象同名，两个 `main.py`、两张「用户表」；预算和时间约束决定方案，要最快还是要最稳。

这里有两种信息不足要分开。ReAct 式的「先观察再行动」解决的是环境信息不够，Ask Clarification 解决的是用户意图不够，一个问环境，一个问人。先收集信息也不等于先猜一个目标做完：读日志、跑 `--dry-run`、在 staging 复现，这是探索；把邮件写好发出去再问「是这个收件人吗」，就是拿不可逆动作代替了澄清。我常用的规则是：下一步如果不能 undo，又至少有一个同样合理的其他解释，就停下来问一个能改变动作选择的具体问题，别问开放式的「您想做什么」。

问本身也有成本，打断、延迟，用户也不一定答得对，所以问题要问得好。选项要互斥、覆盖主要假设，比如「给 Alice 还是 Bob 的账户」；带上你已经看到的证据，减轻用户的负担；一次只解决一个会改变计划的歧义，别做成问卷。开放式的「请提供更多信息」几乎等于没问，还把责任推回给了用户。

训练时把 `ask_user` 和 `search`、`edit` 一起放进动作空间，用工具 schema 约束问题格式。策略要是从没在歧义 prompt 上因为乱猜受过罚，就会学成从不提问。SFT 示范全是直接行动，模型会把提问当成偏离；示范全是「先问一句」，又会在能查到的事实上打扰用户。所以数据要两类都覆盖：意图有歧义必须问，环境未知必须查。产品上也要设好：没有 `ask_user` 通道时，高风险动作直接拒绝，别默默猜。

评测用隐藏目标：相同的输入对应不同的隐藏目标，只有澄清之后才能稳定成功，乱猜就有一半任务失败。拿前面那句「把那个文件删了」，隐藏目标分别设成测试目录和主仓，混进普通 SWE 任务里，就能看出策略有没有学会分界。指标同时看三样：不可逆动作前该问的有没有问，可逆探索阶段有没有多余提问，澄清之后成功率是不是真的上去了。只鼓励多问，agent 会连能查的工作都不自己做；只鼓励少问，高风险动作前又会漏掉必要的澄清。提问次数本身不能当 KPI。SWE-agent 一类系统也说明，接口方不方便「先看再改」，会强烈影响要不要问人：观察工具越强，需要用户澄清的就越只剩意图，文件内容 agent 自己能看到。

## 追问

**是不是不确定就该问？**
不用。廉价观察能消解的，先观察；观察完还剩下会导向不同高代价动作的假设，才问。把不确定直接等同于提问，会得到一个话痨 agent。

**问什么？**
问能翻转决策的那一维：对象、权限、不可逆的范围。模型自己能查的事实别问。问题带上选项和已经看到的证据，别用开放式的「请补充信息」。

**用户答错了怎么办？**
把澄清结果当成一个仍可能错的假设。高风险动作继续保留确认或者放在 sandbox 里，不可逆步骤必要时再确认一次，别把一句回复当成绝对的 ground truth。

**这个行为怎么训练？**
把 `ask_user` 放进动作空间。在歧义数据上，乱猜给负奖励，恰当提问后成功给正奖励，再单独评测过问和漏问。SFT 示范也要两类都有，不然模型会塌到永远问或者永远不问。
