## 真题记录

- 公司：百川智能
- 团队 / 岗位：大模型实习；具体团队原帖未披露
- 届别 / 流程：实习；一面
- 面试时间：原帖未披露；帖子发布于 2026-02-12
- 来源类型与可信度：牛客候选人原帖，B（公司、实习性质、轮次与发帖时间明确，届别和面试日期未披露）
- 原始措辞：**“上线了吗 线上如何评估 使用量是多少”**

线上评估我会拆成四块看：用户价值、任务可靠性、成本延迟、安全风险，再按用户群和任务类型切开。使用量只说明有人在用，请求多了也可能是失败重试或者机器人，要配上完成任务数、活跃用户分母、留存和实验对照才能解读，QPS 不能当效果。原帖把「上线了吗 / 怎么评估 / 使用量」连在一起问，没有公开数字就直说，别编一个 DAU。

前提是上线前把任务契约定好：一次任务从哪开始，什么算成功、部分成功、放弃、人工接管，trace 要能回放。主指标尽量贴近用户价值，比如完成率、接受后没再改写的比例、节省的时长、复用和留存。同时按任务类型看 tool success、重试、hallucination / 违规、p50/p95、tokens 和成本。高风险业务要有抽样人工审计和 kill switch。离线集过了不代表线上好，分布、工具失败、用户改写都会拉开差距，见 `arl-eval`。

使用量怎么读，举个例子：某周请求数涨了一大截，看着很好，拆开一看，每个任务的调用次数翻了倍，完成率没动，多出来的量主要是重试。所以至少要区分 UV、激活率、任务数 / 活跃用户、完成任务数、留存和调用深度，再按新老用户、入口、权限、场景分 cohort。没有分母的「用了很多」答不了这题。重要变更用 A/B 或逐步放量，和基线对照，再结合用户反馈和 failure bucket，才能把用量变化归到能力上，排除季节性或渠道的影响。面试官问「使用量是多少」时，我会说没有公开数字，我会报完成任务数和 cohort 留存，原始调用次数不拿来当主指标。评测维度可以对照 `kuaishou-agent-eval-dims`、`jd-agent-eval-beyond-qa`、`xiaohongshu-agent-business-eval`。

## 追问

**为什么不把 token 当主指标？**
Token 是成本。主指标应该是用户价值，成本和延迟当约束，免得选出一个又贵又慢的「成功」。

**失败重试会不会把用量做高？**
会。所以要同时看任务成功和每个任务的调用次数，用量单独涨先当告警处理。

**离线指标很好，但没人用？**
查入口、权限、延迟，以及任务定义和真实需求对不对得上。用户采用程度和模型能力要分开分析。

**怎么快速回滚？**
按失败桶和安全事件设 acceptance checks。用量暴涨，但完成率掉、违规升，就该 kill switch，别继续放量。
