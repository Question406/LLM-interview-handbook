模块化 Agent 把“决定怎么做”和“真正执行”分开。规划器提出子目标，执行器根据当前状态调用工具，并检查结果是否符合预期。模型可以帮助理解任务，但退款、支付等关键动作仍需要明确的程序控制。

如果只让模型不断想下一步，却没有参数检查、预算和终止条件，它可能重复下单、跳过确认，或者一直调用失败的工具。

## 规划器负责拆任务，执行器负责检查和调用

Plan-and-Execute 先列出子目标，再执行；ReAct 则交替思考、调用工具和读取结果。关键业务通常用确定性工作流约束模型：模型理解用户意图、补齐必要字段，程序管理状态转移。

调度层要知道哪些工具允许使用、哪些步骤互相依赖，以及参数要符合什么格式。没有依赖的步骤可以并行，有依赖的必须等前一步完成。串并行的延迟影响见 `ali-latency-3tools`。

每一步还要声明预期结果。工具返回错误或不可信内容时，不能直接把它当成下一步指令。实际结果偏离预期时，可以触发局部重规划，见 `agent-when-to-replan`。

模块化便于替换：换模型时不必重写工具层，换物流供应商时不必重训规划器。代价是各模块的输入输出约定要稳定。它与单次打分系统的区别见 `ali-score-vs-agent`。

## 每一步要写清哪些规则

至少明确输入和输出格式、超时时间、最多重试几次，以及重复执行会不会产生额外副作用。

网络短暂失败可以重试。订单不存在或不符合政策，重试相同调用通常没有意义，需要换策略。写操作应有幂等键，让同一请求重复执行时不会重复扣款或创建多张订单。

日志要能串起整条执行轨迹，并记录工具版本或指纹，检测重复调用。步数、金额或延迟超过预算时，执行器必须停止，不能依赖提示词劝模型结束。

## 根据失败原因选择替代方案

- 短暂错误：在次数上限内重试。
- 工具不可用：使用等价工具或可用缓存。
- 任务过大：缩小到能完成的子目标，并向用户确认需求。
- 风险高或连续失败：转人工处理。

退款、支付等不可逆动作的确认应由代码强制执行，见 `ali-hitl-risk` 和 `ali-guardrail`。降级后要记录状态变化和原因，不能只回复“稍后再试”来掩盖失败。

## 面试追问

- **为什么不全部使用 ReAct？** 每步思考和上下文处理会增加成本与尾延迟；权限和幂等也难单靠模型保证。关键路径用工作流约束更容易控制。
- **计划错了怎么办？** 比较实际观测和预期，优先局部重规划，避免每一步都重新规划全部任务。
- **怎样防止死循环？** 统计相同调用的指纹和重复错误，并限制总步数。这些规则要在执行器里实现。
- **如何验收模块化？** 固定工具测试更换模型，再固定模型测试更换工具。这样才能区分模型能力提升和运行框架的改进。
