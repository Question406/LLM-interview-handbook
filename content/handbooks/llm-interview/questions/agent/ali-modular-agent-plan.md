Modular Agent 我会把「决定怎么做」和「真正执行」拆开：规划器提出子目标，执行器根据当前状态调用工具，并检查结果是否符合预期。模型帮忙理解任务，退款、支付这些关键动作由程序控制。如果只让模型不断想下一步，没有参数检查、预算和终止条件，它可能重复下单、跳过确认，或者一直调一个失败的工具。

规划方式上，Plan-and-Execute 先列子目标再执行，ReAct 交替思考、调用工具和读取结果。关键业务通常用确定性工作流约束模型：模型理解用户意图、补齐必要字段，程序管理状态转移。调度层要知道哪些工具允许用、哪些步骤互相依赖、参数要符合什么格式；没有依赖的步骤并行，有依赖的等前一步完成，串并行对延迟的影响见 `ali-latency-3tools`。每一步还要声明预期结果，工具返回错误或不可信内容时，不能直接当成下一步的指令；实际结果偏离预期，就触发局部重规划，见 `agent-when-to-replan`。

每一步至少写清输入输出格式、超时时间、最多重试几次，以及重复执行会不会产生额外副作用。网络短暂失败可以重试；订单不存在或不符合政策时，重试同样的调用通常没意义，要换策略。写操作要有幂等键，同一个请求重复执行也不会重复扣款或多建订单。日志要能串起整条执行轨迹，并记录工具版本或指纹，用来检测重复调用。步数、金额或延迟超过预算时，执行器必须停下来，不能靠提示词劝模型结束。

fallback 按失败原因选。比如查物流时供应商接口超时，先在次数上限内重试；接口整个不可用，就换等价工具或者用可用的缓存；任务太大，就缩小到能完成的子目标，并和用户确认需求；风险高或者连续失败，转人工处理。退款、支付这类不可逆动作的确认由代码强制执行，见 `ali-hitl-risk` 和 `ali-guardrail`。降级后要记录状态变化和原因，别只回一句「稍后再试」把失败盖过去。

模块化的好处是方便替换：换模型不用重写工具层，换物流供应商不用重训规划器。代价是各模块的输入输出约定要稳定。它和单次打分系统的区别见 `ali-score-vs-agent`。

## 追问

**为什么不全部用 ReAct？**
每步思考和上下文处理会增加成本和尾延迟，权限和幂等也很难单靠模型保证。关键路径用工作流约束更容易控制。

**计划错了怎么办？**
比较实际观测和预期，优先局部重规划，避免每一步都重新规划整个任务。

**怎样防止死循环？**
统计相同调用的指纹和重复错误，限制总步数，这些规则写在执行器里。

**怎么验收模块化？**
固定工具测换模型，再固定模型测换工具，这样才能区分模型能力的提升和运行框架的改进。
