## 真题记录

- 公司：百川智能
- 团队 / 岗位：大模型实习
- 届别 / 流程：实习；一面
- 面试时间：原帖未披露；帖子发布于 2026-02-12
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“多 agent 如何如何做的协作”**

多 Agent 协作要先定协议：共享的任务状态、每个角色的输入输出、每项资源由谁唯一写入，然后再从路由、流水线、辩论复核里选一种拓扑。交接、冲突解决、超时和失败升级都要写进协议，评的是端到端任务成功，轮数说明不了什么。做成几个 chatbot 互相聊天是最常见的错法。而且多 Agent 只在单个模型的上下文或技能过载时才值得拆。

拿同一面问到的表格 / SQL 场景举例，它天然就是一条流水线：一个 Agent 理解用户意图，一个写受限 SQL，一个解释和校验结果。共享 state 里放任务目标、已检索的证据、表格句柄、未决问题和权限。每个角色接口要短，规划、检索、SQL、校验各管一段。同一资源只能有一个 writer，免得互相覆盖。交接要结构化，用 JSON 或工具参数，别靠「请你接着说」。失败时重试当前角色、换工具或者升级给人，设好超时，禁止两个 Agent 无限讨论下去。

拓扑常见三种。路由器加专家，主控挑一个专家执行，简单也好测。流水线是抽取、执行、校验串起来，适合表格和 SQL，见 `baichuan-complex-table-extract`。辩论 / 复核是让独立的 checker 专门给高风险结论找错，成本高，留给信贷解释、不可逆写入这类场景。

也要知道什么时候不该拆。上下文装得下、工具面不大、角色职责又说不清时，拆开只会多出交接错误和重复调用，单 Agent 配清晰的 Skill 往往更稳。评测看最终任务成功、冲突次数、重复调用、越权和延迟。权限始终在网关，角色提示不能提权，见 `agent-tool-permissions`。可以对照 `arl-multiagent`、`pdd-multi-vs-single-agent`、`xiaohongshu-multiagent-quality`。

## 追问

**冲突谁说了算？**
共享 state 的唯一 writer，加上显式的冲突规则，比如校验角色可以否决执行角色。辩论得再长也解决不了。

**要不要共享全部对话？**
不要。只传接口需要的字段，串扰少，注入面也小。

**怎么发现拆错了？**
交接失败、重复调用工具、端到端成功率不涨但费用涨，这时就该合并角色。

**和单 Agent 路由有什么差别？**
路由是选一条技能执行，多 Agent 是多个角色并发或者走流水线。先证明单 Agent 不够，再拆。
