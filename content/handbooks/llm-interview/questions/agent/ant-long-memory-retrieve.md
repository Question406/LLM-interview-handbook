## 真题记录

- 公司：蚂蚁集团
- 团队 / 岗位：大模型
- 届别 / 流程：原帖未披露；一面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“你是怎么设计agent的记忆系统？”**；**“长期记忆如何存储？如果历史记录量非常大，怎么优化查询效率？”**

我会把记忆分层：当前任务频繁用的放在会话 state 里，跨会话的事实和偏好抽成结构化条目，带用户、时间、权限和失效策略；历史很大时，先用时间分区和规则把候选缩小，再混合召回加 rerank，不必每次把全部历史放进 prompt。蚂蚁场景还要能审计「记了什么、谁能看」。只答「上了 LangChain Memory」或者「全量 embedding 每次 top-k」，面试官会继续往下追。

分层是这样分的。工作记忆是当前轨迹的 state，计划、工具句柄、没填完的槽位，生命周期就是这个任务。情景记忆是跨会话的事实和偏好，写入前先抽取、确认、脱敏。程序记忆是 Skill / SOP，走版本库管理，不放聊天日志里。每个条目带 `user_id`、task_type、时间、权限、置信度和失效策略。完整对话只当原始附件，检索的对象是结构化摘要。RAG 检索的是外部文档，Memory 保存的是 Agent 自己积累的状态，要记录来源，区别见 `meituan-memory-vs-rag`；分类见 `agent-memory`，短长分工见 `byte-short-long-memory`。

历史很大时怎么查，举个例子：用户问「上次那个理财偏好还算数吗」。先用意图或规则缩候选，本任务类型、近 $N$ 天、当前租户，再在按时间分区的索引上做向量加倒排的混合召回，对 top-$k$ rerank，语义这一路加上时间衰减。要是问的是身份证号、订单号，就直接走倒排，查询路由单靠向量不行。超长会话先滚动摘要，摘要失败就回源附件。金融权限在召回前过滤，无权的记忆不能进窗口。

工程上可以再分冷热：热层是会话 state 和最近的摘要，温层按用户 / 任务建倒排，冷层放对象存储挂原始附件。p95 超时就降级成「只查热层 + 请用户确认」，别去扫完全部历史。向量索引按时间分区，避免每次全库 ANN。写入要有配额和冲突处理，用户的更正优先于旧推断，过期制度随生效日期失效，污染怎么修见 `byte-memory-pollution`。评测看正确记忆的召回、错误记忆污染率和 p95 查询延迟，检索评估见 `agent-memory-retrieval`。

## 追问

**为什么不每次塞全文？**
当前指令会被挤出窗口，过期事实会被当成约束，成本也随历史线性涨。分层检索是为了让召回可控，记得更多不是目的。

**摘要会不会丢关键约束？**
会。关键约束要结构化存储，并在 compaction 之后做回归检查，见 `agent-memory-retrieval`。

**向量检索不够吗？**
不够。ID、错误码、精确偏好需要倒排，权限和时间必须做硬过滤。

**谁有权读这条记忆？**
按用户和租户的 ACL 来，tool 写入的内容默认不能升权。审计要记下写入者、来源和读取的会话。
