## 真题记录

- 公司：京东科技
- 团队 / 岗位：AI 全栈 Agent 研发
- 届别 / 流程：原帖未披露；一面
- 面试时间：原帖未披露；帖子发布于 2026-06-11
- 来源类型与可信度：牛客候选人原帖，B（公司、岗位、轮次与发帖时间明确，届别和面试日期未披露）
- 原始措辞：**“如果一个工具调用上下文太长了，你怎么处理”；“当你的工具列表太多了，工具很多，你想怎么优化”**

我会把工具当成带权限、版本、成本和副作用的检索对象：完整目录留在 registry，模型只看到当前候选工具的简短 schema，选中了再展开；单次调用返回太长，就抽字段、留句柄。把完整目录一次性塞进 prompt 的话，列表越长越容易选错，token 也越多，能被注入影响的内容范围也跟着变大。

比如电商里有好几个同名的「查单」「改单」，一起摆在模型面前，它往往每次都调最通用的那个搜索接口，再到超长 JSON 里自己找字段。这就是列表治理失败的典型症状，也说明「上下文太长」和「工具太多」经常一起爆。

## 工具太多：先筛候选，再展开

先用任务 intent、实体、用户权限和业务域过滤，再用 embedding、词法路由或轻量分类器召回少量候选。第一轮只给名称、一行能力说明、风险等级、必填字段，模型选中后再加载完整 schema、示例和 policy。权限过滤要放在检索之前，没有 ACL 的工具不能因为 description 相似被召回，否则路由就成了越权通道；检索到的 description 也绝不能自动提升权限。成本高或副作用大的工具，在短 schema 里就标上风险，执行层再卡一道，别等模型自觉。电商工具里同名的「查单 / 改单」尤其多，短描述要写清是读还是写、作用在哪张表。

候选集多大，用评测定，看工具选择准确率和 recall@k，别固定成「永远 5 个」。置信不够或者调用失败时，先扩大候选或者向用户澄清，再允许搜 registry，别一失败就把全量目录倒进窗口。schema 校验失败时提示缺了哪个字段；选错工具就扩大候选，别重复同一个非法调用。目录更新要做版本化和 deprecation，防止旧 schema 或者同名不同义的接口还在被调。router 的评测看 recall@k、工具选择准确率、token 和 latency、错误副作用，以及候选集变化后的回归，这些都属于 Agent 评测，QA 准确率覆盖不到，见 `jd-agent-eval-beyond-qa`。

## 单次 Observation 太长：抽字段、留句柄

工具返回整页 JSON、长 HTML、大表时，别原样回灌。按当前任务需要的字段做结构化抽取，用 schema 的字段白名单来筛，比让模型「自己总结一下」稳；分页 token、对象 ID 留作句柄，原始结果放进可检索缓存，需要细节再按句柄二次读取。截断要可逆，日志里能找回原文，窗口里只放摘要；不可逆的截断会让下一步填错 ID。这和对话的三级压缩是同一个思路，近处留能行动的原文，远处留句柄，见 `byte-three-level-compress`。

## 追问

**路由漏召回了怎么办？**
保留一个「搜索工具目录」的元工具，失败时扩大 k，同时用 recall@k 盯着，别只优化 token。

**和 Skill 渐进披露是一回事吗？**
是同一类，都是先目录后展开。Skill 是程序化知识包，工具是可执行 API，两者都能检索，但权限模型不同。

**同名工具怎么防止调错？**
用完全限定名加版本，短描述写清业务域（订单还是售后），别只靠模型读一句介绍。

**上下文长，是因为对话历史还是工具定义？**
先拆开测。工具定义用这里的分层披露，对话历史用压缩，别用同一种截断硬砍。
