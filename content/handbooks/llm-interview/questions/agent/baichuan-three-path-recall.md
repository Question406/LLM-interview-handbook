## 真题记录

- 公司：百川智能
- 团队 / 岗位：大模型实习
- 届别 / 流程：实习；一面
- 面试时间：原帖未披露；帖子发布于 2026-02-12
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“三路召回如何做的”**

三路召回一般是稀疏、稠密、结构化 / 规则各一路，每路先独立召回 top-$k$、做权限和过期过滤，再进统一候选池融合排序。三路互相补充，减少单一检索方式漏掉相关结果；权重按 query 类型调，低置信时才三路全开。只背「BM25 + 向量 + 再加一路」就结束，面试官一定会往下追。

三路各补一块。稀疏路是倒排、BM25 或学习稀疏，专有名词、ID、错误码靠它稳住。稠密路是 embedding ANN，负责抓同义改写和语义相近的文档。结构化 / 规则路处理类目、时间、权限、表格主键或者运营置顶。在案例库或检索增强生成（RAG）场景里，第三路也可以是高质量 few-shot 案例库的精确检索，和文档库分开建索引，免得案例和知识互相污染。三路分数量纲不同，别直接相加。

举个例子，用户问「错误码 E-xxx 是什么意思」，这是明确的 ID，可以短路只走倒排；问「为什么我的订单一直在处理中」，是开放问句，主要靠稠密；问「上个月华东区的退款政策」，带了明确的过滤条件，就走结构化。融合可以用 RRF、加权分或者小模型 rerank，权重按这种 query 类型变：导航 / ID 偏稀疏，开放问句偏稠密，带过滤条件走结构化。别每次都开满，低置信或多跳时再三路开齐。

评估看分层的 recall@$k$、下游任务成功和延迟。导入侧照样要做切块、版本和 ACL，否则三路只是把脏数据召回得更全。Query 改写是前段，算不上第四路索引，改写后还要保留原 query 走稀疏，防止 drift，见 `baichuan-query-rewrite-model-choice`。两路混合见 `ant-bm25-hybrid`，ES 和向量的取舍见 `byte-es-to-vector`。

## 追问

**第三路一定是规则吗？**
不一定。可以是知识图谱、案例库或运营置顶，它补的是稀疏和稠密都弱的那类信号。

**RRF 和学权重怎么选？**
冷启动用 RRF 稳；有标注之后再学一个 query 分类器来输出权重。固定 1:1:1 通常不是最优。

**三路的延迟怎么控制？**
并行召回加短路。p95 超预算时先砍稠密 ANN 的 $k$，权限过滤别砍。

**和 rerank 是什么关系？**
召回负责不漏，rerank 负责精排。精确 ID 没进池，rerank 救不回来。
