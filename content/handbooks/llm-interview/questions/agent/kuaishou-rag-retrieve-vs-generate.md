## 真题记录

- 公司：快手
- 团队 / 岗位：大模型算法
- 届别 / 流程：26 校招；一面
- 面试时间：原帖未披露；帖子发布于 2025-12-30
- 来源类型与可信度：牛客候选人原帖，A（公司、届别、岗位与轮次明确）
- 原始措辞：**“如果 RAG 系统输出错误答案，你怎么判断是检索模块的问题，还是生成模块的问题？有没有设计过归因实验？”**

常见误区是：凭「检索分数高不高」拍板。分数高仍可能证据不含答案跨度，或生成无视证据去编。快手 26 校招一面明确追问归因实验，因此需要对同一 query 做受控替换，不能只凭感觉判断。评估体系若不能支撑这种实验，谈不上 检索增强生成（RAG） work，见 `kuaishou-rag-eval-build`。一个 case 可以双因，报告要写主因和次因。

## 最小替换实验

对同一 query 固定解码随机种子或温度，只换输入证据：

1. **换 gold 检索**：答案变对 → 主因是覆盖或排序不足（漏召、切块、新鲜度、路由）。
2. **只留 gold 证据、禁止额外知识**：仍错或编造未出现字段 → 主因是生成 / 输入提示（prompt） / 解码。
3. **打乱顺序或加入干扰文档**：变错 → 上下文使用不稳健，属生成侧的证据利用问题，也可能是 rerank 把噪声排太前。

同时记自动化信号：recall@$k$、证据是否包含答案跨度、是否引用了未检索字段、该拒答时有没有拒。检索分数只是信号之一。干扰文档实验能区分「不会用证据」和「证据根本不在」。京东幻觉兜底也依赖同一套分组统计，见 `jd-rag-hallucination-fallback`。

## 分组统计修复，分别回归

检索桶：改切分、混合检索、rerank、索引新鲜度、query 改写。生成桶：引用必须对齐 span、关键字段走抽取头、更强「仅依据上下文」指令，或对生成模型单独 监督微调（SFT）。双因就两头都改，但每次只动一层做对照。

评测集按这两桶分别回归，避免「总准确率升了但检索更差、生成在背答案」。无答案题用来抓生成侧乱补参数知识。修复后重复替换实验：gold 检索仍应稳住生成；打乱证据时忠实率不该崩。线上把用户纠正按错误类型分别统计打标，否则迭代会来回拧。实验的控制变量是证据，不是换模型：同一生成配置下只替换检索输入，结论才站得住。若生成温度高导致同证据有时对有时错，先降方差再归因，否则会把解码噪声误判成检索问题。双因 case 很常见，漏召让模型靠参数补全，看起来像生成幻觉，根因仍是覆盖。报告里写「主因检索、次因生成越界」比逼自己单选更诚实，修的时候也知道先补哪一层。

## 追问

- **没有 gold 证据怎么做替换？** 先小规模人工标必须召回的 chunk，再用以校准自动 oracle；不要用「另一个大模型检索」当 gold。
- **分数高但替换显示检索有问题？** 常见于答案跨度不在 top-$k$ 文本里，或切块把数字和单位拆开。看覆盖，不看相似度。
- **生成对了但引用是假的？** 算忠实失败，归生成 / 引用对齐，即使任务层碰巧对。
- **能不能用消融（关掉检索）代替替换？** 关掉检索测的是闭卷能力，不是「当前检索是否够」。归因要的是替换，不是卸掉整模块。
