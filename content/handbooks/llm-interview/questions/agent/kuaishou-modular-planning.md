- 届别 / 流程：日常实习；二面
- 面试时间：原帖未披露；帖子发布于 2026-03-31
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“在 Modular Agent 中，多步规划是如何实现的？”**；**“针对多个工具的调用链路，你的调度策略是如何设计的”**

Modular Agent 的做法是把规划、执行、记忆分开：规划器输出一张可检验的步骤图（DAG），执行器按依赖推进，结果写回显式 state。调度看数据依赖、权限和预算，失败时只重规划受影响的子图。「模型一次把步骤说完，然后按文本顺序执行到底」是常见的错答，计划要写成可检验的图，一段散文没法检验；谁先写在 prompt 里谁先跑，那也算不上调度。

举个例子，任务是「汇总这个作者最近的素材数据，然后发一条动态」。拉素材元数据和拉作者信息之间没有数据依赖，两个节点入度为零，可以并行；发布要先查权限再写，有依赖，得串行，而且发布是高风险工具，放在最后并加确认。几路只读汇总完，才进入写节点。

规划器输出的每一步都绑定候选工具、成功条件和预期观测。结果写回显式 state，下一步只读 state，不靠模型回忆上一步的原话。计划要带预算，最大步数、最大并行度、费用上限，防止规划器写出无限展开。记忆模块负责回答「这步还是原任务吗」，用户中途改口，或者检索漂到相邻产品，就触发局部重规划，别把旧 DAG 执行完；意图漂移的工程处理见 `kuaishou-agent-intent-recovery`。Modular 也不等于「多几个 prompt 角色」：规划器不能直接打有副作用的工具，执行器不能擅自改目标。两者之间的接口是 state 和 DAG，分角色是为了权限隔离。

## 调度和失败处理

调度策略可以讲得很具体。无依赖的节点并行，受并发和 QPS 配额限制；有数据依赖的串行，下游以实际的 observation 为准，不假设上游一定成功；发布、删除、消耗额度这类高风险工具放最后，并加确认；只读失败可以马上换参数或换工具，写操作超时要先查最终状态，避免重复提交，见 `kuaishou-tool-timeout-empty-result`。并行还要讲清合并点：三路只读汇总后再进写节点，部分失败时是降级、重试还是整支取消。

失败时先分清是参数错、权限错还是环境的瞬态错，只重跑受影响的子图，已经成功的节点产出保留。连续 $k$ 步没有进展，或者观测和预期冲突，才做全局 re-plan，见 `agent-when-to-replan`。每步都重规划会抖动、也贵；死守过期计划，工具一变更就空转。评测看必要节点覆盖、非法顺序、无效调用、多余的全局推倒次数。快手二面同一帖还问了评估维度，规划对不对要用节点覆盖来量，BLEU 量不了，见 `kuaishou-agent-eval-dims`；Planning 的量化最后也落回这张图：节点有没有、边合不合法、失败后重规划的范围有多大。

## 追问

**并行会不会把配额打满？**
会。并行度要挂配额和超时；高 QPS 下的三工具正是同面问的场景，评估集要有负载。

**计划和 ReAct 那种每步思考怎么选？**
结构稳定的 SOP 用 DAG；环境很不确定时允许局部 ReAct，但用 rule-based checks 限制重规划的次数。

**模型规划出的边执行不了怎么办？**
执行器按字段和类型规范（schema）校验依赖和权限，非法边直接拒绝、要求重规划，别「尽量跑」。

**记忆污染会怎么破坏调度？**
旧任务的「下一步」被当成本任务的依赖，就会调错工具。用写入 acceptance checks 和任务 ID 隔离，见 `byte-memory-pollution`。
