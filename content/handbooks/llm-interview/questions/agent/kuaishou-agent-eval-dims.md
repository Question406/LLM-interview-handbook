- 原始措辞：**“Agent 评估体系包含哪些核心维度？如何量化衡量Planning能力与Hallucination Rate?”**

常见误区是：用最终回答的流畅度，或单一 QA 准确率代表 Agent。快手 LLM 二面连续追问评估、规划调度和 RAG 是否有效，需要分别解释过程中的问题。Agent 会选工具、填参、决定继续或停，答对但乱调工具在工程上不合格，京东侧同构问题见 `jd-agent-eval-beyond-qa`。原帖还问高 QPS 下三工具延迟，评估集应含负载与超时 case，见 `kuaishou-tool-timeout-empty-result`。

## 核心维度：成功、过程、成本、安全

至少分开报这些，不要合成一个「Agent 分」：

- **任务成功**：用户目标是否达成（字段对、动作真正生效）。
- **规划**：必要子目标是否出现、顺序是否可行、是否过早终止。
- **工具**：选对工具、参数合法、无越权、无效调用次数。
- **观察使用**：是否根据返回改计划，而不是忽略报错继续编。
- **幻觉 / 无依据断言**：事实或工具结果无法对齐的比例。
- **安全违规**：越权、泄漏、高风险未确认。
- **成本**：步数、文本处理单位（token）、延迟；失败恢复是否成功。

切片按意图、工具失败类型、是否超时。只优化成功率会得到爱重试、爱编造成功的策略。

## Planning 与 Hallucination Rate 怎么量化

Planning 不要用计划文本的 BLEU。给任务写 gold 计划图（必要节点与偏序），看：必要节点覆盖、非法顺序（未查权限就写）、过早终止、多余步骤。探针可以是「给残缺 state 补计划」或中途注入环境变化，看会不会死守过期计划，见 `agent-when-to-replan`、`kuaishou-modular-planning`。

Hallucination Rate：先定义断言。分母用全部事实断言或全部回复中的可核验句，分子是无法在检索 / 工具结果中对齐的断言。工具幻觉（编造 API 返回、伪造 request ID）必须单独桶，不能和文档幻觉混报。自动对齐（span / 结构化字段）加人工校准；按场景切片，推荐理由、数据指标、政策条款的幻觉代价不同。流畅、自信的错答要算进分子。RAG 侧三层指标见 `kuaishou-rag-eval-build`。分母必须写死：Planning 覆盖率的分母是 gold 必要节点，不是模型自己生成的步骤数；幻觉率的分母是可核验断言，不是 token 数。分母一漂，周报上的「下降」没有意义。高 QPS 切片要单独报超时后的诚实率：任务失败但正确说明超时，优于编造成功。二面把评估和调度连问，是因为没有这些分母，调度策略无法回归。

## 追问

- **成功但规划很烂算不算过？** 工程上不算。多余调用和不可恢复路径会在负载下爆。过程分要单独卡阈值。
- **没有 gold 计划图怎么办？** 先标必要节点（必须调用的工具与先后约束），不要试图标唯一完整计划。
- **幻觉率用模型打分行不行？** 可做初筛，必须用证据对齐和人工校准；否则评测模型会和被测模型一起幻觉。
- **延迟要进评估吗？** 要。同面问了多工具高 QPS，评估集应含超时与空返回，看是否诚实反馈而不是编造成功。
