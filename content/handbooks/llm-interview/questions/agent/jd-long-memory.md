## 真题记录

- 公司：京东
- 团队 / 岗位：零售平台产品与研发中心
- 届别 / 流程：二面
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“Agent的长期记忆系统是什么”**；**“和大模型交互的时候Prompt过长怎么处理”**

错法：「把聊天记录全存进向量库」，或把超长 Prompt 只答「换 128k 模型」。零售二面把记忆和 MCP / Skill 连问，考的是状态、做法、连接三层不要糊成一个库。错误记忆比没记忆更危险：模型自述「用户喜欢便宜货」一旦入库，后面推荐会系统性偏。

## 分层：工作记忆、情景日志、长期记忆

工作记忆是当前窗口：本轮 query、已调工具的 observation、未完成槽位（SKU、收货地址、优惠券）。情景日志是本任务轨迹：试过哪些检索、哪些接口失败，任务结束可丢。长期记忆才是跨会话可检索的结构化状态：用户确认过的偏好、工具核实过的事实、未完成任务句柄。

写入必须过滤。只入库两类：用户明确确认的偏好，以及订单 / 库存接口核实过的事实。模型「我觉得你想退货」不入库。每条带 `source`、时间、置信度和失效条件（地址变更、SKU 下架）。冲突时用户显式修正优先，其次工具事实，再次旧记忆。零售还要租户隔离：记忆不能跨账号泄漏。分类与冲突策略见 `agent-memory`、`byte-short-long-memory`。

## Prompt 过长：先抽槽位，再压历史

超长不是先摘要。先把不可压缩槽位抽到状态字段：订单号、SKU、金额、时效、售后单号，这些丢了任务就断。历史对话做滚动摘要，只留决策和未决问题。大工具输出（商品详情、评价列表）落对象存储，上下文只留句柄和一两句可引用摘要，需要时再读。这和 `byte-three-level-compress` 的近轮原文 / 中期摘要 / 远期笔记同一思路。

窗口预算要硬切：系统约束和当前槽位优先于闲聊。检索长期记忆时按当前意图过滤，不要把全部偏好灌进 prompt。评测看槽位是否还在、错误记忆是否被引用、任务能否继续，别只看 token 降了多少。窗口只推迟溢出，槽位外置和按需读句柄才是工程解。

## 记忆不是 Skill，也不是 MCP

同面 MCP / Skill 是「连接与做法」，记忆是「状态」。MCP 发现并调用库存、物流接口；Skill 写「退货怎么走、允许哪些工具、失败怎么退」；记忆存「这单已申请退货、用户要上门取件」。三者塞进同一个向量库，检索会把 SOP 和用户隐私搅在一起。见 `jd-skills-essence`。和 RAG 的差别见 `meituan-memory-vs-rag`：RAG 按需取外部知识，记忆沉淀跨会话状态。零售二面若追问「记忆系统长什么样」，答结构化记录：字段、来源、失效条件、租户 ID 都在，检索只是入口。没有 schema 的向量库存聊天，既无法遗忘也无法审计，上线后客诉无法追责到某一条错误偏好。

## 追问

- **错误记忆怎么纠？** 带来源和内容哈希，被订单接口或用户否定后回滚并记负例，不能靠下一轮「请忽略」。见 `byte-memory-pollution`。
- **整段客服对话要不要当长期记忆？** 不要。抽确认过的偏好和结构化槽位即可，原文最多做可过期的情景日志。
- **记忆和接口缓存有何不同？** 缓存是短 TTL 的工具结果；记忆是跨会话、带 provenance 的用户状态，要可遗忘、可审计。
- **和 RAG 冲突时听谁的？** 权威知识库（价保政策、库存）优先于未确认记忆；记忆只约束个性化，不覆盖事实。
