## 真题记录

- 公司：京东
- 团队 / 岗位：零售平台产品与研发中心
- 届别 / 流程：二面
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“Agent 的长期记忆系统是什么”**；**“和大模型交互的时候 Prompt 过长怎么处理”**

Agent 的长期记忆是跨会话可检索的结构化状态：用户确认过的偏好、工具核实过的事实、没做完的任务句柄，每条都带来源、时间、置信度和失效条件。Prompt 过长时，我先把不能丢的槽位抽出来单独存，再压历史，大的工具输出放到外面按需读。「把聊天记录全存进向量库」或者「换 128k 模型」都答不到点上，窗口变大只是推迟溢出。

错误记忆比没有记忆更危险。比如模型自己总结了一句「用户喜欢便宜货」，一旦入库，后面的推荐就会系统性地偏。所以写入要过滤，只入库两类：用户明确确认的偏好，以及订单、库存接口核实过的事实。模型说「我觉得你想退货」，不入库。每条记录带 `source`、时间、置信度和失效条件，比如地址变更、SKU 下架。冲突时，用户的显式修正优先，其次是工具事实，最后才是旧记忆。零售还要做租户隔离，记忆不能跨账号泄漏。分类和冲突策略见 `agent-memory`、`byte-short-long-memory`。

记忆可以分三层看。工作记忆就是当前窗口：本轮 query、已调用工具返回的 observation、还没填完的槽位（SKU、收货地址、优惠券）。情景日志是这次任务的轨迹，试过哪些检索、哪些接口失败了，任务结束就可以丢。长期记忆才是上面说的跨会话结构化状态。面试官追问「记忆系统长什么样」，就答结构化记录，字段、来源、失效条件、租户 ID 都在，检索只是入口。只用向量库存聊天、不定义 schema，既没法遗忘也没法审计，上线后出了客诉，也追不到是哪一条错误偏好。

## Prompt 过长怎么处理

先抽槽位，摘要放在后面。订单号、SKU、金额、时效、售后单号这些不可压缩的槽位抽到状态字段里，丢了任务就断。历史对话做滚动摘要，只留决策和未决问题。商品详情、评价列表这类大工具输出落到对象存储，上下文里只留句柄和一两句可引用的摘要，需要时再读。这和 `byte-three-level-compress` 的近轮原文、中期摘要、远期笔记是同一个思路。

窗口预算要硬切，系统约束和当前槽位优先于闲聊。检索长期记忆时按当前意图过滤，别把全部偏好塞进 prompt。评测看槽位还在不在、错误记忆有没有被引用、任务能不能继续，token 用量降了多少只是附带的数字。槽位外置、按需读句柄，才是工程上的解法。

这题零售二面是和 MCP、Skill 连着问的，考的是状态、做法、连接三层分不分得清。MCP 和 Skill 管「连接与做法」，记忆管「状态」：MCP 发现并调用库存、物流接口；Skill 写「退货怎么走、允许哪些工具、失败怎么退」；记忆存「这单已申请退货、用户要上门取件」。三者塞进同一个向量库，检索会把 SOP 和用户隐私搅在一起，见 `jd-skills-essence`。和检索增强生成（RAG）的区别见 `meituan-memory-vs-rag`，RAG 按需取外部知识，记忆沉淀跨会话状态。

## 追问

**错误记忆怎么纠正？**
每条带来源和内容哈希，被订单接口或用户否定后就回滚，并记一条负例。靠下一轮说一句「请忽略」没用，见 `byte-memory-pollution`。

**整段客服对话要不要当长期记忆？**
不要。抽出确认过的偏好和结构化槽位就够了，原文最多做可过期的情景日志。

**记忆和接口缓存有什么不同？**
缓存是短 TTL 的工具结果；记忆是跨会话、带 provenance 的用户状态，要能遗忘、能审计。

**记忆和 RAG 冲突时听谁的？**
权威知识库（价保政策、库存）优先于未确认的记忆。记忆只约束个性化，不覆盖事实。
