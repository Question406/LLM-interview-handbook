## 真题记录

- 公司：商汤
- 岗位：大模型算法实习；二面
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“多轮对话怎么处理”**

多轮要处理三件事：指代（「上一张表的第二列」）、状态（已抽出的字段）、上下文预算。实现是 slot 状态机 + 最近 $K$ 轮 + 图像区域引用，别把所有历史帧和全文工具结果塞进窗口。二面若只答「把聊天记录拼起来」，会丢「指的是哪张图哪个区域」。一面数据清洗（`sensetime-data-clean`）保证槽位可核验；多轮首先是产品状态设计，数据切分是第二步。商汤文档/票据场景里，用户下一句几乎总是指上一张图的某个区域，纯文本历史解决不了这个问题。

## 状态留下，历史按需

已确认槽位结构化留下，例如 `{amount: 1280}`；历史只留与当前任务相关的轮次；工具结果摘要回写（「第 2 列表头 = 税额」），不回整张 JSON。用户先上传发票再指「右上角红章旁边」时，要记住上一张图的区域引用（bbox），而不是把第一轮整段 OCR 再拼一遍。窗口爆了优先丢无关闲聊和重复 OCR，不要随机丢早期已确认槽，用户会觉得模型忘了刚才填过。

适用：文档理解、客服填表、带图指代。单轮 OCR 不必上状态机。训练若切成单轮、上线却拼多轮，分布会崩。这和「不用训练也能做多轮」不矛盾：推理侧先有同一套状态序列化，训练再补指代和槽位更新样本。

## 数据与评测怎么设计

训练必须带多轮指代、槽位更正、改图再问。构造：复制成功轨迹，只改一轮指代对象或更正一个槽，看模型是否改对而不污染其它槽。评测按轮次报：指代正确、槽位保持、错误更正、超长对话是否仍记住关键槽。不要只报最后一轮答案对。上下文压缩若切错块（`pdd-chunk-size-overlap` 同类问题），区域引用会丢，要和切图/切表策略一起测。

失败模式：只拼文本、丢掉区域；或为省 token 丢掉早期槽。对照「全文拼接 vs 状态机+摘要」，看正确率和 p95 token。

二面若追「具体怎么落地」，按一次会话走：上传图 → 抽槽并写 bbox → 用户指代「那个红章旁边」时用区域检索而不是全文 OCR → 更正税额只改对应槽，其它槽保持。评测加两类对抗：中途换图、用户否定上一轮字段。换图后旧 bbox 必须失效，否则会张冠李戴。窗口策略写成规则：已确认槽常驻、工具摘要可再查、原文只留最近 $K$ 轮与当前指代相关的句。我会收一句：多轮是状态和指代，不是更长的聊天记录；训推共用同一套序列化，才不会「训练单轮、推理多轮」。

## 追问

- **训推不一致怎么防？** 训练带多轮指代和槽位更新，上线用同一套状态序列化回放；禁止训练单轮、推理多轮。
- **$K$ 怎么定？** 按任务槽位数和平均指代跨度扫；先保证已确认槽常驻，再谈最近 $K$ 轮原文。
- **工具结果为什么不能全文回灌？** 表格 JSON 会挤爆窗口、淹没指代。摘要 + 可再检索的指针更稳。
- **和一面清洗题怎么衔接？** 清洗保证字段可核验；多轮把已核验槽当状态。脏槽一旦写入，后面轮次会当事实用。
