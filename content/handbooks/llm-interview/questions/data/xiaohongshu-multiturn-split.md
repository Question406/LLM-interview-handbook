## 真题记录

- 公司：小红书
- 团队 / 岗位：Hi lab 日常实习
- 届别 / 流程：日常实习；一面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“多轮对话轮数，说明多轮训练数据拆分的trick和原因，训推一致吗”**；还问多轮截断与记忆优化

陷阱是把整段会话当一条 CE，或训练从不截断、线上却滑窗。评委要的是 **loss 边界与截断协议和线上一致**。一条会话拆成多个样本，每个样本的标签是某一助手轮，前面的 user / tool / 历史助手只当条件（mask）。整段 CE 会让模型背早期轮，且长度不均导致短会话被淹没。同类切分见 `sensetime-multiturn`。

## 切点与工具对

工具调用必须 `user → call → result` 成组，不能在 observation 中间切开，否则模型学到「没看到结果就往下说」。Thinking / 工具 XML 标签版本必须与线上一致：训练开 Thinking、推理关，等于训推分布错位。过长则切窗：保留最近轮 + 结构化记忆（已确认的约束、未完成子目标），丢掉中间闲聊。记忆检索与污染见 `byte-short-long-memory`、`agent-memory-retrieval`。

截断超参（最大轮数、token 预算、摘要策略）应写入同一套配置，而不是训练脚本一份、serving 一份。原帖还问检索 top-k 固定还是模型选——那是推理侧预算，应与切窗同一配置面讲清，展开见 `xiaohongshu-posttrain-gain`。

## 训推一致怎么验

对照实验：同一会话在训练打包器与线上预处理各跑一遍，比对 token 化后的 prefix。不一致的典型来源：系统提示差异、工具 schema 字段顺序、截断从左还是从右、是否保留失败工具轮。收益评估用多轮任务成功（中途澄清后是否仍能完成），而不是单轮 CE。单轮 loss 降、多轮任务掉，就是切分或截断协议错了。

失败模式：只对最后一轮算 loss 却在线上要求中间轮也能答；切开 tool result；摘要模型与主模型口径不同导致状态丢失。

## 截断、记忆与配置单

多轮一长，上下文必然切。切的原则是 **保留决策所需状态，丢掉闲聊 token**。状态包括：用户已确认的约束、未完成的子目标、最近一次工具结果、以及安全相关的拒答理由。闲聊和重复致谢优先丢。摘要应结构化（键值），不要再生成一篇散文再让模型去读——散文摘要自己会丢字段。记忆写入与检索见 `byte-short-long-memory`，污染（把猜测写进长期记忆）要单独防。

训推一致写成一张配置单：chat template 哈希、最大 token、从哪侧截断、是否保留失败工具轮、Thinking 开关、工具 schema 版本、检索 top-k。训练打包器与 serving 预处理器对同一会话做差分测试，token 对不上就视为 bug。原帖问 top-k 固定还是模型选，应放进这张单子：它改变的是每一轮的上下文分布，和切窗是同一类训推问题，展开见 `xiaohongshu-posttrain-gain`。

轮数本身不是越大越好。训练里出现过的最大轮数应覆盖线上 P95，但超长尾用记忆而不是无限上下文硬塞。只训最后一轮省算力，却让中间轮的助手话术变弱；全轮都算 loss 则早期轮被重复看见。选择要写进方案，并用多轮任务成功验证，而不是用单轮 CE。差分测试要覆盖「带工具的长会话」和「纯闲聊短会话」两类：前者查 tool 对是否被切开，后者查是否误把致谢当状态留下。Serving 若多一档压缩或换 tokenizer，必须重新跑同一套差分，否则训推一致只在实验室成立。记忆摘要的键要和线上读取的键同名，避免训练写 `constraint`、推理读 `用户要求`。

## 追问

- **所有历史助手轮都算 loss 吗？** 可以，利用率高，但早期轮会被重复看到；只训当前轮更贴线上逐步生成。需在数据量与一致性之间写明选择。
- **切窗会不会丢约束？** 会，所以要结构化记忆，而不是只丢中间句。丢了「用户说过过敏」这类约束会变成安全事故。
- **如何证明训推一致？** 打包器差分测试 + 同一模板哈希，而不是口说「我们用了 chat template」。
- **工具对为什么不能拆？** observation 是环境给的条件，不是模型该预测的 token；切开会让模型在没看到结果时编造。
- **Thinking 标签不一致会怎样？** 训练有、推理无，等于条件分布整体错位，表现为乱插标签或漏推理。
