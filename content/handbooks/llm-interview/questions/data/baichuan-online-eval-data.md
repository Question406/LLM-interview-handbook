## 真题记录

- 公司：百川智能
- 团队 / 岗位：大模型实习
- 届别 / 流程：实习；一面
- 面试时间：原帖未披露；帖子发布于 2026-02-12
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“线上评估指标数据如何构造”**

常见误区是：「再标一份离线集」，或者把每次重试算一次成功。本题要讲数从哪来、分母是什么：把生产 trace 收成可分析表，不要另起标注项目。没有稳定分母的「准确率」不能上看板。使用量、满意度另卡解读；这里只构造能做前后对比的事实表。

## 一行一个用户任务，重试挂同一 task

从日志抽：`session` / `task_id`、入口、模型与 prompt 版本、检索命中、工具错误码、最终状态、用户改写 / 点踩、延迟和 token 用量。构造规则：

- 一次用户意图一行；自动重试、换工具挂在同一 `task_id`，成功只计最终态；
- 成功 / 放弃 / 转人工的定义与离线 rubric 对齐，否则线上线下不可比；
- 机器人、内部调试、压测流量单独 `cohort` 标记，不进主分母；
- 时间窗与发布版本对齐：对比 $v_a$ vs $v_b$ 只用各自稳定窗口，避免发布当天的混合流量。

脱敏：PII 哈希或剥离；抽样人工审计校正自动标签（点踩不等于任务失败）。加权按入口 cohort（新用户 / 高价值场景），避免头部简单任务淹没长尾。

构造完的事实表至少有这些列：`task_id`、入口、模型版本、prompt/skill 版本、检索索引版本、工具链、最终态、用户行为码、延迟、token、cohort。缺版本列就无法做前后对比，缺 `task_id` 就会把重试算成新样本。

## 实验：先锁分母，再报分子

上线一个指标前做三件对照：（1）同一批 session 用新旧成功定义，看排名是否翻；（2）把重试拆成多行 vs 一行，看「成功率」虚高多少；（3）去掉内部流量后，版本对比符号是否变。分母漂移时冻结看板，不要调权重把曲线拉平。

和离线 Preference / AUC 的关系见 `data-offline-online-metric-gap`：线上事实表是分母，离线集只是诊断切片。没有这张表，后训练「涨了」无法归因到模型、检索还是入口 mix。

## 追问

- **重试算成功几次？** 一次任务最多一次成功。重试是过程，不是新样本。
- **点踩能当失败吗？** 不能直接当。要和最终态、转人工一起编码，抽检校准。
- **为什么必须版本对齐？** 模型与 prompt 混在同一天，差值无法归因。先锁分母再谈涨跌。
