## 真题记录

- 公司：百川智能
- 团队 / 岗位：大模型实习
- 届别 / 流程：实习；一面
- 面试时间：原帖未披露；帖子发布于 2026-02-12
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“线上评估指标数据如何构造”**

线上评估数据我会直接从生产 trace 收成一张事实表，一行一个用户任务，先把分母定清楚再算分子，不另起一个标注项目，也不再标一份离线集。没有稳定分母的「准确率」不该上看板。使用量、满意度另外解读，这里只构造能做前后对比的事实表。

最常见的坑是把每次重试都算成一次样本。比如用户申请一次退款，工具超时自动重试了两次，第三次才成功，这应该是一个任务、一次成功；拆成三行的话，成功率就被扭曲了。

## 字段和构造规则

从日志里抽 `session` / `task_id`、入口、模型与 prompt 版本、检索命中、工具错误码、最终状态、用户改写 / 点踩、延迟和 token 用量。构造时守住几条规则：一次用户意图一行，自动重试、换工具都挂在同一个 `task_id` 下，成功只计最终态；成功 / 放弃 / 转人工的定义和离线 rubric 对齐，不然线上线下没法比；机器人、内部调试、压测流量单独打 `cohort` 标记，不进主分母；时间窗和发布版本对齐，对比 $v_a$ 和 $v_b$ 只用各自的稳定窗口，避开发布当天的混合流量。

PII 做哈希或剥离。自动标签要抽样人工审计来校正，点踩不等于任务失败。加权按入口 cohort（新用户 / 高价值场景）来做，免得头部的简单任务把长尾淹没。

建好的表至少要有这些列：`task_id`、入口、模型版本、prompt/skill 版本、检索索引版本、工具链、最终态、用户行为码、延迟、token、cohort。缺版本列就做不了前后对比，缺 `task_id` 就会把重试当成新样本。

## 上线前先验分母

一个指标上线前我会做三组对照：同一批 session 用新旧两种成功定义，看排名会不会翻；把重试拆成多行和合成一行各算一次，看「成功率」被虚抬了多少；去掉内部流量后，版本对比的符号会不会变。分母一漂移就冻结看板，别靠调权重把曲线拉平。

和离线 Preference / AUC 的关系见 `data-offline-online-metric-gap`：线上事实表是分母，离线集只是诊断切片。没有这张表，后训练「涨了」没法归因到模型、检索还是入口 mix。

## 追问

**重试算成功几次？**
一个任务最多算一次成功。重试是过程，不产生新样本。

**点踩能直接当失败吗？**
不能。要和最终态、转人工一起编码，再抽检 calibration。

**为什么一定要版本对齐？**
模型和 prompt 在同一天一起变，差值就没法归因。先锁分母，再谈涨跌。
