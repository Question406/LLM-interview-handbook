## 真题记录

- 公司：美团
- 团队 / 岗位：大模型算法；二面业务专项
- 届别 / 流程：原帖未披露；二面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“针对字段提取业务，需要设计哪些维度的 Reward？”**；**“是否遇到过 Reward Hacking，如何识别与解决？”**

字段抽取的奖励分数（reward）我会拆成六个可执行、可单独监控的维度，用入单成功率和人工改写率做 acceptance checks；识别 hacking 靠的是一组专门的反例探针，看哪个维度在涨、业务效果却没动。让同一个 LLM 给 JSON「打个漂亮分」，或者只看加权总分，都看不出问题。

后半问才是拉开差距的地方。举个例子，模型学会了永远输出一个合法的空 JSON，schema 那一维拿满分，总 reward 也在涨，可字段 F1 接近 0，入单成功率纹丝不动。把「能解析、能填默认值、能复制 prompt」当成成功，是字段业务里最常见的 shortcut。另外，标注质量（`meituan-label-quality`）不过关的话，reward 拆得再细也是在拟合脏标签。

## 六个维度

第一是关键字段的精确匹配或 F1，比如门店、时间、金额、地址。第二是类型、枚举和数值范围合法。第三是必填项齐全。第四是字段之间的约束，时间顺序对、金额非负、地址和门店一致。第五是 JSON 能解析、符合字段和类型规范（schema）。第六是原文里找不到依据的编造给负分。

各维的权重按业务代价定：编造出能下单的属性、必填缺失，这些的权重要大于「措辞漂不漂亮」。「整体像不像」这种判断别塞进同一个标量。诊断思路和 `data-reward-eval-flat` 一样，总分涨、端到端不涨，先拆开看各维和结果的相关性，再怀疑 hacking。

## 怎么识别和切断 hacking

信号是某一维突然飙升、总 reward 也在升，入单成功却不升；模型开始输出空字段、万能默认值、复制 prompt，或者永远合法的占位符。最小的识别实验是做一个探针集：「永远输出合法空 JSON」「复制用户原话当地址」「金额一律填 0」，再加上缺字段、时间冲突、原文没有价格却写出价格这类反例，看这些轨迹的分维分和总分是不是仍然很高。schema 维满分、字段 F1 接近 0，就说明权重把可解析当成了成功。维度相关性也能看出来：某一维和端到端成功率的相关逐周下降，这一维的均值却还在升，就是 overoptimization。

发现 hacking 后，先冻结那一维的学习率或权重，再去修数据和验证器（verifier），继续加大 RL 步长只会让取巧更严重。具体手段有加约束项和反例、随机人工审计、给单一维度的权重设上限，必要时改用规则引擎或下游校验器当 oracle。修复顺序是先改 reward 定义和反例，换更大的 policy 没用。字段抽取本来就适合规则 oracle，RL 用在规则判不清的歧义上就好，别把整条 JSON 丢给同一个生成模型打分。

对照实验要报分维 reward、端到端成功率、空字段率、无依据编造率。只报加权总分，hacking 那半问就等于没回答。

## 追问

**为什么不用 LLM-as-reward？**
字段对错能规则化。LLM 评分可能和生成模型共享对格式的偏好，会把外观好看的 JSON 误判为正确，所以 LLM 最多拿来做抽检 calibration。

**空字段怎么处理？**
必填为空给负分；选填为空不奖不罚，免得模型靠「全空但合法」刷 schema 分。

**发现 hacking 先调什么？**
先冻结那一维，加反例和约束，再谈学习率。加大步长只会进一步强化取巧。

**和评测刷平有什么区别？**
评测刷平是 proxy 和真指标脱节；这题还要指出具体的 shortcut，比如占位符、默认值、复制 prompt。
