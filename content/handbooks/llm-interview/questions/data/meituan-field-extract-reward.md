## 真题记录

- 公司：美团
- 团队 / 岗位：大模型算法；二面业务专项
- 届别 / 流程：原帖未披露；二面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“针对字段提取业务，需要设计哪些维度的 Reward？”**；**“是否遇到过 Reward Hacking，如何识别与解决？”**

字段抽取的 reward 必须可执行，不要让同一个 LLM 给 JSON「打漂亮分」。二面要拆成可单独监控的硬规则，并以入单成功 / 人工改写率做门禁，而不是只看加权总分。标注质量（`meituan-label-quality`）不过关，reward 再细也是在拟合脏标签。这题后半问 hacking 才是区分点：会背六维但说不出「哪一维在涨、业务没动」的探针，等于没做过 RL。把可解析、可默认、可复制 prompt 当成成功，是字段业务里最常见的 shortcut。

## 六维硬规则，维维可监控

1. 关键字段精确匹配 / F1（门店、时间、金额、地址）。
2. 类型、枚举与数值范围合法。
3. 必填齐全。
4. 字段间约束（时间顺序、金额非负、地址与门店一致）。
5. JSON / schema 可解析。
6. 对原文无依据的编造给负分。

各维权重按业务代价定：编造可下单属性、必填缺失，权重大于「措辞是否漂亮」。不要把「整体像不像」塞进同一标量。和 `data-reward-eval-flat` 同一诊断：总分涨、端到端不涨，先拆维度相关性，再怀疑 hacking。

## 识别与切断 hacking

信号：某一维飙升、总 reward 升，但入单成功不升；模型学会空字段、万能默认值、复制提示词、输出永远合法的占位符。实验上做反例集（缺字段、冲突时间、原文无价格却写出价格），看该维分是否仍高。解法是加约束项与反例、随机人工审计、限制单一维权重上限、必要时改用规则引擎 / 下游校验器当 oracle。发现 hacking 后先冻结该维学习率或权重，再修数据和 verifier，而不是继续加大 RL 步长。

对照要报：分维 reward、端到端成功率、空字段率、无依据编造率。只报加权总分，算没回答 hacking 这半问。

识别 hacking 的最小实验：把「永远输出合法空 JSON」「复制用户原话当地址」「金额一律填 0」做成探针集，看这些轨迹的分维分和总分是否仍高。若 schema 维满分、字段 F1 接近 0，说明权重把可解析当成了成功。还可以看维度相关性：某一维与端到端成功率的相关若逐周下降，而该维均值仍升，就是 overoptimization。修复顺序是改 reward 定义和反例，不是换更大的 policy。字段抽取适合规则 oracle，把 RL 用在规则判不清的歧义上，不要整条 JSON 丢给同一个生成模型打分。

## 追问

- **为什么不用 LLM-as-reward？** 字段对错能规则化；LLM 分会跟生成模型共谋「好看 JSON」。LLM 最多做抽检校准。
- **空字段怎么处理？** 必填空给负分；选填空不奖不罚，避免模型靠「全空但合法」刷 schema 分。
- **发现 hacking 先调什么？** 先冻该维、加反例与约束，再谈学习率。加大步长只会把 shortcut 学得更死。
- **和评测刷平怎么分？** 评测刷平是 proxy 与真指标脱节；本题还要指出具体 shortcut（占位符、默认值、复制 prompt）。
