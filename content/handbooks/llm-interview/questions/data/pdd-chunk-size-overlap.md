## 真题记录

- 公司：拼多多
- 团队 / 岗位：AI Agent
- 届别 / 流程：一面（检索增强生成（RAG） 流程）
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“文档如何切块？Chunk 大小和重叠窗口是根据什么确定的？”**；**“为什么使用当前的切块策略？”**

我会按文档结构切，目标是一块里正好装下一个能回答问题的单元，大小和重叠再用召回实验去扫。死用固定 500 字，或者背开源框架默认的 chunk_size，面试官一追「为什么」就答不上来。

举个例子，退货政策里写着「签收后 7 天内可退货，定制商品除外」。按固定 token 数硬切，很可能把「退货 7 天」和后面的条件切进两块，召回分再高，模型拿到的也只有半句，答不全。所以政策文档按条款切，商品按规格表切，FAQ 按问答对切。SKU 库按规格表切，是因为答案单元本来就是一张表；政策按条款切，是因为条件句必须和结论在同一块。表格不要按行切断，表头丢了，数据就看不懂了。

结构定了再扫大小。块太小缺上下文，太大噪声多，向量表示也更难突出相关的那部分，大块会稀释 embedding，小而完整的单元更好检索。重叠只用来覆盖跨 chunk boundaries 的句子，比如上一句给主语、下一句才给数字。经验上常落在一成到两成，但这个数要自己扫，别背。重叠过大等于同一句话进索引好几次，既浪费配额，又让 rerank 看到一堆近重复，所以 rerank 前要做近重复合并，免得同一句占两个槽。索引配额紧的时候，优先减小 overlap，别盲目加大块。

实验我会这样摆：固定 token、按标题、按表格 / SKU，再加几档不同的 overlap，报分层 Recall@$k$（按类目、语言切）、引用是否落在金标块、端到端答对、索引体积和 p95。只报平均召回，会被头部类目拉高。这里 Recall 的分母是人工标出的相关块集合，随便 top-k 命中不算。评测集本身也要按文档类型分层（`pdd-offline-eval-coverage`），不然切块结论换个类型就不成立。

面试官追问「为什么用现在这套」，我会说：在当前这批文档类型下，这个配置在召回和忠实上 Pareto 更好，overlap 也没有把 rerank 变成近重复排序。换一批文档，就得重跑同一张对照表，会议纪要的切法套不到 SKU 库上，旧阈值也不能当公司标准。多模态商品页还要让图注、规格表和主图 OCR 落在同一个可引用单元里，否则后面的图文一致检查（`pdd-multimodal-consistency`）会误报。

## 追问

**Recall 的分母是什么？**
人工标出的相关块集合，「模型引用过的块」不能当分母。分母不清楚，不同切块方案的实验就没法比。

**重叠是不是越大越稳？**
不是。重叠过大会重复计费、污染 rerank，去重也更难做。

**表格怎么切？**
表头跟着数据走，或者整表放一块，检索后再截相关的行。按行硬切会丢列名。

**能不能一种大小打天下？**
不行。政策、SKU、FAQ 的可回答单元长度不一样，要按类型分别扫。
