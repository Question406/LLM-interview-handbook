## 真题记录

- 公司：拼多多
- 团队 / 岗位：AI Agent
- 届别 / 流程：一面（RAG 流程）
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“文档如何切块？Chunk 大小和重叠窗口是根据什么确定的？”**；**“为什么使用当前的切块策略？”**

切块目标是「一块里有一个可回答单元」，不是固定 500 字。政策文档按条款，商品按规格表，FAQ 按问答对。硬切 token 会把「退货 7 天」和条件拆开，召回分再高也答不全。一面要能复述实验：不同 chunk 配置的召回、引用忠实和 p95。原帖还问 Recall，准备补一句分母是相关块集合，不是随便 top-k 命中。拼多多 Agent 岗还会追「为什么现在这套」：答当前文档类型下的 Pareto，别背开源框架默认 chunk_size。

## 先结构，再扫大小与重叠

按标题 / 表格 / SKU 规格尽量完整切；表格不要按行切断导致表头丢失。大小用离线 Recall@$k$ / 下游任务扫：太小缺上下文，太大噪声多、embedding 被冲淡。重叠只覆盖跨边界句子，经验上常落在一成到两成，但必须自己扫，不要背一个数。重叠过大等于同一句进索引多次，浪费配额还让 rerank 看到近重复。

确定依据是实验，不是博客默认值。换文档类型要重扫，不要把会议纪要的切法套到 SKU 库。多模态商品页还要让图注、规格表和主图 OCR 落在同一可引用单元，否则后面图文一致检查（`pdd-multimodal-consistency`）会误报。

## 实验怎么报

对照：固定 token、按标题、按表格/SKU、不同 overlap。报告分层 Recall@$k$（类目 / 语言）、引用是否落在金标块、端到端答对、索引体积与 p95。只报平均召回会被头部类目拉高。覆盖评测集（`pdd-offline-eval-coverage`）要按文档类型分层，否则切块结论不可迁移。切块策略的「为什么」一句话：当前类型下，该配置在召回与忠实上 Pareto 更好，且 overlap 没有把 rerank 做成近重复排序。

一面还可能追「现在为什么用这个」。准备一句：SKU 库按规格表切是因为答案单元是表而不是段落；政策按条款切是因为条件句必须和结论同块。overlap 只留给「上一句主语、下一句数字」这种跨边界，并在 rerank 前做近重复合并，避免同一句占两个槽。索引配额紧时优先减小 overlap，而不是盲目加大块。大块会稀释 embedding，小而完整的单元更好检索。换一批文档必须重跑同一张对照表，不能把旧阈值当公司标准。

## 追问

- **Recall 的分母是什么？** 人工标出的相关块集合，不是「模型引用过的块」。分母不清，切块实验不可比。
- **重叠是不是越大越稳？** 不是。过大会重复计费、污染 rerank，还让去重变难。
- **表格怎么切？** 表头跟数据走，或整表一块再在检索后截相关行；按行硬切会丢列名。
- **一种大小打天下吗？** 不行。政策、SKU、FAQ 的可回答单元长度不同，要分类型重扫。
