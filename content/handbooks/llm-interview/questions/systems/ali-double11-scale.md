我觉得最大的挑战是让关键业务在降级以后仍然能正确运行，换更大的模型、加更多 GPU 解决不了这件事。要动的是六块：限流与降级、缓存高频路径、异步化与削峰、状态外置、可观测与熔断、成本预算。面试官想听的是你懂电商大流量下 AI 系统的工程约束。

先看峰值是什么样。峰值 QPS 远高于日常，热点 SKU 很集中，订单、库存、支付这些下游自己也会抖。日常客服的量不必按双十一去堆容量，但降级开关要提前埋好。Demo 里那套多轮 ReAct 原样去扛峰值，p99 会被串行工具调用和越来越长的 prompt 拖慢。

拿零点的「券能不能叠」举例。这类问题占了请求的大多数，直接在网关打到缓存加规则模板就能答；只有「订单异常要改地址」这种才进大模型 Agent。会话状态放 Redis，扩容时不绑单机。库存接口超时就回一句「系统繁忙，先为你记下」，别让 Agent 连着重试把下游打穿。降级之后 idempotency key 还得保留，免得重复下单。不可逆的写操作，acceptance checks 也不能因为高峰就摘掉，见 `ali-guardrail`、`ali-hitl-risk`。

按层说一遍就是这样。流量层，网关限流、队列削峰、关键和非关键分流；算力层，小模型和模板 fallback，大模型只服务复杂单，简单的「查物流」「催发货」走模板或小模型；状态层，会话和记忆外置，避免单机亲和；依赖层，工具超时、舱壁隔离、缓存商品和订单热点；发布层，灰度、熔断、回滚、审计。限流本身也要分层：网关 QPS、单用户并发、下游库存舱壁，免得一个热点 SKU 把推理集群打满。

成本要一开始就当约束，别等事后看账单。每类意图先给一个 token 预算和模型档位，超了自动降级。观测要有排队深度、工具 p99、降级比例、重复下单和资损，没有这些，扩容只是把 Demo 的失败放大。工具日志把 attention 窗口撑爆，会同时拉高延迟、降低模型利用上下文的准确性（`ali-attention-agent-limit`），所以高峰期要截断过长的工具观测，把状态存到外部系统。

Demo 常见的坑是：三个工具同步串行、prompt 里塞全量历史、会话粘在单机内存、工具失败无限重试。改造的时候我会先画关键路径：鉴权 → 意图分流 → 只读缓存 → 少数复杂单进大模型 → 写路径幂等加 HITL，然后才谈模型尺寸。发布必须能回滚到模板路径，不能出现模型挂了、整个客服一起挂的情况。

## 追问

**成本怎么控？**
意图分级加 token 预算，超预算就降级，在请求进来时就控住，别等事后看账单。

**降级会不会答错？**
模板路径只覆盖能规则化的意图；覆盖不了的就排队或转人工，别用过期缓存编政策。

**和 100 倍流量那道手撕题有什么关系？**
是同一套东西：缓存、异步、降级、幂等。见 `ali-algo-scale-100x`。
