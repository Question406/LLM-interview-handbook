这是分层问题，不是二选一。陷阱是把「智能降级」交给模型临场决定总超时，或反过来只用死规则、任务价值再高也一刀切。硬预算保护 SLA、成本和外部系统；动态策略只在预算**之内**选怎么降。熔断打开后必须可恢复：checkpoint、取消下游、避免重复副作用，而不是丢一个 500。多员工打满和租户隔离是另一层，见 `xiaohongshu-multitenant-limit`；本卡问的是**一条任务链自己怎么停、怎么降**。

## 硬预算不可交给模型

总 deadline、单工具 timeout、最大重试 / token 花费、权限和并发上限应是 deterministic guardrail。它们保护的是下游搜索、支付、写操作和 SLO，模型没有权限「再试一次就好」——它优化的是任务完成，会系统性超时。执行器按剩余预算给每个 step 切分时间：后面还有两跳检索，当前工具就不能吃掉 80%。依赖连续失败或错误率过阈值时打开 circuit：对新请求 fail-fast，而不是把线程堆在超时边上。写类工具（发帖、改状态、扣积分）必须幂等键 + 取消尚未开始的下游，否则熔断重试会双写。这些规则用配置和代码实现，离线单测，不进 prompt。模型可以建议「值得再搜一轮」，执行器可以拒绝。面试把「规则」说成保护边界，把「智能」说成边界内的策略，不要把两层揉成「我们用 LLM 做熔断」。circuit 的打开 / 半开 / 关闭要有冷却时间和探针，和微服务熔断同一套状态机，只是探针对象从 HTTP 换成了工具错误率。

## 预算内才能动态降级

硬边界之内，策略可以选：换小模型、减 search depth、跳过可选步骤、用缓存 / 摘要、输出部分结果、或请用户确认延长。输入应是任务价值、成功概率、剩余预算和风险，而不是「模型觉得还能撑」。离线要用切片验证：降级不能系统性牺牲某类用户（例如只对长尾 query 砍检索、只对某类笔记跳过审核辅助）。用户侧明确显示完成了什么、跳过了什么、能否继续；静默降级会变成质量事故。指标同时看 deadline miss、partial-success、重试风暴、circuit 打开时长和恢复成功率。只看平均成功率会把「快速失败的好熔断」判成质量下降。降级顺序建议与租户过载时一致：先砍并行和宽度，再换模型，最后才拒收，避免用户立刻重试把依赖再打穿。验收时改一类、复测一类，不要同时改 timeout、模型和检索深度。团队争论「硬规则还是智能降级」时，把它翻译成两层所有权：平台组拥有 deadline、熔断状态机、幂等和取消；策略组拥有预算内的模型档位、检索宽度和是否问用户。所有权不拆开，规则会被业务方当成障碍绕过，智能又会把 SLA 改掉。复杂任务链还要给每个 step 打上「可取消 / 有副作用 / 可缓存」三种标记：可取消的直接丢；有副作用的必须幂等键；可缓存的降级时优先命中。没有标记，熔断只能一刀切，看起来像只会硬规则。有了标记，动态降级才有动作空间，而这空间仍然被硬预算包着。

用户可见的失败要比内部 500 更完整：说清已完成的步骤、跳过的步骤、能否从 checkpoint 继续。只回「超时」会逼用户重试，把熔断变成风暴。产品文案和熔断状态机是同一设计的两面，面试里主动提这一点，说明你想过恢复而不是只想过切断。

## 追问

- **为什么总 timeout 不能让模型改？** 它是对外部系统和账单的契约；模型优化任务完成，会系统性超时。可以建议延长，由执行器或用户批准。
- **熔断打开后做什么？** fail-fast、保存 checkpoint、取消未开始的下游、对用户给可恢复结果，禁止无幂等重试写操作。
- **动态降级怎么验收？** 按任务类型看 partial-success 和用户继续率，而不是只看最终成功率。要防止某类用户被系统性砍掉。
- **和限流的关系？** 限流防一个租户打满池子，见 `xiaohongshu-multitenant-limit`；熔断防依赖病了还往里打。两者都要，主键不同。
- **重试风暴怎么发现？** 同一 task id 的工具调用次数、错误率和超时同向涨。先关自动重试，再查依赖，而不是先加机器。
- **半开状态是什么？** 冷却后放少量探针请求，成功再关闭 circuit，失败维持打开。没有半开，要么永远拒、要么立刻打穿刚恢复的依赖。
- **所有权怎么拆？** 平台组拥有 deadline、状态机、幂等和取消；策略组拥有预算内的档位和是否问用户。不拆开就会互相绕过。
- **step 要打什么标记？** 可取消、有副作用、可缓存。没有标记，熔断只能一刀切，动态降级没有合法动作。
