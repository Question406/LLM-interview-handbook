我会先把 p95/p99 拆开量，再按工具的依赖图改：没有数据依赖的工具并行，高频意图走缓存或固定 workflow，缩短输入提示、少暴露工具，LLM 段再考虑投机或小模型草稿，最后用超时降级和限流兜底。换更大的模型，或者把三个工具一律串进 ReAct、每步再「思考一下」，只会更慢。

拿客服里常见的组合举例：查订单、查物流、查售后政策。前两个互不依赖，可以并行；政策可以按类目缓存。要是必须用上一步的结果，比如查单 → 算价 → 支付，就保持串行。并行只用在读路径上，强一致的写路径串行，并用请求 id 对齐同一份快照，免得读到脏数据。SLA 也要写清楚：非关键工具超时可以跳过，关键工具只能降级，不能静默丢掉。

并行省的是实际耗时，token 消耗不会因此变少。三轮串行 ReAct 会叠三次输入预填充（prefill），也就是处理输入并建立缓存；工具结果如果还回灌成长上下文，后面的轮次会更慢。所以能一次规划出要调哪些工具，就别一步步猜。投机解码和小模型草稿只加速 LLM 那一段，工具 RT 占大头时收益接近零，见 `sys-specdecode`、`sys-serving-metrics`。

高频意图要绕开多轮 LLM。像「快递到哪了」，用小模型分类，再走缓存或固定 workflow，不用每单让大模型重新挑工具。首包分类走轻量模型，复杂的再升级。上下文和工具字段与类型规范（schema）也要压，只暴露当前意图相关的工具，减少 prefill。工具说明膨胀是隐性的延迟：五十个 schema 全塞进去，首个 token 的等待时间（TTFT）就会涨。限流和隔离按意图来，高峰时保查物流，把闲聊和推荐降级，别让非关键请求占满队列、拖慢关键请求。

量测要切到对的瓶颈。把 p95/p99 拆到 LLM 的 prefill 和 decode、各个工具的 RT、网关排队。如果 p99 高在物流接口而不在 LLM，就给物流设超时，降级成「以承运商页面为准」，换 70B 没用。缓存要带失效：订单状态用短 TTL，政策可以长缓存。没有依赖图和分层延迟，优化顺序一定会搞反。

## 追问

**并行会不会读到脏数据？**
只读查询可以并行，并对齐同一份快照；写路径、支付、改地址保持串行。见 `ali-hitl-risk`。

**三个工具必须串行怎么办？**
那就砍 LLM 的轮次和 prefill：一次规划、固定 workflow、压缩 schema。

**小模型分流会不会分错？**
会，所以设置信阈值，低置信回退到大模型；监控错误路由率，平均 RT 说明不了这个。

**投机解码什么时候值得？**
瓶颈在逐 token 生成（decode），而且草稿和终稿分布接近的时候。工具 RT 占主导就先做超时和缓存。
