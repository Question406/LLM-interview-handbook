## 真题记录

- 公司：京东
- 团队 / 岗位：Agent 开发
- 届别 / 流程：27 暑期实习；二面
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“JMeter 压测的具体参数是怎么设置的？”**

这块容易背菜单：线程组、监听器、断言，却说不出目标 QPS 和成功标准。面试官要的是 **假设 → 参数 → 看什么曲线**，不是 JMeter 有哪些控件。Agent 压测和普通 HTTP 差在：流式首包、整轮（含工具）、错误率与限流是三套数。只报平均响应时间会掩盖 p99 和 5xx。我先说压的是网关、编排层还是模型本身；把 LLM 和检索混在一个平均延迟里，优化方向会指错。

## 先定目标再填线程

数字假设要开口说。例如：目标 50 QPS、错误率 $\lt 1\%$、网关 p95 $\lt 800\,\mathrm{ms}$、首 token p95 $\lt 1.5\,\mathrm{s}$、整轮 p95 $\lt 8\,\mathrm{s}$。没有这组数，后面的线程数没有锚。

线程约等于目标并发：若平均整轮 4 s、要 50 QPS，粗算并发 $\approx 50\times 4=200$（Little's law）。Thread Group 的 Number of Threads 对这个量级，不是随便填 1000。Ramp-up 拉 1-2 分钟，避免启动尖峰被当成容量上限。Scheduler 持续时间至少覆盖预热（模型 CUDA graph、连接池、缓存变热）和一段稳态；过短只测到冷启动。Loop 用「持续 $T$ 秒」而不是固定 10 次，否则长尾请求还没回来测试就停了。

## 断言、切片和 Agent 特有项

HTTP 200 不够：要 JSON 业务码、必填字段、工具是否超时。流式接口分别打时间戳：首 token、工具往返、最终包。Sampler 超时必须大于工具 SLA，否则 JMeter 自己掐断，模型侧还在跑，错误率被测歪。

流量要切片：只压检索、只压模型、整条 Agent 分开报。混在一起优化会指错组件。参数化用 CSV 多样化 query，避免同一 prompt 把 prefix cache 打满、QPS 虚高。连接：HTTP Keep-Alive、连接池大小和网关限流对齐；压测机本身不要先成为瓶颈（单机线程过多、带宽不够就加 slave）。

限流触发率要单独报：被 429 的比例不是「成功」，也不是纯粹失败，是容量边界。和线上一致的超时 / 熔断配置才有意义；压测环境把 timeout 开到 60 s，线上 8 s 掐断，数字不可比。

## 报告什么，不报告什么

交付物：QPS、错误率、p50/p95/p99、首 token、整轮、限流比、超时比。不要只给平均。Agent 还要报工具失败是否被编排吞掉（看起来 200、其实没调成）。对比优化前后必须同脚本、同数据、同预热。说清压的是哪一层：网关、编排、vLLM/SGLang、还是 Redis。本手册超时空返回卡负责「失败怎么对用户说」，本题负责「参数怎么设才测得到那个失败」。

面试官要听的是一次完整假设，而不是控件清单。例如：目标 50 QPS、整轮约 4 秒所以线程约 200，ramp-up 90 秒，持续 15 分钟覆盖预热和 KV 池变满，断言检查业务码和工具字段，分别打首 token 与整轮。然后说明我会看 p95/p99、错误率、429 比例，而不是平均 RT。Agent 压测还要声明工具是 mock 还是真依赖：真依赖会把下游库存接口打满，数字不可用；全 mock 又测不到工具超时。折中是工具用录制回放，模型走真实 serving。脚本参数化 CSV，避免同一 prompt 把前缀缓存打满导致 QPS 虚高。压测机线程、网卡、打开文件数先自检，否则瓶颈在客户端。对比优化前后必须锁脚本、数据和预热策略，否则「快了 20%」没有对照。开口先说压哪一层，再报线程怎么从 Little's law 算出来，这题就过了。

## 一次完整假设

开口用一组具体数字：目标 50 QPS、错误率低于百分之一、首 token p95 一点五秒、整轮八秒。线程约等于 QPS 乘平均整轮时延，ramp-up 一两分钟，持续覆盖预热和稳态。断言查业务码和工具字段。分别报排队、LLM、工具。工具用录制回放，避免打爆下游。对比优化必须锁脚本。这比背 Thread Group 菜单像做过。

## 追问

- **线程数怎么来的？** 目标 QPS $\times$ 平均整轮时延（Little's law），再加余量。ramp-up 避免启动尖峰被当成容量上限。不要背「通常 200 线程」。整轮变长时要重算线程，否则实际 QPS 达不到目标。
- **为什么要分首 token 和整轮？** 用户体感在首包，GPU 成本和工具超时在整轮。只报平均 RT 会把流式体验和好坏工具混在一起。两个百分位都要，再加错误率和 429。
- **断言只查 200 行不行？** 不行。Agent 常 HTTP 200 但业务码失败、字段空、工具超时被编排吞掉。断言要落到 JSON 和必填字段，否则压测在报成功、线上在报空答。
- **压多久？** 覆盖 CUDA graph / 连接池预热，再跑到 KV 池和缓存变热甚至变冷。几分钟打满平均没有意义，长尾和限流要在稳态里出现。
- **JMeter 适合压 LLM 吗？** 适合压网关和编排 QPS。模型侧更常用专用 serving 压测，把并发、输入长度、输出长度分开扫。面试必须声明压的是哪一层，混层平均会指错优化。
