## 真题记录

- 公司：京东
- 团队 / 岗位：Agent 开发
- 届别 / 流程：27 暑期实习；二面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“在实际业务场景中，你怎么判断什么时候需要加缓存？为什么不能只用 MySQL？”**；同面还问 Redis 单线程为何高并发

陷阱是「QPS 高就上 Redis」或「有缓存就不用 MySQL」。缓存换的是 **读延迟和峰值容量**，买的是 **短暂不一致**。权威写（下单、库存、支付）仍以 MySQL / 主库为准。Agent 场景还要区分：缓存的是检索结果、工具幂等读、会话 state，还是模型完整回答——后者容易把过期政策/价格说成事实。评测要看击中后的陈旧答案率，不只看 QPS。同面单线程卡讲 Redis 为什么快，本题讲什么数据配进它。

## 什么该进缓存

满足多数再加：读多写少、同样 query 反复打、允许秒到分钟级过期、或要扛尖峰。Agent 里典型：

- **检索短名单**：同一商品问句的向量召回，TTL 短，key 带类目/租户。
- **工具幂等读**：库存展示、物流轨迹；写操作不缓存。
- **会话 state**：多轮槽位、已选 SKU，避免每轮回 MySQL。
- **限流计数 / 幂等键**：滑动窗口、去重，MySQL 不擅长。

计算贵的结果（一次 embedding、一次 RAG 拼接）也可以 cache，但必须带模型版本和索引版本，否则上线新 embedding 仍命中旧向量。不要缓存「当前用户的待支付订单」当权威；展示可以，结算前必须回主库。

## 为什么不能只用 MySQL

连接数、磁盘延迟、行锁扛不住检索 + 会话那种小 key 高 QPS。MySQL 也没有向量 HNSW、滑动窗口、原子 INCR 这类结构。把会话 JSON 塞进行里每轮 `UPDATE`，会把 binlog 和锁打满。Redis 单线程避免锁，靠内存和 I/O 多路复用堆吞吐，见 `jd-redis-single-thread`。但它不是事实源：重启、驱逐、主从延迟都会丢或旧。双写顺序、缓存击穿（热 key 失效瞬间打爆 MySQL）、雪崩（同一 TTL）要有对策：互斥重建、随机 TTL、空值短缓存。大 key、热 key 仍会堵事件循环，缓存用错一样慢。

## 失效和验收

失效优先版本号或商品变更总线删 key，而不是只靠 TTL。Agent 回答若引用了价格/库存，展示路径可缓存，下单路径必须读主库。击中后若陈旧答案率升高，应缩短 TTL 或改直读，而不是加机器。分层：本地进程缓存极热点配置，Redis 会话和检索，MySQL 订单。LLM 前缀缓存是另一层（GPU KV），不要和 Redis 混成「我们有缓存」。验收：命中率、陈旧率、回源 QPS、错误率。只报命中率会被追问「过期价推给用户了没有」。

判断「要不要加缓存」可以变成一张检查表：读多写少吗、算得贵吗、短暂不一致可接受吗、失效有总线或版本号吗、击穿和雪崩有对策吗。五条里缺「可接受不一致」或「失效路径」，就不要加。电商里商品详情、检索短名单、会话槽位通常过关；库存扣减、支付状态、券核销不过关。不能只用 MySQL 的理由也要具体：会话每轮 `UPDATE` 会打满行锁和 binlog；检索 QPS 是小 key 高并发，磁盘页缓存救不了；限流滑动窗口和原子计数不是 SQL 的形状。Redis 补的是这些形状，不是替代事实源。Agent 还有一层模型前缀缓存，那是 GPU 上的 KV，key 带模型和 schema 版本，和 Redis 会话缓存分层，不要说「我们已经有缓存了」就把两层混为一谈。面试用一个具体场景收束：同一商品问句三秒内打来十次，检索结果可缓存；用户点下单，价格和库存必须回主库。

## 检查表怎么用

五问都过再加缓存：读多写少、计算贵、短暂不一致可接受、失效有版本或总线、击穿雪崩有对策。缺「可接受不一致」就不要加。展示库存可以短 TTL，扣减必须回 MySQL。Agent 检索短名单和会话槽位通常过关；把完整模型回答当永久事实不过关。Redis 补的是小 key 高 QPS、TTL、原子计数这些 MySQL 不擅长的形状，不是事实源。前缀缓存是 GPU 另一层，key 带模型和 schema 版本。

## 追问

- **库存能不能缓存？** 展示可以短 TTL，让列表页抗尖峰；下单、扣减、支付状态必须以 MySQL / 主库为准。把权威写放进会过期的 Redis，超卖和错价都是事故。生成用的价格要带时间戳，过期则回源。
- **为什么不能只用 MySQL？** 会话每轮更新会打满行锁和 binlog；检索是小 key 高并发，磁盘页缓存救不了；滑动窗口限流和原子 INCR 不是 SQL 的形状。连接数也会先被打满。
- **击穿怎么防？** 热 key 失效时互斥重建或逻辑过期；空结果也短缓存，避免不存在的商品把 MySQL 打穿。TTL 加随机抖动防雪崩。版本号或商品变更总线删 key，比纯 TTL 更干净。
- **模型回答能缓存吗？** 仅当事实稳定且 key 含模型版本和索引版本。价格、库存、个性化、政策条款不要当永久答案。检索短名单可以缓存，最终话术要小心陈旧。
- **和单线程那题怎么衔接？** 本题决定「放不放」；那题决定「放进去会不会堵循环」。大会话 JSON 不该进单个 string。两题一起答才完整。
