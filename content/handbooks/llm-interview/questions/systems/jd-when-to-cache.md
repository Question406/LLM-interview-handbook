## 真题记录

- 公司：京东
- 团队 / 岗位：Agent 开发
- 届别 / 流程：27 暑期实习；二面
- 面试时间：原帖未披露
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“在实际业务场景中，你怎么判断什么时候需要加缓存？为什么不能只用 MySQL？”**；同面还问 Redis 单线程为何高并发

我会在读多写少、相同请求反复出现、计算结果昂贵，而且业务允许短暂不一致时加缓存。缓存能降低读延迟、承接尖峰，但数据过期和失效也要一起设计。下单、库存和支付等权威写仍以 MySQL / 主库为准。

比如商品列表可以短暂使用缓存库存，结算时则必须回主库确认。Agent 里还要区分检索结果、工具幂等读、会话 state 和完整模型回答：缓存最终回答时，过期政策或价格可能被继续说成事实。因此验收要看命中后的陈旧答案率。

## 先选数据，再定失效方式

满足多数再加：读多写少、同样 query 反复打、允许秒到分钟级过期、或要扛尖峰。Agent 里典型：

- 检索短名单：同一商品问句的向量召回，TTL 短，key 带类目/租户。
- 工具幂等读：库存展示、物流轨迹；写操作不缓存。
- 会话 state：多轮槽位、已选 SKU，避免每轮回 MySQL。
- 限流计数 / 幂等键：滑动窗口、去重，MySQL 不擅长。

计算贵的结果（一次 embedding、一次 检索增强生成（RAG） 拼接）也可以 cache，但必须带模型版本和索引版本，否则上线新 embedding 仍命中旧向量。不要缓存「当前用户的待支付订单」当权威；展示可以，结算前必须回主库。



连接数、磁盘延迟、行锁扛不住检索 + 会话那种小 key 高 QPS。MySQL 也没有向量 HNSW、滑动窗口、原子 INCR 这类结构。把会话 JSON 塞进行里每轮 `UPDATE`，会把 binlog 和锁打满。Redis 单线程避免锁，靠内存和 I/O 多路复用堆吞吐，见 `jd-redis-single-thread`。但它不是事实源：重启、驱逐和主从延迟都可能导致数据丢失或陈旧。双写顺序、缓存击穿（热 key 失效瞬间打爆 MySQL）、雪崩（同一 TTL）要有对策：互斥重建、随机 TTL、空值短缓存。大 key、热 key 仍会堵事件循环，缓存用错一样慢。

## 用陈旧率和回源压力判断效果

失效可以优先用版本号或商品变更总线删 key，TTL 用来限制遗漏更新后的陈旧时间。Agent 回答若引用了价格/库存，展示路径可缓存，下单路径必须读主库。命中后若陈旧答案率升高，应缩短 TTL 或改为直读；增加机器解决不了数据过期的问题。分层：本地进程缓存极热点配置，Redis 会话和检索，MySQL 订单。LLM 前缀缓存是另一层（GPU KV），不要和 Redis 混成「我们有缓存」。验收：命中率、陈旧率、回源 QPS、错误率。只报命中率会被追问「过期价推给用户了没有」。

## 追问

**库存能不能缓存？**
展示可以短 TTL，让列表页抗尖峰；下单、扣减、支付状态必须以 MySQL / 主库为准。把权威写放进会过期的 Redis，超卖和错价都是事故。生成用的价格要带时间戳，过期则回源。
**为什么不能只用 MySQL？**
会话每轮更新会打满行锁和 binlog；检索是小 key 高并发，磁盘页缓存救不了；滑动窗口限流和原子 INCR 不适合用逐条 SQL 操作实现。连接数也会先被打满。
**击穿怎么防？**
热 key 失效时互斥重建或逻辑过期；空结果也短缓存，避免不存在的商品把 MySQL 打穿。TTL 加随机抖动防雪崩。版本号或商品变更总线删 key，比纯 TTL 更干净。
**模型回答能缓存吗？**
仅当事实稳定且 key 含模型版本和索引版本。价格、库存、个性化、政策条款不要当永久答案。检索短名单可以缓存，最终话术要小心陈旧。
**和单线程那题怎么衔接？**
本题决定「放不放」；那题决定「放进去会不会堵循环」。大会话 JSON 不该进单个 string。两题一起答才完整。
