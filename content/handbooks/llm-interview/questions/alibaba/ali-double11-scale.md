错法：「换更大模型 / 加更多 GPU」。把 Agent Demo 改造成双十一级流量，最大挑战是限流与降级、缓存高频路径、异步化与削峰、状态外置、可观测与熔断、成本预算。先保证正确的关键路径可降级存活。面试官听的是：你懂电商大流量下 AI 系统的工程约束。编排框架选型见 `ali-framework-choice`，工具链延迟见 `ali-latency-3tools`。

## 峰值约束：QPS、热点、下游抖动

峰值 QPS 远高于日常、热点 SKU 集中、订单/库存/支付下游也会抖动。日常客服量级不必按双十一堆容量，但降级开关要提前埋好。大模型只服务复杂单，简单「查物流 / 催发货」应走模板或小模型。Demo 的多轮 ReAct 原样抗峰值，p99 会被工具串行和 prompt 膨胀拖死。

按层答：

1. 流量：网关限流、队列削峰、关键/非关键分流；
2. 算力：小模型/模板兜底，大模型只服务复杂单；
3. 状态：会话与记忆外置，避免单机亲和；
4. 依赖：工具超时、舱壁隔离、缓存商品/订单热点；
5. 发布：灰度、熔断、回滚、审计。

## 例子：零点「券能不能叠」

该类占请求大多数。网关打到缓存加规则模板；只有「订单异常要改地址」才进大模型 Agent。会话状态放 Redis，扩容不绑单机。库存接口超时则返回「系统繁忙，先为你记下」，而不是让 Agent 连着重试把下游打穿。降级后必须保留幂等键，避免重复下单。不可逆写操作的闸门不能因为高峰而摘掉（`ali-guardrail`、`ali-hitl-risk`）。

## 成本是一等约束，不是事后账单

先给每类意图一个 token 预算和模型档位，超预算自动降级。观测要有：排队深度、工具 p99、降级比例、重复下单、资损。没有这些，扩容只是把 Demo 的失败放大。Attention 窗口被工具日志撑爆会同时打延迟和走神（`ali-attention-agent-limit`），高峰期必须截断 observation、外置 state。

Demo 常见坑：同步串行三个工具、prompt 里塞全量历史、会话粘在单机内存、工具失败无限重试。改造成峰值系统时，先画关键路径（鉴权 → 意图分流 → 只读缓存 → 少数复杂单进大模型 → 写路径幂等+HITL），再谈模型尺寸。限流要分层：网关 QPS、单用户并发、下游库存舱壁，避免一个热点 SKU 把推理集群打满。发布必须可回滚到模板路径，而不是「模型挂了整个客服挂了」。

## 追问

- **成本怎么控？** 意图分级 + token 预算 + 超预算降级，而不是事后看账单。
- **降级会不会错答？** 模板路径只覆盖可规则化意图；覆盖不了的排队或转人工，不要用过期缓存编政策。
- **和 100 倍流量手撕题的关系？** 同一套：缓存、异步、降级、幂等。见 `ali-algo-scale-100x`。
