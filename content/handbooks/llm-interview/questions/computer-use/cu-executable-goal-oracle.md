正确性要写在环境状态上：从初始状态出发，断言允许的终态和副作用，轨迹只拿来做归因。OSWorld 一类评测的核心也是终态脚本，没有逐步做像素匹配。LLM judge 最多当辅助信号，不能当唯一的 verdict。

另外两种常见做法各有毛病。指定唯一的点击序列，会把合理的捷径判成失败；只让 LLM 看截图或者自然语言总结来当裁判，又会被措辞、截图不全和「看起来做完了」骗过去。

## 把目标写成状态合同

以「完成报销」为例，oracle 应该检查目标条目已创建、金额和币种正确、没有重复提交、草稿没有残留、敏感附件没有外发，按钮按什么顺序点它不关心。约束分成 `must-hold`、`must-not-hold` 和可选质量项三类，每一项都要能被脚本、API、文件系统或应用状态读到。快捷键、搜索、不同菜单，走哪条 UI 路径到达同一个终态都算对。禁止状态（错账户、错权限、误删、把文件发到外网）和正例一样重要，漏掉 deny 就等于在奖励乱点。文件「存在」也不够，内容和路径都要校验。

## 怎么实现、记什么

Oracle 读的是最终文件、数据库行、浏览器 cookie / URL、邮件桩和下载目录，不去回放点击日志。「发送 / 支付 / 删除」这类带副作用的动作，用 mock 服务接收请求并校验字段，别真打生产。每次要记下任务版本、初始 snapshot hash、每条断言的通过 / 失败、读到的实际值，以及有没有发生允许范围外的外部写入。断言要幂等，能在终态上重复执行。和时间有关的任务要冻结时钟，不然同一个终态脚本会因为「今天」变了而翻车。评测包和 oracle 代码同版本发布，oracle 悄悄变严或变松，历史分数就没法比了。

## Oracle 自己也会错

所以要维护三类样本：人工确认过的正例（包含多条合理路径）、near-miss 负例（金额差一元、提交了但选错项目），以及环境噪声。然后报告 oracle 的 false accept / false reject，别把评测脚本当成天然真值。评测上容易被刷的地方有：只检查页面上有没有「成功」文案，不检查重复提交，忽略禁止状态，或者让模型写一段「我已完成」交给另一个模型打分。

判定规则写成一句话就是：任务成功 = 全部 must-hold ∧ 没有任何 must-not-hold；轨迹只用于归因，不用于打分。写 oracle 的顺序是先列「业务上怎样算办成」，再翻译成可读取的状态，最后才考虑 UI。如果某条断言只能靠看截图判断，说明它还算不上可执行合同，应该去改 fixture 或 mock，别靠加一个 LLM 裁判来补模型容易失败的任务。写任务时同步写负例：少填一个必填项、金额差最小货币单位、重复提交一次，oracle 都必须判失败。没有负例测试，oracle 错误接受的情况很难被发现。

每个任务配一份 oracle 说明书，写清 must-hold、must-not-hold、怎么读取状态和已知误判。新任务先让人工走两条不同路径验证正例，再用 near-miss 验证负例，都通过了才进正式集。

## 追问

**为什么不锁死点击序列？**
快捷键、搜索、不同菜单都能完成同一件业务。锁死序列测到的是模仿，测不到目标有没有达成。

**文件存在就算成功吗？**
不够。还要校验内容和禁止的副作用，否则 Agent 写个空文件或者写错目录也能过。

**oracle 和 LLM judge 怎么分工？**
状态和副作用走脚本；LLM 最多辅助看截图、解释失败原因，它的意见不进正式分数。

**时间敏感的任务怎么办？**
冻结时钟，或者断言相对时间。这样同一个终态脚本不会因为日期变化而不稳定，定时弹窗也干扰不了 oracle 的判分。
