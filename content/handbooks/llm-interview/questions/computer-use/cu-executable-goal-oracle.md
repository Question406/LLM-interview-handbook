开放式 GUI 任务若指定唯一点击序列，会把合理捷径判失败；若只让 LLM 看截图或自然语言总结当裁判，会被措辞、截图不全和「看起来做完了」骗过。正确性应写在环境状态上，不是写在 trajectory 上。OSWorld 一类评测的核心也是终态脚本，不是逐步像素匹配。LLM judge 最多做辅助信号，不能当唯一 verdict。

## 把目标写成状态合同

从初始 fixture 出发，断言允许的终态和副作用，而不是按钮顺序。例如「完成报销」应检查：目标条目已创建、金额与币种正确、无重复提交、草稿未残留、敏感附件未外发。把约束分成 `must-hold`、`must-not-hold`、可选质量项。每一项都必须能被脚本、API、文件系统或应用状态读到。允许不同 UI 路径到达同一终态：快捷键、搜索、不同菜单都可以。禁止状态（错账户、错权限、误删、把文件发到外网）与正例同等重要，漏掉 deny 就是在奖励乱点。文件「存在」不够，还要校验内容和路径。

## 怎么实现、记什么

Oracle 读最终文件、数据库行、浏览器 cookie / URL、邮件桩、下载目录，而不是回放点击日志。对「发送 / 支付 / 删除」类副作用，用 mock 服务收请求并校验字段，不要真打生产。记录：任务版本、初始 snapshot hash、每条断言的通过 / 失败、读到的实际值、是否发生了允许范围外的外部写入。断言应幂等、可在终态重复执行。时间相关任务要冻时钟，否则同一终态脚本会因「今天」翻车。评测包与 oracle 代码同版本发布；oracle 静默变严或变松都会让历史分数不可比。

## Oracle 自己也会错

维护三类样本：人工确认的正例（含多条合理路径）、near-miss 负例（金额差一元、提交了但选错项目）、以及环境噪声。报告 oracle 的 false accept / false reject，而不是把评测脚本当天然真值。评测上能刷的是：只检查页面出现「成功」文案、不检查重复提交、忽略禁止状态、让模型写一段「我已完成」给另一个模型打分。

任务成功 = 全部 must-hold ∧ 没有任何 must-not-hold；轨迹只用于归因，不用于打分。写 oracle 时先列「业务上怎样算办成」，再翻译成可读状态，最后才考虑 UI。若某条断言只能靠看截图，说明它还不是可执行合同，应改 fixture 或 mock，而不是加一个 LLM 裁判补充模型容易失败的任务。写任务时同步写负例：少填一个必填项、金额差最小货币单位、重复提交一次，oracle 必须判失败。没有负例测试，就很难发现 oracle 错误接受的情况。

每个任务附一份 oracle 说明书：must-hold、must-not-hold、如何读取状态、已知误判。新任务先用人工走两条不同路径验证正例，再用 near-miss 验证负例，通过后才进正式集。

## 追问

- **为什么不锁死点击序列？** 快捷键、搜索、不同菜单都能完成同一业务；锁序列测的是模仿，不是目标达成。
- **文件存在就算成功吗？** 不够。还要校验内容和禁止的副作用，否则 Agent 可以写空文件或写错目录。
- **oracle 和 LLM judge 怎么分工？** 状态与副作用走脚本；LLM 最多辅助看截图解释失败，其意见不进入正式分数。
- **时间敏感任务怎么办？** 冻时钟或断言相对时间，避免「今天」让同一终态脚本因日期变化而不稳定，也避免定时弹窗干扰 oracle 判分结果。
