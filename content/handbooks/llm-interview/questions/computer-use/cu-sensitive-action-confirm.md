把「二次确认」做成模型在网页里自己点「确认」按钮，或只按 tool 名（`click` / `type`）分类，是这题最常见的翻车。Computer-use 的敏感动作发生在 UI 语义上：看起来像普通点击，实际是转账、删库、改权限、外发。确认必须是系统控件，默认 deny，超时取消，并写审计；模型不能既提议又批准。我会讲分类合同、确认 UI 隔离，以及红队测「绕过确认」，而不是测「模型会不会说小心」。这和 `cu-security-evaluation` 的 deny-state 一致，和 `agent-approval-boundaries` 的人审分层是同一控制面。

## 按 UI 语义分类，而不是按 tool 名

敏感集合至少覆盖：资金移动、不可逆删除、权限 / ACL 变更、对外发送、安装 / 提权、导出含秘密的文件。分类器吃的是解析后的目标：按钮名、对话框文案、收款人、金额、收件人域、路径，而不是 `click(x,y)`。同一 `click` 点「保存草稿」和点「确认转账」风险完全不同。白名单只允许用户显式授权过的（收款人、域名、目录），且有金额 / 次数上限，过期收回。风险分可写成 $r(a) = s(a)\cdot u(a)$，其中 $s$ 是动作类严重度，$u$ 是参数不确定性；仅当 $r(a)\lt\tau_{\mathrm{auto}}$ 才免确认，其余默认 deny。阈值 $\tau$ 按产品损失标定，不要按模型自报置信。

## 确认必须在系统侧

确认 UI 由 harness 弹出：展示解析后的关键参数（收款人全名、金额、附件 hash、将要删除的路径），用户点系统按钮才放行。禁止把「确认」画进被控浏览器，也禁止模型生成一个假对话框再自己点。超时 $T$ 内无响应视为取消，动作为 deny 并记审计。连续同类请求要聚合，避免审批疲劳；疲劳后的「全点允许」应视为安全事故，而不是效率优化。日志字段：动作类、解析参数、是否确认、确认耗时、是否超时、是否白名单命中。没有这些字段，出事只能说「当时点了」。

红队至少覆盖：诱导连续点击、截图上伪造系统确认框、隐藏真实收款人只显示昵称、把高风险按钮做成看起来像「下一步」。评测报：敏感动作未确认执行率、确认绕过成功率、正常低风险任务被过度拦截率。只报「模型说了请确认」不算过关，环境里副作用已经发生就是失败。评测上能刷的是：用 tool 名黑名单代替语义分类；确认框画在网页里；超时当允许；不测伪造确认 UI。确认是控制面，和模型是否「小心」正交；默认 deny，超时取消，系统控件，参数可见。

Anthropic 一类 computer-use 安全说明的核心也是：模型操作计算机时，破坏性动作不能只靠模型自检。生产上把确认策略写成与工具权限同一张表，而不是事后 prompt。白名单要可撤销；一次「记住这个收款人」不能变成永久自动转账。现场能讲清「谁弹出确认、超时算什么、伪造框怎么测」，这题就答完了。

## 追问

- **为什么不能让模型自己点网页确认？** 被控页面是不可信环境，伪造确认框或改收款人后，模型点的是攻击者的按钮。
- **只拦 `send_email` 够吗？** 不够。普通 `click` 也能提交支付表单；必须解析 UI 语义和参数。
- **和 `cu-security-evaluation`？** 那题定义攻击成功与 deny-state；本题是生产闸门：敏感动作如何强制人审。
- **和 `agent-approval-boundaries`？** 那题是通用人审分层与防疲劳；本题落到 computer-use 的系统确认控件与伪造 UI 红队。
- **超时为什么默认取消？** 默认允许等于把无响应当授权；资金和删除类动作必须 fail-closed。
