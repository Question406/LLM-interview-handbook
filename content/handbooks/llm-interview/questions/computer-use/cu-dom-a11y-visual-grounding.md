A11y / DOM 对按钮名、角色、`disabled`、层次强，但对 canvas、图标按钮、自定义绘制弱。纯视觉对自定义控件和真实像素几何强，却缺「这是提交还是取消」的语义，坐标还会随分辨率、DPR 漂。生产 GUI agent 几乎都是树检索候选再截图确认坐标，不是二选一。我会讲融合管道、冲突怎么仲裁，以及评测必须带二者不一致的案例。本题偏定位融合；观测表征见相关 observation 题。

## 管道

1. 从 a11y / DOM 按角色、名、可见性、可聚焦性取 top-$k$ 节点，得到语义候选和粗 bbox。过滤 `disabled`、`aria-hidden`、零面积节点。
2. 在截图上对候选做局部重排或坐标回归：把指令和图像对齐到点击点，而不是在整屏上盲点。
3. 冲突仲裁：意图信任可访问名（「提交」），几何信任视觉（按钮实际中心）。两者一致才高置信点击；不一致则缩小截图再问，或改用键盘 / 无障碍接口，而不是平均两个框。
4. 动作发出后用新快照做断言：焦点、URL、节点状态是否按预期变。点击回执成功不等于业务前进。

记录每步：候选节点 ID、树 bbox、视觉点、是否冲突、最终动作来源（tree / vision / keyboard）。没有这些字段，失败只能笼统叫 grounding。

## 不一致从哪来

动态 DOM、虚拟列表只渲染可见行、iframe、遮挡、CSS 变换、Retina 坐标翻倍、a11y 树滞后一帧、canvas 无节点、自定义绘制的可点区域 bbox 为 0。评测必须含这些，而不是静态截图点选。跨分辨率时把坐标归一化到截图像素，而不是屏幕物理像素。iframe 要带 frame 偏移；虚拟列表要先 scroll-into-view 再取树。树与视觉持续冲突应降置信并升级，而不是连点。评测上能刷的是：只在原生控件静帧上测融合精度；不测 disabled 仍「能点」的视觉诱饵；忽略 DPR。评测集应强制包含：同名按钮、图标无文本、虚拟列表、iframe、Retina、disabled 视觉诱饵、canvas 控件。指标拆开树召回、视觉点命中、冲突仲裁正确率、点后状态验证。只报端到端点击成功，会把「树找到了但点偏」和「树根本没有节点」混在一起。落地日志没有候选 ID 与冲突标记，融合策略无法迭代。冲突率本身应是健康指标：一直为 0 说明你没测到真实 UI；一直很高说明树或视觉有系统性偏差。生产上对冲突设阈值，超过就改用键盘或升级，而不是继续盲点。这套字段也能喂给 `cu-failure-taxonomy` 的 grounding 层。

树负责语义候选，视觉负责几何确认，冲突就缩小或改通道，发出后再断言状态。这是 computer-use 定位的主路径，不是两个模型投票。

融合策略要可配置：仅树、仅视觉、先树后视觉，三者在同一任务集上对比。生产默认先树后视觉，canvas / 零 bbox 自动降级到视觉。评测报告必须含冲突样本，否则融合没有被测到。

面试官要听融合而不是站队。树给名字和角色，视觉给可点几何，冲突就缩小或换通道，点完断言状态。能举 disabled 图标和零 bbox 两个反例，这题就答完了。

## 追问

- **为什么不只用视觉？** 同屏多个相似图标时语义消歧靠名字；disabled 按钮视觉上仍「能点」。
- **为什么不只用 DOM？** 大量现代 UI 的可点区域不在树里，或 bbox 是 $0$。
- **冲突时优先谁？** 先缩小范围再问；高风险动作优先键盘 / a11y 接口。几何以视觉为准，语义以树为准，不要对两个框取平均。
- **零 bbox 怎么办？** 视为树失败，改走视觉 grounding，并在日志里记 `tree_bbox_empty`。
