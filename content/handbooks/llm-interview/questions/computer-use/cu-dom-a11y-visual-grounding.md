我会先用 DOM / Accessibility Tree 检索候选，再用截图确认坐标，生产里的 GUI agent 几乎都是这么做的，两边都要用。

原因是两边各缺一块。A11y / DOM 能清楚给出按钮名、角色、`disabled` 状态和层次，但对 canvas、图标按钮和自定义绘制的控件，信息可能不够。纯视觉对自定义控件和真实的像素几何很强，却分不清「这是提交还是取消」，坐标还会随分辨率和设备像素比（DPR）变化。比如页面上并排两个长得一样的图标按钮，光看截图很难分清哪个是删除，树里的名字一眼就能区分；反过来，一个 canvas 画出来的按钮，树里可能根本没有节点。下面讲融合管道、冲突怎么仲裁，以及评测为什么必须带二者不一致的案例。这题偏定位融合，观测怎么表征见观测结果（observation）相关的题。

## 管道

先从无障碍信息 / DOM 里，按角色、名字、可见性和可聚焦性选出 top-$k$ 节点，得到语义候选和粗略的目标框，同时过滤掉 `disabled`、`aria-hidden` 和零面积的节点。

然后在截图上对这些候选做局部重排或坐标回归，把指令和图像对齐到具体的点击点，不在整屏上盲点。

两边对不上时要仲裁：意图信任可访问名（「提交」），几何信任视觉（按钮的实际中心）。两边一致才高置信地点击；不一致就缩小截图再问，或者改用键盘 / 无障碍接口，别把两个框平均一下。

动作发出去之后，用新快照做断言，看焦点、URL、节点状态有没有按预期变化。点击回执成功，不代表业务往前走了。

每一步都要记下候选节点 ID、树 bbox、视觉点、有没有冲突，以及最终动作来自 tree / vision / keyboard 哪一路。没有这些字段，失败就只能笼统地叫 grounding。

## 不一致从哪来

不一致的来源很多：动态 DOM、虚拟列表只渲染可见行、iframe、遮挡、CSS 变换、Retina 坐标翻倍、a11y 树滞后一帧、canvas 没有节点、自定义绘制的可点区域 bbox 为 0。评测必须包含这些情况，只做静态截图点选是测不出来的。跨分辨率时，坐标要归一化到截图像素，别用屏幕物理像素；iframe 要带上 frame 偏移；虚拟列表要先 scroll-into-view 再取树。树和视觉持续冲突时，应该降置信并升级处理，不要连点。

评测分数很容易虚高，比如只在原生控件的静帧上测融合精度，不测 disabled 却看起来「能点」的视觉诱饵，或者忽略 DPR。所以评测集要强制包含同名按钮、没有文字的图标、虚拟列表、iframe、Retina、disabled 视觉诱饵和 canvas 控件。指标也要分开统计：结构树的候选召回率、视觉点击点的命中率、冲突处理正确率，以及动作后的状态验证结果。只报端到端点击成功，会把「树找到了但点偏了」和「树里根本没有节点」混在一起。

冲突率本身也是健康指标：一直为 0，说明没测到真实 UI；一直很高，说明树或视觉有系统性偏差。生产上给冲突设阈值，超过就改用键盘或者升级。这些字段也能喂给 `cu-failure-taxonomy` 的 grounding 层；日志里没有候选 ID 和冲突标记，融合策略就没法迭代。

融合策略最好做成可配置的，仅树、仅视觉、先树后视觉三种在同一任务集上对比。生产默认先树后视觉，遇到 canvas 或零 bbox 自动降级到视觉。评测报告里一定要有冲突样本，否则融合等于没被测过。讲的时候可以拿 disabled 图标和零 bbox 控件当例子，说明融合策略怎么处理失败。

## 追问

**为什么不只用视觉？**
同屏有多个相似图标时，要靠名字做语义消歧；而且 disabled 按钮在视觉上看起来照样「能点」。

**为什么不只用 DOM？**
很多现代 UI 的可点区域不在树里，或者 bbox 是 $0$。

**冲突时听谁的？**
先缩小范围再问，高风险动作优先走键盘 / a11y 接口。几何以视觉为准，语义以树为准，别对两个框取平均。

**零 bbox 怎么办？**
当成树失败，改走视觉 grounding，并在日志里记 `tree_bbox_empty`。
