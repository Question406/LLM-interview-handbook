## 真题记录

- 公司：京东
- 团队 / 岗位：后端
- 届别 / 流程：一面
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：“你觉得ai ide 设计的时候怎么定位，怎么防止类似数据库的幻读情况，如果让你来设计一个ai ide该怎么做”（原帖提到 ACP / MCP）

我会把 AI IDE 定位成一个带事务语义的工作区执行器：读有快照，写有 CAS，失败有重试，聊天只是 UI。防「幻读」的办法是让每次决策绑定一个工作区版本，补丁只能相对这个版本打，版本对不上就拒绝、重读、重新规划。MCP / ACP 管的是怎么连、怎么发现工具，解决不了工作区在推理过程中被改掉的问题。

数据库幻读是同一事务内两次读到不同的行集。AI IDE 里的对应情况是：Agent 读了 `foo.py`，生成补丁的同时用户改了函数签名，补丁打在一棵过期的树上。如果 Host 不校验 `base_hash`，apply 会在错误的 AST 上成功，测试红了，大家还以为是模型笨。

## 怎么设计

一次 turn 先绑定明确的工作区版本，用 git commit 或文件内容哈希都行。turn 开始时冻结可见树，没纳入快照的外部写入对本次规划不可见，或者直接触发 invalidation。工具返回必须带版本戳（path + hash + mtime），模型后续的 edit / apply_patch 只能相对这个基准。

写的时候走乐观并发：补丁带 `base_hash`，类似 CAS，write 前比较基准，不一致就返回 conflict，拒绝静默覆盖，也不把 hunk 硬套进新文件。conflict 之后把新文件和新 diff 喂回下一个 turn，逼模型重规划。这里靠的是版本绑定，让模型「再读一遍」当保证没用，再读本身也可能和写交叉。

测试运行也要绑版本，跑的是快照里的树，别跑磁盘上此刻的树，否则「测试绿了」和「补丁对应的代码」不是同一份。多个子 Agent 并行修改同一目录会增加这类并发冲突，所以每个 Agent / 子任务一个可写副本或 branch，各自 sandbox，禁止共享可写目录，除非显式 checkout 同一快照；合并走显式 rebase，或者把可写区串行化。

权限也放在 Host：删除、改配置、跑任意 shell 走白名单和二次确认，模型只提议，Host 执行。MCP 负责 tools/resources 的 list 与 call，ACP 一类协议管 IDE 会话和编辑器事件，把编辑器事件推进会话，但二者都替代不了文件锁、工作区快照和权限边界。同面的 MCP 权限题可以连起来说：连得上不等于写得对。

验收目标是测试通过、diff 可应用、冲突可重试，「感觉改对了」不算。评测用「并发编辑后补丁是否仍然适用」，别只报单测通过率；还要报冲突检测率，该冲突却静默合并，比冲突后重试危险得多。

## 数据库类比别讲过头

这里没有真正的 SQL 事务隔离级别可以搬，要的是工程上的版本绑定和互斥。三种异常可以都提一下：脏读对应「读到半写入的文件」，写没完成就让另一个 Agent 读了，用文件锁或原子替换防；不可重复读对应同一个 turn 里两次 `read_file` 内容不同，用快照防；幻读对应「文件集合变了」，新文件出现、旧文件删除，list_dir 两次结果不同。原题点名的是幻读，重点放在集合和基准哈希上。

## 追问

**和脏读、不可重复读怎么区分？**
脏读是读到未提交的数据，幻读是行集变了。IDE 里更像后者，文件集合或内容在两次工具调用之间变了；半写的文件更像脏读，用原子写来防。

**git 能当锁吗？**
能当版本基准，当不了互斥，还得阻止对同一工作树的并行 write。commit hash 是快照 id，不是 mutex。

**多窗口怎么处理？**
每个窗口绑定自己的 snapshot id，跨窗口写同一个文件走同一个 CAS。

**评测怎么构造？**
在 Agent 读完文件、写补丁之前插入一次人类编辑，看系统是报 conflict 还是静默生成坏补丁。再加一项「测试跑在哪棵树上」。

**MCP 能不能带版本？**
可以让 resource 读取返回 etag，但校验仍在 Host，协议只负责把 etag 传回来。
