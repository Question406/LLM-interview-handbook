## 真题记录

- 公司：京东
- 团队 / 岗位：后端
- 届别 / 流程：一面
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：“你觉得ai ide 设计的时候怎么定位，怎么防止类似数据库的幻读情况，如果让你来设计一个ai ide该怎么做”（原帖提到 ACP / MCP）

常见误区是：以为 MCP / ACP 已经解决了隔离。协议只解决「怎么连、怎么发现工具」，不解决工作区在推理过程中被改掉。数据库幻读是同一事务内两次读到不同行集；AI IDE 的类比是：Agent 读了 `foo.py` 再跑测试，用户或另一个 Agent 已改文件，补丁打在过期树上。

## 定位为受控的工作区执行器

Agent 在已授权的工作区中执行任务。可执行目标是测试通过、diff 可应用、冲突可重试，不是「感觉改对了」。一次 turn 绑定明确的工作区版本：git commit 或文件内容哈希。工具返回必须带版本戳（path + hash + mtime），模型后续的 edit / apply_patch 只能相对这个基准。write 前比较基准，不一致则拒绝静默覆盖，改为重读 → 再规划。子 Agent 各自 sandbox，禁止共享可写目录，除非显式 checkout 同一快照。评测用「并发编辑后补丁是否仍适用」，不要只报单测通过率。

## 隔离靠锁与 sandbox，不靠会话协议

MCP 负责 tools/resources 的 list 与 call；ACP 一类协议管 IDE 会话与编辑器事件。二者都不替代文件锁、工作区快照和权限边界。设计清单：

1. 快照：turn 开始冻结可见树；未纳入快照的外部写入对本次规划不可见，或触发 invalidation。
2. 乐观并发：补丁带 `base_hash`，类似 CAS；冲突返回 conflict，而不是把 hunk 硬套进新文件。
3. 隔离：每个 Agent / 子任务一个可写副本或 branch；合并走显式 rebase。
4. 权限：删除、改配置、跑任意 shell 走白名单与二次确认；模型只提议，Host 执行。

「幻读」防的是读到的集合在决策完成前变了。解决办法是让决策绑定版本，而不是让模型「再读一遍」当保证，再读本身也可能和写交叉。同面 MCP 权限题连起来：连得上不等于写得对。

设计口试要落到一次失败例子。Agent 根据旧 `foo.py` 生成补丁，用户同时改了函数签名；若 Host 不校验 `base_hash`，apply 会在错误 AST 上成功，测试红了还以为是模型笨。正确路径是 conflict → 把新文件和新 diff 喂回下一 turn，强迫重规划。测试运行也要绑版本：跑的是快照里的树，而不是磁盘上此刻的树，否则「测试绿了」和「补丁对应的代码」不是同一份。子 Agent 并行修改同一目录会增加这类并发冲突：必须 branch 或串行化可写区。定位上，AI IDE 是带事务语义的工作区执行器：读有快照，写有 CAS，失败有重试，聊天只是 UI。ACP 把编辑器事件推进会话，不保证这些事务。评测除了补丁适用率，还要报冲突检测率：该冲突却静默合并，比冲突后重试更危险。

和数据库类比不要讲过头。没有真正的 SQL 事务隔离级别可搬；要的是工程上的版本绑定与互斥。脏读对应「读到半写入文件」（写未完成就让另一个 Agent 读），用文件锁或原子替换防；不可重复读对应同一 turn 两次 `read_file` 内容不同，用快照防。幻读对应「文件集合变了」：新文件出现、旧文件删除，list_dir 两次结果不同。三种都要提，但原题点名幻读，重点放在集合与基准哈希。

## 追问

- **和脏读 / 不可重复读？** 脏读是未提交；幻读是行集变化。IDE 里更像后者：文件集合或内容在两次工具调用间变了。半写文件则更像脏读，用原子写防。
- **git 能当锁吗？** 能当版本基准，不能当互斥；还要阻止对同一工作树的并行 write。commit hash 是快照 id，不是 mutex。
- **多窗口怎么处理？** 每个窗口绑定自己的 snapshot id；跨窗口写同一文件走同一 CAS。
- **评测怎么构造？** 在 Agent 读文件后、写补丁前插入人类编辑，看系统是 conflict 还是静默坏补丁。再加「测试跑在哪棵树上」。
- **MCP 能不能带版本？** 可以让 resource 读返回 etag；校验仍在 Host，协议只负责把 etag 传回来。
