文档 Agent 最危险的一步，是把流畅的自然语言直接变成财务写入。发票看错一行、合计对不上、把注释金额当应付，格式却仍然合法。分层合同：先有带 provenance 的结构，再 schema 校验，最后才是工具 action；高风险写入必须可审计、可拦。解释性文字不能点回像素，bbox 才能让人在 PDF 上复核。DocLayNet 一类 layout 数据解决的是版面，不是「直接过账」。

## 分层，而不是端到端写库

流水线按顺序：layout / reading order → 表格单元格或图表元素 grounding → 字段抽取 → 业务 schema 映射 → 工具调用。每个输出字段带页码、bbox 或单元格坐标、原文片段、置信度。没有 provenance 的数字不允许进入不可逆 action。图表要区分视觉编码（柱高、图例颜色）与读出的数值，并保留取数位置，避免「看起来是 30%」却写进 3%。多页 PDF 必须带页码，否则同行错位无法审计。记录字段级 provenance hash，便于抽检时跳回原件，而不是只存模型生成的 JSON。

## 执行前校验什么

写入前做类型、必填、币种、日期、税率与合计等式检查；用独立 OCR / 解析器或检索到的原文交叉验证，而不是让同一 VLM 既抽取又裁判。冲突时走人工，而不是取模型更自信的那边。合计等式失败应阻塞写入并标冲突字段，不要静默四舍五入凑平。对「创建付款、改主数据、发邮件」设单独确认；Agent 最多提交带证据包的草稿。日志记录校验器通过项、冲突项、以及谁批准了最终写入。低置信度字段即便格式合法也不能自动过账。

## 评测不要只看提交成功

分别衡量：layout / 单元格 grounding、字段 F1、provenance 是否指向真正原文、schema validity、业务 action 成功率、高风险误写率。只看表单提交成功，会放过「金额合法但张冠李戴」。能刷的点：合成表结构极规整；oracle 不查合计约束；用 LLM 对比「抽取文本是否像」；负例缺少近邻行错位、页眉页脚当正文、多币种、扫描倾斜。上线清单钉死：字段 schema、provenance 必填、合计等式、独立解析器交叉、高风险人工闸门、误写率。缺 provenance 的 JSON 只适合草稿，不适合过账。模型读错一行时，挡住并回原件，而不是再生成一段解释。评测集要包含合计冲突和近邻行错位，并单独报误写率。

字段级放行：低置信或校验失败的字段留空并转人工，允许其它字段先写草稿。禁止为了完成率用模型猜测填平。误写率按金额加权，大额错误不能被大量正确小字段平均掉。

没有 bbox 的金额不能过账，合计冲突不能静默凑平。把「读 PDF」和「写财务系统」拆开。

## 追问

- **为什么 provenance 比解释重要？** 解释不能点回像素；bbox 才能让人在 PDF 上复核。
- **合计等式失败怎么办？** 阻塞写入并标冲突字段，不要静默四舍五入凑平。
- **和 GUI oracle 的差别？** 文档侧的终态是结构化记录加证据链；GUI 侧更多是应用状态和副作用。
- **OCR 和 VLM 谁当主抽取？** 交叉验证，不一致就转人工；不要让同一模型既抽取又当裁判，否则 provenance 会变成无法复核的自我证明链条，抽检也会失去落点。
