要证明泛化，关键在 split：按未见 app、未见网站、未见布局家族、跨平台、跨任务语义来切训练和测试，grounding 和端到端执行分开报。在同一批 App 截图上既训练又测试，再宣称「泛化到桌面和手机」，证明不了什么。

举个例子，训练集里有某个购物 App，测试集换了它的皮肤和文案，模型分数很高，可这还是同一个设计系统，不算未见 UI。同一站点换 CSS、同一 Android 包换皮肤，最多算弱分布外数据（OOD，即与训练数据明显不同的数据）。

先说一条样本要绑什么：指令、screenshot 和 / 或 DOM / 无障碍信息树、候选元素或目标框、目标元素、动作类型、坐标或文本参数，还有执行后状态。缺了执行后状态，模型只会点，不知道点完对不对。坐标要带截图版本、分辨率和设备像素比（DPR），Android 逻辑像素、macOS 点、浏览器 CSS 像素各是一回事，不记清楚，跨设备标签就是错的。最好在数据管道入口就统一到截图像素，禁止各平台各用各的原点。平台差异（状态栏、刘海、窗口装饰、触控和点击）要当显式特征或独立分组，别默默平均掉。混入合成数据时，生成器不能复制评测模板，也不能留下稳定的视觉捷径，比如永远是红按钮、可点元素永远在屏幕正中。

再说怎么切、怎么报。训练日志记下每条样本的 app、平台、模板 ID，评测按这些键做 leave-one-out。训练 / 评测去重要做截图近重复和模板 ID，光查文件名不够。指标分开报 point / bbox 命中或交并比（IoU，即两个区域的交集与并集之比）、action validity、full-task success。只报端到端，「记住流程」会冒充「会定位」；只报 grounding，又看不到执行和状态验证。跨平台数字按 OS 切片，平均分会把 Windows 差、Android 好的差异盖住。OS-Atlas 一类工作强调的是多平台元素定位数据，端到端成功率不能直接叫泛化。

如果模型只在熟悉页面上表现好，先查泄漏：评测截图近重复、任务模板重叠、合成器用了测试集的布局信息。发布前做一次截图近重复扫描，训练和测试的感知哈希重叠写进附录，重叠高就先清数据，再谈架构。泛化要到独立环境里重测，比如未见的 App 商店页、未见的桌面软件、不同的 OS 主题。几种做法容易误导人：测试集和训练集共享设计系统还叫 zero-shot；端到端成功了就认定 grounding 已经泛化；把同一个 Electron 壳换皮当新平台。报告里写清 split 键（app / 站点 / 平台 / 模板 ID）、近重复去重阈值、坐标空间（CSS / 逻辑像素 / 截图像素），grounding 和 e2e 分列。没有 split 说明的跨平台数字，默认当同分布刷分看。这些做法比换 backbone 更能避免假泛化。跨平台分数别编，写清 split 规则就行。

## 追问

**为什么 grounding 和执行要拆开？**
点对了但没提交，和流程对了但点错，要改的地方完全不同。

**合成数据最大的风险是什么？**
模板泄漏和捷径。模型学会「点最亮的按钮」，到真实的灰按钮就崩了。

**跨平台最常见的标签错误是什么？**
把 Android 逻辑像素当成截图像素，或者忽略了状态栏偏移。

**同一套组件库换肤算 OOD 吗？**
只算弱 OOD。强泛化要未见 app 和未见布局家族，并且按平台单独报表，别把崩掉的 OS 平均掉之后对外说已经能跨平台泛化。
