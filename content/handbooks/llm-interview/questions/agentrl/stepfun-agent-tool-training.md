## 真题记录

- 公司：阶跃星辰（StepFun）
- 团队 / 岗位：Agent 算法
- 届别 / 流程：原帖未披露；轮次未披露
- 面试时间：原帖未披露；帖子发布于 2026-03-30
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“针对具体业务场景，怎么训练 agent 调用工具，reward function 怎么设计和优化的”**

先让「成功」变成能实际检查的东西，再分两段训：SFT 教会合法调用和失败恢复，然后在版本固定的沙箱里用当前策略 sampling 做 RL，奖励按硬性条件、最终结果、可验证过程和成本分层。比如退款任务，最后回复「已退款」不算数，要去查订单和退款状态。

拿查单后退款这个例子往下讲。先把环境定义清楚：输入状态、能看到哪些工具、JSON 参数规范、权限、每个操作怎么改变环境，以及怎么判断退款完成。退款、发券、改库存这种不可逆的操作要单独标出来，训练探索时不能写进生产环境。如果还没有可靠的成功判定规则，就先把可执行检查建起来，再考虑 RL，不然训练分不清真的成功和模型声称成功。

然后用 SFT 教工具选择、从输入和工具结果里填参数、使用返回结果、失败恢复和正确终止。示范里除了成功路径，也要有失败和恢复，见 `arl-trajectories`。之后在版本固定的沙箱里，用当前策略重新 sampling 轨迹；工具、页面或权限变了就要重新采，旧日志不能直接当成当前策略的数据，见 `arl-offpolicy-reuse`。

奖励可以分四层，见 `arl-reward`。最底下是硬性条件，参数格式非法、越权、副作用无法确定，直接判失败，别的项加多少分都抵消不了。然后是最终结果，查业务终态，比如退款完成没有、工单关了没有。再是可验证的过程，订单号存不存在、原因码在不在枚举里、回答有没有用真实的工具结果。最后是成本，在结果正确的前提下减少多余的调用和步骤，免得模型靠多走几步拿奖励。调权重 $\lambda$ 之前，先看各项和人工确认过的成功结果是否一致：硬性条件没过，最终结果奖励记零；某个过程项和实际成功不相关，先停用。

诊断时把错误分开统计：工具选错、参数错误、执行失败、没用好工具结果、规划问题、环境问题，每类都看奖励分布、有效样本组、KL、成功率和错误率。训练配比要保留难题、失败样本和低频工具，免得模型只学会简单任务和高频工具的捷径。上线前注入错误工具和错误参数，过程奖励应该下降；只改等价 JSON 的格式，正确性评分不该变。这样能确认模型学到的是业务执行，固定格式本身拿不到分。日志怎么设计见同一场面试的 `stepfun-react-io-blocks`。

## 追问

**没有沙箱能训练吗？**
RL 很难可靠地做。至少要有一个能重置、能回放的模拟状态机，让奖励可以复现。

**SFT 和 RL 谁先？**
通常先 SFT，让模型能完成一部分任务，再上 RL。只有稀疏的最终奖励时，随机探索很难学到东西，见 `arl-sparse-reward-exploration`。

**线上工具变了怎么办？**
按新的环境版本处理。旧轨迹过滤后可以拿来做行为克隆，但不能直接当成当前策略的 policy gradient 数据。
