## 真题记录

- 公司：小红书
- 团队 / 岗位：大模型算法
- 届别 / 流程：秋招；一面
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“如何保证多智能体协同的效果？”**

靠协议、共享状态和分层评测来保证，多加几个 Agent 互相讨论保证不了。我会先把角色、共享黑板、移交和仲裁写成固定的约定，再分别评测单个 Agent 和全局任务。另外，能用单 Agent 加工作流解决的，先证明拆分降低了可测的错误，再上多 Agent，否则「各自正确、整体失败」几乎是默认结局。

比如检索 Agent 拿回两份互相矛盾的证据，规划 Agent 挑了一份接着往下写，审核 Agent 看对话很顺就放行了，每个人的单步看着都没错，最后结论是错的。只看对话流畅度，模型会学会「礼貌地达成错误共识」。

约定有四项。角色上，谁规划、谁检索、谁审核，各自的输出 字段和类型规范（schema） 固定，没有 schema 的自由对话不能当协同。状态上，共享黑板只放已验证的字段，原始工具返回和工人写的散文都当不可信；版本号随写入递增，避免两个人改同一个字段。移交上，输入输出字段、超时、重试上限都写进协议，失败要回滚或者标 pending，别悄悄换个人接着编。仲裁上，结论冲突时按优先级仲裁或升级人工，平均两段胡话没有意义，安全和发布相关的以审核侧为准；校验优先的处理可以对照 `sensetime-perceive-vs-dynamic`。线上还要能回放谁在什么时候写了黑板，不然协同失败了没法归责。协同效果首先看协议有没有被遵守，其次才是工人模型强不强。

训练时给全队同一个 $+1$，分不清哪些成员没有贡献，可以冻结一部分 Agent，或者用局部 验证器（verifier） 提供信号，见 `arl-multi-credit`。通信变成空洞的客套话，也是一种 hack。

评测要分层，单步工具正确率看工人自己会不会干，全局任务成功看团队有没有做成，再加上越权和安全违规、延迟和调用成本、冲突后有没有按协议停下或升级。还要主动注入几种情况：工人返回冲突的证据、审核该拦却放行了、共享状态被某个人写脏。指标和 `arl-eval` 对齐，outcome、轨迹质量、成本、恢复都要有。多 Agent 别当默认架构，拆分的收益要体现在可测错误下降上，人设变多不算。秋招面试里把这套说成「先合同后模型」，比罗列 multi-agent 论文名词更贴近这一问。

## 追问

**什么时候不该上多 Agent？**
任务分解稳定、工具就那么一小撮、错误靠一个校验器就能抓住的时候。先用固定流，见 `sensetime-perceive-vs-dynamic`。

**共享状态被写脏了怎么办？**
断言版本和哈希，脏写入丢弃并回滚，别让下游在脏黑板上继续推理。

**局部奖励会不会伤害全局？**
会。要抽检局部指标和团队成功的相关性，工人刷子任务的时候就关掉局部分。

**怎么证明拆分有用？**
在同一批任务上和单 Agent 工作流对比全局成功、冲突率、越权和延迟。拆分后这四项没有变好，就收回去。
