## 真题记录

- 公司：小红书
- 团队 / 岗位：大模型算法
- 届别 / 流程：秋招；一面
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“如何保证多智能体协同的效果？”**

保证效果不是「多几个 Agent 互相讨论」。小红书秋招这问要听协议 + 状态 + 评测。能单 Agent 加工作流解决的，先证明拆分降低了可测错误，再上多 Agent。否则各自正确、整体失败是默认结局。冲突与校验优先的处理对照 `sensetime-perceive-vs-dynamic`。

## 角色、黑板、仲裁先写死

四条合同：

1. **角色：** 谁规划、谁检索、谁审核，输出 schema 固定。没有 schema 的自由对话不能当协同。
2. **状态：** 共享黑板只放已验证字段；原始工具返回和工人散文当不可信。版本号随写入递增，避免两人改同一字段。
3. **移交：** 输入输出字段、超时、重试上限写进协议。失败要回滚或标 pending，不要 silently 换人接着编。
4. **仲裁：** 结论冲突时按优先级或升级人工，不平均两段胡话。安全 / 发布相关以审核侧为准。

训练上 team $+1$ 分不清酱油工，应能冻一侧或打局部 verifier，见 `arl-multi-credit`。通信变成空洞客套也是 hack。协同效果首先是协议是否被遵守，其次才是工人模型强不强。

## 评测必须分层，否则会「看起来在合作」

缺任何一层都会假好：

- 单步工具正确率（工人自己会不会干）；
- 全局任务成功（团队有没有做成）；
- 越权 / 安全违规；
- 延迟与调用成本；
- 冲突后是否按协议停或升级。

只看对话流畅度，模型会学「礼貌地达成错误共识」。评测应注入：工人返回冲突证据、审核应拦却放行、共享状态被一人写脏。指标要对齐 `arl-eval`：outcome、轨迹质量、成本、恢复。不要把多 Agent 当默认架构。拆分的收益必须是可测错误下降，而不是人设变多。秋招面试里把这套说成「先合同后模型」，比罗列 multi-agent 论文名词更贴近这问。线上还要能回放谁在何时写入黑板，否则协同失败无法归责。

最后我会补一句：先写角色、已验证共享状态、移交和仲裁；再用单步 vs 全局 vs 安全分层评测。能单 Agent 解决的不要拆。冲突不投票，失败要回滚。

## 追问

- **什么时候不该上多 Agent？** 任务分解稳定、工具少于一小撮、错误能被一个校验器抓住。先固定流，见 `sensetime-perceive-vs-dynamic`。
- **共享状态被写脏怎么办？** 断言版本与哈希，脏写入丢弃并回滚。不要让下游在脏黑板上继续推理。
- **局部奖励会不会伤害全局？** 会。必须抽检局部指标与 team 成功的相关，工人刷子任务时关局部分。
- **如何证明拆分有用？** 同一任务上对比单 Agent 工作流：全局成功、冲突率、越权、延迟。拆分后这四项没有变好，就收回去。
