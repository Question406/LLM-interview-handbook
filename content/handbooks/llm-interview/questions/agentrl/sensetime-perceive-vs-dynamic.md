## 真题记录

- 公司：商汤
- 岗位：大模型算法应用实习；二面
- 来源类型与可信度：牛客候选人原帖，A
- 原始措辞：**“固定的「感知-推理-校验」流程和动态多 Agent 最大区别是什么。”**；**“如果拆成感知/推理/校验 Agent，哪些能并行，哪些要顺序，什么时候需要反向通信。”**；**“校验 Agent 和推理 Agent 结论冲突时怎么处理”**

最大的区别在于拓扑是什么时候定的。固定的「感知-推理-校验」在发布时就把角色和边写死了，延迟、权限、失败模式都能预期，好评测，也好限权；动态多 Agent 在运行时按任务现组团队，能并行、能临时加专家，但冲突、成本和 responsibilities 都更模糊。商汤这一面的三问其实是同一张图。

固定流相当于编译期拓扑：谁先谁后、每个角色能看到哪些工具、校验看哪些字段，发布时就定好了。每条边都能测，权限能收紧，延迟能估。缺点是遇到没见过的专家需求，比如突然要 OCR 一张新表，只能硬走完死流程，或者整条链失败。动态多 Agent 是运行时调度，orchestrator 按任务拉感知专家、推理、校验，边是临时的，好处是能绕路，也能多路传感器并行。代价是团队 reward 更难分配，见 `arl-multi-credit`，还容易变成「大家聊天、没人负责」。视频、多模态场景变化多，动态组很诱人，但别默认它更强。我在面试里会说，能用固定流解决的，先证明拆分降低了可测的错误，再动态化。商汤业务里视频场景多变，动态组的卖点是能临时加专家模型，让三个生成模型自由辩论没什么价值。模块怎么拆见 `sensetime-agent-three-modules`。

拆成三个 Agent 以后，哪些并行、哪些顺序很清楚。多路感知，比如不同摄像头、检索、OCR，在同一个时间窗里各自跑，结果写进共享快照，部分只读检索也可以和感知重叠。推理必须等「已对齐的感知快照」，不能边看边改世界；任何写操作或对外动作生效前，都要过校验。反向通信发生在校验失败时，把结构化错误（缺字段、证据冲突、越权）打回给推理，允许有限次修复；超时或者修两次还冲突，就升级，别无限吵下去。打回去的 payload 应该是错误码加上缺哪些证据，再生成一段反驳散文，只会把延迟和 hallucination 一起放大。共享黑板上只放已验证的字段，原始模型输出一律当不可信，见 `xiaohongshu-multiagent-quality`。

冲突的处理原则是校验优先，不投票平均。比如推理说「可能有人」，校验说「证据不足」或者「规则禁止」，只要涉及安全、误报或不可逆动作，就以校验和规则为准。推理只负责提候选，用多数票把不确定性平均成「可能没人、也可能有人」没有意义。产品上，高严重度的直接停下来升级人工；低严重度的允许推理在约束内改假设，再送去校验。别让两个生成模型互相说服。

## 追问

**动态组什么时候值得上？**
任务类型事先不知道、需要临时加专家模型，而且你已经有冲突协议和成本上限。不满足这些，固定流更可控。

**校验会不会成为瓶颈？**
会。只读感知可以并行，校验也可以对独立的证据分片做，但合并前的 validation 必须放在动作之前。用延迟预算来管，别为了并行跳过这项检查。

**反向通信几次算够？**
先定上限，比如两次，再定错误 schema。没有结构化错误码的互喷，直接升级。

**和训练有什么关系？**
固定流更好做过程奖励；动态组可以先冻住工人，只训调度，见 `arl-multi-credit`。
