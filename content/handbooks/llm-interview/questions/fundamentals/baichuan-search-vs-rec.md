## 真题记录

- 公司：百川智能
- 团队 / 岗位：大模型实习
- 届别 / 流程：实习；一面
- 面试时间：原帖未披露；帖子发布于 2026-02-12
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“了解搜索推荐相关内容吗”**

了解。两者的区别在目标函数：搜索有明确的 query，优化相关性、准确率和召回率；推荐常常没有 query，靠画像、上下文和行为序列选下一次展示什么，优化的是曝光后的停留、成交这些消费行为。RAG 检索更像搜索，它有当前问题当 query，要找的是能支撑回答的证据，「用户可能还想看」的下一篇和它无关。只说「都是召回加排序」，或者把推荐点击直接当检索增强生成（RAG）的正负例，都答偏了。

样本和偏差也不一样。搜索离线常用 Recall@$k$、nDCG、点击后满意度，在线看点击后问题有没有解决；相关文档需要标注或弱监督，位置偏差还在，但至少有 query 能对齐。推荐离线用 AUC 或 impressions 上的 NDCG，在线看消费；样本受曝光策略影响，没曝光不等于不相关。比如一篇热门笔记被推给了很多人、点击很多，拿它当 RAG 的金标，模型就会把「被推荐过的热门笔记」当成唯一正确的证据，冷门但真正回答了问题的文档被当成了负例。RAG 在线该看的是引用对不对、用户是不是少追问了，下一篇的停留时长说明不了什么。nDCG 只看排序位置，也评不了生成有没有超出证据。

这一问在百川这一面是个总纲，后面的 Query 改写、三路召回、例子库、RAGAS 都要落在「有 query 的检索」上，别用推荐的口吻回答。改写（`baichuan-query-rewrite-model-choice`）优化的是搜索 query 的可检索性，和推荐标题的点击率是两回事。三路召回（`baichuan-three-path-recall`）是 lexical、dense、结构化并行再融合，对应 hybrid 搜索，讲成推荐的多路精排，就说不清 query 在哪。例子库（`baichuan-case-library-construction`）是带权限的相似题检索，金标是「这条案例能不能支撑回答」，「相似用户点过」不算。RAG 评测（`baichuan-ragas-eval`）把忠实和召回拆开，推荐 AUC 高不代表证据够用。整条 RAG 管线见 `fund-rag`。Agent / RAG 里召回失败了，应该走改写或多路召回，别拿推荐模型去补「猜你想问」。

权限是另一条硬边界。推荐里常见的「看过类似笔记的人还看了」不能突破文档 ACL；RAG 必须按当前用户的可见性过滤，过滤发生在召回之后、生成之前。不可见的文档一旦进了 contexts，忠实度指标可能照样很高，但这是安全事故，算不上检索成功。例子库还要按租户隔离，不能把 A 客户的工单检索给 B 客户当 few-shot。

如果简历里只有推荐经验，我会主动用「有 query 对无 query」画出边界，讲清曝光偏差、样本选择偏差，以及为什么隐式反馈不能直接当 RAG 的正负例。能迁移过来的是排序和融合的经验，比如学习排序、校准；「没有 query、猜下一次曝光」这部分迁移不过来。隐式反馈最多当弱监督的候选，去偏之后再进人标。常见的失败有：认为文档被点过就足以支撑回答；把 nDCG 当幻觉指标；把三路召回讲成推荐的多路精排，却说不清 query。

## 追问

**RAG 为什么更像搜索？**
有当前 query，目标是相关证据，和下一次曝光无关。

**推荐数据能用来训检索吗？**
要先去曝光偏差、补负例和权限，不能直接当 gold，否则热门点击会变成假相关。

**改写属于哪一边？**
属于搜索侧的 query 理解。推荐侧对应的是召回触发和标题改写，问题不一样。

**没有 query 的 Agent 记忆算搜索还是推荐？**
有当前问题或状态描述时仍然是检索；纯粹「猜用户下一步」才像推荐。
