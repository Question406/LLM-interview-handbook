## 真题记录

- 公司：百川智能
- 团队 / 岗位：大模型实习
- 届别 / 流程：实习；一面
- 面试时间：原帖未披露；帖子发布于 2026-02-12
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“了解搜索推荐相关内容吗”**

常见误区是：「都是召回加排序」，或者把推荐点击直接当检索增强生成（RAG）的正负例。二者目标函数不同：搜索有明确 query，优化相关性、准确率和召回率；推荐常无 query，选择下一次展示的内容，并优化消费行为。本面后面的 Query 改写、三路召回、例子库都是搜索组件，不要用推荐口吻回答。改写见 `baichuan-query-rewrite-model-choice`，三路召回见 `baichuan-three-path-recall`，例子库见 `baichuan-case-library-construction`。RAG 管线见 `fund-rag`，评测见 `baichuan-ragas-eval`。

## 目标、样本与偏差

搜索：用户给 query，系统回文档 / 商品；离线常用 Recall@$k$、nDCG、点击后满意度。相关文档需要标注或弱监督，位置偏差仍在，但至少有 query 可对齐。推荐：用画像、上下文、序列，指标偏曝光后的停留 / 成交；样本受到曝光策略的影响，未曝光不等于不相关。把推荐的隐式反馈直接当 RAG 金标，会把「被推荐过的热门笔记」当成唯一正确证据。

RAG 检索更像搜索：有当前问题当 query，要的是能支撑回答的证据，而不是「用户可能还想看」的下一篇。改写优化的是搜索 query；dense + 关键词 + 结构化是多路召回；例子库是带权限的检索，不是协同过滤。

## 怎么接到大模型项目

若只做过推荐，我会主动画边界：有 query 的检索 vs 无 query 的排序。Agent / RAG 里，召回失败应走改写或多路，而不是用推荐模型补「猜你想问」。评估时检索召回与生成忠实要拆开；推荐 AUC 高不代表证据够用。权限与安全：例子库和笔记检索都有可见性约束，推荐里常见的「相似用户看过」不能突破权限。

失败模式：认为文档被点击过就足以支撑回答；把 nDCG 当幻觉指标；三路召回讲成推荐的多路精排却说不清 query。

## 接到百川这面的题组

原帖同一面还会问改写、三路召回、例子库、RAGAS。搜索 / 推荐这问是总纲：后面每一问都要落在「有 query 的检索」上。改写（`baichuan-query-rewrite-model-choice`）优化的是搜索 query 的可检索性，不是推荐标题点击率。三路召回（`baichuan-three-path-recall`）是 lexical / dense / 结构化并行，再融合，对应 hybrid 搜索而不是推荐的多路精排。例子库（`baichuan-case-library-construction`）是带权限的相似题检索，金标是「这笔案例能否支撑回答」，不是「相似用户点过」。RAG 评测（`baichuan-ragas-eval`）拆忠实与召回，推荐 AUC 帮不上忙。

若简历只有推荐：主动说清曝光偏差、样本选择偏差，以及为什么隐式反馈不能当 RAG 正负例。可以迁移的是排序与融合经验（学习排序、校准），不能迁移的是「无 query 猜下一曝光」。权限是另一条硬边界：推荐里「看过类似笔记的人还看了」不能突破文档 ACL；RAG 必须按当前用户可见性过滤，否则准确率再高也是事故。

指标对照：搜索离线用 Recall@$k$ / nDCG，在线用点击后是否解决问题；推荐离线用 AUC / NDCG on impressions，在线用消费。RAG 在线应对「是否引用正确、是否少追问」，不是下一篇停留时长。权限过滤发生在召回之后、生成之前：不可见文档进了 contexts，忠实度指标仍可能很高，但这是安全事故不是检索成功。例子库还要按租户隔离，不能把 A 客户工单检索给 B 客户当 few-shot。若只做过推荐，面试用「有 query vs 无 query」画边界，再主动接上改写和三路召回。隐式反馈最多当弱监督候选，必须去偏再进人标。

## 追问

- **RAG 为什么更像搜索？** 有当前 query，目标是相关证据，不是下一曝光。
- **推荐数据能用来训检索吗？** 需去曝光偏差、补负例与权限，不能直接当 gold。热门点击会变成假相关。
- **改写属于哪边？** 搜索 query 理解；推荐侧对应的是召回触发与标题改写，问题不同。
- **nDCG 能评幻觉吗？** 不能。它只看排序位置，不看生成是否超出证据。
- **没有 query 的 Agent 记忆算搜索还是推荐？** 有当前问题或状态描述时仍是检索；纯「猜用户下一步」才像推荐。
