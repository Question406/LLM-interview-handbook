我会按文档结构、问题粒度和 reranker 能力来调，不背固定的 token 数。Chunk 太小，句子找不到指代对象，召回一堆碎片，生成时拼不回完整的规定；太大，embedding 被多个主题稀释，关键词被淹没，几个 chunk 就占满窗口。Overlap 是为了不让跨段的定义在 chunk boundaries 被切开，并非越大越稳。所以别一上来报「512 / 50」，先讲失败模式，再讲按结构切分和 parent-child：小块负责召回，父级或邻窗负责生成，用召回和忠实度一起验收。

举个例子，合同里写「乙方逾期交付的，应按日支付违约金，但本条第二款情形除外」。按固定窗切，前半句和「第二款情形」可能落在两个 chunk 里，模型只看到前半句，就会给出一个缺了例外的答案。

## 太小、太大、overlap 各自坏在哪一步

检索和生成是两条链，三种问题坏在不同的地方。太小时召回可能命中了，但证据不自洽，比如看得到「该条款适用」却看不到主语，rerank 也缺上下文，生成只能靠模型自己补，忠实度下降。太大时向量变成多个主题的平均，语义检索更偏向「这篇文档像查询」，找不准「这段话回答了查询」；送进 LLM 以后，真正相关的几句可能落在中间被忽略。Overlap 让跨 chunk boundaries 的实体和定义能同时出现在某个 chunk 里，降低漏召回，代价是索引膨胀，同一段落被多个 chunk 带进 context，浪费窗口，模型还会看到重复句子。

没有跟语料无关的最优宽度。代码函数、法律条款、论文段落、日志行的语义单元本来就不一样，用同一个字符窗去切，只是把问题推迟到调 overlap 的时候。代码按函数 / 类切，能让签名和文档字符串留在同一块；法律按条、款切，能让「适用条件 + 法律效果」在一起；对话按轮切，避免把两个人的话黏成一个向量。固定 token 窗是这些结构都用不上时的退路。

## 先按结构切，再定窗口

更好的顺序是先按 heading、函数、条款、空行切出候选语义块，再对超长的块做二次切分、加少量 overlap。结构切分失败时（纯扫描件、没标题的 wiki），再退回固定窗。二次切分的目标是单块能被 embedding 区分开，同时单块或「块 + 邻居」足够回答一类典型问题。

Overlap 只需要覆盖句子在 chunk boundaries 被切断的那段长度，按典型句子长度定就行，用不着块长的一半。已经按结构切了，overlap 可以很小甚至为 0。Overlap 太大，相邻 chunk 几乎互为副本，ANN 返回一堆近重复，rerank 也失去区分度；应用层要按 ID 或页码去重，免得 top-k 全是同一段的滑动窗。

问题粒度也要匹配。用户问「第 3.2 条赔偿上限」，块应该接近条款大小；问「这份合同总体风险」，就需要更大的 parent 或摘要索引。一种 chunk 大小服务不了两种问题分布，混合查询的系统往往维护两级索引：细粒度做精确定位，粗粒度或摘要回答主题问题。只调一个 `chunk_size` 去迁就所有问题，总会在某一类上系统性地失败。还要考虑 embedding 模型的有效长度，块远长于它擅长的窗口，就等于把多个主题平均进一个向量。切块参数是检索模型的超参，要在同一批问题上做网格搜索，别从博客上抄一个数。

## Parent-child / window 检索：小块召回，大块生成

实践里常用小 chunk 负责召回、大 span 负责生成。句级或小节级的 embedding 提高召回分辨率；命中以后往上取 parent 节，或取前后句窗口，把指代补全再送给 LLM；需要的话再在扩大后的候选里用 reranker 排序，别先把窗口塞满。窗口检索（sentence window）是同一思路的局部版，命中句向两侧扩。

这样就不用为了「预防切错」把 chunk 做大，也不用切得很碎再指望 overlap 把章节还原回来。实现上，子块要带 parent id，召回后先去重到父级再送 LLM，免得五个子块把同一节重复贴五次。

评测要同时看小块的检索召回、拼回后的问答忠实度，以及平均送入的 token 数。只优化召回，会把 overlap 和块长越推越高；只优化延迟，又会切得过碎。索引更新成本也随 overlap 线性变差，热更新的语料上这个参数一点也不免费。说到底，chunking 要处理的是「召回分辨率」和「生成上下文」这对矛盾，靠一个魔法数字解决不了。

## 追问

**有没有默认的 token 数？**
没有跨语料通用的。从文档结构出发，在验证问题上把召回、忠实度、context 长度一起看着选。代码、条款、对话的单元本来就不同，先按结构切，再谈窗长。

**Overlap 能替代语义切分吗？**
不能。它只修补充 edge-case tests 切断，修不了「一块里塞了三个主题」。结构可用时 overlap 可以很小。

**为什么还要 parent-child？**
召回要的是可区分的小单元，生成要的是完整的局部上下文，一个粒度很难同时满足。命中后按 parent 去重，避免同一节被贴多次。

**块太大时 LLM 会怎样？**
相关句被稀释，而且长上下文中部的利用率本来就差，是检索和位置叠加出来的问题，单靠加大窗口解决不了。先把块切对，再考虑要不要换更长上下文的模型。
