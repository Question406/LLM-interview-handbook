Fine-tuning 把行为或知识写进 weights，更新慢、难审计，但推理不必每次检索。RAG 把知识放在外部索引里，易更新、可溯源，但依赖检索质量和上下文窗口。别答成「有私有数据就上 RAG、要变强就微调」。我会先问三件事：知识多快过期、要不要引用、要改的是事实还是稳定技能。常见生产系统是二者结合，而不是二选一。知识过期快、要引用、要按权限过滤，把事实放索引；要改的是语气、格式、工具纪律和拒答，把行为写进权重。不要用微调替代实时数据库，也不要指望检索自动教会稳定 procedure。评测应拆开：更新文档不重训是否仍对，去掉检索后格式还在不在。

## RAG 擅长可变事实与可引用证据

适合 RAG 的信号很具体：

- 知识频繁更新：价格、政策、内部文档、API 变更，权重来不及追；
- 必须引用证据：客服、合规、医疗辅助需要指出段落，而不是「模型记得」；
- 外部 / 私有语料远大于能写进参数的量，且权限随文档变。

RAG 的失败模式也具体：检索召回不到、chunk 切错、证据在上下文中间被忽略、索引与线上文档不一致。它不自动教会模型稳定的复杂 procedure，多步工具协议、输出 schema、拒答边界，更像 Skill / SFT 的职责。不要用 RAG 替代「把格式做对」的微调，也不要指望换 embedding 就能让模型学会新的推理习惯。延迟和成本是隐式约束：每次请求都检索 + 长 context，会比纯生成更贵。若答案几乎总来自同一份短手册，把手册放进 prompt 或轻度微调可能更简单。选型时先画知识的时间尺度：按分钟变的走检索；按季度变的可以索引或定期微调；几乎不变的技能（如何调用内部 API、如何拒答）放进权重更划算。私有知识还涉及权限：检索可以按 ACL 过滤文档，微调很难从参数里「删除某个人不该看见的句子」。

## Fine-tuning 擅长稳定行为，不擅长当实时数据库

适合微调的是 **分布上的行为**：语气、格式、工具调用习惯、解题套路、安全拒答、在固定领域里把能力抬上去。这些不需要每次从文档里抄。LoRA / SFT / 偏好对齐都属这一侧。

不适合用微调替代的是实时事实库。文档改一版就重训不经济，也难以审计「这句话从哪来」。过拟合少量内部文案还会把旧事实焊死，比 RAG 过期更难发现。论文对照（如微调 vs 检索注入知识）的常见结论是：事实类注入检索更灵活，任务技能与格式则微调更稳。不要把某一篇的具体百分数背成定律，要能讲这个分工。低延迟自动化（分类、结构化抽取、固定工作流）也常走微调或小模型：检索栈太重，而且不需要开放域证据。若延迟预算很紧、知识又相对静态，微调或蒸馏往往赢。微调还有灾难遗忘：为了记新手册把通用能力训掉。RAG 把这件事隔离在索引侧，这是它在「知识」上相对于 FT 的结构优势，不是生成质量上的万能优势。

## 结合方式：检索管事实，微调管用法

生产上常见分层：

- 用 RAG 提供当前证据；
- 用 SFT / 偏好学习让模型 **会用** 证据：引用格式、不知道就说不知道、多文档冲突时如何处理；
- 文档权限走检索侧过滤，而不是指望模型「记住谁能看」。

选型 checklist：更新频率高 → 偏 RAG；要引用 → 偏 RAG；要改的是格式 / 工具 / 风格 → 偏微调；两者都有 → 检索 + 针对「带证据的回答」做 SFT。评测也要拆开：无检索时的技能、有检索时的忠实度、文档更新后是否零训练即可正确。只报一个混合分数，会把「检索挂了」和「模型不会遵循格式」混在一起。结合时还有第三层：对检索结果做 rerank / 压缩，这是系统问题，不是再训一个更大的生成模型就能代替的。我会用「事实放哪、行为放哪、证据怎么引用」三句话收，不争论「RAG 和 FT 谁更强」。

## 追问

- **知识在权重里和在索引里差在哪？** 权重里难更新、难引用、难按权限过滤；索引里可热更新，但推理依赖召回，且占用上下文。权限尤其适合检索侧过滤。更新频率是选型的第一问。
- **RAG 能否代替对齐？** 不能。安全策略、拒答、工具纪律是行为，应微调或系统约束。检索只能提供材料。把政策 PDF 塞进索引，模型仍可能不遵守。
- **微调之后还要不要 RAG？** 常常要。微调后模型更会用上下文，并不等于把全世界记进参数。文档一更新，索引比重训便宜。
- **如何验收？** 分别做：文档更新不重训的正确率（RAG）、去掉检索后的格式/技能（FT）、以及带噪声检索时是否幻觉（结合）。只报一个混合分会掩盖故障层。
