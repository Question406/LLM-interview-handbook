## 真题记录

- 公司：拼多多

- 原始措辞：“Token 是如何划分的？为什么 strawberry 在部分模型中会被拆成多个 Token？”；“为什么大模型以 Token，而不是字符或完整单词作为基本处理单位？”

用 token（子词）是在压缩和开词汇之间取折中：字符级序列太长，单词级词表太大、新词全是 OOV，子词两头都照顾到。`strawberry` 被拆开是 BPE 合并优先级的结果，算不上 bug；模型看见的是子词 id 序列，没有字母列表，所以「数一数里面有几个 r」这类题容易错。

常见的误区是把 tokenizer 当成「对人类单词的对齐」，再推论模型能按字母数 r。

## 字符、单词、子词各牺牲什么

字符级的词表极小、没有 OOV，但序列长度按字膨胀，注意力是 $O(n^2)$，长依赖更难建，中英文混排、空格、标点都会变成超长串。单词级在英文里可以按空格切，但词表巨大，新词、拼写错误、SKU、表情全是 OOV；中文还要先分词，分词器的错误会直接写进 id。子词（BPE / Unigram）按语料频率把高频片段合并成词表项，低频词退回更短的片段，压缩比介于字符和单词之间，而且是开词汇的：没见过的词仍能用已知子词拼出来。

BPE 的训练是迭代合并：初始为字符（或 byte），每次把当前语料里出现最多的相邻对合成一个新符号，直到词表到 $V$。编码时用同一张合并表做贪心，能合就合，合不上就停。所以「一个英文单词是几个 token」由训练语料的统计决定，和语言学规则无关。

## 为什么 `strawberry` 会被拆

这个整词在词表里的合并优先级不够，或者带了前置空格 / 大小写变体（`strawberry` vs `Ġstrawberry`），编码器就走了更短的子词路径，例如 `str` + `aw` + `berry`。模型前向时从没看见「完整单词形态」，更没有隐式的字母列表，所以「数 r」失败在表征上，和「不会数数」是两码事。

不过这类题要主动拆成两层讲。第一层是切分：模型输入是 id 序列，除非把词再拆成字符特征，它拿不到字母。第二层是计数能力：就算切成整词，自回归模型也不保证能精确计数，这是算法能力，怪不到 tokenizer 头上。只把失败归因于拆词，会被追问「那换成整词就能数对吗」。完整的答法是：拆词解释了为什么形态不可见；要数对，得靠显式的字符级工具、程序，或者在数据里教过计数格式。

## 业务上意味着什么

SKU、快递单号、emoji、中英混排、拼音缩写都会被切碎。评测长度、上下文窗口、计费都按 token 算，按字或按词都对不上。同一句话换个 tokenizer，长度和切点都会变，所以不能跨模型比「多少 token」。换词表等于换离散空间，embedding 和输出头都要重训，后处理对齐不了。Agent 岗还要落到 SKU / 券码：检索和工具参数应该按规范化的字符串处理，别按「看起来像一个单词」的 token 边界去切。BPE 不会按业务字段切，字段抽取的边界要自己定。

中文场景再补一句。空格分词对中文几乎不可用，把单字当「单词」，词表和序列又都不经济。子词把高频词（的、是、可以）收成短 token，把人名、品牌、错别字退回更碎的片段。这解释了为什么同一个模型对常见书面语压缩得很好，对直播口播和商品标题 token 却暴涨：这些文本的统计不在词表的高频合并路径上。评测集如果和预训练语料的切分习惯差得远，长度预算和计费预估都会偏。

## 追问

**Byte-level BPE 解决什么？**
任意 Unicode 都能落到 byte，彻底消灭「未知字符」。中文常被切成多个 byte 再合并，词表不必为每个汉字单列一项。

**能按空格强制不拆吗？**
可以加 special token，但会膨胀词表，而且只覆盖你枚举过的词，下周出个新品牌又是 OOV。

**Unigram 和 BPE 有什么区别？**
Unigram 用语言模型打分来选切分，BPE 是贪心合并。面试先讲 BPE 的合并表就行，被追问再补 Unigram 可以对切分多次采样。

**和 embedding 是什么关系？**
每个 token 一个向量。词被拆开以后，「词」的语义要靠多层注意力拼回来，没有免费的整词槽位。

**先用 jieba 预分词再 BPE 呢？**
早期中文常这么做，但分词错误会写进 id，也和新词冲突。现代多语词表更常直接做 byte / unicode BPE。
