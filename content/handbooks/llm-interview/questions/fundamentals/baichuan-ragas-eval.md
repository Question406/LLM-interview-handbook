## 真题记录

- 公司：百川智能
- 团队 / 岗位：大模型实习
- 届别 / 流程：实习；一面
- 面试时间：原帖未披露；帖子发布于 2026-02-12
- 来源类型与可信度：牛客候选人原帖，B
- 原始措辞：**“ragas评估指标 评估流程 数据如何获取”**

这块容易直接答成：RAGAS 分数等于业务成功，或者每次改 prompt 偷偷改评测集。RAGAS 一类框架用 LLM-as-judge / 启发式，从一次调用的 query、contexts、answer 拆维度，适合回归检索到生成这条管线，但 judge 自己会漂，必须用小规模人工金标校准（`fund-judge`）。检索组合见 `fund-rag`；搜索与推荐不要混金标见 `baichuan-search-vs-rec`。同类拆分思路见 `ali-rag-eval`、`jd-rag-accuracy-eval`。

## 指标拆什么

常见维：答案对上下文的 **忠实度**（有没有编证据外事实）、答案与问题的 **相关性**、检索上下文的 **精确 / 召回**（是否包含解题证据）。高上下文召回、低忠实度 = 检索对了生成胡编；高忠实、低相关 = 只敢复述无关段落。不要用一个总分盖住。切片按语言、表结构、是否多跳、是否长文档来。报告时我会 **同时给业务任务成功和 RAGAS**，避免只优化 judge。

## 流程与数据从哪来

流程：冻结索引与模型版本 → 对评测集跑检索和生成 → 保存 query / contexts / answer → 算各维 → 按切片看 → 抽检与人工不一致的 case。提示词迭代时冻结评测集。数据优先用已有带引用的文档问答、表格问答和线上会话抽样；没有金标时用强模型生成再人工改，或从日志里找「用户纠正过」的负例。每条至少要有可定位的证据文档 ID。线上抽样要注意曝光偏差，不能把点击当「证据充分」（`baichuan-search-vs-rec`）。

失败模式：用会漂的 judge 当唯一 KPI；评测集与训练集文档重叠；只报平均 faithful，安全 / 多跳 slice 崩了看不见。

## 落地时的最小实验记录

一次 RAGAS 回归应留下：索引哈希、embedding / 检索器版本、生成模型与解码、$k$、chunk 策略、评测集版本。缺一项，下周分数动了你不知道是谁的功劳。指标不要合成一个「RAGAS 总分」当唯一看板：忠实度、答案相关、上下文精确、上下文召回至少分列，并按多跳 / 表格 / 长文档切片。人工校准每周或每两次大改抽一小批，算与 judge 的一致率；低于阈值就冻结自动分数，只看人审。这和 `fund-judge` 那套纪律一样。

数据上，线上日志最值钱的是「用户改写了问题」或「点了引用不对」的负例，比再让 GPT 造一百条同质问答有用。没有引用字段的会话，先补证据文档 ID 再进评测，否则忠实度没有参照。搜索点击不能直接当「上下文充分」：位置偏差会让热门但无关的段落显得相关（`baichuan-search-vs-rec`）。表格问答要把单元格坐标当证据，而不是整页 HTML。

和业务成功同时报：工单是否解了、引用是否被点开、用户是否再次追问。RAGAS 涨、工单不降，说明你在优化 judge 而不是产品。改 prompt 时评测集冻结；改索引时生成配置冻结，交叉对照。数据侧最小增量是：从线上抽一周会话，补证据 ID 与是否解决标签，而不是先造一千条合成问答。合成题容易和教师同分布，judge 分数会虚高。表格、多跳、低资源语言必须单独成层，否则平均忠实度看起来健康、真实用户全卡在表上。校准集要与开发提示词隔离，避免「改完 prompt 再在校准集上看起来更一致」。

## 追问

- **没有参考答案能评吗？** 忠实度可以相对 contexts 评；相关性仍建议有人标或业务标签校准。
- **RAGAS 能替代人审吗？** 不能。它是回归仪表，人审定义口径。judge 漂了分数仍会很好看。
- **数据最少要有哪些字段？** query、检索到的 contexts、生成 answer、证据文档 ID；最好还有任务成功标签。
- **上下文召回高、忠实度低说明什么？** 检索可能对了，生成在编。先加引用约束或拒答，而不是先换检索器。
- **评测集能和训练文档重叠吗？** 不能按文档泄漏。重叠会让召回虚高，见 `data-contamination`。
