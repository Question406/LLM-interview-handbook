## 真题记录

- 岗位：阿里校招分布式

## 定义

分布式事务要让跨库、跨服务的几次写，要么一起成功，要么一起回到原点。2PC 是资源管理器协议：协调者先 `prepare`，参与者锁住资源并投票，再 `commit` 或 `rollback`。它追求强一致，但协调者宕机或网络分区时，参与者可能一直持锁，阻塞窗口大。TCC 把「锁资源」上收到业务：`Try` 预留（冻结库存、预扣余额），`Confirm` 真正提交，`Cancel` 释放预留。它是补偿型，不依赖数据库 XA。Seata 是阿里开源的分布式事务框架，校招要能区分 AT 和 TCC：AT 拦截本地 SQL，记 undo log，二阶段自动提交或反向补偿，侵入小；TCC 模式则要求业务自己实现三个方法。

还有两个常被塞进同一题的亲戚。Saga 把长事务拆成一串本地事务，失败就按相反顺序补偿，适合行程、物流这种跨时长流程。本地消息表 / 事务消息走最终一致：本地库和消息一起成功，下游自己幂等。能不用分布式事务就不用，钱和库存这种不变量才值得上 TCC。

## 对比 / 分层

| | 2PC / XA | TCC | Seata AT | Saga / 消息 |
| --- | --- | --- | --- | --- |
| 一致 | 强，阻塞 | 业务强，窗口短 | 接近强，依赖锁和 undo | 最终一致 |
| 侵入 | 数据源要支持 XA | 三个业务方法 | 改代理数据源 | 补偿或消息 |
| 锁 | 资源管理器长锁 | Try 只锁预留量 | 行锁 + 全局锁 | 几乎不锁全局 |
| 失败 | 协调者单点、阻塞 | 空回滚、悬挂、幂等 | undo 对不上、脏写 | 补偿也失败要人工 |
| 适用 | 少见的同构 DB | 资金、库存 | 普通业务少侵入 | 可回补的流程 |

TCC 三个经典异常必须能口述。空回滚：`Cancel` 比 `Try` 先到，Cancel 要做成空操作并记下，避免 Try 晚到又预留成功。悬挂：Try 被拦截后迟到，却已经 Cancel 过，Try 不能再预留。幂等：Confirm / Cancel 会被重试，必须用事务单号做唯一约束。AT 的代价是全局锁：未完成的分布式事务会挡住对同一行的写，热点商品不适合纯 AT。

## 阿里场景

下单涉及订单服务、库存、优惠券、积分。校招讲分层落地，别全链路 TCC。订单和库存中心：库存 `Try` 冻结 $1$ 件，下单成功 `Confirm` 扣减，失败 `Cancel` 解冻。优惠券同理，Try 把券标成占用。积分、搜索、短信走消息最终一致，失败重试即可，不必进同一事务。淘天常见做法是「核心用 TCC / 事务消息，外围用异步」。

Seata 在中台项目里出现得多。新服务若 SQL 规整、冲突不高，AT 能少写很多代码；账户、红包、冻结余额这种有明确预留语义的，用 TCC 更干净。双十一时协调者自己也是风险：事务日志要高可用，超时策略要短，避免冻结库存挂一整晚。对账是最后一道网：每天把冻结中、已确认、已取消的单拉出来和库存流水比，TCC 免不了对账。

优先本地事务 + 唯一键 + RocketMQ 事务消息；只有资金不变量被跨服务拆开，才上 TCC。

## 追问

- Confirm 失败了怎么办？重试 Confirm，不要改走 Cancel，状态机要单向。
- AT 的 undo log 丢了会怎样？二阶段无法回滚，要人工按 SQL 对账。
- 和事务消息怎么选？一边写库一边通知下游，用事务消息；两边都要预留资源，用 TCC。
- 为什么 2PC 在微服务里不受待见？连接跨服务持有、协调者阻塞、和连接池不对付。
- Saga 补偿失败？做成可重试补偿，最后进人工工单。
- 全局事务超时如何定？略大于下游 P99 之和，太长会占库存，太短会误 Cancel。
- 如何证明幂等？同一 `xid` 重复 Confirm，库存只少一次，有唯一索引兜底。
