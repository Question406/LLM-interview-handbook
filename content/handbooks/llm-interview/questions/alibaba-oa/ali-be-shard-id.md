分库分表最关键的是分片键：查询要能带上它，数据要能靠它打散，订单常按买家 ID 或订单号哈希。分片以后单表自增不能再当全局 ID，雪花 ID 本地发号、趋势递增，风险在时钟回拨和机器位冲突。发号和分片是一套设计，我会放在一起讲，别拆成两道独立的八股。这是阿里校招的题。

分库分表是把一张逻辑大表按分片键拆到多个物理库表，分散单机的存储和请求压力。按时间分片适合日志和冷热分离。拆完以后一台数据库不再有全部数据，二次查询、跨片 `JOIN`、跨片排序分页都要在应用层做。分片键选错就会出现热点片，比如头部卖家、秒杀商品。

雪花 ID 用 $64$ 位整数编码：$1$ 位符号 + $41$ 位毫秒时间 + $10$ 位机器 + $12$ 位序列，同一台机器每毫秒理论上能发 $4096$ 个号，而且大致按时间有序。它依赖本地时钟，NTP 回拨会让时间部分变小，下一毫秒的号可能和历史撞上。机器位冲突（容器漂移、复制出相同的 workerId）同样会撞号。

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 哈希取模 | 打散均匀 | 扩容要迁移；按时间范围扫要全片 |
| 范围 / 按时间 | 扩容简单、冷热清晰 | 新片或头部范围易热 |
| 一致性哈希 | 扩缩迁移少 | 实现和虚拟节点运维更重 |
| 雪花 | 本地发号、趋势递增 | 时钟、workerId |
| DB 号段（Leaf Segment） | 不依赖时钟，批量取号 | 依赖 DB，要双 buffer |
| 号段 + 雪花混合 | 生产常见 | 要讲清各自失败域 |

查询按带不带分片键分开处理。带分片键的点查走单片；只带非分片键的，比如按手机号查订单，要靠全局二级索引、异构文档，或者允许扫少量分片。跨片分页时每片取一页再归并，或者用搜索的 search_after，禁止 `LIMIT 100000,20` 这种深分页。事务上，单片用本地事务；跨片只能用 TCC / 消息，别指望分布式 JOIN 加 XA。扩容时，二倍取模可以成对迁移，一致性哈希按环搬，按时间分片则新数据写新片、旧片只读。

雪花的时钟回拨有三种处理：直接拒绝（安全，但可用性差）、等回拨结束、借用上次的时间并借用序列。口头说「禁止回拨 + 监控时钟偏移」就够，不必背 64 位怎么划分。

## 放到阿里的场景里

淘宝订单典型是按买家维度分库分表：C 端「我的订单」永远带 `buyer_id`，单片点查。卖家后台「我店铺的订单」不带买家键，走搜索或卖家维度的宽表，别对 $1024$ 张订单表做 scatter-gather。秒杀爆款如果按商品 ID 分片，单库会被打穿，要再按买家哈希，或者把热点库存拆桶。TDDL / ShardingSphere 这类中间件负责路由，分片键怎么设计仍然是业务自己的活。

ID 这边，阿里和美团都有号段服务的实践。校招可以一句话对比：雪花无中心、快，怕时钟；Leaf 号段中心化、好审计，怕 DB。订单号往往还会带上分库分表位，运维拿到号就知道落在哪张表，不用反查路由。扩容要在双十一前做完：新库先双写，或者按号段切开，活动当天不要现场加片。迁移不停服的顺序是双写、校验、切读，最后停旧写。

时钟回拨在线上的典型表现是，虚拟机热迁移或者闰秒以后，发号器突然报错或静默撞号，唯一索引把下单打失败。预案是发号器启动时拒绝回拨，并对 NTP 告警。workerId 用配置中心或 Redis 租约分配，别写死在镜像里。

## 追问

**热点卖家怎么拆？**
对这个卖家再哈希到子片，或者单独给一个库，再加缓存。

**雪花 ID 能当聚簇主键吗？**
能。它趋势递增，比 UUID 友好，但还是不如纯自增紧凑。

**号段用完了怎么续？**
双 buffer 预取下一段，避免同步打 DB。

**分片以后唯一索引怎么做？**
先保证片内唯一，全局唯一靠发号；跨片的唯一约束要额外建一张索引表。

**为什么不按用户名分片？**
字符串分布不均，用户改名还要搬数据。
