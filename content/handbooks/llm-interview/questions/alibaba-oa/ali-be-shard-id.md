## 真题记录

- 岗位：阿里校招

## 定义

分库分表是把一张逻辑大表按分片键拆到多个物理库表，目的是把单机容量和 QPS 切开。分片键必须同时满足「查询能带到」和「数据能打散」。常见是买家 ID、订单号；按时间分片适合日志和冷热分离。二次查询、跨片 `JOIN`、跨片排序分页都要在应用层做，数据库不再是单一真相的全集。全局唯一 ID 是分片后的配套问题：不能再依赖单表自增。雪花 ID 用 $64$ 位整数编码：$1$ 位符号 + $41$ 位毫秒时间 + $10$ 位机器 + $12$ 位序列，理论上同一机器每毫秒 $4096$ 个号，且大致时间有序。

风险我先说。分片键选错会出现热点片（头部卖家、秒杀商品）。雪花依赖本地时钟，NTP 回拨会让时间部分变小，下一毫秒可能和历史撞号。机器位冲突（容器漂移、复制出相同 workerId）同样撞号。所以发号和分片是一套设计，不是两道独立八股。

## 对比 / 分层

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 哈希取模 | 打散均匀 | 扩容要迁移；按时间范围扫要全片 |
| 范围 / 按时间 | 扩容简单、冷热清晰 | 新片或头部范围易热 |
| 一致性哈希 | 扩缩迁移少 | 实现和虚拟节点运维更重 |
| 雪花 | 本地发号、趋势递增 | 时钟、workerId |
| DB 号段（Leaf Segment） | 不依赖时钟，批量取号 | 依赖 DB，要双 buffer |
| 号段 + 雪花混合 | 生产常见 | 要讲清各自失败域 |

查询分层：带分片键的点查走单片；只带非分片键（按手机号查订单）要全局二级索引、异构文档，或允许扫少量片。事务分层：单片本地事务；跨片只能 TCC / 消息，不要幻想分布式 JOIN 加 XA。扩容分层：二倍取模可以成对迁移；一致性哈希按环搬；按时间则新数据写新片，旧片只读。

雪花的时钟策略也要分层：直接拒绝（安全、可用性差）、等待回拨结束、借用上次时间并借用序列。我会说「禁止回拨 + 监控时钟偏移」，不背 64 位划分。

## 阿里场景

淘宝订单典型按买家维度分库分表：C 端「我的订单」永远带 `buyer_id`，单片点查。卖家后台「我店铺的订单」不带买家键，走搜索或卖家维度的宽表，而不是对 $1024$ 张订单表做 scatter-gather。秒杀爆款如果按商品 ID 分片，单库会被打穿，要再按买家哈希，或把热点库存拆桶。TDDL / ShardingSphere 这类中间件负责路由，但分片键设计仍是业务的活。

ID 方面，阿里和美团都有号段服务的实践。校招对比句：雪花无中心、快，怕时钟；Leaf 号段中心化、好审计，怕 DB。订单号往往还要带分库分表位，让运维拿到号就知道落在哪张表，不必反查路由。扩容双十一前就要做完：新库先双写或按号段切开，活动当天不要现场加片。

时钟回拨的线上故事：虚拟机热迁移或闰秒，发号器突然报错或静默撞号，唯一索引把下单打失败。预案是发号器启动时拒绝回拨，并告警 NTP。workerId 用配置中心或 Redis 租约分配，不要写死在镜像里。

## 追问

- 分页跨片怎么做？每片取一页再归并，或用搜索的 search_after，禁止深分页 `LIMIT 100000,20`。
- 热点卖家怎么拆？对该卖家再哈希到子片，或独立库，并加缓存。
- 雪花能当聚簇主键吗？趋势递增，比 UUID 友好，仍不如纯自增紧凑。
- 号段用完怎么续？双 buffer 预取下一段，避免同步打 DB。
- 分片后唯一索引怎么做？先保证片内唯一，全局唯一靠发号；跨片唯一要额外索引表。
- 数据迁移怎么不停服？双写 + 校验 + 切读，最后停旧写。
- 为什么不按用户名分片？字符串分布不均、改名要搬数据。
