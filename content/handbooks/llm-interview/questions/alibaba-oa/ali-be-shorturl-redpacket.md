## 真题记录

- 岗位：阿里校招系统设计常考（短链 / 红包 / 限流）

## 定义

短链把长 URL 映射成短码，用一次跳转换可分享的入口。写路径是发号或哈希得到短码，写入映射表；读路径是根据短码查原链，返回 $301$ 或 $302$。$301$ 可被浏览器和 CDN 永久缓存，省回源但改指向困难；$302$ 每次回源，便于统计和撤链。短链要处理碰撞、循环跳转、钓鱼黑名单、过期和点击统计。它是读多写少：一条短链生成一次，被打开千万次。

抢红包是写冲突：一个红包 $N$ 个名额、总额固定，很多人同时抢。写路径是原子扣名额、记下领取、再异步入账。金额分配要么预拆（发红包时就算好每份），要么实时随机但守住「剩余人数和剩余金额」约束。二倍均值法是实时算法：第 $i$ 个人从 $(0, 2 \times \text{剩余}/\text{剩余人数})$ 里随机，期望公平且不会把余额过早抽干。两者都要幂等和审计，但热点形态相反。

## 对比 / 分层

| | 短链 | 红包 |
| --- | --- | --- |
| 主矛盾 | 读放大、安全 | 写冲突、资金正确 |
| 存储 | 映射表 + 缓存 | 库存令牌 + 领取记录 + 账户 |
| 发号 | 号段 / 雪花 / 哈希 | 红包 ID + 用户维度唯一 |
| 失败 | 404、拦截钓鱼 | 抢完、重复抢、入账失败回补 |
| 统计 | 异步点击，不挡跳转 | 异步入账，对账兜底 |

短链分层：发号层保证唯一；存储层 MySQL 做权威、Redis 做热映射；接入层做黑名单和循环检测（A→B→A）；观测层把点击丢 MQ。自定义码是用户指定短码，必须唯一约束，并禁保留字。对长 URL 取哈希摘要作为短码要处理碰撞：冲突就加盐再哈希，或退化到发号。

红包分层：预热时把「剩余份数」放 Redis；抢的时候 `DECR`，小于 $0$ 回补并返回抢完；成功才写领取记录（用户+红包唯一键）；入账走 MQ，失败重试，最终回补名额。预拆金额适合晚会固定场次，实时随机适合微信式拼手气。防刷：验证码、设备、同一用户限频、风控分。

## 阿里场景

淘宝分享商品、会场、直播间会生成短链。读路径极热：大 V 一条链接被转发，CDN 和 Redis 必须挡住映射查询。统计「这个会场带来多少点击」不能同步写 DB，否则跳转变慢，分享体验先死。钓鱼是合规红线：生成时校验域名白名单，跳转页可加中间提示。循环短链会把自己打爆，检测跳转深度。过期活动链用 TTL，避免映射表无限涨。

红包出现在年货节、直播打赏、天猫乐园。和秒杀的差别：秒杀是同一价格同一 SKU；红包是总额约束下的随机切片，还要防「最后一个人分到 0.00 或把余款独吞」。二倍均值保证最后一份等于剩余。入账进钱包是资金操作，必须异步且幂等，不能在抢的锁里调支付。直播间红包比普通红包更热，名额预分到多个 Redis 桶，再在桶内 `DECR`。

审计：短链留生成者、原链、拦截记录；红包留每笔领取金额、时间、入账流水。资金差错靠流水回放，不靠当时的内存状态。

## 追问

- 短链用 $62$ 进制多少位够？$6$ 到 $8$ 位通常够亿到百亿级，按发号空间算 $62^n$。
- 为什么不直接哈希长 URL？碰撞和无法递增扫描；发号更好控。
- $301$ 改不了指向怎么办？活动链用 $302$，品牌短链才 $301$。
- 红包如何保证总额分完？最后一份不随机，直接给剩余。
- 重复抢怎么拦？唯一键，已领取直接返回原结果。
- 入账失败库存回补会不会超发？回补和领取记录在同一状态机里，已入账禁止回补。
- 短链和红包能共用秒杀架构吗？排队和原子减可以借鉴，短链不必预减，红包必须管金额约束。
