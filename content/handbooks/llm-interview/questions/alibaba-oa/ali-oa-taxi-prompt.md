这题要把每条计费细节都写成模型没法自由发挥的步骤：先抽参数，再逐步代入公式，最后只输出约定的 JSON。评测看的是 Prompt 有没有把规则写死、输出能不能解析，考的不是算法实现。

失分几乎都在细节上：谁乘 $1.2$、谁向上取整、谁默认为 $0$。比如夜间坐 $16.2$ km、等候 $24$ 分钟、带 $2$ 件大件行李，正确答案是 $83$ 元；把 $1.2$ 乘到总价上就成了 $87$。所以我会把这些细节写成一张检查清单，并且禁止模型输出散文。

## 题面

用一段系统 prompt，让模型从用户的自然语言里抽出行程要素，严格按计费规则算出费用，并且只输出约定 JSON。公开复盘里的关键字段是 `thinking`、`base_fare`、`night_surcharge`、`fare`。

规则是：起步 $3$ km /$10$ 元；$3$ 到 $15$ km 每公里 $3$ 元；超 $15$ km 每公里 $4$ 元（不足 $1$ km 进位）；等候每满 $5$ 分钟 $2$ 元；夜间 $23$:$00$（含）到次日 $05$:$00$（不含）车费 $\times 1.2$ 再进位；大件行李每件 $5$ 元且不参与夜间加收。没写明的字段按缺省处理：等候 $0$、行李 $0$、时间没提就算白天。夜间看上车时间是否落在 $[23{:}00,\,05{:}00)$。

## Prompt 怎么写

骨架是四块：角色、抽取、逐步公式、强制 JSON。距离先向上取整成整数公里 $D=\lceil X\rceil$，再套三段价；夜间只作用在 `base_fare` 上；等候用 $\lfloor T/5\rfloor\times 2$；行李 $N\times 5$。每个字段都给默认值，模型就不会回头去问用户。

下面这段可以直接贴进评测框，字段名不要改。

```text
你是出租车计费系统。用户用自然语言描述行程。你必须先抽取参数，再按下列步骤计算，最后只输出一个 JSON 对象，不要输出 JSON 以外的任何文字、Markdown 或解释。

# 参数抽取
从用户描述中提取：
- X：行驶距离（公里）。未提及则 X=0。
- T：等候时间（分钟）。未提及则 T=0。
- N：大件行李件数。未提及则 N=0。
- night：是否夜间。若明确写了夜间 / 凌晨，或上车时间落在 23:00（含）到次日 05:00（不含），则 night=true，否则 night=false。未提及时间则视为白天。
05:00 整点不算夜间。23:00 整点算夜间。

# 计算步骤（必须逐步代入数字）

## 1. 整数公里
D = ceil(X)。X 已经是整数则 D=X。0 公里仍按行程处理。

## 2. 基础车费 base_fare（整数元）
起步价 10 元，包含前 3 公里（含 D=3）。
- 若 D <= 3：base_fare = 10
- 若 3 < D <= 15：base_fare = 10 + (D - 3) * 3
- 若 D > 15：base_fare = 10 + 12 * 3 + (D - 15) * 4
不足 1 公里在第 1 步已经进位，这里不要再对分段内部单独四舍五入。

## 3. 夜间车费 vehicle
- night=true：vehicle = ceil(base_fare * 1.2)，即有小数就向远离 0 的方向进到整数。例如 19.2 -> 20。
- night=false：vehicle = base_fare
等候费和行李费绝不参与 *1.2。

## 4. 等候费 wait_fee
wait_fee = floor(T / 5) * 2
只收完整的 5 分钟段。24 分钟只能收 4 段 = 8 元，余下 4 分钟不收。

## 5. 行李费 luggage_fee
luggage_fee = N * 5
行李不加收夜间。

## 6. 总价
fare = vehicle + wait_fee + luggage_fee

# 输出格式
只输出如下 JSON（字段必须齐全，类型必须正确）：
{
  "thinking": "用中文写出每一步代入的数字和中间结果，包括 D、base_fare、vehicle、wait_fee、luggage_fee、fare",
  "base_fare": 基础车费整数,
  "night_surcharge": true或false,
  "fare": 总费用整数
}

night_surcharge 填抽取到的 night，不要填加收金额。
base_fare 填第 2 步的基础车费，不要改成夜间后的 vehicle。
```

## 拿四个反例自测

Prompt 写到能覆盖规则就够了，不用往评测框里堆示例堆到溢出。这道题没有算法代码，自测就是拿下面四个反例在本地跑一遍，看 JSON 里的数对不对。

**例 1：白天 $2.3$ km，没提等候和行李。**

- $D=\lceil 2.3\rceil=3$
- $D\le 3$，`base_fare`$=10$
- 白天，`vehicle`$=10$，`night_surcharge`=`false`
- `wait_fee`$=0$，`luggage_fee`$=0$
- `fare`$=10$

不足 $1$ km 的进位发生在整段距离上，别先按 $2$ km 算再另加一截。

**例 2：夜间 $16.2$ km，等候 $24$ 分钟，大件行李 $2$ 件。**

- $D=\lceil 16.2\rceil=17$
- `base_fare`$=10+12\times 3+(17-15)\times 4=10+36+8=54$
- 夜间：`vehicle`$=\lceil 54\times 1.2\rceil=\lceil 64.8\rceil=65$
- `wait_fee`$=\lfloor 24/5\rfloor\times 2=4\times 2=8$（按完整段数取整，$24/5$ 不做四舍五入）
- `luggage_fee`$=2\times 5=10$
- `fare`$=65+8+10=83$

错把 $1.2$ 乘到总价上，会变成 $\lceil(54+8+10)\times 1.2\rceil=87$，这是最常见的扣分点。

**例 3：白天恰好 $15$ km，等候 $4$ 分钟，没有行李。**

- $D=15$，`base_fare`$=10+(15-3)\times 3=46$
- 等候不足 $5$ 分钟，`wait_fee`$=0$
- `fare`$=46$

**例 4：$05{:}00$ 上车，距离 $3.01$ km。**

- $05{:}00$ 不在夜间区间里，按白天算
- $D=\lceil 3.01\rceil=4$，`base_fare`$=10+1\times 3=13$，`fare`$=13$

## 追问

**夜间加收最容易错在哪？**
乘错对象。把夜间乘数乘到等候费或行李费上，或者把 `base_fare` 填成加收后的车费，JSON 都会和隐藏评分对不上。

**除了夜间，还有哪些计算细节常丢分？**
等候 $24$ 分钟按 $5$ 段收费，或者距离 $3.2$ km 忘了先 `ceil`。这两处在 Prompt 里都要写一句反例提醒。

**用户没提等候和行李，模型会怎样？**
缺字段不给默认值，模型会开始追问用户，输出就不再是纯 JSON，解析直接失败。

**不足 $1$ km 是每段算完再进位，还是先取整再分段？**
先把总距离进成整数公里，再套 $3/15$ 的分界。两种写法在常见样例上结果一致，Prompt 里写死一种就行。
