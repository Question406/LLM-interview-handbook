## 真题记录

- 岗位：阿里校招；和双十一故事最贴

## 定义

限流是在系统能力之上主动拒绝或排队，保护核心链路不被突发流量打死。漏桶把请求放进队列，以恒定速率 $r$ 流出，桶满则拒；它把突发削平，下游看到的是匀速。令牌桶以速率 $r$ 往桶里放令牌，桶容量 $b$，一次请求可拿走 $k$ 个令牌；桶里有存货时允许突发，长期平均仍不超过 $r$。固定窗口会在窗口边界叠出 $2$ 倍峰值，滑动窗口更平滑。集群限流要把计数放到 Redis / Sentinel 的共享状态上，单机计数管不了多副本。

CAP 和 BASE 是限流之上的取舍语言。CAP：分区发生时，只能在强一致（C）和持续可用（A）里选一边。限流组件自己通常选 AP——计数不准一点也要能拒掉超额请求，而不是为了精确计数而拒绝所有流量。BASE（Basically Available、Soft state、Eventually consistent）说的是业务：库存预扣、积分到账允许短时间不准，但下单入口必须可用。双十一的正确叙事是**先限流、排队、降级，再谈分布式事务**，不是一上来上 TCC。

## 对比 / 分层

| | 漏桶 | 令牌桶 | 固定窗口 | 滑动窗口 |
| --- | --- | --- | --- | --- |
| 突发 | 不允许，削平 | 允许到 $b$ | 窗口边界双倍 | 较平滑 |
| 实现 | 队列 + 恒速出 | 计数 + 时间补令牌 | 计数器 | 多槽或 Redis ZSET |
| 适用 | 保护匀速下游 | 网关、开放 API | 粗配额 | 用户级 QPS |

防护分层从外到内：接入层（网关 / WAF / CDN）按 IP、UID、接口拒；应用层 Sentinel 按资源规则；线程池 / MQ 做隔离，避免一个下游拖死整机；最里才是数据库和分布式事务。规则分层：系统阈保护机器，用户阈防刷，业务阈保护库存。CAP 对照：ZooKeeper / etcd 选 CP，分区时宁可不可写；DNS、缓存、限流计数选 AP。BASE 对照：预扣库存是软状态，对账后最终一致。

集群限流的坑：Redis 本身成为单点。用滑动窗口 + Lua 保证原子加减，超时则「失败开」还是「失败关」要按接口定：读推荐失败开，下单失败关。单机限流做第一道，集群做第二道，避免 Redis 抖动时完全裸奔。

## 阿里场景

双十一零点，商品详情和结算会冲到单接口十万 QPS。网关令牌桶先把突发收成内部可消化的量，多出来的进排队页，而不是把流量直接灌进交易库。Sentinel 在淘天体系里是标准组件：按资源名限流、熔断、热点参数（对某个 itemId 单独限）。漏桶更适合调用下游结算通道：银行接口只要匀速，突发会被对方封。

CAP 的口述可以落到注册中心和库存。配置中心短时间读到旧阈值，总比读不到阈值放进行好，这是 AP。库存中心在机房断开时，不能为了强一致把下单全停——核心 SKU 用本地预扣 + 事后对账，这是 BASE。TCC 只留给真正跨了资金的那一小段，而且要被限流保护，否则 Try 会把冻结单堆爆。

降级清单比算法更像阿里：关推荐、关评价、关个性化、保下单和支付。限流不是把用户一棒子打死，而是把非核心体验摘掉。面试画「接入限流 → 本地缓存 → MQ 削峰 → 降级开关 → 核心事务」比只背公式分高。

## 追问

- 令牌桶突发 $b$ 怎么定？按下游能扛的瞬时并发，而不是拍脑袋。
- 用户级和接口级哪个先？先接口保系统，再用户防刷，避免一个小号打满。
- Redis 限流 Lua 失败怎么办？读接口放行并告警，写接口拒绝。
- 限流和熔断差在哪？限流是配额，熔断是下游错误率高了先断开。
- CAP 能不能三个都要？分区时不行；平时正常运行看起来像 CA。
- 排队如何做公平？按 UID 哈希到队列，避免同一用户占多条。
- 如何验证限流有效？压测看通过率和下游 QPS 是否被削平，而不是只看规则配了没有。
