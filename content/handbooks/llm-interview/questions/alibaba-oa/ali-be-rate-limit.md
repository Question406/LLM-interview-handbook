漏桶和令牌桶的差别在于允不允许突发：漏桶以恒定速率放行，下游看到的是匀速；令牌桶可以把攒下的令牌一次用掉，长期平均仍受速率限制。CAP 和 BASE 是在限流之上做取舍的语言，限流组件自己一般选可用，业务上用最终一致换下单入口不停。这是阿里校招的题，也是最贴双十一故事的一道。

限流是在系统能力之上主动拒绝或排队，保护核心链路不被突发流量压垮。漏桶把请求放进队列，以恒定速率 $r$ 流出，桶满就拒，突发被削平。令牌桶以速率 $r$ 往桶里放令牌，桶容量 $b$，一次请求拿走 $k$ 个令牌，桶里有存货时允许突发。固定窗口会在 window boundaries 叠出 $2$ 倍峰值，滑动窗口更平滑。

| | 漏桶 | 令牌桶 | 固定窗口 | 滑动窗口 |
| --- | --- | --- | --- | --- |
| 突发 | 不允许，削平 | 允许到 $b$ | window boundaries 双倍 | 较平滑 |
| 实现 | 队列 + 恒速出 | 计数 + 时间补令牌 | 计数器 | 多槽或 Redis ZSET |
| 适用 | 保护匀速下游 | 网关、开放 API | 粗配额 | 用户级 QPS |

集群限流要把计数放在 Redis / Sentinel 的共享状态上，单机计数管不了多副本。可 Redis 本身又会成为单点。做法是滑动窗口加 Lua 保证原子加减；Redis 超时以后是「失败开」还是「失败关」，按接口定，读推荐失败开，下单失败关。单机限流做第一道，集群做第二道，Redis 抖动时还有单机这层保护。

防护从外到内分几层：接入层（网关 / WAF / CDN）按 IP、UID、接口拒；应用层 Sentinel 按资源规则限；线程池 / MQ 做隔离，避免一个下游拖死整机；最里面才是数据库和分布式事务。规则也分层：系统阈值保护机器，用户阈值防刷，业务阈值保护库存。顺序上先按接口限、保住系统，再按用户限、防刷，避免一个小号打满。

CAP 说的是分区发生时，强一致（C）和持续可用（A）只能选一边。ZooKeeper / etcd 选 CP，分区时宁可不能写；DNS、缓存、限流计数选 AP。限流组件计数不准一点也要能拒掉超额请求，为了精确计数把所有流量都拒掉就本末倒置了。BASE（Basically Available、Soft state、Eventually consistent）说的是业务：库存预扣是软状态，积分到账允许短时间不准，对账后最终一致，但下单入口必须可用。所以双十一我先讲限流、排队、降级，再谈分布式事务，开口就上 TCC 会跑偏。

## 放到阿里的场景里

双十一零点，商品详情和结算会冲到单接口十万 QPS。网关令牌桶先把突发收成内部能消化的量，多出来的进排队页，别把流量直接灌进交易库。排队要公平，就按 UID 哈希到队列，避免同一个用户占好几条。Sentinel 是淘天体系里的标准组件，按资源名限流、熔断，还能做热点参数限流（对某个 itemId 单独限）。漏桶更适合调用下游结算通道：银行接口只要匀速，突发会被对方封。

CAP 可以落到配置中心和库存上讲。配置中心短时间读到旧阈值，总比读不到阈值直接放行好，这是 AP。库存中心在机房断开时，不能为了强一致把下单全停：核心 SKU 用本地预扣加事后对账，这是 BASE。TCC 只留给涉及资金的那一小段，而且前面要有限流保护，否则 Try 会把冻结单堆爆。

降级清单比算法更像阿里会问的：关推荐、关评价、关个性化，保下单和支付。限流和降级都优先砍非核心功能的流量。面试时画一条「接入限流 → 本地缓存 → MQ 削峰 → 降级开关 → 核心事务」，比只背公式分高。

## 追问

**令牌桶的突发容量 $b$ 怎么定？**
按下游能扛的瞬时并发来定，别拍脑袋。

**Redis 限流的 Lua 执行失败了怎么办？**
读接口放行并告警，写接口拒绝。

**限流和熔断有什么区别？**
限流管的是配额；熔断是下游错误率高了，先把调用断开。

**CAP 能不能三个都要？**
分区时不行。平时正常运行，看起来像 CA。

**怎么验证限流真的有效？**
压测，看通过率和下游 QPS 有没有被削平，光看规则配没配不算数。
