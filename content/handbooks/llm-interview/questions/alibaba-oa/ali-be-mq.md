Kafka 是分区日志，throughput 极强，适合日志、埋点和对接 Flink；RocketMQ 偏业务消息，事务消息、延时和死信开箱即用，交易链路更常用。两者给的都是至少一次投递，不丢要靠整条链路配齐，不重复要靠业务幂等。MQ 是阿里校招的特色题。

先说模型。消息队列把同步调用拆成发送、存储、消费三段。主题按分区（Kafka）或队列（RocketMQ）切开，同一分区内有序，跨分区一般无序。生产者要的是投递确认，写到约定的副本数才算成功；消费者要管位移，处理完再提交可能重复，先提交再处理可能丢。所以 MQ 通常提供至少一次，业务自己做幂等，才能接近恰好一次。

不丢消息是一整条链路，开一个配置解决不了。生产端发送失败要重试，进程关闭前要 flush，消息只在发送端内存里不能算成功。存储端靠刷盘和副本，Kafka 用 `acks=all` 等 ISR，RocketMQ 用同步刷盘或同步双写；Kafka 典型的丢消息配置是 `acks=1`，Leader 刚写完就宕机。消费端失败就不提交，重试，进死信，禁止 catch 住异常假装成功，也别先提交后处理。重复投递靠幂等吸收：用业务主键、去重表或 Redis set，让重复的消息只产生一次副作用。Kafka 的 `enable.idempotence` 只解决**同一生产者会话里**重复写 Broker，管不到消费者重复处理，Broker 幂等和业务幂等是两回事。

| | Kafka | RocketMQ |
| --- | --- | --- |
| 模型 | 分区日志，消费者拉，位移自管 | 队列 + 消费组，Broker 管进度更重 |
| throughput | 顺序写、零拷贝，日志/埋点极强 | 够用，更偏业务消息 |
| 顺序 | 分区内有序 | 队列内有序，有顺序消息语义 |
| 事务 / 半消息 | 事务 API 有，业务侧用得少 | 事务消息是阿里主推：本地事务 + 半消息回查 |
| 延时 / 重试 | 要自己做 | 延时等级、死信开箱 |
| 生态 | 大数据、Flink | 阿里云、交易、MetaQ 血统 |

可靠性按业务分三档：丢了可以接受的指标用最多一次；订单、扣款用至少一次；本地 DB 和发消息必须一起成功的，用事务消息。顺序上，全局顺序代价极大，业务尽量设计成「同一订单号进同一分区」。积压是速率差，生产持续高于消费，原因可能是消费慢、下游超时，也可能是分区热点。分区数必须 $\ge$ 有效消费者数，否则加机器也吃不满。

## 放到阿里的场景里

下单成功后要通知库存、积分、搜索索引。流程可以这么讲：本地事务写订单表，同时发 RocketMQ 半消息；本地提交成功再 commit 半消息，失败就回滚半消息；Broker 会回查本地订单状态，查本地事务单是否已经提交，已提交就提交消息，否则回滚。这样就不会出现「单写了消息没发」或者反过来。这是阿里常考的事务消息，比「先发消息再写库」安全。日志、点击流、搜索增量同步更适合 Kafka：量大，可以丢少量，要和 Flink 对接。

积压在大促很常见。比如优惠计算消费慢，队列堆到百万。先扩消费并行度，但并行度受分区数限制，所以主题规划阶段就要按峰值除以单消费者能力来开分区。如果是下游库存中心超时，就在消费端熔断，非关键消息降级丢弃或进延迟重试，关键的扣减进死信交给人工。营销推送积压了可以丢，扣款不行，要有明确的业务分级。重复消费的经典坑是用户连点、消息重投，积分加了两次。用 `userId + orderId + bizType` 做唯一键，插入失败就当成功。

## 追问

**怎么保证同一订单的扣库存和写流水有序？**
订单号哈希到同一分区，单线程消费这个分区。

**进了死信之后怎么修？**
先修 bug，再按业务键重放，重放必须幂等。

**延迟消息用什么做？**
RocketMQ 用延时等级；Kafka 要自己做，用时间戳或者独立的 delay topic。

**消息体多大合适？**
数 KB 级。图片和合同放 OSS，消息里只带 URL。
