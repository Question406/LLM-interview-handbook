## 真题记录

- 岗位：阿里校招，MQ 是特色题

## 定义

消息队列把同步调用拆成「发送、存储、消费」。主题按分区（Kafka）或队列（RocketMQ）切开，同一分区内有序，跨分区一般无序。生产者要的是投递确认：写到约定副本数才算成功。消费者要的是位移：处理完再提交，可能重复；先提交再处理，可能丢失。校招先说清：MQ 通常提供至少一次，业务自己做幂等，才能接近恰好一次。

「不丢」是一条链路，不是一个配置开关。生产端：发送失败重试、关闭进程前 flush、不要把消息只放在发送端内存里当成功。存储端：刷盘和副本，Kafka 用 `acks=all` 等 ISR，RocketMQ 用同步刷盘或同步双写。消费端：失败不提交、重试、进死信，禁止 catch 之后假装成功。幂等是消费端的对偶：用业务主键、去重表或 Redis set，让重复投递只产生一次副作用。积压是速率差：生产持续高于消费，或分区数不够、消费线程堵在下游。

## 对比 / 分层

| | Kafka | RocketMQ |
| --- | --- | --- |
| 模型 | 分区日志，消费者拉，位移自管 | 队列 + 消费组，Broker 管进度更重 |
| 吞吐 | 顺序写、零拷贝，日志/埋点极强 | 够用，更偏业务消息 |
| 顺序 | 分区内有序 | 队列内有序，有顺序消息语义 |
| 事务 / 半消息 | 事务 API 有，业务侧用得少 | 事务消息是阿里主推：本地事务 + 半消息回查 |
| 延时 / 重试 | 要自己做 | 延时等级、死信开箱 |
| 生态 | 大数据、Flink | 阿里云、交易、MetaQ 血统 |

可靠性分层：最多一次（丢可接受的指标）、至少一次（订单、扣款）、事务消息（本地 DB 和发消息要一起成功）。顺序分层：全局顺序代价极大，业务尽量设计成「同一订单号进同一分区」。积压分层：先看是消费慢、下游超时，还是分区热点；分区数必须 $\ge$ 有效消费者数，否则加机器也吃不满。

Kafka 的 `enable.idempotence` 只解决**同一生产者会话里**的重复写 Broker，不解决消费者重复处理。Broker 幂等和业务幂等不是一回事。

## 阿里场景

下单成功后要通知库存、积分、搜索索引。正确故事是：本地事务写入订单表，同时发 RocketMQ 半消息；本地提交成功再 commit 半消息，失败则回滚半消息；Broker 回查本地订单状态，避免「单写了消息没发」或反过来。这是阿里常考的事务消息，比「先发消息再写库」安全。日志、点击流、搜索增量同步更适合 Kafka：量大、可丢失少量、要和 Flink 对接。

积压在大促很常见。优惠计算消费慢，队列堆到百万。先扩消费并行度，但并行度受分区限制，所以主题规划阶段就要按峰值除以单消费者能力来开分区。下游库存中心超时，则在消费端熔断、把非关键消息降级丢弃或进延迟重试，关键扣减进死信人工。重复消费的经典坑：用户连点，消息重投，积分加两次。用 `userId + orderId + bizType` 做唯一键，插入失败就当成功。

## 追问

- 如何保证同一订单的扣库存和写流水有序？订单号哈希到同一分区，单线程消费该分区。
- 半消息回查查什么？查本地事务单是否已提交，已提交则提交消息，否则回滚。
- Kafka 丢消息的典型配置？`acks=1` 且 Leader 刚写完就宕机；消费者先提交后处理。
- 死信之后怎么修？修 bug，按业务键重放，重放必须幂等。
- 延迟消息用什么做？RocketMQ 延时等级；Kafka 用时间戳或独立 delay topic。
- 积压时能不能丢弃？营销推送可以，扣款不行；要有明确的业务分级。
- 消息体多大合适？数 KB 级，图片和合同走 OSS，消息只带 URL。
