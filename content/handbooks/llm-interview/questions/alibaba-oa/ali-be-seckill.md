秒杀是极小库存、极高并发、极短时间的交易，我会先承认绝大多数请求注定失败，然后把失败挡在越外层越好。一万件商品、百万次点击，失败路径必须比成功路径便宜，所以用 CDN、本地缓存、排队和库存预减挡掉大部分请求，只让成功的几千个进入订单、支付和履约。把下单服务水平扩到百万 QPS 解决不了问题。这道题出自牛客上的阿里 Java 面经，和 LRU 同场。

目标有三个：峰值下系统不崩，卖出的件数不超过库存，同一用户不能靠连点买走多件。让所有人公平地慢慢买，不在目标里。流量先分读写：浏览和进会场是读，可以近乎无限缓存；抢按钮是写，必须收敛。超卖有两层，一层在缓存，Redis 减成负数还放行；一层在数据库，两个事务都读到 stock=1。幂等是同一用户、同一场次、同一 SKU，多次请求只生成一笔有效单。

从外到内画五层，不用背组件名。

| 层 | 做什么 | 挡住什么 |
| --- | --- | --- |
| 静态 / CDN | 会场页、按钮图、倒计时 | 读放大 |
| 活动缓存 | 开售前把库存、资格放 Redis | 打 DB 读库存 |
| 网关排队 | 令牌 / 队列，把十万 QPS 收成内部几千 | 线程池和下游 |
| 预减库存 | Redis `DECR` 或分段库存原子减 | 超卖和无效下单 |
| 异步成单 | MQ 写订单，DB `UPDATE ... WHERE stock>0` | 最终一致与对账 |

和普通下单比，普通下单同步走优惠、库存、订单，强一致；秒杀把库存校验提前、成单延后，用短时间的软状态换可用。和限流题比，限流是通用保护，秒杀是限流加预减加售罄短路。售罄以后缓存要立刻变成「已结束」，所有读请求不再回源。

防超卖的两种原子手段要能对比。Redis `DECR`，结果小于 $0$ 就回补并拒绝，快，但 failover 时要小心。DB `UPDATE sku SET stock=stock-1 WHERE stock>0` 靠行锁保证不超卖，但扛不住百万并发，只能留给预减成功的那一小撮。分段库存把 $1000$ 件拆成 $10$ 个桶，降低单 key 热点，代价是可能一个桶卖光了另一个桶还剩，要合并剩余库存。

## 放到阿里的场景里

天猫整点秒杀，零点前页面全部静态化，库存预热进 Redis，按钮背后是独立域名和独立集群，和日常购物车隔离，避免秒杀拖垮全站。用户点击后先过验证码和资格校验（会员、预约），再进排队。排队拿到令牌才 `DECR`；成功就发 MQ，订单服务落库时用条件更新再守一道。用户连点用 `buyerId+skuId+activityId` 唯一键挡住，返回同一个订单号。资格和唯一键都按账号算，同一用户开十个设备也不会按设备多放行。售罄以后读路径只读「已结束」标记，连 Redis 预减都不再走。

流量再乘 $100$ 时，别只说加机器：同一个热点 key 的写请求仍然集中在一台机器上，加机器解决不了。先水平扩排队和 Redis 分片；热点 SKU 用本地计数加分组统计；页面静态化再激进一点；推荐、评价、个性化这些非核心功能降级。压测也要用真实的热点 key 分布，平均打所有 SKU 测不出问题。支付超时未付要回补库存，回补也要幂等，否则超卖的镜像问题就是「少卖」。活动结束后对账，核对 Redis 库存、订单和资金流水，差异进工单。预减是手段，对账收口。

黄牛和刷子靠设备指纹、预约制、答题、会话绑定来挡，否则技术层做得再好，也会被脚本打成普通的高 QPS。校招点到「防刷在限流之前」就行。

## 追问

**Redis 主从切换导致库存回档怎么办？**
预减以 DB 条件更新为准，Redis 只当 acceptance checks，事后对账。

**为什么不直接用 DB 行锁？**
锁等待会把连接池打满，连成功的请求也会超时。

**分段库存分得不均，怎么收尾？**
活动后半段把剩余库存合并到少数几个桶，或者接受略微少卖。

**下单的 MQ 消息丢了怎么办？**
用事务消息或本地消息表，库存冻结单可以回查。

**和抢红包差在哪？**
秒杀是同一 SKU 的热点库存，红包偏随机金额和防刷，见短链 / 红包那道题。
