## 真题记录

- 来源：牛客阿里 Java 面经（秒杀 / LRU 同场）

## 定义

秒杀是「极小库存 × 极高并发 × 极短时间」的交易。目标不是让所有人公平慢慢买，而是让系统在峰值下不崩，卖出的件数不超过库存，同一用户不能靠连点买走多件。定义先把流量分层：浏览和进会场是读，可以近乎无限缓存；抢按钮是写，必须收敛。超卖定义成两层：缓存层超卖（Redis 减成负数还放行）和数据库层超卖（两个事务都读到 stock=1）。幂等定义成：同一用户同一场次同一 SKU，多次请求只生成一笔有效单。

淘天气味在于承认「绝大多数请求注定失败」。一万件商品，百万点击，失败路径必须比成功路径更便宜。所以秒杀不是把下单服务水平扩到百万 QPS，而是把失败挡在更外层：CDN、本地缓存、排队、库存预减。成功的几千个请求才进订单、支付、履约。

## 对比 / 分层

从外到内画五层，比背组件名更像做过。

| 层 | 做什么 | 挡住什么 |
| --- | --- | --- |
| 静态 / CDN | 会场页、按钮图、倒计时 | 读放大 |
| 活动缓存 | 开售前把库存、资格放 Redis | 打 DB 读库存 |
| 网关排队 | 令牌 / 队列，把十万 QPS 收成内部几千 | 线程池和下游 |
| 预减库存 | Redis `DECR` 或分段库存原子减 | 超卖和无效下单 |
| 异步成单 | MQ 写订单，DB `UPDATE ... WHERE stock>0` | 最终一致与对账 |

和普通下单对比：普通下单同步走优惠、库存、订单，强一致；秒杀把库存校验提前，把成单延后，用短时间的软状态换可用。和限流题对比：限流是通用保护，秒杀是限流 + 预减 + 售罄短路。售罄后缓存要立刻变成「已结束」，所有读请求不再回源。

防超卖的两种原子手段要能对比。Redis `DECR`，结果小于 $0$ 就回补并拒绝，快，failover 要小心。DB `UPDATE sku SET stock=stock-1 WHERE stock>0`，行锁保证不超卖，但扛不住百万并发，只能留给预减成功的那一小撮。分段库存把 $1000$ 件拆成 $10$ 个桶，降低单 key 热点，代价是可能一边卖光一边另一桶还剩，需要把剩余对并。

## 阿里场景

天猫整点秒杀：零点前页面全静态，库存预热进 Redis，按钮背后是独立域名和独立集群，和日常购物车隔离，避免秒杀拖垮全站。用户点击后先过验证码和资格（会员、预约），再进排队。排队拿到令牌才 `DECR`；成功发 MQ，订单服务落库并用条件更新再守一道。用户连点用 `buyerId+skuId+activityId` 唯一键，返回同一订单号。售罄后读路径只读「已结束」标记，连 Redis 预减都不再走。

流量再乘 $100$ 时，不要说「加机器」。先水平扩排队和 Redis 分片；热点 SKU 用本地计数 + 分桶；页面静态化再激进一点；非核心（推荐、评价、个性化）降级。单 key 热写成一台机器，加机器没用。支付超时未付要回补库存，回补也要幂等，否则超卖的镜像是「少卖」。对账在活动结束后把 Redis、订单、资金流水三对，差异进工单。这才像淘天：预减是手段，对账是信仰。

黄牛和刷子要提一句：设备指纹、预约制、答题、会话绑定，否则技术层做得再好也被脚本打成普通高 QPS。校招点到「防刷在限流之前」即可。

## 追问

- Redis 主从切换导致库存回档怎么办？预减以 DB 条件更新为准，Redis 只做闸门，事后对账。
- 为什么不直接 DB 行锁？锁等待会把连接池打满，成功者也会超时。
- 分段库存不均怎么收尾？活动后半段把剩余合并到少桶，或允许略微少卖。
- 下单 MQ 丢了？事务消息或本地消息表，库存冻结单可回查。
- 同一用户开十个设备？资格和唯一键按账号，不以设备放行。
- 如何压测？用真实热点 key 分布，不要平均打所有 SKU。
- 和抢红包差在哪？秒杀偏同一 SKU 的热点库存，红包偏随机金额和防刷，见短链/红包题。
