这三个问题按失效的形态区分：穿透是 key 根本不存在，击穿是一个热点 key 刚好过期，雪崩是大量 key 同时失效。分布式锁是另一条线，最低标准是 `SET key token NX PX ttl` 加锁，释放时用 Lua 比较持有者 token 再删除。这是阿里校招后端面的题。

缓存的作用是把高频读从 DB 卸到内存。穿透是查一个缓存和 DB 里都没有的 key，每次都打到 DB，常见于乱猜商品 ID 或者爬虫。空值缓存就是给这种 key 存一个短 TTL 的负缓存，能防穿透，但不该永久占内存；布隆过滤器可以挡在网关，先丢掉明显非法的 ID。

击穿是一个热点 key 过期的瞬间，所有请求都去 DB 重建，单点把库打满。互斥锁重建是只放一个请求去查 DB。逻辑过期是值一直留在缓存里，过期时间写在 payload 里，由少数线程异步刷新，读请求始终命中，用短暂的脏读换稳定。

雪崩是大量 key 同一时刻过期，或者 Redis 进程宕掉，流量集体回源。TTL 加随机抖动把过期时间错开，再加集群、多级缓存和限流降级。

| 问题 | 现象 | 首选手段 | 加强 |
| --- | --- | --- | --- |
| 穿透 | 随机 / 空 key 打 DB | 空值短 TTL | 布隆 / 布谷过滤器挡在网关 |
| 击穿 | 单热点过期 | 互斥锁重建 | 逻辑过期 + 单飞 |
| 雪崩 | 同时过期或缓存挂 | TTL 加随机抖动 | 集群、多级缓存、限流降级 |
| 锁误删 | TTL 到期被别人抢走 | token + Lua 删 | Redisson 看门狗 |
| 热 key | 单 key 打满网卡 / CPU | 本地缓存、分片复制 | 读写分离、拆 key |

一致性上常用 Cache-Aside：业务先读缓存，没命中读 DB 再回填；更新时先改 DB 再删缓存。双写缓存容易和并发读交错出脏数据，所以删缓存比更新缓存更常见。缓存和 DB 长期不一致时，用对账任务按主键重放，删缓存强制回源。

锁这边，TTL 必须比临界区长，否则要靠看门狗续期；续期失败要当作没拿到锁，不能继续写。单个 Redis 实例的 `SET NX` 在主从 failover 时可能丢锁（主还没同步完就切换了），校招说到这一层就够。Redlock 有争议，别当标准答案背。热 key 和大 key 单独处理：大 value 拆字段，避免无界的 `HGETALL`；`KEYS *` 会阻塞主线程，要用 `SCAN`。

## 放到阿里的场景里

商品详情是穿透和击穿的经典现场。下架或根本不存在的 itemId 被刷，没有空值缓存就会把商品库打穿；爆款在整点改价，缓存一齐失效，重建查询又重，就是击穿。做法是不存在的 ID 缓存 $30$ 秒空对象，布隆过滤器在接入层丢掉明显非法的 ID，爆款用逻辑过期、后台线程刷新。双十一还会叠一层本地 Caffeine，把最热的 SKU 挡在单机内存里，Redis 只收第二层。

锁用在库存预扣，或者防优惠券超发。`SET lock:coupon:{id} {requestId} NX PX 3000`，释放时 Lua 校验 `requestId` 再 `DEL`。临界区只做「读库存、判断、写库存」，IO 不要放进锁里。看门狗续期适合「下单要调三个下游」这种长临界区，但下游超时就必须停止续期并回滚。阿里云上更多用的是 Tair，语义接近 Redis，面试用 Redis 命令讲，提一句生产上可能是 Tair 就行。

雪崩在发布窗口也常见：有人把活动商品的 TTL 都设成整点 $00$:$00$，零点集体失效。TTL 要改成基准值加上 $0$ 到 $300$ 秒的随机值。Redis 集群挂了也要有降级：只读本地缓存、关掉个性化、保住下单主路。

## 追问

**先删缓存再更新 DB 行不行？**
不稳。并发读会把旧值再填回缓存，更稳的是先改 DB 再删缓存，或者延迟双删。

**布隆过滤器误判怎么办？**
误判只会让请求被当成「可能存在」去查一次 DB，代价是多一次查询；别把它反过来用，否则会漏掉真数据。

**锁过期了，业务还在跑怎么办？**
写入必须带版本或 token，锁过期后禁止再写；或者用看门狗续期，并监控续期失败。

**Redlock 为什么有争议？**
多个实例各自独立超时，时钟漂移和 GC 暂停都会破坏互斥的假设。

**热 key 怎么发现？**
看慢日志、`hotkeys`、网卡打满、单个分片 CPU 偏高。
