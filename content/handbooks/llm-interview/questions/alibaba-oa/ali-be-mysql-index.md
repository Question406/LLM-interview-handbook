## 真题记录

- 岗位：阿里校招；AI 笔试选择也出现过全表扫描条件

## 定义

InnoDB 索引是 B+ 树。聚簇索引叶子就是整行，主键顺序即物理顺序。二级索引叶子只存索引列 + 主键，查完往往要拿主键回表。联合索引 $(a,b,c)$ 按 $a$、$b$、$c$ 依次排序，所以**最左前缀**：查询必须从 $a$ 用起，$a$ 等值后才能用 $b$，中间断了后面用不上。范围条件会截断：`a=? AND b>10 AND c=?` 里 $c$ 基本用不上。覆盖索引指 `SELECT` 的列都能从二级索引叶子拿到，`EXPLAIN` 的 Extra 是 `Using index`，省掉回表。

全表扫描是优化器认为「走索引 + 回表」比「按聚簇顺序读全表」更贵时的选择。不是语法错误，是代价判断。选择性低（性别、状态只有几个值）、结果集占比大、统计信息过期、对列套函数导致无法用索引，都会让它放弃索引。口述时把「能不能用」和「值不值得用」分开，面试官最喜欢听这句。

## 对比 / 分层

| 写法 | $(a,b,c)$ 能否用 | 说明 |
| --- | --- | --- |
| `a=?` | 能 | 最左前缀 |
| `a=? AND b=?` | 能 | 继续向右 |
| `b=?` | 不能 | 缺 $a$ |
| `a=? AND c=?` | 只用 $a$ | $b$ 断开 |
| `a=? AND b>1 AND c=?` | $a,b$ | 范围后切断 |
| `a LIKE 'x%'` | 能 | 前缀匹配 |
| `a LIKE '%x'` | 不能 | 前导通配 |
| `DATE(a)=...` | 通常不能 | 列上套函数 |

回表分层：二级索引找到一堆主键，再回聚簇随机读。回表行数大时，优化器宁愿扫表。索引下推（ICP）把部分 `WHERE` 下到引擎，减少回表，但覆盖索引更干净。排序分层：`ORDER BY` 与索引顺序一致才能免 filesort；`a=? ORDER BY b` 可以，`ORDER BY c` 不行。

全表的常见触发：没有合适索引；`OR` 两侧各走不同索引且合并代价高；隐式类型转换（`varchar` 列和数字比）；`!=` / `NOT IN`；取样统计认为命中率太高。优化顺序：先 `EXPLAIN` / `EXPLAIN ANALYZE`，再考虑改 SQL、改索引，最后才 HINT。HINT 是逃生舱，不是日常手段。

## 阿里场景

订单表高频查询是「某买家最近的订单」：`WHERE buyer_id=? AND create_time>? ORDER BY create_time DESC`。联合索引 `(buyer_id, create_time)` 既满足最左，又能覆盖排序。若只有 `create_time` 或只有主键，大促期间就是全表或大范围扫。卖家维度的后台检索（按商品标题模糊搜）走搜索引擎，不该逼 MySQL `LIKE '%鞋%'`。

覆盖索引的实例如：对账只需要 `order_id, status, amt`，建 `(status, order_id, amt)` 或把常用列放进联合索引，避免回表打爆缓冲池。状态字段单独索引往往被优化器放弃，因为「已完成」占 $90\%$，选择性太差。阿里规范里也强调：不要给低基数列建单列索引，把它放在联合索引的第二列，跟在高基数列后面。

发布后统计信息没更新，新表从空涨到千万行，优化器还以为表很小，会选错计划。大促前对核心表做分析、看慢查询，比临时加 HINT 可靠。

## 追问

- 主键为什么建议自增或趋势递增？减少页分裂；随机 UUID 当主键会碎页。
- 索引是不是越多越好？写放大、优化器更难选，只保留被 `EXPLAIN` 证明用到的。
- `IN` 很多值还能走最左吗？能，但值太多可能改成扫表。
- 覆盖索引能含主键吗？二级索引叶子已有主键，不必再写一遍，除非要改变顺序。
- 函数索引 / 生成列怎么破 `DATE(col)`？把计算列存下来再建索引。
- 回表一定慢吗？命中少、主键顺序好时可以接受；要看行数和磁盘。
- 如何证明走了索引？`EXPLAIN` 看 `type`、`key`、`rows`、`Extra`，再用慢日志对一下真实耗时。
