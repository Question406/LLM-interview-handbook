这几道选择题考的都是两个相近概念的区别：TCP 流控和拥塞控制观测的对象不同，Best Fit 选的是够用的最小块，`HAVING` 在分组之后才过滤，互斥锁和信号量差在计数和谁来释放。下面每条先讲清概念，再给一道可选题干和正确的 interpretation，最后接一个阿里场景。

## 真题记录

这些题出自阿里 AI 研发 0325 和淘天 / 国际实习的选择题。公开出现过的有：基本有序数组选哪种排序、TCP 流控 vs 拥塞、`GROUP BY` + `HAVING`、内存分区 Best Fit、互斥锁 vs 信号量、取数博弈 DP、HTTPS/TLS、全表扫描触发条件。

实习场的选择还覆盖 OS / 数据库 / 设计模式，按「5:3:2」把算法当主分、选择当稳分。

## TCP 流控与拥塞控制

TCP 要保证可靠字节流，流控和拥塞控制都在限制发送速率，只是保护的对象不同。流控保护接收方：对端通告接收窗口 `rwnd`，告诉你「我缓冲区还剩多少」，发送方不能把对端撑爆。拥塞控制保护网络：发送方自己维护拥塞窗口 `cwnd`，用慢启动、拥塞避免、快重传、快恢复去估路径能消化多少。实际的发送窗口是 $\min(\textit{rwnd}, \textit{cwnd})$。一个看对端缓冲，一个看丢包 / RTT / ECN。

| | 流控 | 拥塞控制 |
| --- | --- | --- |
| 保护谁 | 接收方应用缓冲 | 中间网络 |
| 信号 | `rwnd`、窗口更新 | 丢包、三次重复 ACK、超时、ECN |
| 窗口 | 对端通告 | 本地估计 `cwnd` |
| 典型题眼 | 零窗口、窗口探测 | 慢启动门限、AIMD |

拥塞控制的几个阶段要能说出来。慢启动时 `cwnd` 指数涨到 `ssthresh`，之后进入拥塞避免，接近线性地加。超时被认为更严重，门限降到一半并回到慢启动；三次重复 ACK 走快恢复，`cwnd` 不会被打回 $1$ 个 MSS。

同场笔试还爱考「基本有序数组选哪种排序」：插入排序期望接近线性，快排 / 堆排没有这个红利。那是另一题，别和 TCP 混在一起。

### 可选题干

关于 TCP 流控和拥塞控制，下列说法正确的是？

- A. 流控和拥塞控制都由接收方计算，发送方只负责重传
- B. `rwnd` 表示对端接收缓冲，`cwnd` 表示发送方对路径拥塞的估计，发送窗口取二者较小值
- C. 拥塞窗口就是接收窗口的别名，出现丢包时把 `rwnd` 减半
- D. 流控只存在于 UDP，TCP 只有拥塞控制

### 正确的 interpretation

选 B。A 把拥塞控制派给了接收方；C 把两个窗口混成了一个名字；D 说反了，UDP 没有这两套窗口。口述时可以补一句：零窗口时发送方要发窗口探测，否则对端恢复后连接会僵死。

### 阿里场景

网关到交易服务走的是短连接或连接池里的 TCP。大促出现超时，先分清是对端处理不过来，还是链路丢包。对端处理不过来时应用层堆积，`rwnd` 缩小甚至零窗口，该扩线程或限流；链路丢包时 `cwnd` 被打下来，该查网卡、丢包和重传。把所有超时都说成「拥塞控制」，会把扩容方向带偏。如果同场出现 HTTPS/TLS，可以补一句：TLS 在 TCP 之上做握手和加密，不替代窗口机制。

### 追问

**为什么取 $\min$，不取 $\max$？**
两个约束要同时成立，取松的那个就会违反更紧的那个。

**Nagle 和延迟 ACK 叠加会怎样？**
小包会被延迟，交易系统里常把 Nagle 关掉。

**QUIC 还要这一套吗？**
QUIC 在 UDP 上重做了拥塞控制，思想类似。

## Best Fit

动态分区分配里，空闲块是一个列表。Best Fit 在所有放得下请求的空闲块里挑最小的那块，想让浪费的内部碎片最小。First Fit 从低地址往上扫，碰到第一块够用的就切；Worst Fit 挑最大的空闲块，希望切完还剩一块较大的可用。这些都是连续内存分配策略，和分页的页框分配是两回事。

| | First Fit | Best Fit | Worst Fit |
| --- | --- | --- | --- |
| 选择 | 第一块够用的 | 够用的最小块 | 最大块 |
| 速度 | 通常最快 | 要扫完全表或靠有序树 | 也要找最大 |
| 碎片 | 前部碎、后部留大块 | 剩下很多难以再利用的小碎块 | 大块被迅速切掉 |
| 适用 | 通用默认 | 请求尺寸差异大、想抠空间 | 少用 |

分页和伙伴系统是另一套思路：外碎片少，内碎片是页内浪费。笔试题如果给「空闲分区 $12, 10, 20$，请求 $11$」，Best Fit 选 $12$，不选 $20$。

### 可选题干

内存动态分区采用 Best Fit 时，下列哪项正确？

- A. 总是选地址最低的空闲块，所以一定最快
- B. 在能满足请求的空闲块中选最小者，内部浪费小，但容易留下更碎的残块
- C. 总是选最大空闲块，以减少外部碎片
- D. Best Fit 保证不会产生外部碎片

### 正确的 interpretation

选 B。A 说的是 First Fit，C 说的是 Worst Fit。D 错在外部碎片的含义：空闲总和够、单块不够就是外部碎片，Best Fit 往往更碎。实现上可以用按大小排序的空闲树，省掉「扫全表」，但碎片形态不会变。

### 阿里场景

在 JVM 或容器里你不会手写 Best Fit，这题考的是「分配策略和碎片」。堆外 DirectBuffer 反复分配释放，如果每次都按「刚好大小」扣，会剩下一堆没法复用的小段，表现是本地内存涨、堆却不涨。大促前预分配固定规格的缓冲（类似 slab），比每次 Best Fit 更像生产做法。伙伴系统、G1 Region 也都是在规避这种细碎。

### 追问

**外部碎片怎么收？**
做压缩 / 紧致，成本高。

**Next Fit 是什么？**
从上次结束的位置继续做 First Fit。

**为什么现代 OS 主要用分页？**
为了避免外部碎片，代价是接受页内碎片。

## GROUP BY 与 HAVING

这题的关键是 SQL 的逻辑执行顺序，大致是 `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY`。`WHERE` 在分组前过滤行，不能用聚合别名；`GROUP BY` 把行收成组；`HAVING` 在分组后过滤组，这里才能写 `COUNT` / `SUM`。开了 `FULL_GROUP_BY` 时，`SELECT` 列表里只能是分组列或聚合。

| | `WHERE` | `HAVING` |
| --- | --- | --- |
| 时机 | 分组前，行级 | 分组后，组级 |
| 能写聚合吗 | 不能 | 能 |
| 典型 | `status='paid'` | `COUNT(*)>10` |
| 索引 | 更容易走索引下推 | 往往先分组再滤 |

几个常错的写法：`WHERE COUNT(*)>1` 非法；`HAVING amt>100` 里的 `amt` 如果既不是聚合也不是分组列，严格模式下非法。`WHERE` 能消掉的行就别留到 `HAVING`，行越少分组越便宜。`HAVING` 里写分组列本身是合法的，例如 `HAVING buyer_id % 10 = 3`，但这类过滤更该下推到 `WHERE`，否则白白分组。

全表扫描那道题常和这条一起出：`WHERE` 对列套函数、或者选择性太差，优化器会放弃索引，见索引题。另外，MySQL 某些模式下 `HAVING` 能引用 `SELECT` 别名，但不可移植；笔试按标准 SQL 走，当作 `WHERE` 里不能用别名。

### 可选题干

查询「成交次数大于 $10$ 的买家」，下列哪条正确？

- A. `WHERE COUNT(*) > 10 GROUP BY buyer_id`
- B. `GROUP BY buyer_id HAVING COUNT(*) > 10`
- C. `HAVING buyer_id GROUP BY COUNT(*) > 10`
- D. `WHERE buyer_id GROUP BY COUNT(*)`

### 正确的 interpretation

选 B。A 把聚合放进了 `WHERE`，语法和语义都不对；C、D 的顺序和对象都乱了。完整例句是 `SELECT buyer_id, COUNT(*) AS cnt FROM orders WHERE status='paid' GROUP BY buyer_id HAVING COUNT(*) > 10`：先用 `WHERE` 丢掉未支付的订单，再用 `HAVING` 滤组。

### 阿里场景

商家后台的「复购用户」就是这条 SQL。大表上先靠 `(status, buyer_id)` 把已支付的订单收窄，分组才跑得动；把全部订单丢进 `HAVING` 会扫爆。导出报表有时在应用层分组，是因为分库后 `GROUP BY` 只能片内聚合，还要二次归并。笔试如果只给单表，按标准 SQL 选就行。双十一临时统计「每个会场下单超过 $N$ 笔的买家」也是同一个模式：先 `WHERE` 会场和时间，再 `GROUP BY buyer_id HAVING COUNT(*)>=N`，千万别在 `WHERE` 里写 `COUNT`。

### 追问

**`COUNT(*)` 和 `COUNT(col)` 差在哪？**
后者不计 `NULL`。

**`GROUP BY` 和 `DISTINCT` 什么时候等价？**
只选分组列、没有聚合的时候。

**窗口函数 `COUNT() OVER` 和分组是一回事吗？**
不是，它不合并行。

**`HAVING` 能走索引吗？**
分组之后通常没法再靠单行索引过滤，所以能提前滤就提前滤。

**把 `ONLY_FULL_GROUP_BY` 关掉会怎样？**
可能选出组内不确定的行，结果不可复现，生产环境别关。

## 互斥锁与信号量

互斥锁（mutex）保护临界区：同一时刻最多一个线程持有，只有持有者能释放，相当于「这把钥匙只配一把锁」。信号量是一个计数器：`P` / `wait` 把计数减一，减不动就阻塞；`V` / `signal` 加一并唤醒等待者。初值为 $1$ 时可以模拟互斥，初值为 $N$ 时表示 $N$ 份资源，比如连接池、停车位。条件变量要配一把互斥锁，等的是「条件成立」，和资源个数无关。

| | 互斥锁 | 信号量 | 条件变量 |
| --- | --- | --- | --- |
| 计数 | 0 / 1 | $0 \ldots N$ | 无独立计数 |
| 谁释放 | 持有者 | 可以是另一线程 V | 另一线程 notify |
| 典型 | 改共享对象 | pooling 资源、汇合 | 生产者-消费者 |
| Java | `synchronized` / `ReentrantLock` | `Semaphore` | `Condition` / `wait` |

死锁四条件在这里仍然适用。读写锁是互斥锁的变体，读共享、写独占。自旋锁适合短临界区，长 IO 时别自旋。笔试里的取数博弈 DP、设计模式是加分题，和锁无关，分开准备。

### 可选题干

下列关于互斥锁和信号量的说法，哪一项正确？

- A. 互斥锁和信号量完全等价，任何信号量都能无条件换成 mutex
- B. 互斥锁保护临界区且通常由持有者释放；信号量用计数控制 $N$ 份资源，V 操作可由其他线程执行
- C. 信号量不能实现互斥，只能实现同步
- D. 条件变量本身就带计数，可以替代信号量做连接池

### 正确的 interpretation

选 B。A 忽略了 $N>1$ 和「非持有者也可以 V」；C 错，二元信号量能做互斥，只是职责更宽；D 把条件变量当成了计数器。连接池用 `Semaphore(N)` 或队列更直接。

### 阿里场景

下单服务访问库存的 HTTP 客户端，连接池用信号量限制 $N$ 个在途请求，超出的排队或快速失败，这就是限流在进程内的对应物。订单对象上改金额要用互斥锁，换成「谁都能 V」的信号量，就会有线程释放自己没持有的锁。双十一把信号量初值开到 $5000$，下游却只有 $200$ 个连接，等于没限，线程池会被下游超时灌满。锁和限流用的是同一套语言：配额用计数，临界区用互斥。

### 追问

**为什么 mutex 必须由持有者释放？**
否则所有权就乱了，调试时会看到「没拿到锁却在临界区」。

**公平信号量会怎样？**
饥饿少了，throughput 也降了。

**`synchronized` 能当信号量用吗？**
不能直接管 $N$ 份资源，要用 `Semaphore` 或多个条件。

**怎么避免死锁？**
统一加锁顺序、加超时、缩小临界区。
